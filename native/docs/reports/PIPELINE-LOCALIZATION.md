1. **외부 경로 변동이 크게 동반된 사건:** 약80.23초에 PC→노트북 송신9.960ms/수신61.686ms, 반대 송신15.413ms/수신68.800ms였다. 같은 PC 시각 주변 ±100ms에서 노트북/공유기 Windows RTT 최대55/53ms, 로컬 ping managed 완료 최대0.664ms, 별도 스레드 간격 최대16.015ms였다. 약110.34초도 외부 RTT43/57ms, 로컬 완료0.568ms였다. PC 전체 managed 완료 지연만으로 이 사건들을 설명하기 어렵다. NIC/OS 네트워크 경로·공유기·공유 외부 경로가 남는다. NIC 물리 도착 시각은 측정하지 않았다.
2. **PC 콜백/managed 완료 지연이 동반된 사건:** 약51.41초에는 PC→노트북 송신91.628ms/수신95.412ms, PC 캡처 콜백 간격69.976ms/송신 큐22.182ms였다. 반대는 송신14.986ms/수신98.620ms였다. 같은 주변 시간창에서 로컬 Windows RTT는0ms이나 managed 완료는48.232ms, 공유기 RTT8ms/managed48.058ms였다. 별도 스레드는21.725ms 이하로 비교적 짧았다. 패킷이 외부에서 늦어지는 문제 외에 앱/런타임 콜백 처리가 지연되는 종류도 존재한다. ThreadPool starvation·GC·다른 부하 중 하나로 확정하지 않았다.

30ms 초과 수신 간격은25/31회였다. PC→노트북에서는 송신 반환 이후15회, 캡처 전달2회, 송신 큐/dispatch6회, 혼합2회로 분류됐다. 반대는 송신 반환 이후30회/혼합1회였다. 전부 같은 네트워크 원인이라고 합치지 않는다. 출력 `Read` 사이30ms 초과는노트북1회(30.197ms)/PC0회였다.

OS 수신 이벤트와 앱 콜백을 직접 비교하려 했으나 일반 Windows 실행 토큰에는 관리자 권한이 없어 ETW 시작이 `Access is denied`로 실패했다. 이는 Windows 권한 제한이며 자동 승인 검토의 거절은 아니다. 이후 사용자 승인과 UAC 관리자 실행으로 아래 추가 시험을 완료했다.

관리자용 [trace-network.ps1](../../trace-network.ps1)을 준비했다. 현재 Windows의 `Microsoft-Windows-Kernel-Network` 제공자 스키마를 검사하고 주소·포트·길이·PID 등의 허용 필드만 있음을 확인했다. 기본125초/최대180초/32MiB 순환 파일이며, 자신의 고유 ETW 세션만 종료한다. 패킷 바이트·음성은 수집하지 않지만 다른 앱의 네트워크 주소/PID도 포함할 수 있다. 아래150초 시험에서 실제 관리자 수집·정상 종료를 검증했다.

```powershell
# 관리자 PowerShell에서, 두 PC 상세 추적과 동시에 실행할 다음 단계
./native/trace-network.ps1
# 수집 없이 제공자 필드만 검사
./native/trace-network.ps1 -ValidateOnly
```

이 도구도 NIC 하드웨어 도착 시각을 제공하는 것은 아니다. ETW 이벤트 누락/순환 파일 덮어씀을 확인하고, UDP endpoint·길이·PID·시간 간격으로 연계해야 한다. 이벤트에는 RTP timestamp가 없어서 같은 크기 패킷의 단순 순번 매칭을 확정 근거로 쓰면 안 된다.

추가 검증: 진단 도구 경고0/오류0 빌드, Python 시각 분석 self-test, PowerShell 구문·실제 제공자 메타데이터 스키마 검사 통과. 권한 없는 실제 시작은 수집 없이 실패함을 확인했다.

## 관리자 OS UDP 추적 — 수신 경계 확인 완료

사용자가 관리자 실행을 승인했고 UAC를 통해 추적을 시작했다. OS 수집은150초, 두 PC 통화는12:07:58~12:10:01 KST 약120초였다. 원본과 분석은 `.local/os-network-054/`에 보존했다. 추적의 `stopExitCode`는0이며 세션은 종료됐다.

- ETW36,879개 이벤트/71개 버퍼, **이벤트 손실0개**. 파일4,653,056바이트로32MiB 순환 상한에 도달하지 않았다.
- 시험 PC 프로세스의 UDP24,727개를 [export-network.ps1](../../export-network.ps1)로 추출했다. 상대와의 같은 UDP endpoint tuple에서 수신12,357개/송신12,366개였다. 이 숫자는 RTP뿐 아니라 같은 소켓의 STUN/DTLS/RTCP도 포함한다.
- 앱 상세 기록은 PC 수신12,003개, 양방향 RTP매칭각11,995개, 분석각11,394개였다. 양쪽 error/기록 초과0개, recorder 최대PC0.056ms/노트북0.237ms였다.
- UTC/QPC 앵커의 반폭 불확실성은±1.253ms였다. 같은 호스트의 간격 비교에는 고정 오프셋이 소거되지만, 절대 시각의 미세 차이를 복호화 시간으로 확정하지 않았다.

**이번 PC 앱 수신의30ms 초과 간격54개 전부가 OS UDP 이벤트에서도 비슷한 빈 구간으로 나타났다.** 각 구간 양끝에서 가까운 OS 이벤트를 찾고, 내부에는 양끝5ms를 제외해도 UDP 이벤트가 없는지 검사했다. 허용된 시각 오차를 넘거나 내부 이벤트가 있으면 같은 원인으로 분류하지 않도록 했다.

| PC 앱 수신 간격 | 대응 OS UDP 이벤트 간격 | 내부 UDP 이벤트 |
|---:|---:|---:|
| 57.844ms | 57.798ms | 0개 |
| 57.298ms | 57.270ms | 0개 |
| 56.400ms | 56.380ms | 0개 |
| 55.535ms | 55.516ms | 0개 |

PC OS 송신 이벤트 간격은중앙값9.995ms/P95 10.598ms/최대13.899ms였다(통화 시작5초·끝1초 제외). 이 실행에서 PC OS 송신 이벤트 이전에 큰 송신 공백이 생긴 것은 아니다. 반대 방향의 노트북 RTP 송신 간격은최대30.669ms로 일부 송신 변동은 남아 있다.

결론은 **이 실행의 PC 큰 수신 간격은 Windows UDP 이벤트가 찍히기 전부터 존재했고, 그 뒤 SIPSorcery 수신 콜백·복호화·디코더에서 만들어진 대기는 주원인으로 관측되지 않았다**는 것이다. 앱 수신54개 중 상대 송신 반환 이후 추가 변동52개, 상대 송신 쪽1개/혼합1개로 분류됐다. OS 수신 경계에 공백이 있다고 전부 네트워크 원인이라는 뜻은 아니다.

이 제공자는 NIC의 물리 수신 시각이 아니다. 원인은 상대 송신, 무선/공유기 등 네트워크, NIC·드라이버·DPC, OS의 해당 이벤트 이전 처리 중에서 더 구분해야 한다. 두 PC의 절대 시각을 빼서 단방향 지연을 계산하지 않았고, 이벤트에 RTP 식별자가 없으므로 개별 패킷의 정확한 OS→앱 지연으로 제시하지 않는다. 이전 실행에서 확인된 PC 콜백 지연 사건도 이 결과 때문에 부정되지 않는다.

다음 조사는 **양쪽 OS 이벤트의 동시 대조 또는 NIC/인터페이스 경로 대조**다. 현재 증거만으로 수신 버퍼나 코덱을 바꿔 이 순간 변동을 해결하려 하지 않는다. NIC·공유기·방화벽 설정은 변경하지 않았다.

재현 도구(관리자 수집 후 일반 분석):

```powershell
./native/trace-network.ps1 -Seconds 150 -OutputPath native/.local/reports/network.etl
./native/export-network.ps1 -InputPath native/.local/reports/network.etl -OutputPath native/.local/reports/udp.json -ProcessId TEST_PROCESS_ID
tracerpt native/.local/reports/network.etl -o native/.local/reports/events.csv -of CSV -summary native/.local/reports/etw-summary.txt -y
python native/TransportProbe/Analysis/analyze_windows_network.py PC_JSON UDP_JSON ETL_ANCHOR_JSON ETW_SUMMARY OUTPUT_JSON
python native/TransportProbe/Analysis/analyze_windows_network.py --self-test
```

분석기는 미완주·기록 초과·ETW 손실·순환 상한 도달·큰 시각 앵커 불확실성·일대일 IPv4 직접 통화가 아닌 자료를 거부한다. 간격 비교·시간 오프셋 불변성·OS 이벤트가 공백 중에 있는 경우·수신 이벤트 누락 시 분류를 self-test로 검사했다.

## 출력 이후와 남은 범위

기존 루프백 측정의 provider 제출→디지털 루프백 검출은 노트북194.75~207.41ms(4회), PC40.25~51.51ms(3회)였다. 노트북 첫 시도1회는 첫 프레임 재생 검증 실패로 제외했다. 앱 수신 큐 이후에도 큰 방향 차이가 남는다. 출력 endpoint/DSP/루프백 캡처·검출 위치가 포함된 값이고 물리 이어폰 지연이나 전체 입→귀 지연으로 확정할 수 없다. 개인 장치 최적화는 현재 범위에서 제외한다.

다음 순서는 다음과 같다.

1. 신호 없는 대조·로컬 ICMP 대조·관리자 OS UDP 이벤트 대조를 완료했다. 다음은 양쪽 OS 이벤트 또는 NIC/인터페이스 경로 비교로 OS UDP 이벤트 이전의 원인을 더 나누는 것이다. 현재 증거만으로 NIC·공유기 설정을 바꾸지 않았다.
2. 수신→디코딩31~36ms를 장치 요청 주기·목표 reserve·현재 PCM으로 더 세분화하고, 그 근거로 버퍼 변경을 비교한다. 먼저 큐를 늘리거나 줄이지 않는다.
3. 캡처 API 전달18~19ms는 WASAPI 패킷 크기·콜백 주기와 함께 비교한다. 물리 장치 지연과 혼합하지 않는다.

## 재현

각 PC에서 같은 방 이름, 다른role로 실행한다. 장치 사용은 사용자 통화와 겹치지 않게 한다.

```powershell
dotnet run --project native/TransportProbe -c Release -- --pipeline-passive https://qlrpal.ddns.net/ UNIQUE_ROOM native/.local/pc.json pc
# 상대 PC: 마지막 role은 laptop, 출력 경로도 상대 PC 경로
# 루프백 신호를 포함하려면 --pipeline-probe 사용
python native/TransportProbe/Analysis/analyze_pipeline.py PC_JSON LAPTOP_JSON OUTPUT_JSON
python native/TransportProbe/Analysis/analyze_pipeline.py --self-test
# 선택: PC에서 별도 프로세스로 ICMP 대조
dotnet run --project native/TransportProbe -c Release -- --icmp-profile LAPTOP_IP GATEWAY_IP native/.local/icmp.json
python native/TransportProbe/Analysis/analyze_icmp.py ICMP_JSON OUTPUT_JSON CONTROL_JSON
```

분석기는 error나 기록 초과가 있는 완주 실패 보고서를 거부한다. 시간 경계에서 매칭되지 않은 패킷은 손실로 계산하지 않는다. 기록의 IP·닉네임은 Git에 올리지 않는다.
