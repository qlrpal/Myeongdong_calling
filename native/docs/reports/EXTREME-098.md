# EXTREME-098 — SRTP 초기 상태 수정과 무효 최적화 제외

2026-10-26 / `codex/extreme-latency`. EXTREME-097의 native Opus 변경 위에서 수행했다. 기존 배포본·공유기 설정·라우팅은 변경하지 않았다.

## 채택한 수정

상류 `SrtpContext.UnprotectRtp`는 인증 전에 `SetInitialSequence`를 호출했다. 정상 첫 순번0이 재전송으로 거부되고, 위조된 첫 패킷이 초기 순번 상태를 설정하는 문제를 회귀 검사에서 재현했다. 최초 인덱스는 지역 변수로 추정하고 인증 성공 뒤 기존 상태 갱신 경로만 사용하도록 변경했다. 원본 SRTP 소스 SHA-256 및 패치 위치를 검증한다.

SDK 식별자는 `10.0.17+myeongdong.2 / udp1-turn1-rtp0`이다. 진단에 `SrtpCipher`를 추가해 실제 협상된 암호화 프로필 이름만 기록한다. 키·salt·암호화 컨텍스트는 내보내지 않는다. 협상 우선순위와 암호화 알고리즘은 변경하지 않았다.

단일 AES128/256-GCM의 RTP 결과를 .NET AES-GCM과 독립 비교한다. 순번 래핑·위조 태그·재전송·순서 변경·키 재유도·동시 SSRC·SRTCP를 검사한다. 이중 AES128/256-GCM에서도 위조 첫 패킷 뒤 초기 순번0 수신과 래핑·재전송을 검사한다. 이전 SDK는 초기 순번0 회귀를 통과하지 못했다. 공개된 고정 시험 키만 사용한다.

## 제외한 후보

단일 GCM 키 스케줄 재사용은 합성 암호화 시험에서 패킷당 할당을 줄였지만 실제 2호스트 6엔진, 90초씩 원본→후보→원본 대조에서 효과가 없었다. 후보와 원본은 같은 바이너리의 프로세스별 스위치로 비교했다.

| 호스트 | A1 MB/s | B MB/s | A2 MB/s | GC 정지 ms/s A1/B/A2 |
|---|---:|---:|---:|---|
| PC |43.363|43.411|43.390|2.957 / 3.131 / 3.025|
| 노트북 |43.088|43.068|43.106|10.585 / 10.649 / 10.690|

세 대조 모두 연결·종료 검사는 통과했다. 키 스케줄 재사용 구현과 실험 스위치는 최종 소스에서 제외했다. SDK가 우선 제안하는 이중 GCM은 해당 최적화 대상이 아니었다. 합성 수치를 통화 성능 향상으로 주장하지 않는다.

## PLC 해석 보완

그룹 분석기에 `plcHoldMs`와 `plcAdvanceMs`를 추가했다. 대기 중 합성한 출력과 재생 기한을 넘겨 시간축을 진행한 보간을 구분한다. 둘 중 어느 값도 물리적 네트워크 손실 그 자체가 아니다.

097의 native 10분 시험을 재분석하면 노트북 내부 링크의 PLC 17122.5ms는 전부 hold이며 advance는0이었다. PC 교차 호스트는 hold9412.5ms/advance44350ms, 노트북 교차 호스트는 hold8012.5ms/advance35650ms였다. 교차 호스트에는 여전히 늦은 패킷과 재버퍼링이 있어 문제 해결로 판정하지 않는다.

## 검증 범위와 한계

두 PC에서 각각3개 엔진을 실행한 시험은 실제6대 PC 부하와 다르다. 실제 음성 입→귀 지연을 새로 측정하지 않았다. 기존 무선/AP 지연 원인을 이번 SDK 수정으로 해결했다고 판단하지 않는다. 원시 보고서와 시험용 백업은 Git 제외 `.local/extreme-098`에 보존한다.

## 최종 빌드의 실제 경로 확인

전체 Release 정적 분석·회귀 검사와 IPv4/IPv6 WebRTC 통합이 통과했다. 노트북에서도 동일 빌드의 SRTP 보호 검사가 통과했다. 최종 SDK의 암호문 digest는 `DF826315C0193445271E8998A91FD88474D528DB8FC826BC14C907F1C92994C0`으로 앞선 수정 후보의 정상 암호문과 일치했다.

최종 2호스트 6엔진90초 직접 경로 시험은 양쪽 종료 코드0, 오류 없음, 정리 성공이었다. 분석기는 양쪽 각각15개 피어 구간을 검증했다. 실제 `SrtpCipher`는 `DOUBLE_AEAD_AES_256_GCM_AEAD_AES_256_GCM`이었다. 이 관측으로 기존 단일 GCM 최적화가 실제 기본 경로에 적용되지 않았음을 확인했다.

해당 시험의 PLC hold/advance 합계는 PC1357.5/6152.5ms, 노트북3967.5/4055ms였다. 여러 수신 스트림의 합계이며 단일 통화 지연이 아니다. 미디어 증가·연결 검사가 통과해도 PLC가 없어졌다는 뜻은 아니다.

기본10ms 제품 흐름은 실제 OCI TURN 중계로2회 통과했다. 음소거·볼륨·재접속·나가기를 수행했으며 양쪽 총32개 피어/단계 구간에서 송수신 카운터 증가와 TURN 경로를 확인했다. 이 경로에서도 이중 AES256-GCM이 관측됐다.

## 복구와 배포 검사

노트북 기존 시험 경로의 덮어쓴 파일은 원본으로 복원하고 파일별 SHA-256을 확인했다. 추가된 파일과 빈 디렉터리만 제거했다. 양쪽 TransportProbe/VoiceNative 시험 프로세스0개를 확인했다. OCI coturn·신호 서버·nginx는 active였다. 공유기·라우팅·전원·오디오 설정을 변경하지 않았다.

일반 및 ReadyToRun StageOnly 배포를 완료하고 각각 실제 실행으로 SDK 식별자·native Opus 활성화를 확인했다. SDK DLL의 SHA-256과 라이선스 포함도 확인했다. 기존 dist는 유지했다. Git 후보 UTF-8·민감정보 패턴·로컬 문서 링크 검사와 diff 공백 검사를 수행했다. 이번 변경은 아직 커밋·푸시하지 않았다.
