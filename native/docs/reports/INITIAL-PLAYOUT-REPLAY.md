# 첫 재생의 오래된 음성 폐기 비교

2026-10-19. 게임 공존 시험의 네 기록을 동일한 RTP 도착 순서·잠금 획득 시각·출력 요청 크기로 재현했다. 입력 파일을 변경하지 않았으며 실제 통화나 게임을 다시 실행하지 않았다. 원본 음성이 없는 메타데이터에 합성 10ms Opus 무음을 대응시킨 정책 비교다. 음질·실제 출력 시각·입→귀 지연을 측정한 결과는 아니다.

## 후보와 검증

기존 저지연 정책은 재버퍼 뒤 복구 시에만 오래된 음성을 덜어낸다. 후보는 첫 재생에도 이 규칙을 적용하여 `예비20ms + 현재 출력 요청량`을 남길 수 있을 때까지 오래된 패킷을 제거한다. 시작 허용량이나 PLC 상한은 늘리지 않는다. 출력 요청이 22ms이면 최소42ms를 남겨야 하므로 10ms 단위 패킷에서는 보통50ms가 남는다.

`freshInitialStart`는 기본 false이며 비교 도구에서만 true로 사용한다. 앱의 생성 경로에서는 활성화하지 않았다. 후보의 최초 폐기도 실험 결과의 `RecoveryDiscardedMs`에 포함된다. 이는 실제 네트워크 손실이 아닌 의도적인 음성 누락이다.

빌드 경고0·오류0. RTP 회귀 검사에 최초100ms 입력에서 기본 정책은90ms를 남기고, 후보는70ms를 폐기해20ms를 남기는 검사를 추가했다. PLC 없이 예비량을 유지하는지 확인했다. 네 기록 모두 기존 모드 재현의 디코딩 프레임 수·PLC 프레임 수·late 패킷 수가 실제 원시 추적과 일치했고, 무음 부족 누적값도 마지막 진단값과 일치했다. 원시 추적은 마지막 1초 주기 진단보다 길어 디코딩 총수를 마지막 진단 프레임 수와 직접 비교하지 않았다.

## 같은 입력에서의 결과

대기는 첫 이벤트부터5초 이내 도착한 패킷 중 실제 재생된 패킷의 `수신 버퍼 진입→재생 요청` P95다. 폐기한 패킷은 이 지연 분포에 포함되지 않는다. 각 회차가 서로 다른 입력을 사용하므로 표의 각 행 안에서만 정책을 비교한다.

| 수신 기록 | 시작 대기 P95 기존→후보 | 전체 무음 부족 기존→후보 | 전체 PLC 기존→후보 | 의도 폐기 기존→후보 |
|---|---:|---:|---:|---:|
| PC 표준 |54.39→44.52ms |30.90→30.90ms |150→150ms |40→50ms |
| PC 짧은 입력 우선 |32.26→31.37ms |0→42.54ms |140→170ms |20→130ms |
| 노트북 표준 |25.36→55.54ms |31.69→31.60ms |140→120ms |80→110ms |
| 노트북 짧은 입력 우선 |23.08→22.89ms |122→182ms |230→230ms |140→200ms |

첫 큐를 줄이면 시작 일부 패킷의 대기는 짧아질 수 있지만, 뒤의 공백에 대한 여유도 함께 줄어든다. 재버퍼·기존 폐기·시계 보정의 후속 상태가 달라져 모든 회차의 지연이 감소하지 않았다. 특히 PC 후보 기록에서는 없던 무음 부족42.54ms와 재버퍼1회가 생겼다. 노트북 후보 기록에서는 부족이60ms 더 늘었다. 최초 폐기량만큼 전체 지연이 개선된다고 계산할 수 없다.

## 결정

**앱 기본값에 적용하지 않는다.** 지연이 우선이어도 이번 후보는 지연 이득이 일정하지 않고 음성 누락·재생 부족을 늘렸다. 기존20ms 예비량·첫 시작 정책을 유지한다. 실험 옵션과 동일 입력 비교 기능은 재검증을 위해 남긴다.

이제 같은 시작 큐를 반복 조정하기보다, 이미 확인된 송신 완료 이후→수신 콜백 이전의 긴 공백과 별개로 정상 구간의 고정 처리 비용을 줄일 대상을 검토하는 것이 타당하다. 물리 네트워크의 긴 공백을 제품 버퍼만으로 해결했다고 주장하지 않는다.
