# EXTREME-087 — 원격 합주 앱 참고: 초기 학습/유지와 지연 표시

2026-10-25 / Windows 게임 병행·WASAPI 저지연 공유 모드·지연 최우선.

## 범위와 참고

- [SonoBus 공식 설명서](https://www.sonobus.net/sonobus_userguide.html): 상대별 버퍼와 Initial Auto를 참고했다. 구현을 복사한 것이 아니며 아래 정책/수치는 이 프로젝트의 선택이다.
- [FarPlay 지연 설명](https://farplay.io/latency/), [SYNCROOM 설명서](https://syncroom.yamaha.com/global/v2/play/manual/index_pc.html), [Jamulus 설명서](https://jamulus.app/wiki/Software-Manual): 장치·네트워크·버퍼를 분리해 설명하는 화면을 참고했다.
- [Microsoft 공유 저지연 API](https://learn.microsoft.com/en-us/windows-hardware/drivers/audio/low-latency-audio): 기존 공유 모드 목표를 유지한다.
- PCM 대조는 기존 도구를 유지한다. 중복 패킷 전송·서버 믹싱은 이 변경에 넣지 않았다. 실제 손실 유형과 다인 부하 증거 없이 전송량/구조를 바꾸지 않는다.

## 제품 변경

`./native/run.ps1 -Experiment opus-learned`

기존 `opus-adaptive`를 바탕으로 상대별 수신 목표 여유만 초기 학습 후 유지한다. 출력 시간 30초 이상을 학습하고 설정 하한에 도달했을 때만 고정한다. 도착 변동 통계·장치 요청/출력 위상 보호·프레임 길이에 따른 안전 하한·시계 보정·큐 상한은 계속 동작한다. 실제 큐나 전체 입→귀 지연을 고정하는 기능은 아니다.

빈 큐의 타임스탬프 보존 대기가 필요하거나 기존 지연 도착 증가 조건이 성립하면 즉시 연속 자동으로 안전 복귀한다. 유지 상태의 3초 구간 중 PLC/부족의 영향을 받은 출력 요청이 200ms 이상이어도 복귀한다. 요청 전체 시간을 사용하므로 실제 PLC 샘플 합계와 다르다. 안전 복귀 뒤에는 소스 초기화 전까지 연속 자동을 유지해 반복 고정/해제 진동을 피한다. 긴 공백 재버퍼링은 유지 상태를 해제하고 기존 복구 상한을 사용한다. 재참가 또는 소스 초기화는 하한부터 새로 학습한다.

진단 JSON/화면에 `ReserveLearningState`, `ReserveRelearns`를 추가했다. 통화 탭 참가자 카드에 최신 네트워크 RTT(15초 초과 시 오래됨 표시), 앱 수신 큐, 출력 장치 주기, 공유 저지연 사용 여부를 표시한다. 큐는 장치 버퍼를 제외하며 장치 주기는 물리 입출력 지연이 아니다. RTT/2나 이 항목들의 단순 합을 실측 입→귀 지연으로 표시하지 않는다.

## 폐기한 가설과 반증

1. 필요한 빈 큐 대기까지 막는 엄격 고정: 50개 각300초 가상 조건에서 재정렬/시계 편차의 PLC가 증가했다. 가변 출력 -500ppm의 마지막20초 PLC25ms로 기존 기준도 실패했다. 폐기했다.
2. 안전 복귀만 추가한 후보: 복구 기준은 통과했지만 입력 주기 변화에서 앱 큐 중앙값이 기존5ms에서 최대10.042ms로 증가했다. 지연 우선 목표에 맞지 않아 높아진 여유를 고정하지 않는 조건을 추가했다.

## 재현과 한계

- `TransportProbe --reserve-learning-checks REPORT.json`: 학습 정책, 50개 각300초 제어된 패킷/가상 시계 시험.
- `TransportProbe --adaptive-clock-candidate-checks REPORT.json`: 동일 조건의 기존 연속 자동 비교.
- `verify.ps1 -NoRestore`: 빌드/정적 분석·관리형 회귀·서버8개 검사. ProductChecks에 학습 상태/안전 복귀/리셋/기존 정책/상한 유지 검사가 포함된다.
- `verify.ps1 -NoRestore -Integration`: 로컬 ICE/DTLS/SRTP/RTCP·가변 프레임·IPv6 통합 검사.

원본 출력은 Git 제외 `native/.local/*087*`에 보존한다. 합성 시험은 실제 두 PC 장치·친구 회선·게임 부하 또는 음향 입→귀 측정을 대신하지 않는다. 기본값 승격이나 일괄적인 지연 감소를 주장하지 않는다. 기존 배포 폴더·서버·공유기·드라이버·라우팅 설정은 수정하지 않았다. 소스와 문서만 변경했으며 커밋/푸시는 하지 않았다.

## 최종 대조 결과

최종 `learned-final-087.json`과 `continuous-087.json`의 동일 50개 각300초 가상 조건을 비교했다. 양쪽 복구 기준 실패0. PLC/부족 합계의 증가 조건0, PLC 감소 최대5ms/300초. 회복 폐기 증가는 최대0.0208ms/300초였다. 5초 이후 500ms 간격 큐 표본의 중앙값/P95 증가는 각각 최대0.0000/0.0417ms였다. 정상 경로 큐와 입력 주기 변화의 높은 여유 고정 문제는 제거됐다. 이는 일관된 지연 단축 입증이 아니며, 기존 연속 자동 대비 큰 성능 이득을 주장할 수 없다.

최종 빌드 경고/오류0, 관리형 회귀 및 서버8개 통과. 안전 복귀 후보의 로컬 IPv4/IPv6 ICE/DTLS/SRTP/RTCP·가변 프레임 통합 통과 후, 마지막 하한 유지 조건은 전체 관리형 회귀와 위50조건으로 재검증했다.
