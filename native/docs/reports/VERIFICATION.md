## 동일 공유기 두 PC 실제 통화

최종 설정은10ms 송신, 저지연10ms 출력,40ms 시작 reserve/80ms 큐 상한입니다. 노트북 최소 입력 주기1.33ms는 표준10ms 입력으로 복귀합니다. 출력 장치 설정은 변경하지 않았습니다.

| 약3분 통화 | PC | 노트북 |
|---|---:|---:|
| 마지막 송신 프레임 |17783|17742|
| 마지막 수신 패킷 |17779|17746|
| 평균 관측 재생 큐 |40.27ms|65.64ms|
| 누적 부족 길이 |130ms|62ms|
| 부족 횟수 |10|3|
| 초과 큐 정리 |1|1|
| 송신 큐 버림 |0|0|

서로 시작/종료 시각이 달라 마지막 누적 패킷 수 차이를 손실률로 해석하지 않습니다.
노트북→PC 루프백10회 성공, 범위 중심값의 중앙값102.46ms. 회차별 시계 범위15.8~31.5ms 및 검출 여유±20ms를 포함하므로 정확한 단일 지연값이 아닙니다. 첫 회차 범위114.6~170.8ms는 별도로 남겼습니다. 캡처 프레임→인코딩 단계의 중앙값19.02ms였습니다.

20ms 시작 reserve/60ms 상한의 첫 시도는 PC 누적 부족2059.7ms /33회 /큐 정리50회로 악화해 철회했습니다. 해당 보고서에는200~300ms 수신 간격도 있어 버퍼만이 유일 원인이라고 단정하지 않습니다. 보정 후 부족이 크게 줄었지만 순간 부족과 큐 정리는 남았습니다.

검사 도중 별도 로컬 스피커→마이크 검사는 검출하지 못해 중단했습니다. 디지털 루프백과 물리 경로 측정을 구분합니다. 후속 인터넷/TURN, 그룹, 장시간, 다양한 장치 검증은 별도입니다.

원본 보고서는 Git 제외 경로 `.local/reports/`에 보존합니다: `pc-ten-ms.json`, `laptop-ten-ms.json`, `pc-ten-safe.json`, `laptop-ten-safe.json`.

## 역방향 추가 검사

PC→노트북 출력 루프백은10회 중9회 검출했습니다. 범위 중심값 중앙값274.50ms, 성공 범위는220.1~347.2ms입니다.1회는 검출 시각이 유효 범위 밖이어서 제외했습니다.
동일 패킷 추적에서 캡처→인코딩은 대체로19ms, PCM 큐17~76ms, **출력 제출→루프백 검출 약198~209ms**였습니다. 따라서 앞선 방향의102ms와 같은 값으로 묶거나 정확한 네트워크/장치 단독 지연으로 해석할 수 없습니다. 남은 출력 경로에는 OS/드라이버/DSP, 루프백 수집 지점과 검출 동작이 포함되어 있으며 원인을 분리하지 못했습니다.
역방향 약3분 통화에서 PC 누적 부족37.15ms/7회/큐 정리0회, 노트북32ms/2회/큐 정리2회, 양쪽 송신 큐 버림0과 장치 오류 없음입니다. 실제 양방향 스트림은 정상이나 순간 부족은 남았습니다.

추가 원본: `.local/reports/pc-ten-reverse.json`, `laptop-ten-reverse.json`.
현재 결론:10ms 송수신·복귀 경로를 검증하고 과도한 버퍼 축소를 철회했습니다. 전체 지연 목표를 달성했다고 선언하지 않습니다. 다음 정밀 검증은 상대 출력 제출→디지털 루프백 수집/검출의 분리, 이후 통제된 동일 환경20/10ms 비교입니다.

## OCI TURN · 2026-10-07

coturn과 voice-native 자동 시작 서비스, Ubuntu UDP3478/49160–49259 규칙, 만료 HMAC 자격 증명 발급을 배포했습니다. OCI 보안 규칙은 사용자가 추가했습니다. 연결 API 회귀 및 새 자격 발급 검사 총7개가 통과했습니다.
`TransportProbe --turn-integration https://qlrpal.ddns.net/`에서 두 피어의 relay 후보가 OCI 공인 IP49185/49204 포트로 선택됐습니다.10ms Opus SRTP 디코딩, 양방향 데이터 채널과 RTCP가 통과했습니다. RTCP RTT21.54/22.99ms, 보고 손실0%. 검증 피어는 같은 PC에서 실행됐지만 음성 경로는 OCI 중계만 허용했습니다. 서로 다른 회선의 친구 통화는 별도 검증입니다.
