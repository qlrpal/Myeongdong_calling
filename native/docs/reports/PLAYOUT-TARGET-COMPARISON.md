# 재생 목표 대기 비교 · 2026-10-16~17

앱 내부 수신 대기를 줄일 수 있는 지점을 찾았지만, 고정 목표를 기본값으로 적용하지 않았습니다. PC에서는 수신 콜백→디코딩 대기가 일부 줄었고, 노트북에서는 낮은 대기와 함께 늦은 패킷의 PLC 대체가 늘었습니다. 기존 안정 버전의 기본 동작과 배포 파일은 유지합니다.

## 조사와 구현

기존 소비율 보정기는 시작 2초 동안 읽기 직후 큐를 학습하여 목표를 20~30ms로 정합니다. 따라서 설정된 최소 여유 20ms와 실제 소비율 보정 목표는 다를 수 있습니다. 이는 시작 위상과 지터를 흡수하는 여유이기도 하므로 전부 불필요한 지연이라고 판단할 수 없습니다.

- JSON에 `ClockTargetMs`와 `ClockFilteredQueueMs`를 추가해 목표와 실제 평활 큐를 구분합니다.
- 진단 도구에만 `--playout-target-probe SERVER ROOM OUTPUT ROLE learned|fixed`를 추가했습니다. `fixed`는 목표 학습 대신 명시된 20ms를 사용합니다.
- Opus 10ms, 고정 여유 20ms, 적응 여유 끔, WASAPI 저지연 요청, 시작 조건, PLC 상한과 소비율 상·하한은 동일합니다. UI에서 실험 모드를 켜지 않습니다.
- `--playout-target-test OUTPUT`은 동일한 패킷 도착을 재현하는 가상 검사입니다. `verify.ps1 -Stress`에 포함했습니다.
- 자동 추적 종료 뒤 2초간 통화를 유지하여 상대의 마지막 진단 주기와 종료가 겹치는 문제를 완화했습니다. 비교 시험 실행 파일은 이 종료 유예 수정 이전 빌드입니다.

## 가상 시간 비교

60초 상당씩 24쌍을 비교했습니다. 출력 요청 5/10/20/40ms, 도착 위상 0/3/7ms, 반복 30ms 수신 정지 유무를 조합했습니다. 실제 오디오 장치·네트워크·주관적 음질 검사가 아닙니다.

규칙적인 입력에서는 두 모드 모두 PLC·부족·큐 정리 없이 진행했습니다. 일부 20/40ms 출력 조건은 후반 평균 큐가 약 5~10ms 줄었습니다. 반면 20ms 출력·위상 0·반복 30ms 정지에서는 기존 PLC/늦은 패킷 0이 실험 모드 PLC 280ms·늦은 패킷 28개로 늘었습니다. 목표 감소의 안정성 비용을 동일한 도착 조건에서 재현했습니다.

## 두 PC 실제 통화

PC 유선 ↔ 노트북 Wi-Fi, LAN 직접 연결, 각 회차 약 120초입니다. 출력은 PC 44.1kHz 스테레오, 노트북 48kHz 스테레오이며 두 장치 모두 엔진 주기 10ms·저지연 경로 활성 상태였습니다. 장치 설정은 변경하지 않았습니다. 음성이나 페이로드는 저장하지 않았습니다.

아래는 시작 후 60초부터 종료 1초 전까지의 **수신 콜백→디코딩**입니다. 통계는 패킷별 같은 수신 PC의 시계로 계산하며 물리적인 입→귀 지연이 아닙니다. PLC 등 카운터는 이 구간 안의 약 1초 간격 진단 표본 차이입니다.

시험상 한계도 있습니다.

- 회차 2 초반에 회차 1의 약 24MiB 보고서 회수가 겹쳤습니다. 시작 5초 이후 전체 구간에는 PC PLC 900ms·재버퍼링 3회, 노트북 PLC 1230ms·재버퍼링 2회가 있습니다. 해당 구간을 목표 변경 탓으로 단정하지 않습니다.
- 회차 3 일부에는 로컬 회귀·부하 검사가 겹쳤습니다. 완전한 통제 A/B/A 자료로 취급하지 않습니다.
- 회차 4는 파일 전송과 별도 검사 종료 후 반복했습니다. 후반 수신 도착 간격 P95/최대는 PC 15.69/51.99ms, 노트북 15.86/42.19ms였습니다. 노트북에서 반복된 늦은 패킷은 낮은 대기로 처리 기한을 놓칠 수 있음을 보여주지만, 한 회차로 정확한 원인별 기여도를 분리하지는 못합니다.
- 회차 1 노트북은 약 120초 끝에서 상대가 먼저 나가 오류가 기록됐습니다. 원본 오류를 유지하고, 수집 기간이 118초 이상인 이 종료 경계 오류에만 내부 구간 분석을 허용했습니다. 조기 종료·다른 오류·추적 퇴출은 거부합니다. 이후 회차는 오류 없이 완료됐습니다.

추적 기록 퇴출은 모두 0이며 기록 처리 최대 시간은 약 0.048~0.159ms였습니다. 후반 구간에서 장치 오류·장치 재시작·무음 부족은 없었습니다. PLC는 무음 부족이 아니며 손상 없는 실제 음성 수신과도 다릅니다.

## 결론과 다음 단계

1. **기본 목표 학습 방식 유지.** 고정 목표는 진단용 실험으로만 남깁니다. 배포 파일·서버·방화벽은 변경하지 않았습니다.
2. 시작 위상에 따라 목표가 20ms 또는 30ms가 되는 점과, 목표가 같아도 큐가 5ms 허용 대역의 아래쪽에 머무르는 점을 조사합니다. 출력 요청 시점과 패킷별 재생 기한을 함께 분석해야 합니다.
3. 다음 후보는 단순한 목표 감소보다, 패킷 도착 변동에 따른 재생 기한/여유 회복입니다. 같은 도착 기록을 재생해 대기·PLC·늦은 패킷을 비교한 뒤, 다른 부하 없는 두 PC 시험으로 확인합니다.
4. 캡처 전달 약 17~19ms 조사는 이 재생 경로의 판단 이후 진행합니다. 이번 수치를 전체 통화 지연으로 합산하지 않습니다.
