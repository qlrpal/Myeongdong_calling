# EXTREME-140 — 유선 기준선의 평상시 수신 여유 단독 비교

2026-11-02 / 기반 `5ce456b`. 입력 불연속 보완과 분리해 평상시 대기를 줄이는 시험이다. 기존113의 무선 조건에서 기각한 결과를 지우지 않고,136 이후 확보한 양쪽 유선 경로에서 같은 변수만 다시 비교했다.

## 조건·가설

같은 메시 버디 LAN측 PC 이더넷/노트북 ASIX1Gbps, 노트북 Wi-Fi 해제, 소켓별 유선 바인딩·직접 UDP·기본 수정 SDK·native Opus LowDelay64·48kHz mono·10ms 프레임·기존 상대별 WASAPI 공유 출력을 유지했다. 프레임·코덱·장치 주기·출력 패딩을 함께 바꾸지 않았다. Tailscale은 유지하되 미디어에 선택되지 않았는지 각 보고서에서 확인한다.

가설은 낮아진 도착 변동에서20ms 수신 여유가 남기는 정상 대기를15/10ms로 줄일 수 있는지다. 단순 큐 감소뿐 아니라 같은 프레임의 호스트 내부 두 기간 합, 전체 품질, 실제 장치 주기와 자원을 비교한다. 실제 마이크 음향 대신 기존 합성 신호를 실제 장치 콜백에서 공급하며 입→귀 측정이 아니다.

각45초 상세 관측의 실행 순서는20→15→20→10→20ms다.15ms 대조는 첫 세 회차,10ms 대조는 마지막 세 회차로 각각 A/B/A를 구성한다. 각 회차는 별도 통화·입퇴장·음소거·재참가·정리 검사이며 한 통화의225초 연속성으로 표현하지 않는다.

실제 두 PC 시험은 개발 CLI 추가 전의 동일 앱 SHA256 `36D9C78AF976DB2BABB02F301684153D14C3717A3208F4CE1A7623703A5A9B6B`를 사용했다. 기존 검사 도구의 같은 엔진 매개변수로 여유만 변경했다. 새 CLI는 그 매개변수를 일반 마이크 통화 비교에 전달하며, 새 CLI 빌드 자체로 두 PC 측정을 다시 했다고 표시하지 않는다. 여섯 실행의 모든 표본 끝점/전송 방식·연결/재참가 소켓과 양쪽6기능·별도 pair merge를 확인했다.

## 평상시 같은 프레임의 기간 합

송신 장치 보고 첫 샘플→송신 API와 수신 인증 콜백→첫 PCM 공급을 같은 SSRC/RTP 시각으로 연결했다. 다른 PC의 절대 시각은 빼지 않았다. 정상 창 필터·샘플 가중·유일 대응을 기존 분석기로 적용했다. 아래는 평균/P95(ms)다.

| 순서 / 여유 | PC→노트북 | 노트북→PC |
|---|---:|---:|
| A1 /20ms |41.545 /50.075|45.077 /50.579|
| B /15ms |40.507 /49.774|34.550 /44.283|
| A2 /20ms |43.743 /52.420|42.482 /47.505|
| C /10ms |39.978 /49.174|30.078 /36.385|
| A3 /20ms |41.637 /50.117|45.793 /51.905|

10ms 후보의 정상 기간 합 평균은 인접20ms 대조보다 PC→노트북 약1.66~3.77ms, 역방향 약12.40~15.71ms 낮았다. 감소량이 설정 차이10ms와 같거나 양방향에 균등하지 않다. 장치/프레임/렌더 위상과 캡처 전달의 실행 간 변동이 섞인다. 특히 이 합은 전송/SDK 일부·장치 공급 이후 출력·내용상 코덱 지연을 포함하지 않으며 물리 입→귀 개선 수치가 아니다. 프레임 첫 공급 시각의 렌더 요청 양자화·정상 재생 생존 편향도 남는다.

다섯 상세 관측의 baseline 표본 차이에서 양쪽 PLC·재버퍼·늦은 폐기·무효/중복·복구 폐기·송신 폐기·PCM 부족·렌더 소진/안전 전환은0이었다. 노트북 입력 불연속은0/3/0/0/1회였다. 따라서 입력 자체의 연속성까지 무오류라고 하지 않는다.

## 실제 사용 비교를 위한 변경

개발용 `run.ps1 -ReceiveReserveMs 10` 또는 앱 `--receive-reserve-ms 10`을 추가했다. 기존 내부 `DiagnosticReserveMs`만 전달하며10~40ms 정수를 허용한다. 프레임·출력·송신·SDK 정책을 묶어 바꾸는 새 극저지연 프리셋은 만들지 않았다. 앱 제목에 비교값을 표시한다. 시작 시 다른 극저지연 실험과의 혼합은 거부한다.

일반 실행은20ms 그대로이며 공개 베타 빌드는 이 CLI 옵션을 받지 않는다. 비교 중에는 기본 모드/저지연 재생 선택을 유지한다. 다른 재생 정책이나 실험으로 바꾸면 그 정책의 여유가 적용될 수 있으므로 같은 조건의 단독 대조로 사용하면 안 된다. 진단의 실제 `TargetReserveMs`를 확인한다. 이 변경은 실사용 마이크로 후보를 재현하는 개발 도구이며10ms의 제품 기본값 채택이 아니다.

```powershell
./native/run.ps1 -ReceiveReserveMs 10
./native/run.ps1                    # 기존20ms로 복귀
```

낮춘 값은 이 PC의 수신 방향에만 적용된다. 양방향 비교는 상대도 같은 조건으로 실행해야 한다. 네트워크 품질이 다르면 결과를 일반화하지 않는다.

PC 출력의 목표 패딩/용량은 모두5.833ms라 추가 안전 전환이0인 것을 소진이 없다는 뜻으로 해석하면 안 된다.

이 사건으로 후보의 무끊김을 선언할 수 없다.20ms를 같은 길이·같은 계측으로 맞춘 새180초 대조는 없으므로10ms가 소진의 원인이라는 결론도 내리지 않는다. 평상시에는 여유 축소 이득이 있지만, 전체 꼬리와 연속성이 함께 검증된 제품 기본값은 아니라는 기존 판단을 유지한다. 새 개발 CLI는 비교 도구로만 남기며 낮춘 값을 권장 기본값으로 게시하지 않는다.
