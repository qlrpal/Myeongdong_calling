# EXTREME-089 — SSH 노트북 실제 직접 연결 A/B/A

2026-10-25. 사용 가능한 노트북 SSH로 최신 동일 빌드의 두 Windows PC를 시험했다.

## 설계

기존 opus-adaptive(A1) → opus-learned(B) → 기존 opus-adaptive(A2), 각90초. 실제 공유 입력/출력과 ICE/DTLS/SRTP 직접 연결을 사용하고 입력 데이터는 합성 음성으로 대체했다. OCI는 신호 교환에만 사용했다. 양쪽 VoiceNative.dll SHA256/MVID가 일치함을 확인했다. 노트북은 별도 임시 시험 폴더에서 실행했으며 기존 설치를 덮어쓰지 않았다.

양쪽 시계 절대값을 빼지 않았다. 아래 비교는 각 호스트의 시작35초 이후 약54초 구간이며 큐는 장치 버퍼를 제외한다. RTT는 네트워크 왕복이며 전체 입→귀 지연이 아니다.

## 관측과 판정

- 세 구간 양쪽 연결/장치 오류0, 송신 큐 드롭0. 기능 완료는 품질 합격이 아니다. 실제 PLC와 출력 부족은 남았다.
- B의 모든 진단 표본에서 양쪽 모두 Learning이며 Holding에 진입하지 않았다. 지속적으로 높아진 수신 여유가 하한으로 돌아오지 않아 유지 조건이 성립하지 않은 것이다. B의 낮은 일부 수치를 유지 정책의 개선량으로 해석할 수 없다. 네트워크 RTT도 구간마다 달랐고 반복 횟수는 적다.
- 마지막30초 기록은 퇴출0. 여섯 방향별 대응 범위(각 약11,852–11,866프레임)에서 송신 앱 시퀀스 공백0, 수신 콜백 관측 누락0, 패킷 길이 불일치0. 관측되었지만 큐에 들어가지 못한 패킷은48–73개로, 입장 기록상 late였다.
- 이것은 해당 짧은 대응 범위에 수신 관측 누락이 없었다는 뜻이다. 90초 전체 무손실, 물리 NIC 송수신, 무선/AP 원인 확정 또는 수신 처리만의 책임을 입증하지 않는다. 도착 지연·마감·버퍼 시간축의 관계는 추가 대조가 필요하다.
- PC 입력 주기10ms, 출력 약10.159ms(44.1kHz 믹스 포맷). 노트북 입력 약5.333ms, 출력10ms. API 출력 지연 참고값은 각각 약11.179/11ms다. 이 수치를 물리 입출력 지연으로 간주하지 않는다.

## 결론과 보존

새 모드의 기본값 승격을 보류한다. 이 환경에서는 유지 정책의 효과보다 실제 지연 도착/출력 부족을 별도로 줄이는 대조가 필요하다. 기존 배포본·시스템 오디오 설정·드라이버·공유기·시스템 라우팅은 변경하지 않았다. 시험 프로세스는 모두 종료하고 진단 원본을 `native/.local/extreme-089/`에 보존했다. 노트북 임시 시험 폴더도 원본 보존용으로 남겼다. 소스 커밋/푸시는 하지 않았다.
