# EXTREME-116 — 정상 공개 주소의120초 직접/TURN 연속성 관측

한국 시각2026-10-28, `codex/extreme-latency` / HEAD `78ef68a`와 기존 미커밋 작업을 보존했다.115에서 수정한 No-IP A 레코드 이후 기존 Release 바이너리로 시험했다. 제품 코드·기본 프레임·수신 여유·배포본·운영 서버 설정을 변경하지 않았다.

## 목적과 조건

30초 기능 검사보다 관측을 늘려 남은 PLC·캡처 불연속·재버퍼 및 재참가 HTTP 실패를 확인한다. 두 실제 PC가 정상 공개 HTTPS와 원래 TURN UDP URL을 사용하며 프록시·hosts 수정·TURN hostname 대체·SSH 신호 포워딩은 없다. SSH는 시험 실행과 파일 수집만 수행한다.

기존 출력, 네이티브 Opus64kbps/10ms, LowLatency 정책, 수신 여유20ms, 통화별 LAN 인터페이스 지정, 실제 공유 WASAPI 장치, 합성 음성 교체 입력이다. 각 경로 baseline120초, 준비2초 제외,250ms 진단 스냅샷 후 음소거/해제·양쪽 퇴장/재참가·종료6검사를 수행한다. 직접→TURN은 경로 기능 확인이며 설정 최적화 A/B/A가 아니다. 같은 집의 두 PC이고 의도적인 게임 부하는 주지 않았다.

## 분석 방법과 관측 한계

기존 양쪽 병합·관측 분석기를 사용한다. 추가 비공개 분석은 각 PC의 로컬 단조 시각에서 인접 스냅샷의 입력 불연속/타임스탬프 오류·PLC 오디오 시간·늦은 폐기·RTP 전방 시간축 공백 증분을 기록한다. 구간 합계가 기존 분석 총계와 일치하는지 검증한다. 카운터 누락·역행은0으로 대체하지 않고 실패시킨다. 신호/오디오의 실시간 경로에 추가 로그를 넣지 않는다.

250ms 간격의 사건 구간은 패킷별 원인 대응이 아니다. 다른 PC의 비동기 시각을 빼거나 양쪽 구간을 직접 정렬하지 않는다. WASAPI DataDiscontinuity 카운터는 드라이버가 전달한 플래그 횟수이며 잃은 오디오 길이·네트워크 패킷 손실 수가 아니다. 기존 입력 구현은 불연속 시 미완성 입력 프레임을 정리하지만, 이번 자료만으로 해당 정리 길이·장치 누락량을 산출할 수 없다.

PC 입력은10ms 공유 주기이며 안전한10ms 미만 주기가 없어 기존 호환 입력 경로를 사용한다. 노트북은5.333ms 공유 주기다. PC의 CaptureExecution은 해당 경로에서 null이므로 노트북 전용 스레드 계측과 동등한 완전 계측으로 해석하지 않는다. CaptureGap/Work P95·최대는 최근 처리창 값이며 전체120초의 콜백별 분포가 아니다. max execution 값도 세션 시작부터의 누적 최대일 수 있다.

두 경로·양쪽의 입력 불연속/타임스탬프 오류·송신 큐 폐기·잘못된 오디오 패킷·렌더 empty 증분은0이었다. 수신 전방 RTP 시간축 공백은 직접 양쪽0ms, TURN PC120ms/노트북110ms였다. 이는 버퍼가 관측한 시간축 공백이며 물리 패킷 손실량으로 단정하지 않는다. 노트북이115의 짧은 시험에서는 불연속을 보고했지만 이번에는0이므로 지속적인 장치 실패로 일반화하지 않는다.

TURN PC의 로컬 baseline 약5.57–5.83초,53.52–53.77초 구간에서 각각60ms PLC·늦은5패킷·전방 시간축 공백50ms·재버퍼1회가 함께 증가했다. 노트북도 자신의 로컬 구간 약5.66–5.92초,53.30–53.55초에서 재버퍼와50ms 시간축 공백을 보고했다. 양쪽 baseline은 독립 로컬 시각이므로 같은 물리 사건이라고 확정하거나 시각 차이를 전송 지연으로 계산하지 않는다. 캡처 불연속 없이 이 증상이 발생했다는 점은 확인했으나 송신 API→UDP→TURN→UDP→SRTP→재생 입장의 정확한 폐기 경계는 이번250ms 집계만으로 분리할 수 없다.

새 RTCP RTT 중앙값은 직접 PC1.55/노트북1.35ms, TURN PC21.72/노트북23.12ms다. 물리 입→귀 지연으로 바꾸거나 내부 큐와 합산하지 않는다. OCI의 coturn/voice-native/nginx는 active, NRestarts0이고 서비스 활성 시각은 시험보다 앞섰다. 최근10분 journal warning 이상 출력 줄 수0이었지만 기본 로그에 없는 서버 내부 큐·CPU 스케줄링·네트워크 문제를 배제하지 않는다.

**기능 회귀는 통과했고 TURN 연속성 개선은 남아 있다.** 이번 결과만으로 수신 여유를 늘리거나 짧은 프레임·전용 송신·Pro Audio를 기본값으로 바꾸지 않는다. 향후 제품 변경은 짧은 스파이크 이후 복구 시간·남는 큐를 측정하는 재현 가능한 버퍼 시험과 실제 같은 조건 대조로 평가해야 한다. 네트워크의 모든 물리 원인을 다시 조사하는 전제는 두지 않는다.

종료 뒤 PC/노트북의 자체 시험 프로세스 잔류0, 공개 DNS OCI 주소 유지·일반 HTTPS health200을 확인했다. 시험용 시스템 설정 변경은 없어서 복구할 항목은 없으며 정상화한 DNS는 유지했다. 이번에는 문서/비공개 오프라인 분석만 추가했으므로 제품 빌드/Integration은 반복하지 않았다. 원본 증분 합계와 기존 요약의 일치를 검증했고 공백 검사를 통과했다. 커밋·푸시는 하지 않았다.
