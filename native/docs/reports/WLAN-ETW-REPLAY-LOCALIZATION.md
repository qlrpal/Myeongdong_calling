# 무선 통계 조회 없는 WLAN ETW·UDP 재생 대조

2026-10-16 KST, 앱0.5.4 진단 도구. 동일한 기록 패턴 UDP를 두 번 재생하며 OS UDP 메타데이터와 WLAN AutoConfig 이벤트를 함께 수집했다. WLAN 통계·연결 품질 API 조회는 실행하지 않았다.

## 결론

**짧은 지연은 재현됐지만, 이를 설명하는 스캔·전원·연결 상태·로밍 알림은 관측되지 않았다.** 양방향30ms 초과 수신 간격은 두 시험 합계23개였고,17개는 OS 송신~상대 OS 수신 사이에서 추가된 변동으로 분류됐다. 최대 수신 간격은56.944ms였다. 이전의 약3초짜리 큰 지연 묶음은 이번에는 재현되지 않았다.

노트북 WLAN 전체 기록은 첫 시험에서 scan enabled=true 알림3개, 두 번째0개다. 첫 시험의3개도 UDP 분석 범위 밖인 수집 시작 약159.4초에 발생했다. **모든 큰 간격의 같은 호스트 앞뒤100ms 창에서 선택한 WLAN 이벤트는0개**였다. 스캔 시작/완료 쌍, 전원/화면 상태, 연결/해제/상태, 긴급 스캔 요청, 로밍 예상 알림도 없었다. 드라이버·펌웨어 내부 동작이 이 공급자에 반드시 드러나는 것은 아니므로 스캔·절전·로밍을 배제하지 않는다.

이번에는 PC 유선→공유기 ping도 다수 지연 창에서 함께 늘었다. 대표56.944ms 간격 주변의 PC→공유기는46ms, 노트북→공유기는52ms였다. 따라서 **최신 자료만으로 노트북 무선 링크에 원인을 한정할 수 없다.** 이전의 무선 쪽으로 치우친 결과는 남지만, 공유기 응답/처리와 공통 LAN 경로, 각 NIC 처리도 다시 조사 범위에 포함해야 한다. ICMP 응답 처리와 UDP 전달은 다를 수 있어 공유기 자체가 직접 원인이라고 확정한 것도 아니다.

## 실행과 자료 유효성

| 구간 | PC 수집 시작~완료 | 노트북 수집 시작~완료 |
|---|---|---|
| 기록 패턴1 |22:54:01.41~22:56:50.36|22:53:58.63~22:56:49.63|
| 기록 패턴2 |22:56:53.59~22:59:43.14|22:56:51.39~22:59:42.40|

- 구간별 합성 UDP120초, ICMP125초, OS UDP ETW145초, WLAN ETW170초. WLAN 수집 활성 확인 후 UDP 수집과 시험을 시작했다. 오디오·코덱·WebRTC는 실행하지 않았다.
- 시험 후 확인한 상대/공유기 경로는 PC 이더넷, 노트북 Wi-Fi였다. 시험 중 경로 전이를 연속 계측한 것은 아니다. PC에 연결된 별도 Wi-Fi의 이벤트도 필터에 포함될 수 있으나 유선 UDP 경로의 무선 통계로 해석하지 않는다.
- 각 호스트의 두 구간은 같은 계획 hash·송신 순번·패킷 크기 순서·예정 시각을 사용했다. PC12,343개, 노트북12,348개를 구간마다 송신했다. OS 송신 길이 histogram도 일치했다.
- UDP/ICMP/network trace/WLAN trace 모두 종료코드0, 자체 세션 정상 종료. WLAN 스키마·이벤트 포함 필터·raw QPC·세션명·분석 시간 범위와 UDP PID를 검증했다. 통계 조회 PID/출력은 없었다.
- network ETL4개 약3.15~15.40MB로32MiB 상한 미만이며 분석 범위를 덮었다. WLAN ETL4개 약0.52~1.31MB. ETL8개 모두 손실 이벤트0개다.
- 대응하는 내부 순번 범위에서 누락·중복·역전0개. 호스트별 ICMP 공통 분석 범위는 약109.98~110.62초다. 두 호스트의 절대 QPC를 빼지 않았다.
- 송신 예정 시각→실제 시작 P95는 PC0.500/0.496ms, 노트북0.713/0.718ms. 최대는 PC8.314/10.238ms, 노트북10.720/5.512ms다. 선언한2ms P95 기준은 통과했지만 모든 패킷이 동일한 실제 시각에 송신됐다는 뜻은 아니다.
- 네트워크·드라이버·절전·오디오 설정은 변경하지 않았다. 수집 완료 후 변환과 분석을 실행했다. 배경 트래픽과 무선 환경은 통제하지 않았다. 원자료는 git 제외 `.local/wlan-events-054`에 보관한다.

## 수신 간격과 OS 경계

수신 간격은 연속 패킷 사이 시간이며, 전체 통화 지연이나 입→귀 지연이 아니다. 시간 단위는 ms다.

| 구간·방향 | 분석 패킷 | P95 / P99 | 최대 | 30ms 초과 | OS 경계 사이 변동 |
|---|---:|---:|---:|---:|---:|
| 기록1 PC→노트북 |11,314|11.414 / 13.331|56.944|7|7|
| 기록1 노트북→PC |11,311|16.295 / 17.227|49.642|5|2|
| 기록2 PC→노트북 |11,377|11.494 / 13.312|43.347|4|4|
| 기록2 노트북→PC |11,376|16.307 / 17.305|44.808|7|4|

나머지는 혼합4개, 송신 OS에서 이미 존재한 간격2개다. 노트북의 원본 송신 패턴 자체가 P95 약16.15~16.17ms여서 수신 P95 약16ms 전체를 네트워크 지연으로 읽으면 안 된다. 23개는 양방향 및 시간상 인접 표본을 포함하므로23개의 독립적 원인 사건은 아니다.

## WLAN 이벤트 결과

명시적 포함 필터로14개 ID만 허용했다. 템플릿 필드와 공급자 수준4를 검증했다. SSID/BSSID·프로필명·키·음성·패킷 내용은 포함하지 않는다.

| 이벤트 | ID | PC 기록1 / 기록2 | 노트북 기록1 / 기록2 |
|---|---|---:|---:|
| 백그라운드 스캔 허용 상태 |14054|102 / 102|3 / 0|
| 스캔 요청·긴급 스캔 트리거 |14040 / 14071|0 / 0|0 / 0|
| 스캔 시작·완료 |20022 / 20023|0 / 0|0 / 0|
| 전원 설정·화면·저전력 상태 |14008 / 14036 / 14067 / 14068|0 / 0|0 / 0|
| 연결·radio·상태·연결 해제 트리거 |14000 / 14011 / 14025 / 14072|0 / 0|0 / 0|
| 이전 네트워크 연결 성공·로밍 예상 알림 |30019|0 / 0|0 / 0|

표는 전체170초 WLAN 기록이다. PC14054는 true가 반복된 **허용 상태 알림**이며 실제 스캔102회가 아니다. 실제 스캔 시작/완료는 별도 이벤트다. PC UDP 내부 분석 범위에는 각66개가 있었지만 큰 간격 앞뒤100ms 창에는 없었다. 노트북3개는 UDP 분석 범위 밖이다.

30019도 완전한 로밍 시작/완료 계측이 아니며, 화면/저전력/전원 설정 알림은 NIC의 실제 sleep/wake나 큐 체류 시간을 직접 측정하지 않는다. 이벤트 없음은 원인 배제와 다르다. WLAN 기록은 ETW 공급자가 제공하는 범위에 한정된다.

## 공유기 대조에서 달라진 점

각 큰 간격에 대응하는 송신 호스트 송신 창과 수신 호스트 수신 창에 각각±100ms를 더해 비교했다. 시각은 호스트 내부 QPC만 사용했다.

| 구간 | 큰 간격 표본 | 노트북→공유기 RTT≥20ms 창 | PC→공유기 RTT≥20ms 창 |
|---|---:|---:|---:|
| 기록1 |12|8|7|
| 기록2 |11|8|8|

첫 시험의 대표 PC→노트북 간격56.944ms는 실제 송신 간격10.037ms, PC OS 송신10.019ms, 노트북 OS 수신56.931ms였다. 주변 PC→공유기 최대46ms/노트북→공유기52ms, 양쪽 loopback0ms였다. 두 번째 대표43.347ms도 주변 PC→공유기29ms/노트북→공유기23ms였다.

첫 시험의 큰 간격 주변 loopback RTT는 모두0ms. 두 번째 노트북은2개 창에서0을 넘었지만 전체 loopback 최대2ms로30ms 이상 변동과 같은 크기는 아니었다. PC loopback은 모두0ms였다. 이것만으로 드라이버/DPC/스케줄링 지연을 배제하지 않는다. 이번 시험에는 그 상세 수집을 동시에 추가하지 않았다.

이전 시험의 큰 묶음에서는 PC→공유기3ms, 노트북→공유기39ms였지만 이번에는 공통으로 증가한 사례가 있다. 한 원인으로 모든 실행을 설명하기보다, **무선 쪽에 치우친 묶음과 공통 LAN/공유기 RTT 변동을 구분**해야 한다. 고정된 ICMP·ETW 부하 자체의 영향과 시간대/배경 트래픽 변화도 남는다.

## 구현과 다음 판단

- `trace-wlan.ps1`/`VoiceWlan.wprp`에 연결 상태와 로밍 예상 알림을 포함한 안전한 이벤트 필터를 추가했다. 활성 sidecar와 수집 QPC 범위를 저장한다. 자신의 고유 WPR 세션만 종료하며 다른 기록은 취소하지 않는다.
- `compare-udp.ps1 -PatternPath PLAN -ReplayOnly -WithWlanEvents`로 통계 조회 없이 두 번 재생한다. WLAN170초·network145초를 별도 세션으로 수집하고 종료 상태를 phase에 남긴다. `-WithWlanMetrics`/`-WlanObserverAb`와 조합하지 않는다.
- `export_raw_wlan.py`는 기존8개/확장14개 필터를 구분해 허용하고, 실제 이벤트가 기록된 필터 밖이면 분석을 거부한다. 과거 자료와의 호환성을 유지했다.
- `analyze_wlan_replay.py`는 계획 재생·OS 경계·ICMP·WLAN을 묶고, 무선 통계 조회 출력이나 미완료·범위 부족 기록을 거부한다. 이벤트0개인 유효 기록도 명시적으로 처리한다.
- 필터/스캔 쌍/상관 창·시계 독립성·조회 금지·기록 범위 검사, 실제 자료 분석 및 PowerShell 구문 검사를 통과했다. 통화 코드·기본 버퍼·배포 패키지는 변경하지 않았다.

**같은 AutoConfig 이벤트 수집을 반복하는 것만으로는 직접 원인을 더 좁히기 어렵다.** 다음 우선순위는 공유기에서 읽을 수 있는 부하·연결별 큐/재시도 자료가 있는지와 NIC 드라이버가 더 세밀한 이벤트를 제공하는지 확인하는 것이다. 공유기 RTT 증가는 UDP 전달 지연과 같지 않으므로, 가능한 경우 제어 응답 처리와 실제 전달 경로도 분리해야 한다. 세부 자료에 접근할 수 없다면 내부 원인 식별 한계를 인정하고, 이미 계측된 앱 캡처 전달·수신→디코딩 대기와 네트워크 순간 변동을 별도 과제로 유지한다. 근거 없이 절전·드라이버 설정이나 재생 여유를 바꾸지 않는다.

이벤트 의미는 시험 호스트의 `Microsoft-Windows-WLAN-AutoConfig` 공급자 manifest를 읽어 확인했다. 포함 필터 형식은 [Microsoft EventFilters 정의](https://learn.microsoft.com/en-us/windows-hardware/test/wpt/eventfilters)를 사용했다. 이전 대조는 [조회 꺼짐·켜짐 보고서](WLAN-OBSERVER-LOCALIZATION.md)를 참조한다.
