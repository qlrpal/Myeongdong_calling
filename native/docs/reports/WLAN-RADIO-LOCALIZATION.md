# 무선 재시도·신호·전원 지표와 UDP 지연 대조

2026-10-16 KST, 앱0.5.4 진단 도구. 이전 통화의 패킷 크기·상대 송신 시각을 합성 UDP로 두 번 재생하며, Native WLAN 통계를 함께 읽었다. 음성·코덱·WebRTC는 실행하지 않았다.

## 결론

**노트북의 무선 재시도와 ACK 실패를 실시간 변화량으로 관측할 수 있게 됐다. 하지만 이 둘이 큰 지연의 직접 원인이라는 증거는 아직 없다.** 두 구간에서 노트북 송신 프레임 대비 재시도 프레임 비율은 약4.45%,4.49%였다. 지연과 겹친 통계 구간에서는5.78%,5.72%였지만, 표본은 각각4개·5개의 약0.5초 구간뿐이다. 통계는 어댑터 전체이고 지연은 수십 ms 단위이므로 이 차이를 인과관계나 통계적 유의성으로 해석하지 않는다.

이전 시험의123개짜리 큰 지연 묶음은 재현되지 않았다. 다만 두 번째 재생에서 **양방향 최대 수신 간격80.581/85.472ms**가 발생했다. 해당 패킷의 송신 간격은 약10/15.96ms였고, 큰 수신 간격은 상대 OS 수신 기록에도 존재했다. 인접한 각 호스트의 ping 기록에서는 노트북→공유기53ms, PC→공유기2~3ms, 양쪽 loopback0ms였다. 기존의 **노트북 NIC/무선 링크/AP 처리 경로** 조사 방향과 일치하지만, 재전송·펌웨어 큐·절전 동작·AP 스케줄링 중 무엇인지 분리하지 못했다.

수신 간격은 앞뒤 패킷의 도착 간격이다. 위80~85ms를 통화의 평균 지연이나 마이크→상대 출력 지연으로 해석하면 안 된다.

## 실행과 유효성

| 구간 | PC 수집 시작~완료 | 노트북 수집 시작~완료 |
|---|---|---|
| 기록 패턴1 |19:30:41.44~19:33:07.06|19:30:40.16~19:33:05.86|
| 기록 패턴2 |19:33:08.30~19:35:33.85|19:33:06.50~19:35:32.21|

- 구간별 UDP120초, ICMP125초, 네트워크 ETW·WLAN 조회145초. 분석은 양쪽 공통 순번 및 호스트별 내부 약110초 범위다. 두 PC의 절대 QPC를 빼지 않았다.
- 네 구간 모두 test/ICMP/trace/WLAN 프로세스 종료코드0, WLAN handle 열기·닫기0. 분석 범위의 열거·조회 오류와 구조 해석 오류0개다.
- ETL4개 모두 손실 이벤트0개, 정상 종료,32MiB 상한 미만이며 분석 범위를 덮었다. raw QPC, 세션명, PID를 검증했다.
- PC는 구간별12,343개, 노트북은12,348개를 송신했다. 계획 hash·크기 순서·송신 순번·예정 시각·OS 송신 길이 histogram이 일치했다. 공통 분석 순번 범위의 누락·중복·역전0개다.
- 예정 시각→실제 송신 시작 P95는 PC0.522/0.515ms, 노트북0.725/0.716ms로 선언한2ms 기준 이내다. 최대값은 PC9.152/11.407ms, 노트북10.873/20.815ms로 일부 송신 스케줄 지연은 남아 있다.
- PC의 상대 경로는 이더넷, 노트북은 Wi-Fi다. PC의 별도 연결된 Wi-Fi도 조회되지만 해당 UDP 경로를 대표하지 않는다.
- 드라이버·절전·네트워크 설정은 변경하지 않았다. ETL 변환과 분석은 모든 타이밍 수집 종료 후 실행했다. 진단 프로세스와 자체 ETW 세션 종료를 확인했다.

## UDP 수신 간격과 OS 경계

30ms 초과 간격의 개수다. 각각 별개의 원인 사건 수와 같지는 않다.

| 구간·방향 | 분석 패킷 | 30ms 초과 | OS 송신~상대 OS 수신 사이 변동 | 최대 수신 간격 |
|---|---:|---:|---:|---:|
| 기록1 PC→노트북 |11,443|2|2|36.269ms|
| 기록1 노트북→PC |11,442|3|0|45.407ms|
| 기록2 PC→노트북 |11,397|3|2|80.581ms|
| 기록2 노트북→PC |11,396|4|2|85.472ms|

나머지는 송신 OS에서 이미 존재한 간격3개, 수신 앱 전달 조사 대상1개, 혼합2개다. 모든 지연을 무선에 귀속하지 않는다. OS UDP 이벤트는 NIC 선로 시각이 아니므로 OS 경계 사이에는 드라이버·펌웨어 처리도 포함될 수 있다.

## 노트북 카운터 변화량

Intel AX201 드라이버는6개 PHY 항목에 **동일한 전체 누적값**을 반복 반환했다. 따라서 합산하지 않고 slot0의 변화량을 대표값으로 사용했다. MAC 송수신 변화량도 PHY 송수신과 일치해, 단순한 미갱신0값과 구분했다. 단, 실제 PHY별 통계라고 가정하지 않는다.

| 지표 | 기록1 | 기록2 |
|---|---:|---:|
| 관측 통계 간격 수 |217|215|
| 송신 프레임 증가 |21,917|21,879|
| 수신 프레임 증가 |22,015|22,069|
| 재시도 프레임 증가 |975|982|
| 여러 번 재시도 프레임 증가 |92|20|
| ACK 실패 증가 |2,168|2,006|
| 재시도 프레임/송신 프레임 |4.45%|4.49%|
| 지연 창과 겹친 구간의 재시도/송신 |23/398(5.78%)|33/577(5.72%)|
| 나머지 구간의 재시도/송신 |952/21,519(4.42%)|949/21,302(4.45%)|

재시도 카운터는 한 번 이상 재시도한 뒤 성공한 MSDU/MMPDU 수다. 모든 재시도 횟수, UDP 손실률, 개별 통화 패킷 수가 아니다. ACK 실패는 예상 ACK 미수신 횟수로 재시도 프레임 수와 같은 분모가 아니다. 두 지표 모두 통화 외 ICMP·SSH·기타 트래픽을 포함한다. failed/FCS 오류 증가와 카운터 리셋은 관측되지 않았다. 이것만으로 무선 문제를 배제할 수 없다.

지연 창은 호스트 자신의 송신 또는 수신 간격을 사용하며 양방향을 합친다. 통계 조회 시작~다음 조회 종료 구간이 창과 겹치는지를 보수적으로 판정한다. 여러 지연이 같은 통계 구간에 겹쳐도 한 번만 계산한다. 펌웨어의 통계 반영 시각까지 검증한 것은 아니다. 최대 지연 근처 약0.51초 통계 구간에서는 재시도 프레임이13개 늘었지만, 어느 패킷이 재시도됐는지는 알 수 없다.

PC Wi-Fi의 PHY 송신·수신·재시도는 모두0으로 고정됐고 MAC 수신만11/20 증가했다. 이는 이번 이더넷 UDP 경로의 무선 재시도가 없었다는 증거로 사용하지 않는다. 실제 활성 PHY 통계를 해당 드라이버가 제공하는지도 확인되지 않았다.

## 신호·전원·조회 자체의 영향

- 노트북 RSSI는 첫 구간−43~−40dBm, 두 번째−42~−39dBm. 최대 지연 전후 조회값은−39dBm이었다. 기록된 표본에서 큰 신호 하락은 없었으나 표본 사이 짧은 변화까지 배제하지 않는다.
- 연결 품질 API의 주파수 원시값은5805로 일정했고, 송신 링크 속도 원시값은 구간 중 변했다. 이 값들은 실측 처리량이 아니다. API 문서와 SDK의 주파수 단위 표기가 달라 원시값을 보존했다. bandwidth 원시값0을0MHz로 해석하지 않았다.
- 양쪽 모두 AC 연결, 시스템 절전 플래그0. 설정된 무선 AC 정책은 최대 성능(0), DC는 보통 절전(2)이었다. **전원 정책·AC 상태는 실제 NIC의 절전 전이·펌웨어 대기 시간을 측정하지 않는다.**
- background scan enabled=true, media streaming mode=false, radio software/hardware=on이 유지됐다. scan enabled는 실제 스캔 실행의 증거가 아니다. radio on은 항상 깨어 있었다는 뜻이 아니다.
- 노트북 조회 묶음 시간 P95는3.250/3.048ms, 최대9.619/9.844ms였다. 조회 시작 간격 중앙값은 약511ms다. PC 조회 묶음 P95는1.702/1.899ms, 최대18.385/2.567ms였다.
- 별도 프로세스의 조회라도 드라이버·펌웨어를 깨우거나 실행 조건을 바꿀 수 있다. 이전 시험보다 지연이 적었던 이유를 코드 개선이나 재시도 감소로 단정할 수 없다. 이번 두 구간은 모두 조회가 켜져 있어 관측 자체의 영향을 분리하지 못한다.

## 구현과 다음 조사

`TransportProbe --wlan-metrics SECONDS OUTPUT`을 추가했다. 읽기 전용 Native WLAN 조회, 실행1~180초, 약500ms 간격, API 코드·조회 시작/종료·Unsigned64 카운터를 저장한다. current_connection·스캔·SSID/BSSID·프로필·키 API는 사용하지 않으며 위치 권한을 변경하지 않는다. 실행은 선택 사항이고 일반 통화 중 자동 실행하지 않는다.

`compare-udp.ps1`에 `-ReplayOnly -WithWlanMetrics`를 추가하고 `Analysis/analyze_wlan_radio.py`에서 기존 raw-QPC 경계 분석과 대조한다. 네이티브 구조 offset/길이/Unsigned64 검사와 분석기 리셋·중복 창 방지 검사를 통과했다. 진단 도구 빌드는 경고0·오류0이었다. 통화 오디오 기본값·배포 패키지는 변경하지 않았다. 원자료는 git 제외 `.local/wlan-radio-054`에 보관한다.

후속 [조회 꺼짐→켜짐→켜짐→꺼짐 대조](WLAN-OBSERVER-LOCALIZATION.md)를 완료했다. 조회를 끈 상태에서도 큰 지연 묶음이 재현됐지만, 조회의 개선 효과나 영향 부재를 확정하지 못했다. 다음은 WLAN ETW 이벤트와 맞춰 스캔·로밍·전원 전이의 실제 이벤트 유무를 조사하는 것이다. 실제 무선 재전송과 AP 큐 체류를 구분하려면 드라이버/AP가 제공하는 더 세밀한 기록이 필요하며, 현재 통계만으로 가능하다고 약속할 수 없다. 이 결과를 근거로 앱의 재생 버퍼를 늘리거나 기본 지연을 바꾸지는 않는다.
