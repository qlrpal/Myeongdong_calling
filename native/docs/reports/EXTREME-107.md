# EXTREME-107 · 공통 출력 후보와 단일 PC 그룹 검증

2026-10-27 / `codex/extreme-latency`. 사용자 요청으로 집 네트워크 물리 원인 조사를 보류하고 앱 완성 작업을 재개했다. 기존 미커밋106 분석/진단 수정을 보존했다. 노트북·OCI에는 접속하거나 변경하지 않았다.

## 현재 구조와 변경 목적

기존은 상대마다 `WindowsAudioDevice`·RTP 버퍼·디코더와 WASAPI 출력 스트림을 만든다.6엔진을 한 PC에 실행하면 각각 상대5명에 대해 총30개 출력 객체가 생긴다. 수신 시계 보정의 독립성은 필요하지만 장치 출력까지 각각 만들 필요가 있는지는 별도 문제다. 이 개수만으로 병목/지연 개선을 단정하지 않는다.

공통 출력 후보는 **상대별 RTP 버퍼·디코더·시계 보정·볼륨을 유지하고**, 같은 출력 콜백에서 즉시 읽어 합산한다. 통화당 WASAPI 공유 출력은 하나다. 추가 PCM FIFO나 다른 프레임/재생 여유를 넣지 않았다. 독점 모드·ASIO·전송/SDK 교체는 없다.

## 실제 수정

- `SharedPlaybackMixer.Read/Add/RemoveAsync`: 고정 scratch와 넓은 정수 합산, 최종 PCM16 포화, 음소거 중 시간축 소비, 비활성 상대 제외, 소스 오류 격리. 구성원 배열은 변경 때만 교체하고 렌더가 구성원 목록 잠금을 잡지 않는다. 진행 중인 읽기가 끝난 뒤 해당 버퍼를 해제한다. 일반40/60ms 요청도 한 번의 상대 읽기로 처리할 scratch를 미리 확보했다. scratch는 읽은 즉시 합산하는 작업 공간이며 재생 대기 큐가 아니다.
- `WindowsAudioDevice`: 기존 출력 초기화·호환 경로·자동 복구를 공통 출력 소유자에도 재사용한다. 상대 sink는 출력 생성 대신 믹서에 등록한다. 재시작은 각 상대 버퍼를 중지/재개하고, 장치 진단은 공통 출력에서 가져온다. `Close` 중복 호출은 같은 완료 작업을 반환해 실제 해제 완료를 기다리게 했다. 입력 정지·출력 해제는 캡처 잠금 밖에서 수행한다.
- `WebRtcCallEngine`: `UseSharedOutput` 선택, 소유자 생성/정리, 상대 제거와 마지막 상대 퇴장 시 공통 출력 해제, 공통 재시작/지연 설정 한 번 적용. 기존 송신·SRTP·UDP 수신·보안 경로는 유지했다.
- `CallDiagnostics/CallForm`: 공통 출력의 등록/활성 상대·소유 출력 수·포화 샘플을 표시한다. 상대별 RTP 지표는 독립 값이지만 장치 지표는 같은 공통 출력이므로 합산하면 안 된다.
- `Program/run.ps1`: 명시적 `-SharedOutput`/`--shared-output true` 선택. 저장된 기존 설정을 자동 이관하지 않는다.
- `SharedOutputChecks`, `LocalGroupOutputProbe`: 가상 비교·실제 장치/로컬 WebRTC 그룹과 명시적 합성 입력 시험 도구를 추가했다. `--audio-devices`는 현재 세션의 활성/default 장치를 읽기만 한다.

## 장치 없는 검사

볼륨/음소거 시간축, 양/음 포화, 큰 요청/부분 읽기, 소스 오류 격리와 재개, 읽기 중 분리 및 재분리 수명을 검사했다. 렌더가 한 소스 읽기에 진입해 있어도 구성원 추가/제거 발표가 막히지 않았고, 실제 제거 완료는 해당 읽기가 끝날 때까지 기다렸다. 믹서는 상대 버퍼의 소유권을 가져가지 않는다.

2.5/5ms Opus 송신과 ±200ppm 가상 시계, 한쪽200ms 입력 공백을 넣었다. 작은 요청과40/60ms 혼합 요청에서 독립 참조 RTP 버퍼를 각각 읽어 합한 결과와 **샘플별 일치**, 디코딩 수·PLC 동일을 확인했다. 큰 요청 fixture는 원래 충분하지 않은 입력/여유에서도 참조와 같은지 보는 검사이며 연속성 합격 조건이 아니다. 이 fixture의 유효성 기준과 정상 짧은 요청 검사를 분리했다.

워밍업 뒤 믹서만5,000회 읽은 현재 스레드 관리형 할당은0바이트였다. 이는 **DSP 국소 결과**이며 RTP/SDK·진단·전체 앱 할당0을 뜻하지 않는다. 읽기 중 예외나 입퇴장 제어 경로에는 별도 객체 생성이 있다.

## 실제 장치 준비와 중단된 시험

최초 RDP 세션은 입력 장치가 없고 출력은 원격 오디오였다. 첫 실제 캡처 시험은 장치 확인에서 시작하지 못했다. 명시적 합성 입력 준비 중 시험 방 이름 길이 제한을 넘긴 도구 오류도 수정했고 실패 원본을 보존했다. 이후 합성 입력/원격 출력 pair는 사용자 RDP 해제 시 장치 재구성 오류로 중단됐다. **이들은 합격 실행이나 일반 물리 장치 품질 검사로 포함하지 않는다.**

사용자가 PC에 직접 로그인한 뒤 실제 기본 입력은 USB 마이크, 출력은 Realtek 헤드폰으로 복구됨을 확인했다. 다음의 완료된 검사는 합성 타이머 입력이 아니라 **실제 공유 입력 콜백에서 합성 음성 fixture로 교체한 오디오**다. 실제 마이크 음성을 저장/전송한 시험은 아니다. 시스템 기본 장치·볼륨·전원·라우팅 설정은 변경하지 않았다.

## 단일 PC 실제 장치 A/B/A

임시 localhost 서버(외부 STUN/TURN 없음), 같은 바이너리, native Opus·수정 SDK·`opus-adaptive`2.5ms·동일 여유·상대 볼륨0.01을 사용했다. 한 프로세스 안의 실제 엔진을2→3→6개 실행하고 다음을 기존 A1→공통 B→기존 A2 모두에서 확인했다.

- 연결·미디어/디코딩 유지·장치 오류 없음.
- 출력 재시작 뒤 각 상대의 재시작 카운터1 증가, 디코딩 계속 진행.
- 상대 음소거 중에도 디코딩 진행, 퇴장 후5엔진·재참가 후6엔진으로 수렴.
- 다른 상대가 모두 나가 혼자 남으면 후보 출력/소스0, 전체 종료 후 새 통화 가능.
- 종료/예외 정리 완료. 후보의6엔진 출력 객체 수6, 기존30.

짧은 six15초 측정은 CPU0.483→0.614→0.440 논리 코어, 합산 PLC460→137.5→40ms였다. CPU/PLC가 함께 일관되게 개선되지 않아 이 값으로 기본값을 바꾸지 않았다.

## 준비 시간 뒤6엔진 반복

일반 공유 장치의 실제 출력 엔진 주기는2.667ms였다. 새 프로세스마다6엔진 연결 후10초 준비 시간을 두고, 공통 R1→기존 RB→공통 R2 각60초를 별도로 측정했다. 이 최종 빌드는 큰 요청 scratch와 확장 참조 검사를 포함한다. 앞선 짧은 검사 빌드와 구분해 해시를 보존했다.

| 지표 | 공통 R1 | 기존 RB | 공통 R2 |
|---|---:|---:|---:|
| 출력 객체 합계 | 6 | 30 | 6 |
| 프로세스 CPU / 논리 코어 | 0.542 | 0.636 | 0.550 |
| 종료 표본 핸들 | 1185 | 1709 | 1183 |
| 종료 표본 스레드 | 100 | 124 | 99 |
| 합산 PLC | 455ms | 205ms | 342.5ms |
| PLC / 출력 요청 오디오 시간 | 0.02548% | 0.01140% | 0.01917% |
| 합산 출력 부족 / 재버퍼 | 0ms / 0 | 0ms / 0 | 0ms / 0 |
| 관리형 할당 합계 | 5.247GB | 5.278GB | 5.249GB |
| GC 정지 합계 | 449.63ms | 473.69ms | 444.58ms |

PLC·출력 요청은 **30개 상대 방향의 합계**다.455ms를 특정 한 사용자가60초 동안 겪은 연속 끊김으로 해석하지 않는다. CPU는 프로세스가 소비한 논리 코어 상당량이며 전체 PC CPU 사용률이 아니다. 핸들·스레드는 프로세스 표본이며 모두 오디오 리소스인 것은 아니다. 할당은 누적 생성량이지 상주 메모리나 누수가 아니다. 출력 객체 수는 앱 소유자 검사이며 OS 전체 세션 감사를 대신하지 않는다.

이 순서에서는 후보의 CPU가 약14~15% 낮고 출력/핸들 수가 줄었지만 PLC는 기존보다 많았다. 큰 폭의 전체 할당 감소도 없었다. **자원 구조 개선과 통화 품질 개선을 동일시하지 않는다.** 실제 지연 감소는 측정하지 않았다.

추가로 기본10ms·공통 출력·6엔진을10초 준비 후30초 검사했다. 디코딩·정상 종료와 출력6개를 확인했고 관측 구간 합산 PLC0ms·출력 부족0ms·재버퍼0이었다. 기본10ms 기존 출력의 동등 반복 비교나 장시간 품질 합격을 대신하지 않는다.

## 채택과 기본값

최종 `verify.ps1 -NoRestore -Integration` 완료: Release 정적 분석/빌드 경고·오류0, 수정 SDK 식별·코덱·송신/수명·믹서/제품·RTP/PLC·서버8개 검사 및 로컬 IPv4/IPv6·가변 프레임 SRTP/RTCP 통합을 통과했다. 빌드 통과와 로컬 기능 성공을 실제 게임/외부망 품질 합격으로 확대하지 않는다.

공통 출력은 구조·기능이 검증된 **명시적 비교 후보**로 남긴다. 기존 출력은 기본값이다. 출력 개수/일부 CPU 이득만으로 후보를 승격하지 않는다. 프레임·RTP 여유·출력 목표를 바꿔 수치를 맞추거나 현재 집 네트워크 문제를 해결했다고 표시하지 않는다.

장치가 없는 세션에서 시험을 가능하게 한 합성 입력은 internal 진단 경로만 사용한다. 일반 실행의 마이크 확인/실제 입력은 유지한다. 사용자에게 입력 실패 시 합성 음성을 자동 전송하지 않는다.

## 실행·복귀와 남은 검사

```powershell
./native/run.ps1 -SharedOutput
./native/run.ps1 -SharedOutput -Experiment opus-adaptive
./native/run.ps1 # 기존 출력
```

자세한 명령·JSON 의미는 [공통 출력 안내](../SHARED-OUTPUT.md)에 있다. 이전 `dist`와 사용자 진단은 변경하지 않았다. 이번 소스는 미커밋이며 요청 없는 커밋/푸시는 하지 않았다. 원본·스크립트·해시·중단/완료 로그는 Git 제외 `native/.local/extreme-107`에 보존한다.

완료된 실제 장치 실행7회의 보고는 모두 error null·실제 캡처 모드였다. 자체 그룹 시험/임시 서버 프로세스가 남지 않았고 기본 입력·출력 ID가 준비 시점과 같음을 최종 확인했다. 사용자의 RDP 전환 외에 시스템 오디오/네트워크 설정 복구가 필요한 변경은 하지 않았다.

독립 두 PC/6개 장치 시계·외부 회선·강제 TURN·실제 게임 부하·물리 장치 분리/재삽입·물리 입→귀 지연은 이번에 미실시다. 명시적 Leave/Join과 같은 장치 재시작은 실제 회선 단절·물리 unplug 시험이 아니다. 기존106의 미해결 공백도 그대로 남아 있다. 이후 기본값 승격은 이 검증과 PLC/마감의 회귀 여부를 확인한 뒤 판단한다.
