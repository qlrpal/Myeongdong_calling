# EXTREME-113 · 10ms 프레임에서 고정 수신 여유20/15/20ms

2026-10-28 / `codex/extreme-latency`. 기존 출력과10ms 프레임을 유지하며 평상시 수신 여유만 줄이는 후보를 실제 PC·노트북으로 비교했다. 기존 미커밋 작업을 보존했고 제품 오디오 알고리즘·기본값·시스템 경로·Tailscale·방화벽·장치 설정·운영 서버·dist는 변경하지 않았다.

## 선택 근거와 판정 기준

112의 기준선에서 PLC 증가 시점 근처에는38–137ms의 최근 패킷 도착 간격 최대값도 기록됐고, 렌더 EmptyEvents는0이었다.250ms 스냅샷/최근 통계라 정확한 패킷 인과관계나 손실 위치를 증명하지 않는다. 물리 네트워크 조사를 재개하거나 렌더 기아를 원인으로 확정하지 않았다.

과거 작은 프레임·적응형 프로필, 공백 재시작 여유와 여러 변수를 섞은 대조를 반복하지 않고 **기본10ms·기존 출력·고정 수신 여유 하나만20→15→20ms**로 비교했다. 기존 내부 `DiagnosticReserveMs`를 시험 도구에 노출했으며 새 제품 프리셋을 추가하지 않았다.

분석기의 후속 대상 조건은 양쪽 큐 중앙값/P95가 각각 두 기준선보다 낮고, PLC 오디오 시간·PCM 공급 부족·재버퍼·늦은 폐기·송신 폐기·잘못된 패킷·렌더 소진이 기준선 최대 범위보다 나쁘지 않은 것이다. 누락 지표는 통과시키지 않는다. CPU 증가와 연결 최대 연속 PLC도 별도로 기록하며 후속 대상 표시가 품질 합격·기본값 승격은 아니다.

## 구현

- `test-pair.ps1 -ReserveMs`/Node `--reserve-ms`: 기본20,10–40ms 범위. 양쪽 값 일치를 요구하고 실제 버퍼 TargetReserveMs도 확인한다. 일반 앱 기본값은 그대로다.
- `PairFunctionalProbe`: 기존 진단 매개변수만 설정하고 보고서/동기화 설정에 수신 여유를 기록한다. 프레임·Opus·출력·장치 주기를 바꾸지 않는다.
- `pair-observation.mjs`의 `--factor reserve` 분석: 대조 중 수신 여유만 달라도 허용하고 나머지 요청/실제 장치 주기·코덱·경로·주소·구조를 확인한다. 기존 출력 구조 대조는 종전처럼 동작한다. 누적 카운터와 마스킹 시간을 사용하며 누락값을0으로 만들지 않는다.

## 준비 실패와 정식 대조의 분리

첫 공개 신호 서버 기준선은 양쪽 기능/정리를 완료했으나 실행 제어가 SSH EOF를 기다리며 멈췄다. 노트북 완료 보고서 pass와 시험 프로세스0을 별도 조회로 확인하고 해당 전용 Python 실행기만 종료했다. 양쪽 원본을 보존했으며 정식 대조에는 포함하지 않았다.

제어를 완료 파일/프로세스 핸들 시간 제한으로 바꾼 다음 세 시도는 **양쪽 모두 HTTP15초 시간 초과로 참가 전에 실패**했다. 별도 health 요청도8초 연결 시간 초과였다. 음성 측정을 시작하지 못했으므로 수신 여유 후보의 실패로 해석하지 않는다. 운영 서버·DNS·라우팅·방화벽을 수정하지 않았다.

이후 PC의127.0.0.1 임시 신호 서버를 기존 인증 SSH의 노트북127.0.0.1 전용 포워딩으로 전달했다. 추가 공개 포트나 서버 설정은 없었다. **SDP/신호만 SSH를 사용하고 실제 음성은 양쪽 LAN 지정 직접 UDP**였다. 임시 서버의 ICE 목록은 비어 있어 TURN/STUN 경로를 사용하지 않았다. 세 조건 모두 같은 임시 서버/포워딩과2초 간격의 완료 파일 조회를 사용했다. 이전 공개 서버 기준선과 수치를 섞지 않았다.

## 정식 실제 두 PC 결과

모든 관측 구간의 PCM 공급 부족·재버퍼·송신 폐기·잘못된 오디오 패킷·렌더 EmptyEvents는0이었다. 연결 최대 연속 PLC는 PC A1/B/A2가20/40/30ms, 노트북은5/40/30ms였다. 각 baseline 첫 표본의 해당 최대값은0이므로 이 증가는 관측 중 발생했다. PLC는 실제 목소리를 들은 주관적 끊김이나 물리 지연 측정이 아니다.

큐 중앙값은 PC 약5.3–7.9ms, 노트북 약4.8–6.5ms 낮았다. PC P95도 낮았지만 노트북 B P95는 A1보다 낮고 A2보다 약0.46ms 높았다. PLC 합계는 B가 A1보다 많고 A2보다 적어 배경 변동이 컸다. B의 더 긴 연속 PLC40ms도 관측됐다. RTCP RTT 중앙값은2.637–3.578ms, 새로운 로컬 보고는10–13개다. 이 수치를2로 나누거나 내부 큐와 합산해 입→귀 지연으로 표시하지 않는다.

실제 장치 주기·장치·포맷·요청 출력·프레임·코덱은 각 호스트 안에서 동일했다. 출력 목표 패딩 등 추가 수치는 원본/분석 JSON에 보존했다. 자원 계측은 C# 프로세스/진단 수집만 포함하며 시스템·audiodg·SSH 전체 비용은 아니다.

## 결정과 미실시

**일반 앱은20ms 유지,15ms의 기본값 승격은 보류한다.** 내부 큐 중앙값을 낮출 수 있다는 관측은 얻었으나 양방향 꼬리 지연과 연속성이 일관되게 유지됐다고 확인하지 못했다. 노트북은 자동 후속 조건도 불충족이다. PC의 조건 통과 표시는 합계/범위 기반의 후속 후보 표시일 뿐, 더 긴 연속 PLC와 CPU 증가를 무시한 채택 판정이 아니다.15ms가 모든 환경에서 더 나쁘다거나 인과적으로 PLC 증가를 유발한다고 확정한 것도 아니다.

후보를 제품 프리셋/자동 설정으로 남기지 않는다. `ReserveMs`는 기존 내부 진단 매개변수를 다루는 시험 옵션으로만 유지한다. 실제 입→귀 지연 개선이나 안정판 완성을 선언하지 않는다. 공개 신호 서버 도달성은 비교 종료 후에도 별도 health 요청에서8초 연결 시간 초과로 남았으며 별개 미해결 사항이다.

외부망·강제 TURN·게임·다인·장시간·물리 장치 분리·물리 입→귀 지연은 이번 후보에서 미실시다. 의도적인 게임 부하를 주지 않았으며 배경 부하와 무선 상태를 완전히 통제하지 않았다. 기존20ms 기준선 사이에서도 PLC 차이가 크므로 한 번의 A/B/A를 통계적 우위/퇴행 확정으로 해석하지 않는다.

## 검증·복구·재현

경고0·오류0 빌드, 제품 검사,11개 Node 실행/병합/분석 테스트와 구문/공백 검사를 통과했다. 분석 테스트는 실제 버퍼 적용 여부, 지정 외 변수 변경과 큐 감소를 PLC 증가로 얻은 후보의 후속 판정 실패를 검증했다. 이번 제품 오디오 알고리즘 변경은 없으며 전체 verify Integration은 반복하지 않았다(111 통과).
