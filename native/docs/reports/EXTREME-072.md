# EXTREME-072 — 소프트웨어 NIC 경계와 DPC/ISR 동시 대조

## 조사 범위와 사전 판정 기준

사용자는 메인 공유기 직결 유선이 불가능하다고 확인했고 중간 보고 없이 가능한 시험을 요청했다. 067~071의 결과를 출발점으로 사용한다. PC 이더넷은 버디 이후 5GHz 무선 백홀이므로 완전 유선 대조로 취급하지 않는다. 기존 MCC·스캔·qWAVE 대조는 반복하지 않는다. 새 설정 변경의 개별 승인 조건은 유지하며, 이번에는 설정 변경 없이 관측한다.

목표는 071 X에서 확인한 앱 RTT 98.7685ms 중 소프트웨어 NIC Tx→Rx 98.6709ms의 내부 후보를 더 나누는 것이다. 이 경계는 실제 전파 송수신 시각이 아니다. 현재 PC에는 Realtek Wi-Fi 하나만 확인됐으며 별도 물리 Wi-Fi 어댑터나 독립 AP 대조는 아직 확보하지 않았다. 논리 VPN 어댑터를 대체 하드웨어로 취급하지 않는다.

| 가설 | 필요한 관측 | 반증 또는 범위 축소 조건 | 관측 한계 |
|---|---|---|---|
| 장시간 DPC/ISR 실행 또는 CPU 점유 | 동일 QPC 사건의 실행 구간·CPU와 패킷 경계 대응 | 충분한 무손실 관측에서 실행 시간이 RTT 대기를 설명하지 못하면 그 사건의 '장시간 실행' 설명은 약해짐 | 짧은 실행은 큐에서 실행 전 대기·펌웨어 지연을 배제하지 않음 |

| 무선 재전송·간섭 | 유효한 재전송·ACK 실패·채널 점유 또는 별도 무선 캡처 | 사건 중 신뢰할 수 있는 기록으로 가설별 예측과 비교 | 기존 Realtek 0 고정 통계는 무효. 현재 AP 통계는 측정 불가 |
| AP 내부 처리·큐 | AP 큐·무선 송수신 시각 또는 독립 관측 지점 | AP 또는 클라이언트 교차 대조에서 가역적 종속성 확인 | 로컬 DNS 응답 큐와 전달 트래픽 큐는 다를 수 있음. 클라이언트만으로 확정 불가 |

사건은 (1) 2.4GHz 단독, (2) 두 로컬 경로 공통, (3) 로컬 정상·외부만 지연으로 구분한다. ±50ms 송신 창의 동시성은 상관이며 동일 패킷·동일 처리 경로의 인과 증거가 아니다. 설정 대조가 없는 이번 시험에서 특정 기능의 인과관계를 확정하지 않는다.

## A — 수집 설계

기존 고정 포트 합성 UDP를 두 source/IP_UNICAST_IF에 바인딩한다. 독립 Python의 로컬 게이트웨이 비재귀 DNS와 자체 echo·OCI·외부 STUN을 150초 기록한다. 기존과 동일한 제한 부하는 자체 OCI에만 보낸다. Pktmon은 DNS/일반 STUN의 고정 시험 포트 6개만, 128바이트·64MiB 순환 제한으로 NDIS/component 경계를 기록한다. 부하 스트림의 payload는 캡처하지 않는다.

WPR은 기존 scheduling 프로필을 바탕으로 ProcessThread/Loader/DPC/Interrupt/CSwitch/ReadyThread만 256MiB 메모리 버퍼에 동시 기록한다. CPU 샘플링·스택·음성·일반 패킷 캡처 없음. 수집 후 각 호스트 raw QPC로 대응하며 무손실·시간 범위·부분 패킷 대응률을 검사한다. 기존 Pktmon 캡처/필터가 있으면 시작하지 않고 WPR은 고유 instance만 시작·종료한다. 시스템 라우팅·공유기·오디오·드라이버·전원 설정·기존 배포본 변경 없음.

원자료와 개인 시험 스크립트는 Git 제외 `native/.local/extreme-072/`에 보존한다. 결과와 종료 확인은 시험 완료 후 아래에 기록한다.

## A — 결과와 보존 범위 검증

150초 합성 대조는 완료했고 두 캡처의 이벤트 손실은 0이었다. Pktmon ETL 2,739,866바이트, WPR ETL 286,261,248바이트. 그러나 WPR 메모리 순환 버퍼에는 DPC/ISR의 **마지막 약 37.62초만** 남았다. 이벤트 손실 0은 순환 덮어쓰기 없음의 보장이 아니다. 명목 150초 전체에 대한 DPC 판정을 하지 않고 실제 QPC 교집합에 한정했다. 더 가벼운 후속 계측에서는 CSwitch/ReadyThread를 제외하고 DPC/ISR와 상태 이벤트의 시간 범위를 보강한다.

| 경로 | OCI P50 / P95 / 최대 | 로컬 게이트웨이 P50 / P95 / 최대 |
|---|---:|---:|
| 버디 백홀 이더넷 | 9.74 / 13.13 / 47.96ms | 1.46 / 3.26 / 35.77ms |
| 메인 2.4GHz | 10.16 / 19.51 / 85.52ms | 1.19 / 10.37 / 77.36ms |

**DPC와 정확히 함께 보존된 사건:** Wi-Fi DNS sequence 4538, appSent QPC 117841.095015:

- 전체 RTT 50.4716ms = 앱→NIC 0.0419 + 소프트웨어 NIC Tx→Rx 50.3417 + NIC→앱 0.0880ms.
- 같은 송신 시각 ±50ms의 이더넷 게이트웨이 최대 3.25ms / OCI 11.01ms. Wi-Fi OCI는 57.21ms, 자체 echo 0.15ms였다.
- 해당 NIC Tx→Rx 구간의 DPC/ISR·timer DPC 449개 중 가장 긴 단일 실행 0.123ms. CPU별 중첩을 합친 가장 바쁜 CPU의 누적 점유 5.8892ms, 가장 긴 연속 점유 0.1230ms였다.
- 다른 정확 대응 DNS sequence 4376도 RTT 42.9690ms / NIC 사이 42.8540ms, 단일 실행 최대 0.116ms / CPU별 최대 누적 4.5591ms였다.

따라서 이 두 사건의 수십 ms 대기를 **하나의 장시간 DPC/ISR 실행이나 연속 CPU 점유**로 설명하는 근거는 없다. 실행 전 DPC 큐 대기, NIC 펌웨어, 무선 절전·전송 및 AP 대기를 배제한 것은 아니다. 서비스 루틴이 ndis.sys로 귀속돼도 그 안의 하위 드라이버 스택은 이번에 수집하지 않았다. ETW MCP의 일반 DPC 경고나 16µs 상한 버킷을 이 수십 ms 사건의 원인 증명으로 사용하지 않는다.

같은 sequence 4538은 tcpip.sys component397부터 NIC385까지 송신에서 약 0.0168ms, 수신에서 NIC385→tcpip397 약 0.0239ms였다. 관측된 필터들의 전달 구간은 짧았고 50ms는 그 사이에서 새로 생기지 않았다. 여러 edge 관측은 최소/최대 시각과 개수를 그대로 보존했으며, component 존재만으로 Nprotect/Npcap/가상 Wi-Fi 필터를 원인으로 지목하지 않는다.

현재 Wi-Fi의 component는 **385**였다. 앞선 071 X의 3을 그대로 쓰면 대응 0이므로 현재 `comp list`의 GUID/MAC/ifIndex=20·rtwlane602.sys로 다시 확인해 분석했다. 이는 이전 MCC 어댑터 재시작 이후 바뀔 수 있는 진단 ID이며 물리 장치 교체 증거가 아니다. 최초 잘못된 ID로 만든 분석 결과는 수정했으며 그 0건을 실제 패킷 부재로 해석하지 않는다.

패킷 대응은 여전히 부분적이다. Wi-Fi DNS 전체 송신/응답 4,845건 중 NIC Rx 대응 794건, Tx/Rx 양쪽 대응 387건이다. 게이트웨이 최대77.36ms와 OCI 최대85.52ms의 완전한 NIC/DPC 내역은 확보하지 못했으며 위 50.47ms 사건과 섞지 않는다. `nic072a-controls.json`, `correlation.json`, `witness-layers.json`에 근거를 보존했다. A 전후 어댑터 고급 속성은 동일했고 Pktmon 중지·필터 없음·자기 WPR instance 종료를 확인했다.

## C — 전체 시간 범위 DPC/ISR와 NDIS 전원·WLAN 상태 대조

CSwitch/ReadyThread를 제외한 가벼운 프로필로 같은 150초 대조를 진행했다. NDIS Power keyword 및 이벤트10023/10047/10048/10057/10067/10072와 기존 제한 WLAN 상태 이벤트만 추가했다. 새 설정 변경 없음. 앞선 B는 XML의 EventCollector 선언 순서가 잘못돼 **WPR 시작 전 검증 실패**로 끝났고 성능 결과가 없다. 선언 순서를 수정하고 `wpr -profiles` 검증 후 C로 새 출력에 실행했다.

WPR 80,740,352바이트 / 154.01초, Pktmon 4,165,216바이트. 두 캡처 손실0. 실제 DPC/ISR QPC 보존 범위 118199.199475~118352.861049로 앱 분석 범위 118204.723467~118347.697115 전체를 덮었다. A의 순환 덮어쓰기 문제를 해결했다. DPC·timer DPC 941,664건, ISR604,909건을 모두 분석했다. xperf의 `DPCTmr`도 포함해야 MCP의 1,546,573개 원시 이벤트와 일치한다. 이 유형을 제외한 중간 분석은 다시 계산했다.

## 사건 분류 — 단독 사건과 공통 후보를 분리

## 전원·무선 상태에서 알 수 있는 것과 없는 것

C의 제한된 WLAN 상태 이벤트90건은 전부14054('AutoConfig background scan Enabled=true')였다. 물리 NIC30건과 가상 Wi-Fi Direct 두 개의60건으로, 실제 스캔 시작·종료나U-APSD 서비스 주기 기록이 아니다. 이 이벤트만으로 스캔이 원인이라고 판정하거나 이미 효과 없던 스캔 설정 대조를 반복하지 않는다.

선택한 NDIS 전원 전환 이벤트는0건이었다. 드라이버가 모든 펌웨어·802.11 절전 상태를 이 이벤트로 내보낸다는 보장이 없으므로 '절전 없음'이나U-APSD/WMM-PS 배제 근거가 아니다. 고급 속성 목록에는 해당 이름의 독립 설정이 없었으며 임의 레지스트리 값으로 만들지 않았다. AP의 신뢰할 수 있는 재전송·ACK·채널 점유·큐 통계는 **측정 불가** 상태다. 기존0 고정Realtek 통계를 다시 유효 자료로 사용하지 않았다.

tracerpt 상태 CSV에는UTF-8/CP949로 엄격히 해석할 수 없는 바이트가 있었다. 원본을 보존하고 byte-preserving 방식으로ASCII provider/ID/GUID 필드만 분석했다. 비ASCII payload를 임의 변환해 뜻을 부여하지 않았다. 사람이 읽는 보고서는UTF-8 한글이다. ETW MCP의 C 요약은 'DPC 미수집'이라고 출력했지만 실제 `dpc_isr` dataset1,546,573건과 raw xperf 기록이 존재했고 networking DPC 조회도 작동했다. 이 요약 문구를 근거로 재수집하지 않았다.

## 현재 결론·복구·다음에 필요한 실제 대조

- 정확히 대응한2.4GHz 사건에서 앱/관측된 상위 필터 전달은 약0.1ms 수준이고, 수십 ms는그보다 아래의 소프트웨어 NIC Tx→Rx 구간에 남는다. DPC/ISR의 장시간 단일 실행 설명은 이번 사건에서 지지되지 않았다.
- 그러나 NIC 내부 큐·실행 전 드라이버/DPC 대기·펌웨어·802.11 절전·무선 재전송·AP 큐는 아직 분리하지 못했다. 공통 후보도 존재해Realtek Wi-Fi 하나로 모든 사건을 설명하지 않는다. **최종 물리 원인 규명 완료가 아니다.**
- A/C 설정 전후 고급 속성 동일. 원래MCC1·무선 모드45/58·메인2.4GHz AP·IP 유지. Pktmon 중지·필터없음·자기WPR instance 종료 확인. 설정 변경이 없어 복구할 변수 없음. 배포본·앱 음성 처리·공유기·라우팅 변경 없음.
- 남은 인과 대조에는 같은 PC/AP에서 대체 Wi-Fi 어댑터 또는 같은 PC/NIC에서 독립 AP가 필요하다. 메인 공유기 직결 유선은 불가능하고, PC에는 대체 물리 Wi-Fi가 연결돼 있지 않다. 독립 AP/USB 어댑터의 실제 준비 가능 여부는 사용자 확인이 필요하다. 준비되면 연결 방식·변수·예상 관측·복구를 구체화해 개별 승인 후 대조한다. 메인2.4/5GHz와 같은 메시 버디를 독립 AP 하드웨어 대체로 재포장하지 않는다.
- 원격으로 추가 가능한 계측만 반복해 물리 분리를 달성했다고 주장하지 않는다. 같은 사건의 관측을 늘려도 하드웨어 도착/송신 시각이나 AP 내부 상태가 새로 생기지는 않는다.
