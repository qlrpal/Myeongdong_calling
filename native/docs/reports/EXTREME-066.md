# 수신 공백·복구와 패킷 길이 대조 (2026-10-21)

## 범위

지연 우선 원칙으로 065 이후의 수신 공백과 복구를 비교했다. 개인 마이크·이어폰 설정과 OS 장치 설정은 변경하지 않았다. 실제 공유 입력/출력과 합성 음성, 1:1 직접 연결/TURN을 사용한다. 게임 부하·다자·물리 입→귀 측정은 포함하지 않는다.

## 수신 공백의 위치

065 A의 마지막 30초에서 SSRC/RTP 시각으로 송신/수신 기록을 짝지었다. 양방향 각각 관측된 30ms 초과 수신 공백 7개는 모두 분석 도구의 `post-send-before-receive-callback` 범주였다. 가장 큰 공백은 PC→노트북 51.493ms(같은 두 패킷의 송신 간격 9.992ms), 노트북→PC 51.898ms(송신 간격 10.881ms)였다.

이는 송신 API 반환 이후부터 수신 콜백 사이에서 큰 간격이 추가됐다는 관측이다. 네트워크·커널·라이브러리 스케줄링을 나눈 결과나 물리적 전송 지연 측정이 아니다. 송신 API 반환 역시 실제 전파 송출 시각은 아니다. 서로 다른 PC 시계의 절대값을 빼지 않고 각 PC 내부의 간격을 비교했다.

수신 버퍼 잠금 대기는 같은 기록에서 최대 PC 약 0.103ms / 노트북 약 0.181ms였다. 대부분의 렌더 공급 작업은 1ms 미만이지만 PC에서 10.269ms 한 건도 관측됐다. 장치 소진의 원인을 하나로 확정하지 않는다.

동일 기록에서 PC의 늦은 수신 85개, 노트북의 120개는 모두 앞서 빈 큐에서 해당 RTP 시각을 손실 보간으로 진행한 뒤 도착했다. 보간 결정→도착 중앙값은 6.008/6.872ms였다. 더 오래 보류하면 일부 패킷을 살릴 수 있지만 스트림 지연·폐기량과 상충하므로 별도 재현 시험을 수행했다.

## 기각한 복구 변경

- 안정 대기 2/3/4/6초와 빈 큐 보류 2.5/5/10/15/20/30ms를 동일 기록에서 비교했다. 연속 PLC 한도 이내이면서 패킷 길이에 정렬되는 경우만 실행한다.
- 064의 좋은 조건에서는 보류를 5ms 이상으로 늘릴 때 지연 중앙값이 낮아 보이면서도 보간/폐기가 크게 늘었다. 재생된 일부 패킷의 지연만으로 최적화를 판정하면 안 된다. 긴 보류는 채택하지 않았다.
- 첫 빈 큐 보류에서 그 시간만큼 적응 여유를 즉시 올리는 후보도 만들었다. 좋은 기록에서는 보간·폐기를 줄였지만 수신→렌더 중앙값이 PC 약 1.77ms / 노트북 약 0.80ms 늘었다. 실기 120초 TURN에서는 PC 18.98ms / 노트북 26.36ms, 부족+보간 약 1.41% / 1.16%로 기준을 통과하지 못했다.
- 해당 여유 반영 후보의 코드·검사는 최종 소스에서 제거했다. 재현용 소스/바이너리와 원시 결과는 Git 제외된 시험 폴더에만 보존했다. 권장 2.5ms 프로필은 그대로다.

## 5ms 적응 프로필

`opus-adaptive-5`는 Opus 5ms, 여유 5~20ms, 연속 PLC 한도 30ms, 공유 출력 엔진 주기+1ms다. 안정 대기는 기존 6초다. 별도의 고정 빈 큐 보류는 없으며, 적응 보류는 실제 5ms 패킷 길이와 상한을 따른다. 약 200패킷/초로 2.5ms 프로필의 절반이다. 고정 여유 `opus-5`와 구분한다.

실제 측정값은 원시 기록 `native/.local/extreme-066/`에 보존한다. 모든 지연 통계는 수신→렌더 공급이며 실제 장치 출력 전이다. 합성 페이로드를 사용하는 재생 시험은 실제 음질 평가가 아니다.

| 최종 5ms 조건 | 수신→렌더 중앙값 / P95 PC | 수신→렌더 중앙값 / P95 노트북 | 부족+보간 PC / 노트북 | 출력 소진 PC / 노트북 |
| --- | --- | --- | --- | --- |
| TURN 5분 | 19.39 / 27.18ms | 17.70 / 19.77ms | 1.041 / 0.777% | 0 / 1회 |
| 직접 2분 | 19.43 / 27.35ms | 22.04 / 23.96ms | 1.406 / 1.128% | 0 / 1회 |

최종 5ms 시험에서 송신 누락·잘못된 패킷·장치 재시작·입력 불연속 증가는 모두 0이었다. 입력 분량은 실시간과 거의 같았다. 하지만 직접 경로는 양쪽 모두 부족+보간 1% 한도를 넘었다. TURN의 PC도 같은 기준을 조금 넘었고, 노트북은 송신/RTP/큐 조건을 통과하더라도 출력 소진 1회 때문에 엄격한 연속성 FAIL이다. 두 조건의 모든 항목을 통과했다고 표시하지 않는다.

별도의 최초 120초 5ms TURN에서는 PC 연속성 PASS, 노트북은 출력 소진 1회만으로 FAIL이었다. 짧은 시험의 좋은 결과를 장시간 보장으로 확대하지 않는다. 이번 결과로 5ms를 일괄 권장값으로 승격하지 않는다.

5ms 기록 여섯 개의 재생에서도 보류 0→5ms를 추가 대조했다. 일부 TURN 기록에서 부족/보간은 줄었지만 폐기가 늘었다. 노트북 직접 기록에서는 보간이 135→465ms, 폐기가 25.15→380ms로 증가했다. 초기 TURN PC 기록에서는 지연 중앙값도 17.45→20.25ms로 늘었다. 일관된 이득이 없어 이 보류 변경도 최종 프로필에 적용하지 않았다.

## 마지막 2.5ms 대조와 최종 선택

같은 최종 빌드의 기존 `opus-adaptive`를 TURN에서 300초 재시험했다. 5ms와 동시에 같은 패킷 손상을 재현한 시험은 아니므로 인과적 우열을 단정하지 않는다.

| 2.5ms TURN 최종 대조 | PC | 노트북 |
| --- | --- | --- |
| 수신→렌더 중앙값 / P95 | 20.05 / 27.51ms | 22.30 / 24.18ms |
| 부족 / 보간 비율 | 0.170 / 0.698% | 0.151 / 0.507% |
| 별도 폐기 비율 | 0.355% | 0.257% |
| 출력 소진 / 송신 누락 / 잘못된 패킷 / 장치 재시작 | 모두 0회 | 모두 0회 |
| 잠정 `continuityPass` | PASS | PASS |
| 입력 장치 불연속 플래그 증가 | 0회 | 3회 |

양쪽 입력 프레임 분량/실제 시간 비율은 약 1.0이고 초과 큐 증가도 없었다. 입력 장치 플래그는 별도 보고 항목이므로 노트북 `strictCapturePass`는 FAIL을 유지한다. 합성 음성은 입력 프레임을 대체하므로 실제 마이크 음성 연속성이나 물리 지연까지 통과했다는 뜻은 아니다.

**기존 2.5ms 적응 설정을 유지한다.** 5ms는 앱/실행 스크립트에서 명시적으로 선택하는 비교용 프로필로만 추가했다. 보류 확장·빠른 축소·첫 보류의 여유 반영은 최종 권장값에 채택하지 않았다. 전체 실행의 연속성 실패 사례와 마지막 5분의 통과를 함께 보존한다. 현재 환경이 언제나 안정적이라고 일반화하거나 추가로 더 낮은 지연을 안정화했다고 주장하지 않는다.

이번 실기는 두 PC 동시 실행 기준 총 18분(120초 네 쌍, 300초 두 쌍)이다. 한 방향의 한정된 원시 기록에서만 수신 지연을 계산하고, 연속성 카운터는 전체 첫/마지막 스냅샷으로 비교한다. 현재 수신→렌더 약 20~22ms는 마지막 대조의 중앙값이며 전체 입→귀 지연이 아니다.

## 도구 보완과 검증

- `--extreme-replay`에 원본 보류 값과 0ms를 항상 포함했다. 실제 원격 패킷 길이가 로컬 길이와 다르거나 검증되지 않은 기록은 거부한다. 혼합 모드에 임의의 길이 페이로드를 대입해 잘못된 비교를 만드는 것을 막는다.
- 기존 `analyze_playout_deadlines.py`가 극저지연 기록의 다른 루트 스키마 때문에 실패하던 문제를 수정했다. 기존 형식의 경계 오류 허용 규칙은 유지하고 새 형식은 오류/잘린 기록/짧은 기록을 거부한다. 시계 오프셋 불변성과 잘못된 입력 검사를 포함한 자체 검사 및 실제 기록 분석을 통과했다.
- Release 빌드 경고·오류 0개. 최종 미디어 코드의 `verify.ps1 -NoRestore -Integration` 전체 통과. 이후 분석 도구만 변경한 뒤 빌드와 실제 5ms 기록 재생, 혼합 패킷 길이 거부 검사를 통과했다.
- 첫 전체 검사에서는 서버 테스트 파일 단위의 일시 실패가 있었다. 서버 코드 변경 없이 단독 8개 테스트와 다음 전체 검사는 통과했다. 원인 확정이나 서버 오류 수정으로 표시하지 않는다. 로그는 `verify.log`와 `verify-final.log`에 보존했다.

재현 명령:

```powershell
./native/run.ps1 -Experiment opus-adaptive
./native/run.ps1 -Experiment opus-adaptive-5
```

```text
TransportProbe.exe --qualification-summary DIRECTORY OUTPUT.json
TransportProbe.exe --extreme-replay INPUT.json OUTPUT.json
python native/TransportProbe/Analysis/analyze_pipeline.py PC.json LAPTOP.json OUTPUT.json
python native/TransportProbe/Analysis/analyze_playout_deadlines.py OUTPUT.json INPUT.json...
```

실험 기록은 `native/.local/extreme-066/`이며 Git 제외다. 커밋·푸시·안정 브랜치·dist 교체는 하지 않았다. 장치/오디오 설정 변경 없이 시험을 끝냈다.
# 후속 정정

이 보고서의 도구는 앱의 명시적인 미디어 인터페이스 설정을 전달하지 않아 OS 자동 경로로 실행했다. ‘직접 연결’을 순수 물리 LAN 시험으로 설명하면 안 된다. [EXTREME-067](EXTREME-067.md)에서 현재 노트북의 Tailscale 우선 경로를 확인하고 지정 LAN 대조를 수행했다. 과거 모든 수신 공백의 원인을 Tailscale로 확정하는 것은 아니다.
