# 0.5.9: 저지연 Opus64 기본값과 검증

2026-10-20. 지연 우선·품질 다음이라는 목표에 따라, 장치 효과와 별개로 앱이 선택하는 코덱의 고정 선행 대기를 줄였다. 기본 송신 프로필을 `LowDelay64`로 바꿨다. 수신 여유20ms,10ms 프레임, RAW/GameChat WASAPI 공유 출력은 유지했다. DTS·Windows 장치 설정은 이번 시험에서 변경하지 않았다.

## 변경

- 기본 프로필: Opus Restricted Low Delay, 목표64kbps, VBR, 복잡도9,48kHz 모노10ms.
- 엔진과 화면이 같은 기본 프로필 상수를 사용한다. 참가할 때 화면의 선택을 엔진에 다시 적용한다.
- 기존 Baseline 및 VOIP/96kbps 선택은 남겨 두었다. 기존 Baseline 비트스트림이 바뀌지 않았다는 검사도 유지한다.
- 제품 버전0.5.9. 서버·전송 형식·SDP 코덱은 Opus 그대로이며, 별도 전용 수신 코덱을 요구하지 않는다.

64kbps는 VBR 목표이며 매 순간의 전송량이 아니다. 기존 라이브러리 자동 설정보다 대역폭 사용이 늘 수 있다. 저지연 모드 자체의 실제 발화 청감 평가를 완료했다고 주장하지 않는다.

## 왜 다시 비교했나

기존 두 PC 비교는 호스트 간 시계 불확실성과 ±20ms 검출 여유가 약4ms 코덱 차이보다 컸다. 이후 같은 호스트의 신호 상관 측정을 구현했지만, 디코딩한 신호를 기준으로 삼으면 코덱으로 밀린 파형 위치까지 기준 신호에 포함되어 선행 대기 차이를 상쇄한다.

코덱 비교에는 **동일한 인코딩 전 원본 PCM**을 기준으로 사용하도록 수정했다. 기존 출력/버퍼 비교는 원래의 디코딩 기준 신호를 유지한다. 보고서에 `referenceKind`와 송신 프로필을 함께 저장하며, 두 기준의 절대값을 직접 비교하지 않는다.

장치 없이 표준 디코더로 검증한 원본 파형 위치는 Baseline309샘플(6.4375ms), 저지연120샘플(2.5ms)이었다. 약4ms의 알고리즘 기여 지연 감소를 확인했다. 실제 실행 시간까지 포함한 전체 통화 지연4ms 감소를 확정한 수치는 아니다.

## 두 장치 공유 출력 A/B/A

각 회차32초·신호14개, Baseline→LowDelay64→Baseline으로 비교했다. 수신 여유20ms·제한 공급·RAW/GameChat을 고정했고, 패킷은 사전 인코딩해 실시간 인코딩 실행 시간과 마이크·네트워크 시계를 제외했다.

| 장치 | 기존 A1 | 저지연64 B | 기존 A2 | 유효 신호 |
|---|---:|---:|---:|---:|
| PC: 패킷 추가→대응 루프백 콜백 중앙값 |50.23ms |47.41ms |51.03ms |각14/14 |
| 노트북: 같은 구간 |166.44ms |162.58ms |171.15ms |각14/14 |

회차별 중앙값만 보면 B가 낮지만, 공통 신호별 A1/A2 평균과 B를 비교한 전체 콜백 차이 중앙값은 PC−1.13ms, 노트북6.20ms였다. 신호별 차이의 중앙값과 전체 회차 중앙값 차이는 같은 통계가 아니다. PC의 음수는 콜백 전달 시각으로 일관된 전체 경로 개선을 입증하지 못했다는 뜻이다.

따라서 이 표를 ‘두 PC 전체 지연이 정확히4ms 감소’의 근거로 쓰지 않는다. PC의 native QPC 절대값은 기존처럼 신뢰 제한이 있다. 코덱 기여 지연은 원본 PCM/표준 디코더 검사를 주요 근거로 삼는다. 장치 주기와 큐 위상·루프백 전달 변동은 여전히 남는다.

모든 회차의 앱 무음 채움과 PLC는0ms였고, 모두 제한 공급과 RAW를 유지했다. 노트북 첫 회차는 초기 장치 소진1회·안전 복귀0회였으며 나머지 회차는 소진0회였다. 소진0회를 모든 실행에 대해 주장하지 않는다.

## 실제 두 PC 통화

명시적 LowDelay64 선택으로 양쪽120초 통화를 완료한 뒤, 같은 프로필을 기본 선택에 연결했다. 실통화 당시 앱 버전은0.5.8 진단 빌드였으며, 이후 기본 선택·화면을0.5.9에 적용했다. 두 PC의 실제 선택 경로는 지정 LAN 직접 연결이었다.

| 항목 | PC | 노트북 |
|---|---:|---:|
| 도구 오류 |없음 |없음 |
| 앱 무음 채움 |0ms |0ms |
| 재버퍼링 |0회 |0회 |
| PLC 보완 |80ms |60ms |
| 늦은 패킷 |3개 |3개 |
| 송신 큐 버림 |0프레임 |0프레임 |
| 출력 재시작 |0회 |0회 |
| 출력 안전 복귀 |0회 |1회 |

PC는 약15.17ms 제한 공급을 유지했다. 노트북은22ms 전체 용량으로 안전 복귀했다. RAW는 양쪽 활성 상태였다. 일부 공백을 PLC로 보완했으므로 ‘끊김이나 보완이 전혀 없었다’고 표현하지 않는다. 마지막 RTCP 수신 보고의 누적 손실은 양쪽0패킷이지만 전체 구간의 모든 순간 지연이 없다는 보장은 아니다.

이 시험은 코덱의 실송수신·재생 안정성 확인이며 루프백 지연 측정은 실행하지 않았다. 마이크 원음은 저장하지 않았다. 새 프로필의 게임 부하·외부망/TURN·장시간 통화 및 실제 발화 청감 평가는 이번 범위 밖이다.

## 기본값 결정

원본 신호 검사에서 고정 코덱 기여 지연이 줄었고, 표준 디코더 호환성과 손실 시 PLC/복구 검사 및 실제 통화가 통과했다. 수신 여유를 줄여 늦은 패킷 위험을 늘리는 변경 없이 코덱의 고정 비용을 낮추는 선택으로 채택했다. 전체 입→귀 지연이 일정하게4ms 줄었다는 판단과는 구분한다.

## 검증·재현

Release 빌드 경고0·오류0. 기존 비트스트림 보존, 원본 기준 코덱 위치, 저지연 CELT 패킷 손실→PLC→재생 복구, 서버7개 및 실제 WebRTC ICE/DTLS/SRTP/RTCP·RTP 재생 통합 검사를 통과했다.0.5.9 화면 미리보기에서 기본 선택이 ‘Opus 저지연 ·64kbps’인 것도 확인했다.

```powershell
./native/run.ps1
./native/verify.ps1 -NoRestore -Integration
./native/TransportProbe/bin/Release/net10.0-windows10.0.19041.0/TransportProbe.exe --codec-render-reference-test
./native/TransportProbe/bin/Release/net10.0-windows10.0.19041.0/TransportProbe.exe --render-codec-path-device OUTPUT.json
# 두 PC에서 같은 방, 각자의 로컬 IPv4와 역할로 실행
./native/TransportProbe/bin/Release/net10.0-windows10.0.19041.0/TransportProbe.exe --bound-lowdelay-soak SERVER ROOM OUTPUT.json ROLE LOCAL_IPV4
```
