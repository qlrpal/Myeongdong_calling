# EXTREME-127 — 자동 사건 순환 기록

2026-10-30 / 기준 `ab9718a`에 미커밋126 보완을 보존하고 진단을 확장했다.

## 목적과 구현

기존 사용자 진단은1초 표본과 누적 값으로 문제 감지는 가능했지만, 수동 상세 기록이 꺼져 있어 프레임별 경계 연결이 부족했다. 전체 고빈도 pipeline 기록을 기본 활성화하지 않고 `IncidentRecorder`의 고정8192개 값 형식 배열과 비차단 TryEnter를 추가했다. 통화당 첫 사건만 사전 최대4096개/사후 최대4096개 또는2초까지 보존하고 다음 참가에서 초기화한다. 기록 충돌과 상한 누락을 보고하며, 실제로 보장하지 않는 초 단위 사전 구간을 주장하지 않는다.

`AudioSendQueue`, `WebRtcCallEngine`, `WindowsAudioDevice`, `RtpOpusPlayoutBuffer`, `SharedRenderPlayer`에서 프레임 생성/폐기·상대별 SDK 송신·SDK RTP 이벤트·인증 후 콜백·버퍼 입장·PLC 읽기·렌더 소진/공급을 연결한다. 자동 트리거와 사건의 정확한 의미는 [자동 기록 가이드](../INCIDENT-RECORDING.md)에 있다. `PipelineTrace`의 기존 수동 경로·경계 해석을 유지하고 UI 진단 JSON에 별도 `incident`를 추가했다. 프레임·큐·오디오 정책·배포본은 바꾸지 않는다.

출력 원래 믹스 형식과 요청 엔진 주기를 추가했다. 호환 출력이 보고하는 최종 형식과 거부 당시 믹스 형식을 구분한다. 사건 GC 누적 횟수는 보존하지만 GC 정지·스케줄링 원인으로 단정하지 않는다.

## 검증

- 워밍업 제외, 첫 트리거 고정, 사건 전후 순서, 시간 동결, 높은 기록량에서 사전 기록/트리거 보존, 리셋/중지, 상한 덮어쓰기 카운터, 다른 스레드의 기록 잠금 충돌 시 즉시 누락 처리, 송신 폐기 프레임 식별과 RTP 시간축을 검사했다.
- 순환 기록10만 회는2.14ms·관리형 할당0bytes였다. 실제 장치나 부하 시험 수치가 아닌 단일 스레드 미세 벤치마크다.
- 실제 Opus 패킷 입장/디코딩/읽기1만 쌍의 끔→켬→끔 A/B/A는108.48→109.57→110.51ms였다. 모두 관리형 할당0bytes, PCM 체크섬1094435950 일치, 출력 부족0이었다. 이 합성 검사에서는 일관된 처리량 악화가 보이지 않았으나 계측 영향0·게임 성능·물리 지연을 입증하지 않는다.
- 기존 상세 기록과 자동 기록을 함께 켠 버퍼에서 수용/중복/늦음/읽기 경계와 동일 PCM을 확인했다.
- 전체 최종 명령: `./native/verify.ps1 -NoRestore -Integration`. 원본 로그는 Git 제외 `native/.local/buildtools-migration/verify-127-final.log`다.
- 최종 결과: 경고0·오류0 빌드와 제품/송신/PLC/설정/읽기 위치·서버/자동 실행기 회귀, localhost IPv4/IPv6 ICE/DTLS/SRTP/RTCP·가변 프레임 통합을 모두 통과했다. 외부 회선·실제 게임 검증이 아니다.

## 미실시와 적용

실제 상대 헤드셋·독립 PC·친구 회선·게임·장시간 다인 자동 기록 비용은 미실시다. 전체 소켓 송신 완료와 SDK 인증/재전송 방지 거부 사유, OS/NIC 수신 경계는 미계측이며 사후 RTPChannel 이벤트를 해당 경계로 취급하지 않는다. 기록 누락0도 전체 패킷 무손실을 보장하지 않는다.

소스는 `./native/run.ps1`로 실행한다. 진단을 저장하면 `incident`를 포함한다. 내부 A/B에는 `WebRtcCallEngine.AutomaticIncidentRecording=false`를 사용할 수 있고 제품 기본값은 켬이다. 기존30초 수동 기록은 독립적으로 유지한다. 기존 dist·공개 베타 ZIP·사용자 설정을 갱신하거나 커밋·푸시하지 않았다.
