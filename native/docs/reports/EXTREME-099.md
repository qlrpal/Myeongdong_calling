# EXTREME-099 — 출력 요청에 맞춘 짧은 공백 보류

2026-10-26 / `codex/extreme-latency`. 지연을 우선하면서 불필요한 PLC 잔여 큐를 줄이는 수정이다. 네트워크 스파이크의 물리적 원인을 해결한 변경은 아니다.

## 문제와 수정

저지연 재생의 짧은 빈 큐 보류는 출력 요청이5ms여도 기존에는10ms PLC를 생성할 수 있었다. 그 다음 요청 전에 정상 RTP가 도착해도 이미 생성한 PLC의 나머지5ms부터 출력했다.

보류 PLC를 해당 출력 요청의 남은 샘플 수에 맞추고 Opus가 지원하는2.5ms 단위로 올림한다. 남은 요청이 작을 때 최대 한 패킷을 미리 만들던 대기를 줄인다. 패킷이 계속 안 오면 남은 보류 예산을 다음 요청에서 사용한다. 기존 총 보류 예산과 연속 PLC 상한은 늘리지 않는다. 미래 패킷이 이미 있는 실제 RTP 공백의 순번 진행도 유지한다.

이 변경은 `transientEmptyQueueHold`가 켜지는 저지연·반응형 재생에 적용된다. 별도 극저지연 실험의 고정/적응 보류 정책은 이번 수정 대상이 아니다. 내부 `demandBoundedHold:false`는 동일 바이너리의 회귀 대조용이며 사용자 설정으로 노출하지 않는다.

재생 리플레이 집계도 PLC 횟수×10ms 대신 실제 `ConcealedMs`를 사용한다. 보류 길이가 달라도 PLC 시간을 정확히 합산한다.

## 검증

- 5ms 출력 요청 대조: 기존은 보류10ms를 생성하고 다음 요청도 잔여 PLC를 출력했다. 수정은 보류5ms만 생성해 다음 요청에서 정상 RTP를 디코딩했다. 해당 조건에서 앱의 출력 요청 전달이5ms 빨라졌다. 장치 이후나 전체 입→귀 지연 수치는 아니다.
- 시계 보정 켬/끔, native/managed Opus에서 해당 재생 회귀 검사가 통과했다. 긴 공백에서는 총 보류10ms, PLC60ms, 재버퍼링1회의 기존 상한을 유지했다.
- 출력240/480/488/960/1920샘플, 도착 위상0/3/7ms, 정지0/30ms, 시계 편차−200/0/+200ppm, 정책4종으로 총360개60초 합성 조건을 실행했다. 정상 도착은 모두 PLC·버퍼 부족 없이 진행했다.
- 동일 고정 목표·보류 정책의 기존/수정 A/B90쌍 중19쌍에서 PLC와 마지막30초 평균 큐가 감소했고71쌍은 같았다. 평균 큐 감소는 최대 약3.69ms, 전체60초의 PLC 감소는 사례당 최대27.5ms였다. 늦은 패킷·재버퍼링·복구 폐기·버퍼 부족은90쌍 모두 같았다.
- Release 정적 분석·전체 회귀·서버 검사·IPv4/IPv6 WebRTC 통합이 통과했다.

원시 결과는 Git 제외 `.local/extreme-099`에 보존한다. 평균 지연의 전면적인5ms 감소나 음질 향상을 주장하지 않는다. 여러 출력 주기·단발 정지의 합성 대조이며 외부 장시간 통화·주관적 음질을 대체하지 않는다. 무선 지연과 남은 늦은 패킷·PLC는 계속 별도로 조사해야 한다.

## 실제 통화 경로 확인

최종 동일 빌드로 PC·노트북의 기본10ms 저지연 재생을 실제 OCI TURN 경로에서 시험했다. 양쪽 종료 코드0, 오류 없음이며 총16개 피어/단계 구간에서 송수신 카운터 증가와 TURN 경로를 확인했다. 장치 선택·마이크 음소거/복구·상대 볼륨·재접속·나가기를 통과했다. 양쪽 진단에10ms 배수가 아닌 보류 시간이 나타나 실제 실행에서도 분할 보류가 사용됨을 확인했다. 이 단일 통화 시험은 지연 개선량의 인과 대조가 아니며 주관적 끊김 해결을 보장하지 않는다.

노트북 시험 경로의 덮어쓴 원본은 복원하고 파일별 SHA-256을 검증했다. 새로 추가한 파일과 빈 디렉터리만 제거했다. 양쪽 잔여 시험 프로세스는0개다. 공유기·라우팅·전원·개인 장치 설정과 기존 dist는 변경하지 않았다. 소스와 보고서 수정은 아직 커밋·푸시하지 않았다.
