# EXTREME-100 — 최신 기준선·송신 대조·재시작 게이트 수정


2026-10-26 / `codex/extreme-latency`, 시작 HEAD `75ddfda`. 작업 시작 시 README·프로브 진입점·WASAPI 장치 검사에 있던 별도 미커밋 변경을 보존했다. 이번 작업은 아직 커밋·푸시하지 않았다.

**평상시 물리 입→귀 지연 감소는 이번에 입증하지 않았다.** 전용 송신 기본값 승격은 기각했다. 정상 버스트 보존/큐 나이 제한과 재시작 불가 결함 수정은 적용했다. 새 분수 출력 진단은 여전히 실패하며 아래에 별도로 공개한다.

## 1. 현재 구조와 확인된 병목

- 기본10ms 제품 구성은 스레드풀에서 제한 채널을 읽어 송신한다. 극저지연 프리셋은 인라인 송신이다. 둘을 같은 기본 경로로 취급하지 않는다.
- 인라인은 캡처 콜백에서 인코딩 후 상대별 SRTP/송신 API를 순서대로 호출한다. 피어 수명이 보호되고 전역 피어 잠금은 없다.
- 상대마다 RTP 버퍼·디코더·시계 보정과 별도 WASAPI 공유 출력이 있다. 단일 믹싱 출력은 이번에 구현하지 않았다.
- 캡처·렌더의 실제 주기는 프레임 길이와 다르다. 기본 기준선의 입력 주기는 PC10ms, 노트북5.333ms, 출력 주기는 PC2.667ms, 노트북10ms였다.

### 기본10ms·직접 경로 기준선

각 호스트에 엔진3개를 만들되 1개씩만 참가한45초 구간이다. 마지막5초 추적의 내부 구간으로 아래 중앙값을 계산했다. 프로브의 기본 정책은 LowLatency20ms이며 OS 장치·라우팅은 변경하지 않았다. 콜백 작업은 PCM 변환 뒤 `Capture` 경계이며 원시 장치 lease 전체 시간이 아니다. 분석기는 대응 송신 origin이 있는 콜백에 한해 변환을 포함한 핸들러 시작→Capture 반환도 별도로 계산한다.

| 호스트 | PCM 캡처 처리 작업 | 인코딩 후 큐 대기 | 장치 보고 첫 샘플→첫 송신 API | 버퍼 입장→출력 요청 전달 |
|---|---:|---:|---:|---:|
| PC |0.052ms|0.019ms|19.093ms|34.514ms|
| 노트북 |0.061ms|0.035ms|18.201ms|35.140ms|

장치 첫 샘플은 WASAPI 보고 시각이고 출력 요청 전달은 물리 재생이 아니다. 수신/출력 대응 표본에는 생존 편향이 있다. 기준선 전체에 PLC·재버퍼링이 있었으므로 완전히 정상인 네트워크의 보편적 지연으로 일반화하지 않는다. 이 표를 더해 입→귀 지연을 만들지 않는다. 송신 큐의 평상시 대기는 이 환경에서 큰 항목이 아니었다.

경로는 `native/VoiceNative/` 또는 `native/TransportProbe/` 기준이다. 송신 나이는 PCM 장치 시각이 아니라 **인코딩 후 프레임 생성→큐 읽기** 기준이다. 읽기 뒤 상대별 API 처리·실제 소켓 완료까지 제한한다는 의미는 아니다. 전용 후보의 예산은 입력 주기와 프레임 길이 중 큰 값이며1~40ms로 제한한다. 실제 시험에서 PC는8프레임/10ms, 노트북은6프레임/5.333ms였다.

## 3. 비교 조건과 결과

### 기존 전용 후보의 결함 재현

같은 SDK·네이티브 Opus·2.5ms 프레임·5~20ms 적응 수신·장치 설정에서 인라인→기존 전용→인라인을 비교했다. 1:1 45초,3명60초,6명90초이며 한 프로세스에 엔진3개씩이다. 프레임 자동 변경은 꺼서 송신 방식과 프레임 변경을 섞지 않았다.

노트북 입력256샘플은 콜백마다2개 또는3개의2.5ms 프레임을 만들었다. 전용 큐 용량3에서 송신 전 폐기가 반복됐다. PC의 실제10ms 묶음은4프레임이었다. worker가 첫 프레임을 처리하는 동안 신선한 두 묶음이 겹치는 결정적 검사에서 기존 용량은2프레임을 폐기했고 수정 용량은 순서와 샘플 오프셋을 보존했다. 별도 가짜 단조 시계 검사에서는 오래된 프레임만 만료시키고 RTP 시간축을 압축하지 않는 것을 확인했다.

### 수정 큐의 최종6엔진90초 A/B/A

최종 품질 근거는 원래 Read 정리 위치를 확인한 `corrected-a1/b/a2`만 사용한다. 앱·SDK·네이티브 Opus 바이너리와 프레임/버퍼 설정이 같음을 검사했다. 다른 선택 값은 인라인/전용이며, 전용의 큐 용량·나이 정책도 해당 후보 구현의 일부다. 아래는 마지막5초 추적 내부 구간이며 시간 단위는 ms다.

### 수신 누락 경계

최종 A/B/A의30방향씩, 총90방향 내부 RTP 식별 구간을 대응했다.

| 단계 | 송신 API 내부 범위 프레임 | 수신 콜백 미관측 | 앱 송신 순번 공백 | 미입장 |
|---|---:|---:|---:|---:|
|A1|58538|0|0|0|
|B|59652|0|200|304|
|A2|58805|0|0|185|

실제 나이/용량 폐기는 송신 전 음성 생략이며 RTP 순번 손실과 같지 않다. 미입장은 입장 로그의 late/duplicate 등과 함께 해석한다.

이 수치는 마지막 제한 추적의 겹치는 RTP 범위만 다룬다. 전체 통화의 미관측0을 뜻하지 않는다. `SendEnd`는 SDK API 반환이지 OS 송신 완료가 아니다. 원시 UDP 수신·SRTP 인증/재전송 검사 거부는 이번 앱 추적에서 미분리다. 과거 미관측을 물리 손실로 단정하거나 과거 SDK 결함이 모든 구간에서 재발했다고 단정하지 않는다.

### 확장한 분수 출력 진단

기존50개 합성 조건에128/256샘플 요청·20ms 묶음12조건과, 실제 노트북 입력 주기256/48=5.333ms를 정확히 모델링한9조건을 추가해 총71조건을 검사했다. 손실 없는 입력에서도 반복 PLC/폐기와 재시작 불가가 재현됐다.

- 재시작 수정: `capture20-render-128/fixed-5`의120초 부족은 약119954.7ms→0, PLC는0으로 유지했다. 정상 묶음마다 정리/대기를 반복하는 결함을 직접 회귀 검사했다.
- 정상10ms 묶음의 기존 정상 예에서는 평균 큐를 유지했다. `render-128/fixed-2.5` 500ms 진단 표본의 마지막20초 평균은4.68→4.68ms, `render-256/fixed-5`는5.02→5.02ms였다.
- **확장21조건 중6조건은 아직 실패한다.** 총10개 실패 항목이며, `render-128/fixed-5`, `render-256/fixed-2.5/auto`, `capture20-render-256/fixed-2.5/fixed-5/auto`다. 대표적으로 `render-256/fixed-2.5`는120초 PLC3750ms, 마지막20초 PLC/폐기625/625ms가 남았다. 손실 없는 합성 조건의 결함이므로 집 무선망으로 설명하지 않는다.

실제5.333ms 캡처→128/480/256샘플 렌더의2.5ms/5ms/auto9조건은 합성 검사를 통과했다. 일부 가능한 장치 조합의 실패를 현재 모든 사용자 경로의 동일 원인으로 일반화하지 않는다.

표준 회귀/부하 검사는 통과했지만 **새 `--fractional-network-checks`는 종료 코드1**이며 결과를 보존했다. 추가 조건을 기존 검사 통과로 위장하지 않는다.

### 최종 계측 끔 대조와 기본 TURN 회귀

최종 앱·SDK·네이티브 Opus 식별자가 같은 `corrected-off-inline/dedicated`6엔진90초를 각각 실행했다. 기록 배열이 비어 있고 `captureTrace:false`임을 확인했다. 아래는10초 준비 후 합산이다.

| 경로·호스트 | 송신 폐기(그중 만료) | PLC 합산 | 부족 합산 |
|---|---:|---:|---:|
|추적 끔 인라인 PC|0 (0)|18057.5ms|12707.8ms|
|추적 끔 인라인 노트북|0 (0)|20425.0ms|11122.2ms|
|추적 끔 전용 PC|0 (0)|18397.5ms|2790.7ms|
|추적 끔 전용 노트북|5 (5)|4860.0ms|1640.0ms|

전용의 만료가 기록이 없어도 발생했다. 추적 켬 전용의 폐기40개와 추적 끔의5개 및 수신 품질이 달라, 계측의 영향이0이라고 판정하지 않는다. 서로 다른 시간의 한 쌍이며 경로 변동도 섞여 전체 차이를 계측의 인과 효과로 확정하지 않는다. 추적 끔 자료에는 상세 패킷 지연 분포가 없어 이를 만들어내지 않는다. 기본 실행에는 고빈도 추적이 꺼져 있다.

추적 끔의 프로세스 CPU/GC 정지(ms/s)도 보존했다. PC 인라인→전용 0.385코어/2.61ms/s→0.420코어/2.71ms/s. 노트북 인라인→전용 0.582코어/10.90ms/s→0.576코어/10.93ms/s. 시스템 전체·audiodg·게임 CPU가 아니며 단일 AB의 숫자를 일반적인 CPU 개선으로 확정하지 않는다.

최종 기본10ms 경로의 실제 OCI TURN 제품 회귀 `corrected-turn`은 양쪽 종료 코드0, 총16개 피어/단계 구간의 송수신 증가를 확인했다. 장치 선택·음소거/복구·상대 볼륨·재접속·기본 장치 재참가·나가기를 확인했다. 실제 다른 장치 분리/전환이나 극저지연 실험의 연속성 합격은 아니다.

## 4. 채택·기각

채택: 기존 전용 실험 경로의 신선한 묶음 보존·큐 나이 제한·폐기 분류, backlog 정리와 시작 조건의 모순 수정, 선택적 계측·재현 도구.

기각: 전용 송신 기본값 승격. 재생 큐 여유를 통째로 한 pull 더 남기거나 부분 프레임이 끝날 때까지 정리를 미루는 후보도 제외했다. 일부 실패를 없앴지만 원래 정상인 `render-128/fixed-2.5`의 평균 큐를 약4.68→9.35ms로 늘렸다. 프레임마다 정리 위치를 옮기는 후보는 다른 드리프트/혼합 요청 조건을 악화해 제외했다. 원시 실패 결과는 `.local/extreme-100/fractional-*`에 남겼고 해당 후보 코드는 제품에 남기지 않았다.

### 중간 빌드 무효화와 추가 회귀

후보 제거 중 Read 정리 블록을 Add에 잘못 옮긴 중간 빌드가 있었다. 최종 diff에서 발견해 원래 위치를 복원했다. `bounded-*`, `untraced-*`, `final-turn` 자료를 최종 수신 품질 근거로 사용하지 않으며, 그 소스·DLL·로그는 보존했다. 위 최종 표는 모두 복원 후 `corrected-*` 재시험이다. RtpOpusPlayoutBuffer의 최종 실행 변경은 Add의 시작 조건 보존 부분뿐이다.

정상 도착이 이미 디코딩한 부분 PCM을 재생 요청 전에 버리지 않는 회귀를 추가했다. 보존한 중간 DLL을 새 검사에 연결한 재현 시험에서는 `Admission performed render-boundary trimming`으로 실패했고, 최종 DLL은 native/managed 모두 통과했다. 추가 검사 도구만 다시 컴파일한 뒤 앱/SDK DLL이 최종 실기 시험과 바이트 단위로 같음을 확인했다.

## 5. 기본값

기본10ms·스레드풀 송신, 극저지연 프리셋의 인라인 송신, WASAPI 공유 모드, 프레임·reserve·출력 여유·코덱·직접 우선/TURN 대체·SDK 보안을 유지했다. 전용 후보는 기존처럼 명시적인 비교용 JSON에서만 선택한다. 기존 dist는 변경하지 않았다.

## 6. 미해결·미실시

최우선 후속은 분수 렌더/도착 묶음의 위상과 정리·소비율 보정이 만드는 반복 PLC를 추가 대기 확대 없이 고치는 것이다. 과거 무선/NIC/AP 조사와 이번 손실 없는 재현을 구분한다. 단일 공통 출력 구조, 실제 게임 프레임타임·게임 부하, 독립6대 PC·친구 회선, 최신 물리 입→귀 p50/p95/p99는 이번에 미실시다. 기본 구성/실험 어느 것도 극저지연 완성으로 선언하지 않는다.
