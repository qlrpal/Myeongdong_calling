# EXTREME-117 — 분수 장치 요청·복귀 위상별 합성 복구 대조

한국 시각2026-10-28, `codex/extreme-latency`, HEAD `78ef68a`와109–116 미커밋 작업을 보존했다. 기존 운영 DNS/서버·제품 오디오 알고리즘·기본값·dist는 변경하지 않았다.

## 가설과 과거 결과

116의 TURN 재버퍼 뒤 앱이 추가 대기를 만드는지 확인하려고 기존 코드를 조사했다.091에서 재시작 여유5/10/15ms 축소는 PLC 증가로 기각됐고, 충분한 후속 패킷을 요구하는 빈 구간 생략은 실제 기록에서 발동0이었다. 그 후보들을 다시 구현하지 않았다.

기존 `RecoveryGapChecks`는10/22ms 요청을 사용했다. 현재 실제 출력의2.667/10ms와 입력의5.333ms처럼 분수 요청을 포함한 검사가 필요했다.128/256/480샘플 요청·0/반 주기 렌더 위상·10/20ms Opus·정상/재정렬/80ms 밀린 도착/160ms 밀린 도착/400ms 손실을 추가했다. 고정20ms·최대60ms PLC·기존 fresh restart 정책을 유지한다. 이는 제어된 합성이며116의 실제 패킷 기록 재생이 아니다.

## 실제 수정

- `TransportProbe/Checks/RecoveryGapChecks.cs`: 읽기 이벤트를 정수 샘플 단위로 생성해2.667/5.333ms를 누적 실수 오차 없이 표현한다. 기존10/22ms 시나리오는 동일하다. 첫 패킷 복귀 후 재생 호출까지의 가상 시간과 렌더 위상을 결과에 추가했다. 기존 신선도 복귀 지표와 구분한다.
- `TransportProbe/Program.cs`: `--recovery-device-period-test OUTPUT.json` 진입점을 추가했다.
- `TransportProbe/Runner/app-checks.mjs`, `verify.ps1`: 새 검사를 core/전체 회귀에 연결했다.
- 출력에 `caseCount`, `qualityQualified:false`, `physicalLatencyMeasured:false`를 기록한다. 기능·상한 검사 성공이 복구 후보 채택이나 물리 지연 합격을 의미하지 않도록 표시한다.

실시간 송수신·장치·SDK 처리에는 계측이나 할당을 추가하지 않는다. 새 제품 모드/후보를 도입하지 않고 원래 존재하던 시험용 bounded-tail과 대조한다.

## 관측과 후속 대조

첫60개 현재 정책 조건에서 정상 재생은 PLC·부족·재버퍼0이었다.160ms 밀린 도착을 해제할 때 패킷을0/0.1/0.2ms에 나누어 전달한다. 렌더가 첫 부분 묶음 사이에 위치하는6조건은 재생이 즉시 재개됐지만, 후속1초의 원본 생성→렌더 호출 나이가 P95 80ms로 남았다. 기준 정상 나이에 한 프레임을 더한 신선도 문턱에 이1초 안에 도달하지 못해 RecoveryToFreshMs는 null이었다. 재생 자체가 멈췄다는 뜻은 아니다.

이 새 위상 조건을 근거로 기존 bounded-tail 후보를 동일 조건에서 대조했다. 해당 후보는 재버퍼 뒤 최신 연속 묶음이 부족하면 렌더 요청을 최대 한 번 더 기다린다. 전체60쌍/120조건 중54쌍은 결과가 같고6쌍은 달랐다.

10ms 프레임·위상0·160ms 밀린 도착의 차이:

| 렌더 요청 | 후속 원본 나이 P95 현재→후보 | PCM 부족 현재→후보 | 의도적 복구 폐기 현재→후보 |
|---|---:|---:|---:|
|2.667ms |80→42.667ms |80→82.667ms |10→90ms |
|5.333ms |80→45.333ms |77.333→82.667ms |10→90ms |
|10ms |80→40ms |80→90ms |10→30ms |

이6조건의 PLC는 각각60ms로 같았다. 큐 신선도는 좋아졌으나 추가 무음과 더 많은 음성 폐기로 얻은 결과다. **기본값 승격을 기각한다.** 특정 합성 위상의 이득을116의 실제 TURN 해결이나 평상시 입→귀 감소로 표현하지 않는다. 다른 조건에서도 일반적인 우위가 있다고 입증하지 못했다.

## 검증과 한계

현재 정책60개 원본과 후보 대조 안의 현재 정책60개 결과가 필드별로 완전히 같음을 확인했다. 최초에 임의의250ms 신선도 복귀 상한을 검사 실패로 두었으나 기존 검사에서도 null 결과를 허용하는 측정 계약과 맞지 않았다. 그 임의 판정을 제거하고 null을 관측 결과로 보존했다. 실패 로그는 Git 제외 경로에 남겼으며 null을 성공적인0ms 복귀로 바꾸지 않았다. 정상 입력·큐120ms·PLC60ms 상한 검사는 유지한다.

최종 경고0/오류0 빌드와 `verify.ps1 -NoRestore -Integration` 전체를 통과했다. 기존 제품/SDK/오디오·버퍼·회복 정책·서버8개·도구11개·localhost IPv4/IPv6 SRTP/RTCP·가변 프레임 회귀가 포함된다. 새 core 진입점은 구문 검사와 같은 최종 바이너리의120조건 실행으로 확인했고 core 전체 명령을 별도로 반복하지 않았다.

가상 이벤트 시간의 원본 생성→렌더 호출은 물리 입→귀가 아니다. 실시간 스케줄링·네트워크·실제 캡처 묶음·코덱 주관 음질을 재현하지 않는다. 정렬된 잠금 순서를 실제 벽시계로 실행하는 시험도 아니다. 실제 두 PC·TURN·게임 대조는 이번 후보에 대해 수행하지 않았다. 실제 자료에 없는0.1ms 분할 도착을 제품 최적화의 근거로 일반화하지 않는다.

제품 정책을 변경하지 않았으므로 기본 경로 복귀 작업이나 시스템 설정 복구는 필요하지 않다. 추가한 검사는 유지하고 효과가 검증되지 않은 제품 옵션은 추가하지 않는다. 자체 회귀 프로세스는 정상 종료했다. 커밋·푸시는 하지 않았다.
