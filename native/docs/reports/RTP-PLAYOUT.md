# RTP 시간축 재생과 Opus PLC · 0.5.0

지연 우선 개선의 첫 단계로 수신 패킷을 RTP 타임스탬프 순서로 보관하고 출력 장치의 읽기 요청에 맞춰 디코딩합니다. 기존의 즉시 디코딩→PCM 큐 경로 대신 사용하며 별도의 타이머나 PCM 시작 대기를 추가하지 않습니다. 송신 코덱 기본값과 OCI 서버는 그대로입니다.

## 동작과 한계

- 48kHz 모노, 10ms 단위 패킷 시간축. 기존 20ms 패킷도 처리합니다.
- 목표 여유20ms는 고정값입니다. 첫 장치 요청 이후 여유를 남기도록 시작하므로 실제 대기량은 장치 요청 크기·리샘플러·입력 도착 형태에 영향을 받습니다. 20ms 종단 지연을 뜻하지 않습니다.
- 재생 시점까지 없는 패킷은 Opus PLC로 10ms씩 보정합니다. 연속60ms까지만 보정하고 이후 새 패킷을 모아 재시작합니다. FEC는 사용하지 않습니다.
- 재생 시점이 지난 패킷과 중복은 다시 디코딩하지 않습니다. RTP 32비트 순환, SSRC 변경, 큰 앞으로의 타임스탬프 불연속을 처리합니다.
- 압축 패킷과 남은 디코딩 PCM 합이120ms를 넘으면 오래된 대기를 버려 압축 패킷60ms 이하를 남깁니다. 장치 재시작 때는 이전 대기를 비웁니다. 재시작은5ms 페이드인합니다.
- 진단의 큐에는 압축 패킷과 남은 디코딩 PCM이 포함됩니다. 장치 내부 대기는 포함하지 않습니다. `DecodedMs`는 정상 디코딩, `ConcealedMs`는 PLC이며 `ConsumedMs`는 둘을 포함합니다. 기존 버퍼 부족은 PLC로 채우고도 모자라 무음을 낸 부분입니다. 부족0만으로 정상 수신을 판단하지 말고 PLC도 확인해야 합니다.
- 화면의 **RTP 순서 재생·손실 보정 (검증)** 체크를 끄면 기존 PCM 경로로 돌아갑니다. 통화에서 나간 뒤 변경합니다. 새 경로는 기본 활성이나 두 PC 장시간/불안정 인터넷 검증은 아직 필요합니다.

실제 출력은 Realtek44.1kHz 스테레오 부동소수점 장치로, 앱의48kHz 모노 PCM에서 리샘플링한 경로입니다. 저지연 출력 활성, 엔진 주기10ms, 마지막 앱 큐55.875ms, 디코딩 P95 0.06ms였습니다. 이 수치는 단일 PC의 합성 입력 재생 결과이며 마이크→상대 출력 지연 개선의 증거는 아닙니다. 큐·디코딩 개별 스냅샷은 다른 순간에 수집될 수 있습니다.

```powershell
./native/verify.ps1 -NoRestore -Integration
# 별도 장치 검사: 작은 합성 신호를 기본 출력 장치에서8초 재생
./native/TransportProbe/bin/Release/net10.0-windows10.0.19041.0/TransportProbe.exe --rtp-device-test
```

통합 검사는 실제 ICE/DTLS/SRTP에서 복호화된 패킷을 받아 순서 변경·중복·10ms 손실을 주입합니다. 정상9패킷+PLC10ms, 부족0을 확인합니다. 물리 장치 검사는 기본 회귀 검사에 포함하지 않습니다.
