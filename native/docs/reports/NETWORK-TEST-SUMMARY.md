# 네트워크 시험 종합 보고서

정리 기준: 2026-10-16 ETW MCP·Pktmon 재시험까지. 최근 지연 조사는 Native0.5.4, Windows PC 유선↔노트북 Wi-Fi, 동일 공유기의 직접 LAN 경로가 중심이다. OCI TURN 검증은 별도 항목이다. 이 문서는 기존 유효 보고서의 종합이며 이 문서를 작성하며 별도 시험을 실행한 것은 아니다.

최신 [ETW MCP·Pktmon 결과](ETW-MCP-PKTMON-LOCALIZATION.md)에서는 연결된 일부 PC→노트북 사례의 긴 간격이 **노트북 Intel NIC 첫 관측 지점부터 이미 존재**했다. 수신 전후가 연결된 것은46개 중12개, 양쪽 전후 모두 연결된 것은5개로 부분 관측이며, NIC 내부·무선/AP 중 직접 원인은 아직 미확정이다. MCP 전용 계층 도구의 로케일·Wi-Fi·고정 번호 제한 때문에 generic 이벤트를 별도 순번 분석기로 교차검증했다.

## 현재 결론

1. **순간 지연은 음성·코덱·WebRTC 없이도 발생한다.** 실제 송신 시각·크기를 재생하는 합성 UDP에서도 수초 동안 반복되는 큰 간격이 재현됐다. 오디오 실행이 이 현상의 필수 조건은 아니다. 앱의 모든 지연 원인이 배제됐다는 뜻은 아니다.
2. **큰 간격의 다수는 송신 OS UDP 이벤트 이후~상대 수신 OS UDP 이벤트 이전에서 추가된다.** NIC/드라이버/펌웨어·LAN·Wi-Fi·AP·공유기와 OS 네트워크 처리가 조사 범위다. 하드웨어 선로 시각을 측정하지 않아 이 중 하나로 특정하지 못했다.
3. **무선에 치우친 묶음과 공통 LAN/공유기 RTT 변동이 모두 있다.** 과거 일부 실행은 노트북→공유기만 크게 느려졌지만, 최신 실행에서는 PC 유선→공유기도 함께 늘었다. “노트북 Wi-Fi가 단독 원인”이나 “공유기가 원인으로 확정”이라는 결론은 부적절하다.
4. **재전송·절전·스캔·로밍의 직접 원인은 미확정이다.** 재시도 카운터는 갱신됐지만 지연과의 관계가 일관되지 않았다. WLAN ETW에서는 설명 가능한 이벤트가 없었으나 펌웨어 내부 동작까지 배제할 수 없다.
5. **고정적인 앱 대기와 네트워크 순간 변동은 별도 과제다.** 앱 캡처 전달 약17~19ms, 수신 콜백→디코딩 시작 약31~36ms는 관측했다. 이 값을 네트워크 지연으로 부르거나 서로 더해 전체 입→귀 지연으로 확정하지 않는다.

## 서로 다른 지연 지표의 의미

| 지표 | 관측 예 | 해석 |
|---|---|---|
| 공유기 ping RTT | 다수 실행의 중앙값 약2~4ms, 순간 수십 ms 상승 | ICMP 왕복/공유기 응답 처리. 음성 편도 지연과 다름 |
| 수신 간격 | 보통 송신 패턴을 반영하며 드물게30~85ms 이상 | 앞뒤 패킷 도착 사이 시간. 해당 패킷의 총 체류 시간이나 평균 통화 지연이 아님 |
| OS 송수신 간격 차이 | 송신 약10ms, 수신 약57ms인 사례 | 두 호스트에서 대응하는 간격의 변화. 고정 단방향 지연은 알 수 없음 |
| 캡처 전달 | 약17~19ms | 첫 샘플 WASAPI 시각→캡처 콜백. 물리 마이크 전체 지연이 아님 |
| 수신 후 앱 대기 | 약31~36ms | 수신 콜백→디코딩 시작. 현재 오디오 큐/출력 소비 구조의 별도 최적화 대상 |
| 물리 입→귀 | 이번 LAN 간격 조사에서 확정하지 않음 | DAC/장치/음향 경로까지 포함해야 함. 위 수치 합산이나 RTT/2로 대체하지 않음 |

노트북 실제 통화의 송신 간격 P95가 약16ms였고, 캡처 콜백에서 이미 비슷한 변동이 있었다. 수신 P95 약16ms 전체가 네트워크 때문에 생긴 것은 아니다. 반면 송신10ms에 수신50~60ms인 경우는 별도로 관측됐다.

## 조사 범위가 달라진 이유

상반된 결과를 하나로 덮지 않고 두 형태로 남긴다.

| 관측 형태 | 대표 근거 | 현재 의미 |
|---|---|---|
| 노트북 경로에 치우친 지연 | 조회 꺼짐 마지막 묶음: 노트북→공유기 중앙값39ms, PC→공유기3ms, loopback0ms | 노트북 NIC/무선/AP 연결별 처리가 유력한 조사 대상 |
| PC와 노트북 공유기 RTT 동반 상승 | 최신56.944ms UDP 간격 주변: PC→공유기 최대46ms, 노트북→공유기52ms | 공통 LAN/공유기 응답·처리, 각 NIC 처리까지 조사 범위에 포함 |

두 수치 행은 서로 다른 실행·통계량이다. 중앙값39ms와 다른 실행의 최대52ms를 직접 비교해 성능 변화로 읽지 않는다. ICMP는 공유기가 직접 응답하지만 테스트 UDP는 전달되는 트래픽이므로, 공유기 ICMP 상승만으로 실제 전달 큐를 원인으로 확정할 수 없다. 모든 현상이 하나의 원인이라는 보장도 없다.

## 무엇이 약해졌고 무엇이 남았나

| 가설 | 현재 판단 |
|---|---|
| 오디오·Opus·WebRTC가 실행돼야 큰 묶음이 발생 | 필수 조건 가설은 지지되지 않음. 합성 UDP로 큰 묶음 재현 |
| 디코딩/재생 큐만이 수신 간격을 만듦 | 다수 간격이 OS 수신 시점에 이미 존재하므로 단독 설명 불가. 앱의 고정 대기는 별도로 존재 |
| 진단 신호 주입만의 문제 | 신호 없는 통화와 합성 UDP에서도 재현. 첫 신호 준비의 별도 멈춤은 확인해 콜백 밖으로 이동 |
| 긴 DPC/ISR CPU 점유 또는 runnable 대기가 주원인 | 동시 계측한 실행에서는 동급 시간의 증거 없음. 다른 실행과 NIC 내부 대기까지 배제하지 않음 |
| 불규칙한 송신 패턴만이 원인 | 같은 패턴 두 재생의 묶음 규모가 달라 충분한 설명이 아님. 환경과의 상호작용은 남음 |
| WLAN 통계 조회가 반드시 원인 | 조회 꺼짐에서도 재현. 조회의 영향 부재나 개선 효과는 미확정 |
| 낮은 RSSI가 직접 원인 | 표본 RSSI는 대략−43~−39dBm이고 지연 전후 급락 증거 부족. 표본 사이 순간 변화·간섭은 미측정 |
| 무선 재전송이 직접 원인 | 활성 카운터는 확인. 관측 구간 비율 약4.26~7.83%지만 지연 창과의 관계가 일관되지 않아 미확정 |
| 스캔·로밍·절전이 직접 원인 | 설명 가능한 허용 이벤트 없음. 공급자가 노출하지 않는 내부 동작은 배제 불가 |
| 공유기 또는 특정 NIC가 단독 원인 | 위치를 직접 분리할 자료 부족. 지연이 쌓인 장치/큐는 미확정 |
| OCI 서버가 최근 LAN 순간 변동의 원인 | 최근 재현 트래픽은 직접 LAN 또는 합성 UDP로 OCI TURN을 거치지 않음. 해당 현상에 OCI 중계는 필수 아님 |

재시도 비율은 성공 전 재시도한 프레임/송신 프레임이며 모든 재시도 횟수나 RTP 손실률이 아니다. Intel 드라이버의6개 PHY에 동일한 카운터가 반복돼 합산하지 않았다. 약500ms 조회는 어댑터 전체이며 ICMP·SSH·기타 트래픽도 포함한다. PC 별도 Wi-Fi의 고정0 카운터도 유선 경로 정상 판정의 근거로 쓰지 않았다.

## 연결·OCI TURN 검증은 별도

[2026-10-07 검증 기록](VERIFICATION.md)에 따르면 OCI coturn과 만료 자격 발급을 배포했고, 동일 PC에서 실행한 두 피어의 미디어를 실제 OCI relay→relay 경로로 강제한 검사가 통과했다. ICE/DTLS,10ms Opus SRTP 디코딩, 양방향 데이터 채널·RTCP를 확인했다. 당시 RTCP RTT는21.54/22.99ms, 보고 손실0%였다.

이것은 **당시의 중계 기능 검증**이다. 현재 서버 상태를 새로 점검한 결과도, 다른 회선 두 사용자의 평균 통화 지연이나 전체 입→귀 지연도 아니다. 외부 친구와의 실제 회선 비교, 직접 경로와 강제 TURN 경로의 통제된 지연 비교는 최근 LAN 시험으로 대체되지 않는다. 운영 구성과 TCP/TLS 우회·장기 자격 갱신 등의 남은 범위는 [서버 문서](../../server/README.md)를 따른다.

## 측정의 신뢰성과 한계

- 각 호스트의 앱/ETW를 raw QPC로 연결했다. 다른 PC의 절대 시각을 빼지 않았다. 초기 UTC 앵커의 해상도 문제는 raw QPC 재분석으로 보완했다.
- 유효한 ETW 자료의 정상 종료·손실 이벤트0·세션/PID/시간 범위와 순환 상한을 확인했다. 합성 UDP는 계획 hash·크기 순서·순번·예정 시각·OS 길이 histogram을 검증했다.
- 합성 UDP 여러 시험의 공통 내부 순번 범위에서 누락·중복·역전0개였다. 이것은 전체 인터넷 환경의 무손실 보장이 아니다. ICMP timeout이 있었던 구간도 있어 ping 실패를 숨기거나 UDP 손실로 바꾸지 않았다.
- 실패·불완전 실행은 유효 비교에서 제외했다. 노트북 절전으로 SSH·통화·ping이 끊긴 실행은 외부 중단으로 구분했다.
- OS UDP 이벤트는 NIC 선로 시각이 아니다. 큐별 체류·무선 airtime·실제 sleep/wake·AP 큐를 직접 측정하지 않았다.
- 시험은 대부분120초의 순차 비교다. 무작위·독립 반복이 아니며 배경 앱·RF 환경·공유기 부하는 통제하지 않았다. 수초 묶음 하나가 높은 간격 수십 개를 만들 수 있다.
- ICMP·ETW·WLAN 조회 자체의 영향은 완전히 제거하지 못했다. 통계 조회 꺼짐은 계측 전체 꺼짐이 아니다. 이벤트 없음과 동작 없음, 상관관계와 인과관계를 구분한다.
- 상세 계측은 선택 실행이며 원본은 git 제외 `.local`에 보관한다. 음성·패킷 내용·세션 토큰은 저장하지 않았고 네트워크/인터페이스 메타데이터는 포함될 수 있다.

## 앞으로의 우선순위

1. **현재 도구가 못 보는 구간의 자료 확보 가능성 확인:** 공유기의 부하·연결별 큐/재시도 통계와 NIC 드라이버 세부 이벤트를 읽을 수 있는지 확인한다. 바로 설정을 바꾸거나 같은 AutoConfig 이벤트 시험만 반복하지 않는다.
2. **현상 분리:** 노트북 쪽에 치우친 묶음과 공통 LAN/공유기 RTT 상승을 별개로 분류한다. 자료가 가능하면 공유기의 ICMP 응답 처리와 UDP 전달 경로를 분리해 본다.
3. **제어 가능한 앱 대기는 별도 최적화:** 캡처 전달 약17~19ms, 수신→디코딩 약31~36ms를 대상으로 단계별 대조를 진행한다. 순간 네트워크 지연을 감추려고 기본 버퍼부터 늘리지는 않는다.
4. **외부망 검증 보완:** 실제 서로 다른 회선에서 선택 경로·RTT·손실·지터·부족/PLC를 함께 비교한다. 직접/강제 TURN 결과와 입→귀 측정은 각각 구분한다.

사용자 마이크·이어폰 설정은 이 조사 범위에서 제외한다. 노트북에는 유선 포트/어댑터가 없어 유선 대조는 진행하지 않았다. 지연 우선·품질2순위라는 제품 목표와 고정20ms 기본 여유는 유지했다.
