# 작은 적응 여유와 빈 큐 복구 · 0.5.3

지연을 우선하면서 짧은 도착 지연 때문에 PLC가 연속되는 경로를 보완했습니다. 소비율 보정과 기본 코덱은0.5.2를 유지하고, 목표 여유와 빈 큐 처리만 추가합니다.

## 동작

- 목표 여유는20ms에서 시작하고 최대40ms까지만 올립니다. 실제 큐에는 출력 요청 크기와 소비율 제어의 위상이 더해질 수 있으므로 실제 대기나 종단 지연의 상한40ms를 뜻하지 않습니다.
- 큐가 비어 있고 뒤쪽 패킷도 없으면10ms PLC를 삽입하되 해당 RTP 패킷을 재생한 것으로 처리하지 않습니다. 조금 늦게 온 원래 패킷을 한 번 재생할 기회를 줍니다. 이때 목표 여유도10ms 올려 소비율 제어에 반영합니다.
- 추가 기다림은20ms 범위입니다. 남은 목표 여유 공간이10ms 미만이면 새10ms 기다림을 넣지 않습니다. 뒤쪽 패킷이 이미 있는 실제 손실 구간은 기존처럼 RTP 시각을 넘겨 PLC로 처리합니다.
- 기다림을 포함한 연속 PLC의 PCM 길이 상한은 여전히60ms입니다. 긴 단절로 이를 넘으면 재버퍼링하고20ms 기준으로 새 패킷을 모읍니다. 네트워크 단절 때문에 재시작 대기에20ms를 추가 부과하지 않습니다.
- 최근256개 표본의 `도착 간격 − RTP 간격` 중 양수 부분을 모아 P95를 계산합니다. RTP 간격도 함께 빼므로 단순한 패킷 손실 간격을 지터로 계산하지 않습니다. 순서가 뒤바뀐 오래된 타임스탬프는 추정에서 건너뜁니다. 이 수치는 RFC3550 지터나 일방향 네트워크 지연과 다릅니다.
- 실제 지연 도착이1초 안에3개 이상이고 간격 초과 P95도5ms 이상이면 여유를10ms 올립니다. 지터가 관측됐다는 이유만으로 대기를 늘리지는 않습니다.
- PLC나 지연 도착 없이30초가 지난 뒤에는1초당1ms씩20ms로 돌아갑니다. 단순 손실이 계속돼 PLC가 발생하면 복귀가 늦어질 수 있습니다. SSRC·장치·시간축 초기화는 여유와 도착 추정을 새로 시작합니다.

지연 우선 요구에 따라 기본은0.5.2의 **고정20ms 여유**입니다. 화면의 **지터 적응 20~40ms**를 켜면 새 적응 기능을 사용합니다. RTP 재생·소비율 보정은 양쪽 모드에서 유지합니다. 통화에서 나간 뒤 변경합니다. 진단에 현재 목표, 여유 증가/감소 횟수, 도착 간격 초과 P95, 기다림으로 삽입한 PLC와 최대 연속 PLC를 추가했습니다. `HeldMs`는 전체 `ConcealedMs`의 부분집합이며 둘을 더하면 중복 계산입니다.

## 같은 도착 조건의 결정적 비교

가상 시간10분 상당17조건을 실행했습니다. 아래 지연 구간은 처음2분 동안2초마다 패킷 도착을 잠깐 막았다가 묶어서 전달하고, 나머지8분은 일정하게 전달합니다. 페이로드·도착 시각·출력 요청은 고정/적응에서 같습니다. 실제 네트워크나 청감 평가는 아닙니다.

| 조건 | 고정 여유 PLC / 지연 폐기 | 적응 여유 PLC / 지연 폐기 |
|---|---:|---:|
| 반복30ms 지연 | 590ms / 59개 | **30ms / 0개** |
| 반복45ms 지연 | 1180ms / 118개 | **410ms / 39개** |

두 적응 조건 모두 재버퍼링0, 무음 부족0이며 마지막 목표 여유는20ms로 돌아왔습니다. 최종 앱 큐 상한120ms와 연속 PLC60ms 경계를 유지했습니다.

일정 도착, 추가 지연0~25ms, 단순1% 손실,100ms 연속 손실, ±200/500ppm,80ms 초기 대기 회복 검사는 기존 결과를 유지했습니다. 손실+지터+느린 클록 조합은 PLC가6360→6370ms로10ms 증가했습니다. 모든 경우 PLC가 감소한다고 주장하지 않습니다. 순수1% 손실만으로 여유를 늘리거나 기다림을 삽입하지 않는 검사도 통과했습니다.

회귀 검사에는 RTP 시각을 보류한 뒤 원래 패킷을 한 번 받아들이는지,20~40ms 제한, 목표 여유 공간 부족 시 기다림 거부, 안정 후 감소, 장치 초기화 복귀를 추가했습니다.

```powershell
./native/verify.ps1 -NoRestore -Stress -Integration
```

정적 분석·기존 회귀·서버7개·17조건 부하·실제 ICE/DTLS/SRTP/RTCP/데이터 채널 검사는 모두 통과했습니다. 로그와 가상 원본은 Git 제외 경로 `native/.local/reports/adaptive-*` 및 `rtp-stress-verify.json`입니다.

## 두 PC 고정→적응→고정 비교

적응 구간의 양쪽 목표 여유는40ms까지 증가했다가20ms로 돌아왔고, 기다림은 각각20ms였습니다. 큐 정리·출력 오류·송신 큐 드롭은 모든 구간0이었고 수집된 RTCP 수신 손실도0%였습니다. 도착 조건은 실제 네트워크에서 시간에 따라 달라지므로 A1의 재버퍼링 감소를 모두 적응 기능의 인과적 개선으로 단정하지 않습니다. A2에서는 고정 방식도 부족 없이 동작했고 PC PLC는 적응보다 적었습니다.

루프백 측정18회 모두 시작 패킷 추적 검증을 통과했습니다. 수신→출력 제출 중앙값과 전체 디지털 루프백 중간값 중앙값은 아래와 같습니다. 방향은 측정 송신자를 기준으로 표기합니다.

### 기본값 결정

적응은 늦은 패킷을 기다리는 만큼 대기를 추가합니다. 이번 구간 큐는 안정된 고정 A2 대비 약19~22ms 높았습니다. 사용자의 지연 우선 요구에 따라 기본값을 고정20ms로 유지하고, 새 적응 기능은 선택으로 제공합니다. 실제 비교 도구는 구간별로 이를 명시적으로 설정하므로 앱 기본값 변경은 위 비교 결과에 영향을 주지 않습니다.

다음 개선은 기다림 삽입을 늘리기 전에 실제 도착 스케줄링 지연과 큐 체류 원인을 좁히는 것입니다. 특히 고정 A1과 A2 차이가 커서 버퍼 변경만으로 모든 끊김을 설명할 수 없습니다. 적응 기능의 인터넷·TURN·장시간 안정화는 추가 검증이 필요합니다.

## 재현과 자료

```powershell
dotnet publish native/TransportProbe -c Release -o native/.local/rtp-adaptive-053
# 양쪽에서 같은 UNIQUE_PREFIX를 사용하고 ROLE은 각각 pc / laptop
./native/.local/rtp-adaptive-053/TransportProbe.exe --adaptive-ab-test https://qlrpal.ddns.net/ UNIQUE_PREFIX pc-report.json pc
```

실제 원본은 Git 제외 경로 `native/.local/rtp-adaptive-053/{pc,laptop}-report.json`, `summary.json`입니다. 노트북 사용자 홈 `voice-rtp-adaptive-053/`에도 프로그램·원본을 남겼습니다. 원음은 저장하지 않았으며 IP·닉네임이 포함된 원본은 Git에서 제외합니다. 검사 프로세스와 SSH는 종료했습니다. 서버·방화벽 변경은 없습니다.
