# EXTREME-090 — 실측 재생·프레임·TURN 검증과 마감 분석

2026-10-25. 목표는 지연 우선의 Windows 공유 모드 통화다. 승인된 노트북 SSH와 기존 격리 시험 실행기를 사용했고 장치/드라이버/공유기/라우팅/서버 설정은 변경하지 않았다.

## 수행한 시험과 판정

1. 089의 두 PC 기록을 합성 패킷으로 재생: 각 수신 측 빈 큐 대기0/2.5/5/10/15/20/30ms × 조용한 구간2/3/4/6초(총56조건). 대기를 늘리면 늦은 패킷 수는 줄지만 PLC·오디오 폐기가 늘 수 있었다. 예: PC 기록의 quiet6에서 hold2.5→30ms는 PLC217.5→502.5ms, 폐기81.271→550.062ms였다. 단순 대기 증가는 채택하지 않았다. 이 재생은 콜드 스타트 이력·실제 디코딩/장치 타이밍·음질을 재현하지 않는다.
2. 실제 두 PC 직접 연결: opus-adaptive-5(5ms)90초 → opus-adaptive(2.5ms)90초. 합성 음성을 실제 공유 입출력과 SRTP로 전송했다. 두 프로필은 빈 큐 대기와 FineClock 설정도 다르므로 단일 프레임 길이만의 인과 실험은 아니다. 실사용 후보 프로필의 비교로 판단한다.
3. 기존 OCI TURN 강제 + opus-auto-frames120초: 양쪽 선택 경로가 TURN임을 확인했고 실제 자동2.5→5→10→5ms 전환을 관측했다. PC의10ms 시험은 약31.7~34.3초, 노트북은34.7~40.9초에5ms로 복귀했다. 자동 제어의 기능 시험이며 최적 프레임이나 품질 합격을 뜻하지 않는다.

모든 실제 시험의 연결/장치 오류0, 송신 큐 드롭0. PLC/부족은 남았다. 아래는 시작35초 이후 구간(직접 약54초, TURN 약84초)이므로 서로 다른 길이의 PLC 합계를 직접 비교하지 않는다.

5ms 프로필의 PLC는 두 수신 측 모두 후속2.5ms보다 많았고 큐 지연도 낮아지지 않아 기본으로 채택하지 않았다. 회선의 시간 변동과 다른 프로필 옵션 때문에 프레임 길이만의 책임으로 확정하지 않는다. TURN과 직접 연결은 모드/시간/경로가 달라 지연·품질의 동등 대조가 아니다.

## 새 분석 도구

`native/TransportProbe/Analysis/analyze_packet_deadline_pair.py SEND.json RECEIVE.json OUT.json`

기존 `analyze_playout_deadlines.py`의 단일 수신 보고서 인터페이스는 유지했다. 새 도구는 정확한 SSRC/RTP 경계 대응 후 다음을 추가한다.

- 늦은 입장 전에 같은 RTP 위치에 PLC/실제 재생이 있었는지, 기록이 없어 미확정인지 구분.
- 렌더 PCM 요청 시간 대비 호출 간격 초과, 렌더 작업/잠금 대기, 수신 콜백부터 버퍼 반환까지의 시간.
- 송신 API 작업과 디스패치 대기, 매칭된 패킷의 수신 간격에서 송신 간격을 뺀 변동. 서로 다른 호스트의 절대 시각을 빼지 않으며 각 호스트 시계 속도 오차는 여전히 한계다.
- 실패 보고서·퇴출된 기록·방향/대응 경계 부족을 거부. 원본 덮어쓰기 방지. 실제 음성/패킷 본문 저장 없음.

기존 도구2개와 새 도구 self-test 통과. 새 self-test는12ms 변동 검출, 독립 시계 오프셋 불변, PLC/재생/미확정 구분, 실패/퇴출 거부를 검사했다. 현재 턴의 앱 실행 코드는 바꾸지 않았으며 기존 기본값과 배포본을 유지했다.

## 발생 위치와 한계

089의 기록에서 렌더 간격 초과 최대 약1.19ms, 렌더 잠금 대기 최대 약0.079ms, 렌더 작업 최대 약1.94ms, 송신 API 최대 약1.49ms, 디스패치 최대 약0.206ms였다. 반면 매칭 패킷의 수신-송신 간격 변동 최대는 방향/구간별 약50~66ms였다. 정확한 대응 범위의 늦은 입장은 모두 같은 RTP 위치의 이전 PLC 이후였으며 실제 패킷 수신 누락과 구분됐다.

새 직접 연결 기록에서는 대응 범위의 수신 관측 누락0, 간격 변동 최대 약54~78ms였다. TURN 기록은 대응 범위 수신 미관측이 방향별5/1프레임, 간격 변동 최대 약90/54ms였다. 미관측은 송신 API 기록과 수신 콜백 사이의 부재이며 물리 회선 패킷 손실 확정은 아니다.

큰 변동을 관측된 앱 렌더 처리나 잠금 대기만으로 설명하기 어렵고, 송신 API 호출과 수신 콜백 사이 구간이 주요 후보다. 이 구간은 양쪽 OS/드라이버/네트워크를 포함한다. 물리 NIC 송수신·무선/AP/통신사 중 어느 위치인지는 이 시험으로 확정하지 못한다. 실제 입→귀 지연이나 모든 사용자의 원인을 주장하지 않는다.
