# 장치 버퍼 반환·초기 재생·OS 수신 경로 개선 (2026-10-21~22)

## 시험 경로 정정

기존 `ExtremeSoak`가 앱의 `SetMediaInterface`를 전달하지 않는 누락을 확인했다. 064~066의 실행은 OS 자동 경로이며, ‘직접 연결’은 ICE가 TURN을 선택하지 않았다는 뜻이다. 물리 LAN 인터페이스 고정까지 검증한 것으로 설명한 부분은 정정한다.

현재 읽기 전용 OS 경로 조회에서 PC→노트북은 이더넷이지만, 노트북→PC는 동일 `172.30.1.0/24`의 Wi-Fi보다 metric 0의 Tailscale 경로를 우선 선택했다. 과거 058에서도 알려졌던 조건을 새 시험 도구에서 빠뜨렸다. 모든 과거 수신 공백을 VPN 하나로 소급 확정하지 않는다.

도구의 `--route-extreme-soak` 마지막 선택 인자로 미디어 IPv4를 전달할 수 있게 수정했다. PC `.88`, 노트북 `.30`으로 미디어 소켓만 bind하고 `IP_UNICAST_IF`를 적용한다. 시스템 라우팅·Tailscale·다른 앱 설정은 변경하지 않았다. 요청 주소와 모든 측정 스냅샷의 실제 선택 값이 같은지 요약 판정에서도 검사한다. 원시 결과에 프로세스 PID를 추가했다.

## OS 수신 경계 확인

이미 관리자 권한인 노트북 SSH에서 기존 `trace-network.ps1`을 실행했다. `Microsoft-Windows-Kernel-Network`의 주소·포트·길이·PID만 기록하며 패킷/음성/토큰은 수집하지 않는다. 각 150초, 순환 상한 32MiB다. `tracerpt -rts`의 원시 QPC를 사용해 노트북 앱 시각과 비교했고 이벤트 유실 0·상한 미도달을 확인했다.

- OS 자동 대조: 23,003,136바이트, 앱 마지막 기록의 30ms 초과 수신 공백 2개. 34.562/30.991ms가 OS UDP에서도 34.622/31.086ms였다. 경계 차이 최대 0.185ms, 공백 내부 UDP 이벤트 0개였다.
- 지정 LAN 대조: 11,730,944바이트, 같은 분석 구간의 공백 4개. 앱 30.753~35.363ms와 OS 30.748~35.417ms가 대응했다. 경계 차이 최대 0.191ms, 공백 내부 UDP 이벤트 0개였다.

따라서 이번에 짝지은 공백 6개는 관리형 WebRTC 콜백 전에 이미 OS UDP 이벤트 경계에 존재했다. 지정 LAN에서도 관측되어 VPN만 제거하면 모든 공백이 없어진다고 주장하지 않는다. OS 이벤트는 NIC 하드웨어 도착 시각이 아니므로 무선망·AP·드라이버·커널을 분리한 확정 결과도 아니다. 같은 tuple의 STUN/RTCP와 RTP를 개별 식별한 측정은 아니다.

ETW MCP에서도 해당 baseline ETL을 load→trace_info/get_sysconfig→analyze 순서로 확인했다. 150.4초, 유실 0이었다. 이 메타데이터 전용 캡처에는 CPU/DPC 샘플이 없으므로 UDP dispatch/CPU/DPC 분석 결과를 만들어내지 않았다. 정밀 대응은 원시 QPC 변환기로 수행했다.

## 오디오 경로 변경

실험 프로필에서만 `StagedDeviceBuffers` 후보를 추가했다. 기존 기본 모드와 안정 배포본은 유지한다.

1. 캡처: 미리 할당한 한 패킷 크기 저장소에 복사하고 WASAPI lease를 반환한 뒤 변환·Opus·SRTP를 처리한다. 원래 장치 시각과 플래그를 보존한다. 지원되는 기본 공유 주기가 5~10ms면 동일한 직접 캡처 경로를 사용할 수 있게 해, 5ms 미만의 불안정한 절대 최소 주기는 요청하지 않는다. 지원되지 않으면 기존 호환 경로다.
2. 출력: 미리 할당한 작업 저장소에서 디코딩/리샘플링을 마친 뒤 WASAPI lease를 얻어 복사·반환한다. 작업 저장소는 재생 FIFO가 아니며 기존 출력 목표·수신 여유를 추가하지 않는다.
3. 초기 재생: 첫 실험 출력 전에 별도의 소프트웨어 인스턴스로 인코딩/디코딩·샘플 보간·PLC 경로를 준비하고 폐기한다. 실제 통화의 코덱 상태·RTP·진단 카운터에는 합성 준비 프레임을 넣지 않는다. 프레임 길이/인코딩마다 한 번 수행한다.
4. 계측: 입력 lease/콜백 최대 시간, 출력 공급/lease 최대 시간, 기상 간격, MMCSS 등록 결과와 소진 시각·단계를 UI/JSON에 추가했다. 공급 중 소진은 새 프레임을 커밋하기 전에 관측하여 숨기지 않는다.

별도 `PeriodWatchdog` 후보는 이벤트가 오지 않을 때 대기 상한을 약 한 엔진 주기로 줄인다. 계속 도는 폴링이나 전역 타이머 설정은 사용하지 않는다. 대조 후 2.5ms 프로필에는 입력과 출력 모두 채택했다. 입력만 활성화한 후보는 노트북 PLC 1.561%로 탈락했다.

`PeriodWatchdog`는 입력, `RenderPeriodWatchdog`는 출력에 각각 적용한다. 장치 버퍼 작업 시간은 GetBuffer 호출 시작부터 반환 처리 종료까지이며 API 호출·스케줄링을 포함한다. 순수 CPU 점유 시간이나 전체 지연이 아니다. 출력 공급 최대값은 시작 전 준비를 포함한 전체와 실제 재생 중 값을 분리했다.

통계 큐는 256개 저장소를 시작 전에 확보하고, 가득 찼을 때 먼저 제거한 뒤 추가해 257번째 추가 시 재할당되는 문제를 피했다. 지터 P95도 정렬 저장소를 재사용하며 입력 RMS는 직접 루프로 계산한다. 생성 후 10,000회 갱신에서 할당 0바이트와 기존 1ms 지터 P95를 확인했다. 전체 통화 경로가 무할당이라는 뜻은 아니다.

변경 전 지정 LAN 대조의 시작 구간에서 PC 공급 최대 16.676ms/lease 최대 17.259ms와 공급 중 소진 1회가 관측됐다. 노트북은 전체 실행에서 공급 최대 36.716ms/lease 36.732ms, 공급 중 소진 3회였다. 초기 2초 이후의 연속성 판정과 시작 구간의 소진을 별도로 보존한다. 이 관측만으로 JIT 하나를 유일한 원인으로 확정하지 않는다.

정확한 설치 버전의 공식 SIPSorcery 소스도 확인했다. UDP 수신 콜백이 동기 처리한 뒤 다음 receive를 등록하는 구조지만, 이번 OS 공백 결과를 해당 코드가 원인이라는 증거로 사용하지 않았다. [설치 커밋의 UdpReceiver](https://github.com/sipsorcery-org/sipsorcery/blob/08c2ed0ad72c423ca06950dee2e842488a219884/src/SIPSorcery/net/RTP/UdpReceiver.cs)를 참고한다.

원시 결과·ETL·변환 CSV·검증 로그는 Git 제외 경로 `native/.local/extreme-067/`에 보존한다.


## 초기 재생 준비와 검증

실험용 직접 WASAPI 출력은 RTP 도착 이벤트로 기존 reserve와 첫 장치 공급분이 준비되기를 최대 100ms 기다린다. 준비되면 첫 실제 미디어를 채운 뒤 장치를 시작하며, 미도착 시 무음으로 시작한다. 정지 요청으로 즉시 빠져나올 수 있다. 추가 정상 재생 FIFO나 고정 100ms 통화 지연을 넣은 것이 아니다. `PrimingWaitMs`, `PrimedWithMedia`를 JSON/UI에 기록한다. PC와 노트북에서 미디어 없는 시간 제한 및 대기 중 종료 실기 검사가 모두 통과했다.

초기 준비가 모든 소진을 해결하지는 않았다. 세 번의 새 프로세스 60초 시험에서 PC의 전체 소진은 모두 0이었다. 노트북은 첫 직접 시험 0, 두 번째 직접 시험은 첫 스냅샷 약 50초 뒤 1회, TURN 시험은 첫 스냅샷 이전 1회였다. 정상 미디어 준비 성공은 세 번 모두 기록됐다. 따라서 초기 공급과 실행 중 공급 지연을 동일 원인으로 확정하지 않는다.

## 마지막 NIC 캡처와 판단의 제한

현재 빌드로 지정 LAN 90초 시험을 추가했다. 두 PC 모두 연결·장치 오류 없이 기능 및 측정 구간 연속성 기준을 통과했다. 입장→재생 P50은 PC 15.43ms, 노트북 17.75ms였다. 노트북 Pktmon은 97초, 1,465,474바이트, 이벤트 유실 0, 정상 종료였고 64MiB 상한에 도달하지 않았다. 관측 컴포넌트는 실제 Intel AX201 Wi-Fi의 ID 13이었다.

**54바이트 제한의 계측 설계 오류:** Ethernet 헤더를 가정했으나 실제 이벤트는 Native Wi-Fi 헤더였다. 보존된 접두부는 IPv4 주소까지 포함하고 UDP/RTP 헤더는 포함하지 않았다. 따라서 RTP SSRC·타임스탬프·순번으로 앱 기록과 정확히 대응하는 분석은 할 수 없다. 같은 IP 방향의 NIC 이벤트와 시간상 가까운 경계만 비교했으며 이를 개별 RTP 일치 결과로 사용하지 않는다.

보존된 마지막 약 30초 앱 기록에는 54.469ms와 31.138ms 공백이 있었다. 그 사이 같은 IP 방향의 NIC UDP 이벤트는 각각 17개와 9개가 있었다. NIC 전체 수신 중단으로 단정할 수 없으며, 해당 이벤트가 통화 미디어인지 확정할 수도 없다. 이전 Kernel UDP 공백 역시 수신 요청 재등록·커널 전달·관리형 스케줄링을 배제하는 증거가 아니다. 무선 장치/망이 유일 원인이라는 결론과 앱 밖이라는 결론 모두 보류한다. 이번 제한 캡처를 완전한 발생 위치 규명으로 포장하지 않는다.

## 완료 범위와 남은 과제

- Release 경고 0 빌드, 정적 분석·회귀 검사·서버 검사·실제 네이티브 SRTP/RTCP 통합 검증 통과. 초기 준비 코드 이후 전체 검증도 통과했다. 이후 UI/장치 검사 도구 추가 후 빌드·실험 회귀 및 두 실기 장치 검사를 통과했다.
- 두 기기의 지정 LAN/강제 TURN 시험은 합계 약 21.5분 수행했다. 실패한 설정 시작은 제외했다. 원시 JSON의 실패·초기 소진과 모든 실험 결과를 보존했다.
- 시험 프로세스, Pktmon과 전용 필터 종료를 확인했다. 시스템 VPN·라우팅·장치 효과 설정을 변경하지 않았다.
- 남은 실제 문제는 PC TURN 부족 기준 초과, 노트북의 드문 초기/실행 중 출력 소진, 정확한 RTP별 NIC→앱 경계 분리다. 게임 부하·원거리 사용자·주관 청취·물리 마이크→귀 지연은 이번 결과로 검증하지 않았다.
- 변경은 `codex/extreme-latency` 작업 트리에만 있다. 안정 브랜치·기존 배포 파일은 변경하지 않았고 커밋/푸시는 하지 않았다. 기존 안정판을 대체할 전면 승인 상태가 아니다.
