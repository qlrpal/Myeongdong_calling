# EXTREME-105 · Wi-Fi 고정 경로의 송신 Tx→수신 Rx

2026-10-27 / `codex/extreme-latency`. 다른 최적화는 보류하고104에서 남은 실제 끊김만 조사했다. 노트북의 **시험 통화 소켓만 Wi-Fi로 지정**하고 PC는 기존 Ethernet 경로를 사용했다. 시스템 VPN·라우팅·공유기·드라이버 설정과 제품 앱/SDK·코덱·프레임·버퍼는 변경하지 않았다.

## 이번 관측으로 좁힌 경계

처음60초 시험의30ms 초과 수신 콜백 공백24건에서, 같은 양끝 RTP 패킷이 모두 송신 API·노트북 TCP/IP·Wi-Fi Tx·PC Rx·콜백에 대응했다. **선택 사건의 큰 간격 증가는 송신 Wi-Fi 소프트웨어 Tx 관측 뒤→PC 소프트웨어 Rx 관측 이전에 있었다.**

| 사건 | 송신 API 간격 | 송신 Wi-Fi Tx 간격 | PC Rx 관측 간격 | PC 콜백 간격 |
|---|---:|---:|---:|---:|
| E1 | 4.068ms | 4.158ms | 131.594ms | 131.646ms |
| E2 | 0.362ms | 0.209ms | 128.278ms | 128.331ms |
| E3 | 11.446ms | 11.563ms | 122.677ms | 122.728ms |

24건 모두 송신 앱 프레임 순번도 인접했다. 해당48개 양끝의 API 시작→Wi-Fi Tx 관측은 최대0.289ms였다. 이 사건들을 송신 앱 큐·인코딩 대기나 PC 캡처 뒤 SDK/디코딩의 수십~100ms 처리로 설명할 근거는 없다. **소프트웨어 Tx는 실제 하드웨어 송신 완료가 아니므로**, 송신 드라이버/펌웨어·매체·AP/메시·수신 드라이버 중 어디인지까지 확정하지 않는다.

## 시험과 수집의 유효성

- 실제 PC↔노트북1:1·합성 음성·`opus-adaptive`·네이티브 Opus·직접 UDP60초. 기존 검증 앱 바이너리를 양쪽에서 동일 해시로 확인했다.
- 노트북의 요청 MediaAddress와 PC가 실제로 본 상대 미디어 주소가 Wi-Fi 주소였음을 모든 진단 표본에서 확인했다. PC의 OS 선택 경로는 Ethernet이었다. WebRTC의 direct 표지만으로 물리 경로를 가정하지 않았다.
- 노트북의 기존 Pktmon에서 실제 Intel Wi-Fi 지점13과 해당 TCP/IP 지점66만 선택했다. PC의 기존 Npcap은 실제 Ethernet 인터페이스·비 promiscuous·시험 상대 UDP·128바이트 prefix·시간/파일 상한으로 제한했다.
- 노트북 ETW 손실0, 파일5,811,671바이트로64MiB 상한 미도달, 정상 중지·필터 복구. raw QPC를 사용했고 앱 송신 trace 전체가 수집 시간 안에 있었다.
- **송신 trace12081개 중10953개(약90.66%)만 각 Tx 지점에서 대응했다.** 이 수집은 불완전하며, 관측되지 않은 프레임을 손실로 판정하지 않는다. 위24건은 모두 양끝이 정확히 대응한 긍정 관측이다. 해당 지점의 각 양끝은 단일 관측으로 기록됐다.
- PC 캡처는 정상 종료0·강제 종료 없음·보고된 인터페이스/pcap/dumpcap 드롭0이었다. 마지막30초 앱 수신11981개와 late208개가 캡처와 모두 유일하게 대응했다. 수신 trace의 late208건은 같은 RTP 시각의 PLC가 콜백 전에 시작된 경우였다.
- 24건의 PC 캡처 이후 콜백 간격 증가 범위는−0.059~+0.140ms였다. 절대 캡처→콜백 지연이 아니라 같은 두 패킷 간격의 차이다.

첫 시험의 진단 구간 PC PLC662.5ms/출력 부족863.46ms/재버퍼18회, 노트북 PLC865ms/부족935ms/재버퍼17회였다. 품질 합격이 아니다. 노트북 Pktmon을 새로 켰으므로 다음 계측 영향 대조도 수행한다.

## 계측 영향 대조

통화별 Wi-Fi 경로·동일 제품 빌드·60초·PC Npcap과 앱 자체 trace는 유지하고, **노트북 Pktmon만 끔 A1 → 켬 B → 끔 A2**로 비교했다. 다른 설정 변경이나 코드 후보 A/B가 아니다. 모든 앱 종료 코드는0, trace 축출은0이었다.

| 조건 / 수신 측 | 진단 구간 PLC | 출력 부족 | 마지막30초 30ms 초과 공백 / 최대 |
|---|---:|---:|---:|
| A1 끔 / PC | 315ms | 17.69ms | 24건 / 53.526ms |
| B 켬 / PC | 80ms | 13.02ms | 1건 / 60.844ms |
| A2 끔 / PC | 122.5ms | 12.71ms | 2건 / 53.086ms |
| A1 끔 / 노트북 | 190ms | 38.06ms | 25건 / 54.669ms |
| B 켬 / 노트북 | 457.5ms | 35ms | 1건 / 56.837ms |
| A2 끔 / 노트북 | 137.5ms | 12.17ms | 2건 / 50.019ms |

PC의 모든 앱 수신/late는 캡처와 유일하게 대응했다(A1:11978/late78, B:11995/late5, A2:11977/late10). 각 수집은 정상 종료했고 Npcap 드롭 보고0이었다. Pktmon을 꺼도 약53ms 공백이 있으므로 이 현상이 켠 상태에서만 나타난 것은 아니다. **계측 영향0을 증명한 것은 아니다.** B의 노트북 PLC는 A1/A2보다 많았고 결과가 방향별로 혼재한다. 최초 시험의131ms급 사건 빈도·크기를 무계측 평상시 값으로 일반화하지 않는다.

### 대조 B에서 다시 대응한 사건

B의 노트북 Tx 수집은12061개 송신 trace 중10525개만 각 지점에 대응했다. ETW 정상 중지·손실0·파일 상한 미도달을 별도로 확인했다. 큰 공백 한 건의 양끝은 두 Tx 지점과 PC Rx에서 모두 정확히 대응했다.

| 송신 API 간격 | TCP/IP Tx 간격 | Wi-Fi Tx 간격 | PC Rx 관측 간격 | PC 콜백 간격 |
|---:|---:|---:|---:|---:|
| 10.625ms | 10.731ms | 10.756ms | 60.805ms | 60.844ms |

해당 양끝의 API 시작→Wi-Fi Tx 관측은0.043/0.174ms였고 송신 앱 순번은 인접했다. 이 사건에서도 큰 간격 증가는 Wi-Fi 소프트웨어 Tx 관측 뒤→PC Rx 관측 이전이었다. 약50.049ms라는 차이는 **패킷 간격 증가**이며 절대 편도 지연이 아니다.

## 분석 도구와 검증

`analyze_tx_rx_intervals.py`는 SSRC·RTP 타임스탬프·wire 순번으로 Pktmon Tx와 PC 캡처를 연결하고, 송신 API 식별은 SSRC·타임스탬프와 앱 순번으로 따로 대응한다. 앱 순번을 wire RTP 순번으로 취급하지 않는다. 여러 Tx edge 관측이 있으면 최소 시각과 범위를 함께 남긴다. source trace 중복·축출·방향 불일치, 수신 캡처 중복/누락은 정확한 사건 대응으로 처리하지 않는다.

각 간격은 해당 호스트/관측기의 시계로 계산한다. 다른 PC의 절대 시각이나 pcap epoch와 앱 QPC를 직접 빼지 않는다. 시간원 진행률이 비교 가능하다는 가정은 남는다. API→Tx 값만 같은 송신 호스트 QPC에서 뺀다. **Tx→Rx 간격 증가는 절대 편도 지연이나 입→귀 지연이 아니다.**

자체 검사는 독립 시각 원점 변경, 누락된 양끝, 중복 수신 캡처, 역순 소스, 축출된 이력의 오판 방지를 확인했다. 실제 데이터 결과는 기존 독립 분석과 같은24건을 대응했다. 제품 코드는 바꾸지 않아 제품 전체 재빌드/새 설정 튜닝을 섞지 않았다.

```powershell
python ./native/TransportProbe/Analysis/analyze_tx_rx_intervals.py --self-test
python ./native/TransportProbe/Analysis/analyze_tx_rx_intervals.py SENDER.json RECEIVER.json TX-RAW.csv RX-RTP.csv OUTPUT.json
```

ETW 정상 중지/손실/상한·Npcap 드롭·수집 시간 범위는 도구 출력과 별도로 확인해야 한다. 이 도구는30ms 초과 콜백 공백을 나열하며, 모든 PLC·출력 부족 사건을 분류하지 않는다.

## 남은 범위

관측 지점 사이에는 송신 NIC 하위 드라이버/펌웨어·무선 전송/재시도·AP/메시 전달·수신 NIC/드라이버 등이 포함된다. 캡처 지점을 실제 전파 송수신 시각으로 해석하지 않는다. 실제 게임·외부 사용자·물리 입→귀 지연 시험도 아니다.

다음 물리 경로 대조 후보는 노트북 Wi-Fi 통화를 고정한 채 PC의 기존 Ethernet 경로와 이미 연결된 Wi-Fi 경로를 통화별로 비교하는 것이다. 이는 NIC와 매체 경로를 함께 바꾸는 대조이므로, 차이가 나더라도 단일 드라이버나 AP를 바로 원인으로 확정할 수 없다. 과거 전원·스캔·qWAVE 조정은 반복하지 않는다. 제품 버퍼 확대나 다른 기능 개발은 계속 보류한다.

## 보존·복구

최초 SSH 연결은 노트북 절전 중 시간 초과됐고 수집/통화는 시작하지 않았다. 사용자가 노트북을 켠 뒤 정상 준비를 확인했다.

원본·수집 스크립트·시각/해시·정상 종료/복구 기록은 ignored `native/.local/extreme-105`에 보존한다. 개인 주소·전체 캡처·자격 증명은 커밋하지 않는다. 자체 Pktmon 세션·필터와 Npcap 프로세스를 정상 종료했고 노트북 시험 파일은 기존 목록으로 원복·SHA256 검증했다. 시스템 VPN/라우팅·기존 배포본·기존 미커밋 변경은 보존했다.
