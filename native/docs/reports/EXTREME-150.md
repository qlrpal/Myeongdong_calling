# EXTREME-150 — 할당 귀속과 진단 통계 무할당화

2026-11-03 / `codex/extreme-latency`, 비교 기반 `ab2833e`. 이전149에서 남은 집중 다인 할당의 실제 경로를 먼저 확인했다. 프레임·수신 여유·출력 정책·송신 스케줄러·SDK 암호화는 변경하지 않았다.

## 가설과 계측

가설은 진단 갱신의 반복 할당이 통화 프로세스의 불필요한 GC 부담에 기여한다는 것이다. 기존97/98에서 다룬 단일 GCM 키 스케줄 후보를 재적용하지 않았다. 실제 기본 협상의 이중 GCM과 다른 후보였으며, 당시 통화 이득이 없어 제외된 상태다.

같은 사용자 권한의 EventPipe `gc-verbose`를30초 수집했다. 동일PC의6개 엔진·30개 상대별 실제 공유 출력·실제 캡처/로컬 WebRTC를 사용하고 입력PCM은 인코딩 전에 합성 음성으로 교체했다. 일반10ms/고정 수신20ms/기존 출력 정책을 유지했다. 프로파일러 자체의 부담이 있으므로 이 구간은 지연·성능 A/B 결과로 사용하지 않는다.

7,432개 할당 tick의 가중 합은792,540,936바이트였다. TraceLog 보고 손실 이벤트0, 스택 없는 할당 tick0, 서로 다른142개 스택이었다. `GcmBlockCipher`가 포함된 스택은360,118,184바이트(45.44%), `ProcessingWindow.Snapshot` 포함 스택은50,502,768바이트(6.37%)였다. 스택 집합별 귀속이며 객체별 정확한 할당량·실제1인 앱의 비율·특정 PLC의 원인 증명이 아니다. GCM 계열은 암호화·복호화와 호출 하위를 합친 집합으로 개별 메서드의 독점 비용과 구분한다.

## 실제 수정

- `PrecisionMetrics.cs / ProcessingWindow.Snapshot`: 최대256개 FIFO의 P95/최댓값 계산에서 LINQ 정렬·배열·정렬 맵 대신 호출별2KiB 스택 scratch와 span 정렬을 사용한다. FIFO는 건드리지 않고 읽기만 한다. 기존 상위 잠금과 스레드 안전성 조건을 유지하며 공유 scratch나 새 잠금은 추가하지 않았다.
- `SelfChecks.cs / --precision-self-test`: 빈 창,1~256개 채움,2,048회 추가/오래된 값 제거, 중복·NaN·±무한대, 연속 읽기 결과를 기존 정렬 정의와 비교한다. 예열 후10,000회 snapshot의 현재 스레드 관리형 할당0도 검사한다.

이 수정은 진단 비용 감소다. 버퍼를 낮추거나 실제 음성의 시간축·입장·인코딩·암호화를 바꾸는 지연 정책이 아니다.

## 합성 계산 비교

별도 프로세스에서 실제 기존/수정 클래스 소스를 같은 실행 파일로 컴파일했다. seed152로 만든256개 고정 값, 각2,000회 예열,100,000회 snapshot을 원본→수정→원본 순서로3회 측정했다. 원본은 매회544,000,000바이트(호출당5,440바이트), 수정은0이었다. 원본 경과450.69~456.38ms, 수정117.81~119.38ms로 이 계산만 약73.8% 줄었다. 순수 반복 계산이며 실제 통화 전체 CPU·입→귀 지연 감소량으로 바꾸지 않는다.

## 회귀와 실제 통화 비교

Release 빌드는 경고/오류0이었다. 첫 전체 검사에서 sandbox 임시 디렉터리 이동이 거부돼 BuildTools 단계에서 중단됐으며 제품 실패와 구분했다. 같은 `verify.ps1 -NoRestore -Integration`을 파일/프로세스 제한 밖에서 재실행해 정적 분석·도구/제품/UI·오디오/복구·서버/실행기·실제 UDP/SRTP·가변 프레임·IPv6 통합까지 통과했다. Windows 관리자 설정 변경은 필요하지 않았다.

프로파일러를 끈 별도 기존→수정→기존 각90초 요청을 완료했다. 동일PC에서6엔진/30출력,10ms 프레임·수신20ms·기존 상대별 공유 출력·합성 음성 교체를 유지했다. 실제 캡처 주기10ms, Realtek 출력48kHz/2채널/float32·주기2.667ms·목표 패딩5.833ms였다. 암호화 프로필은 모두 `DOUBLE_AEAD_AES_256_GCM_AEAD_AES_256_GCM`이며 SDK 바이트도 같았다. 각 회차마다6개 slot·1,068개 표본의 연결/설정을 검사했다. 독립6대PC 시험이 아니다.

수정판 할당률은 두 기준선보다 각각6.06%/6.08% 낮았다. GC 정지율은 이번 세 관측에서 낮았지만 반복 표본이 충분한 일반적 GC/꼬리 지연 개선으로 선언하지 않는다. CPU는 수정판이 두 기준선보다 약간 높았으므로 **CPU 개선으로 채택하지 않는다.** 물리 입→귀나 정상 대기시간 감소는 새로 측정하지 않았다.

## 채택과 남은 일

동일 통계 결과·계산 할당0·실제 통화 전체 할당 감소를 근거로 `ProcessingWindow.Snapshot` 변경을 채택한다. 현재 소스의 진단 계산만 바꾸고 오디오 기본값은 유지한다. 암호화 최적화·전용 송신·새 수신 목표나 프레임 정책은 이번에 추가하지 않았다. 효과 없는 과거 단일GCM 후보도 되살리지 않았다.

상위 할당 경로의45.44%가 GCM 호출 집합이지만 이를 바꾸려면 실제 이중GCM의 내부/외부 키·nonce·AAD·키 재유도·인증 실패·재전송/종료를 별도로 검증해야 한다. 이번 결과만으로 키 재사용이나 협상 변경이 안전/유효하다고 판단하지 않는다. 송신 스케줄러 대조가 필요하면 정상10ms에서 같은 큐 용량·나이 정책을 고정해 비교하며,100의2.5ms 실험을 그대로 기본값으로 바꾸지 않는다.149의 장시간/부하 문제는 별도 미해결 상태다.

## 실행·복구와 한계

원본/수정 바이너리를 각각 고정 복사해 비교하며 기본SDK의 SHA-256은 양쪽 모두 `F997C495945FABFC00C47C2C63C75330BD8BDD2C6F795F70EA3111D1A0503376`이다. `.local/extreme-152`에 프로파일·원본 보고서·바이너리 해시·비교 스크립트·소형 benchmark를 보존한다. 개인정보가 있는 원본이나 EventPipe/ETLX는 커밋하지 않는다. 프로파일 도구는 이 Git 제외 경로에만 설치했으며 앱의 패키지/빌드 의존성에는 추가하지 않았다.

새 빌드는 `./native/run.ps1`, 회귀는 `./native/verify.ps1 -NoRestore -Integration`, 통계만 확인하려면 빌드된 검사기의 `--precision-self-test`를 사용한다. 원래 계산으로 복귀하려면 `ProcessingWindow.Snapshot`의 정렬만 기존 `values.Order().ToArray()`로 되돌려 다시 빌드한다. 기존 공개 베타/dist는 갱신하지 않았다.

이번 시험에서 노트북·OCI·공유기·장치·전원·라우팅·VPN 설정은 변경하지 않았다. 마지막에 소유한 로컬 시험 프로세스0을 확인하고 임시 실행 유지 요청을 해제했다. 실제 게임·독립PC·외부회선·장시간 통화·물리 입→귀는 새로 검증하지 않았다. 기존 다인 PLC/출력 마감/입력 불연속이 해결됐다고 선언하지 않는다.
