# EXTREME-101 · 작은 장치 요청과 입력 묶음 사이의 인위적 PLC

2026-10-26 / `codex/extreme-latency`. EXTREME-100의 미통과 분수 출력 조건을 분리했다. 이 문서는 물리 입→귀 지연 감소나 무선 지연 원인 규명을 선언하지 않는다.

## 구조와 재현한 원인

수신은 압축 RTP 저장소 → 상대별 Opus 디코더/시계 보정 → 장치가 요청한 만큼의 PCM 공급 구조다. 큰 공통 PCM 큐는 추가하지 않았다.

정상 패킷을 10/20ms 묶음으로 전달하고 장치가 128/256샘플씩 요청할 때, 기존 실험 경로는 매 Read에서 압축 큐를 정리하면서 부분 디코딩 PCM도 버렸다. 묶음의 중간 위상에서 이 정리가 반복되면 다음 도착 전 재생할 오디오가 없어져 PLC를 만들고, 이후 도착한 오디오를 다시 정리하는 순환이 발생했다. 손실 없는 가상 입력에서도 재현되므로 이 여섯 조건은 물리 네트워크 손실로 설명할 필요가 없다. 실제 통화의 모든 PLC가 같은 원인이라는 뜻은 아니다.

## 실제 변경

- `RtpOpusPlayoutBuffer.Read`: FineClock가 켜진 실험에서 장치 요청이 관측 입력 묶음보다 작으면 매 요청의 공격적 packet/PCM 정리를 생략한다. `Add`의 강제 backlog 상한과 재시작 정책은 유지한다.
- `ClockReserveSamples`: 이 경우 피드백 기준은 기존 여유와 관측 묶음의 절반 중 큰 값이다. 묶음 사이의 톱니형 큐 평균을 지나치게 낮추어 다음 도착 전에 소진하지 않도록 한다. 시작 조건의 수신 여유를 일괄 올리는 변경은 아니다.
- `PlayoutClockController.SetSubBurstFeedback`: 같은 조건에서만 deadband를 5ms에서 0.5ms로 좁힌다. 정리를 생략한 뒤 정상 큐가 넓은 deadband에 계속 남지 않도록 한다. 보정 속도 상한·하한, 기존 큰 요청 및 기본 모드의 정책은 유지한다.
- `AdaptiveNetworkChecks`: 마지막 20초의 **모든 실제 Read 뒤 큐**를 출력 샘플 수로 가중 집계한다. 500ms 표본만으로 묶음 주기의 큐를 비교하는 aliasing을 피한다. 분수 요청 ±200ppm 시계 대조 12조건을 추가했다.
- `verify.ps1 -Stress`: 기존 50조건을 포함하는 확장 83조건을 실행한다. `--fractional-network-long-checks`는 조건별 가상 300초 비교다.

SDK·Opus 설정·송신 프레임 기본값·WASAPI 공유 모드·장치 설정·라우팅은 바꾸지 않았다. 기존 미커밋 EXTREME-100 변경도 보존한다.

## 동일 입력 A/B

네이티브 Opus, 조건별 가상 120초, 동일 이벤트 순서·10/20ms 입력·3ms 고정 전달·128/256샘플 Read·시작 40ms, 고정 2.5/5ms 및 자동 프레임을 비교했다. A는 EXTREME-100 최종 소스, B는 이번 수정이다. 이 표의 큐는 마지막 20초 모든 렌더 요청을 반영한 값이며 장치 출력 지연은 아니다.

| 입력 묶음 / Read / 프레임 | 전체 PLC A→B | 마지막20초 큐 평균 A→B |
|---|---:|---:|
| 10ms / 128 / 5ms | 65→0ms | 7.663→5.479ms |
| 10ms / 256 / 2.5ms | 3750→0ms | 3.833→5.472ms |
| 10ms / 256 / 자동 | 1142.5→0ms | 4.818→5.472ms |
| 20ms / 256 / 2.5ms | 7500→5ms | 8.667→10.455ms |
| 20ms / 256 / 5ms | 70→5ms | 11.649→10.333ms |
| 20ms / 256 / 자동 | 7500→5ms | 8.667→10.455ms |

B의 위 5ms PLC는 시작 학습 구간에만 발생했다. 여섯 조건 모두 시작 5초 이후 및 마지막20초 PLC·underfill·복구 폐기가 0이다. A의 낮은 큐가 음성 폐기/PLC와 함께 얻어진 경우 이를 저지연 성공으로 해석하지 않는다.

원래 정상인 조건에는 비용도 있다. 10ms/128/2.5ms와 자동은 큐 4.667→5.479ms, 10ms/256/5ms는 5.000→5.477ms, 20ms/128은 9.333→9.542ms다. **모든 조건의 평상시 지연이 줄었다는 결과가 아니다.** 반복 끊김을 없애면서 정상 조건의 추가 큐는 이 비교에서 0.2~0.8ms에 제한했다.

## 채택·기각

- 채택: FineClock의 작은 요청에서만 정리와 시계 피드백을 함께 수정하는 후보. 일반 버퍼 확대나 추가 PCM 큐가 아니다.
- 기각 C1: 부분 PCM을 보존하면서 정리 기준까지 함께 변경. 기존 정상 조건에서 반복 PLC 발생.
- 기각 C2: 기존 정리 기준을 유지하고 부분 PCM만 보존. 마찬가지로 정상 조건 악화.
- 기각 C3: 정리 생략과 좁은 deadband만 적용. 20ms 묶음의 평균 큐를 지나치게 낮춰 반복 소진.
- 최종 후보는 C3에 묶음 위상을 고려한 피드백 기준을 더하고, 변경 범위를 FineClock의 작은 요청으로 제한했다. 전역 FineClock deadband 변경 후보는 남기지 않았다.

첫 baseline-metrics 실행은 파일 복원 후 증분 빌드가 후보 DLL을 재사용하여 A로 사용할 수 없었다. 해당 실행은 제외했다. 소스 갱신 시각을 명시한 재빌드 후 baseline-corrected에서 기존 실패 10개 항목/6조건을 다시 확인했고, final-corrected에서 통과했다. A/B 앱 DLL 해시는 서로 다르다. 합격 기준을 완화하지 않았다.

## 검증 상태와 한계

최종 검증 결과는 아래에 기록한다. 원본·개인 주소·전체 진단은 ignored `native/.local/extreme-101`에만 보관한다.

- 네이티브 71조건×가상120초: 통과. 수정 전 동일 조건 6개 실패.
- 네이티브 확장83조건×가상300초: 통과.
- ±200ppm 분수 시계 대조를 포함한 83조건×가상120초: 통과. 시계 차이 조건은 마지막20초에 최대5ms PLC가 남아 **모든 조건 PLC=0**은 아니다.
- `verify.ps1 -NoRestore -Integration -Stress`: 경고/오류0, 전체 회귀·서버 검사·IPv4/IPv6 통합까지 통과.
- 관리형 Opus의 RTP 재생 검사 및 83조건×가상120초: 통과.

실제 두 PC에서는 합성 음성을 실제 공유 캡처/출력 경로로 공급했다. 1:1 직접 및 강제 TURN을 각60초 실행했고 양쪽 모두 오류 없이 완료했다. 선택 경로는 각각 직접 UDP·TURN UDP였다. 아래 값은 첫/마지막 진단 사이 약59~60초 구간의 누적 차이다.

| 경로 / 수신 PC | 수신 패킷 증가 | PLC | 출력 부족 | 복구 폐기 |
|---|---:|---:|---:|---:|
| 직접 / PC | 23808 | 272.5ms | 50.42ms | 116.60ms |
| 직접 / 노트북 | 23904 | 265ms | 77.27ms | 134.71ms |
| TURN / PC | 23998 | 175ms | 28ms | 71.58ms |
| TURN / 노트북 | 23944 | 357.5ms | 20ms | 297.65ms |

실제 장치 주기는 PC 캡처10ms/출력2.667ms, 노트북 캡처5.333ms/출력10ms였다. 실제 환경에서는 PLC·출력 부족·폐기가 남아 있다. A/B/A 실제 네트워크 비교가 아니므로 이 표로 이전 버전 대비 개선/악화를 판정하지 않는다. 가상 정상 입력의 여섯 실패 수정과 실제 환경 전체 안정화를 구분한다.

6인 엔진90초 시험도 양쪽 종료 코드0, 각15개 상대 창의 송수신·디코딩 증가와 종료 정리를 확인했다. **PC3엔진+노트북3엔진이며 독립된6대 사용자 시험이 아니다.** 초기 구간을 제외한 각 약71.6초×15스트림에서 PC의 PLC 합계7307.5ms(0.680%), 출력 부족5688.94ms(0.529%), 노트북의 PLC6015ms(0.559%), 부족4630.77ms(0.430%)다. 합계는 여러 상대의 시간이며 한 통화의 연속 끊김 길이가 아니다. 기능 완료를 품질 합격으로 해석하지 않는다.

같은 창의 재버퍼는 PC151회/노트북119회, 복구 폐기 합계는 각각7144.46/6214.19ms였다. 작은 프레임 실험의 실제 다인 연속성 문제가 해결됐다는 결과는 아니다.

마지막5초 내부 구간의30방향을 RTP 식별자로 대응했다. 기록된 송신 API 반환59110개 중 수신 콜백 미관측0, 앱 송신 순번 공백0, 수신 버퍼 미입장104개였다. 같은 구간의 미입장 기록은 PC72개/노트북32개 모두 `late`였다. 전체 통화 무손실이나 SRTP 거부0의 증명이 아니며, 송신 API 반환을 소켓 송신 완료로 표현하지 않는다. 이 구간에서는 이미 도착한 오디오가 재생 마감 뒤 거부되는 문제가 남아 있다.

시험 후 노트북 시험 파일48개 복구 목록에 따라 덮어쓴 원본은 SHA256으로 검증·복구하고 새로 도입한 파일만 제거했다. 양쪽 시험 프로세스0, OCI의 coturn·voice-native·nginx가 active임을 확인했다. 공유기·시스템 라우팅·장치 설정·기존 dist는 변경하지 않았다.

위 결과는 가상 전달/재생 시계 시험이다. 실제 하드웨어 입력→출력, 독립 외부 회선, 실제 게임 프레임타임은 측정하지 않았다. 소켓/SRTP 경계에서 미관측인 프레임의 원인, 무선 지연, 다른 장치/도착 묶음의 최적값은 미해결이다.

## 기본값·실행·복귀

기본10ms 제품 모드를 변경하거나 실험 모드를 안정판으로 승격하지 않는다. 적용 범위는 기존 `opus-adaptive`·`opus-auto-frames`·`opus-learned`의 FineClock 경로다. 기존 `opus-adaptive-5` 등 FineClock를 사용하지 않는 모드는 이 변경 대상이 아니다.

```powershell
./native/run.ps1 -Experiment opus-adaptive
./native/run.ps1 -Experiment baseline
./native/verify.ps1 -NoRestore -Integration -Stress
./native/TransportProbe/bin/Release/net10.0-windows10.0.19041.0/TransportProbe.exe --fractional-network-long-checks ./native/.local/fractional-long.json
```

기존 경로 복귀는 `-Experiment baseline`으로 실행한다. 관리형 코덱 대조는 새 PowerShell에서 `$env:VOICE_OPUS_BACKEND='managed'`를 설정한 뒤 검사하고 해당 셸을 종료한다. 사용자 장치나 네트워크 설정을 바꾸지 않으므로 별도 설정 복구는 필요 없다. 기존 dist·서버 배포본은 갱신하지 않았다.
