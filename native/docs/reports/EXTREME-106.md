# EXTREME-106 · 양쪽 Npcap 대응과 통화별 수신 경로 대조

2026-10-27 / `codex/extreme-latency`, 기준 `f634ca0f`. 실제 끊김 조사만 계속했다. 모든 통화 시험은 같은 기존 바이너리·SDK·프레임·코덱·재생 정책으로 수행했다. 시험 후 진단 UI의 손실 수 표기만 바로잡았으며 미디어 동작은 바꾸지 않았다. 이번 시험은 실제 두 Windows 호스트의 합성 음성이며 게임 부하·외부 사용자·물리 입→귀 측정이 아니다.

## 수집 방법과 판정 범위

기존에 설치된 Npcap의 `host_hiprec_unsynced`를 양쪽에서 사용했다. 실제 IP와 NIC GUID를 매 시험 확인하고, 상대 UDP만 비 promiscuous·128바이트 prefix·100초·64MiB 상한으로 수집했다. 고정된 dumpcap 숫자 인덱스를 사용하지 않았다. 시험 통화는60초, 앱 상세 trace는 마지막30초다. PLC·출력 부족·재버퍼는 진단 첫/마지막 표본의 차이이므로 상세 trace와 분모가 다르다.

노트북의 시험 통화는 Wi-Fi를 명시했고 PC의 통화용 소켓만 지정한 NIC를 사용했다. 전역 Tailscale·VPN·기본 라우팅·SSID·공유기·NIC 고급 속성·장치 설정은 변경하지 않았다. WebRTC direct 표지를 물리 경로 확인으로 대신하지 않았다. 양쪽 앱 바이너리 해시를 확인했고 native Opus·수정 SDK·`opus-adaptive` 2.5ms를 유지했다.

수집 중 절전으로 시험이 끊기지 않도록 컨트롤러 프로세스 수명 동안만 `SetThreadExecutionState(ES_CONTINUOUS | ES_SYSTEM_REQUIRED)`를 요청했다. 화면 유지 요청이나 영구 전원 계획 변경은 없으며 종료 시 해제한다. 노트북 capture-off 구간에도 동일하게 유지해 계측 대조에 절전 여부를 섞지 않았다.

양쪽 수집이 있는 초기4회에서 각 송신 trace의12004~12192개 프레임은 모두 송신 캡처와 유일하게 대응했다. 각 수신 trace의 프레임과 late도 모두 수신 캡처와 유일하게 대응했다. 겹치는 송신 API→수신 콜백 구간의 미관측 프레임은 각 방향0이었다. 이것은 해당 trace 구간의 결과이며 전체60초·모든 손실·수집 영향0을 증명하지 않는다.

## 계측 영향 대조

PC Ethernet 수집·앱 trace·통화별 인터페이스를 고정하고 노트북 Npcap만 끔→켬→끔, 이어 켬→끔→켬으로 비교했다. 단일60초 구간의 우연한 변동을 계측 효과로 채택하지 않는다.

| 조건 | PC PLC / 출력 부족 / 재버퍼 | 노트북 PLC / 출력 부족 / 재버퍼 | PC 마지막30초 공백>30ms / 최대 |
|---|---:|---:|---:|
| 최초 양쪽 수집 | 732.5ms / 332.17ms / 6 | 315ms / 22.5ms / 2 | 9 / 250.261ms |
| 끔 A1 | 110ms / 0 / 0 | 542.5ms / 0 / 0 | 4 / 50.718ms |
| 켬 B | 215ms / 0 / 0 | 142.5ms / 0 / 0 | 6 / 60.387ms |
| 끔 A2 | 132.5ms / 0 / 0 | 335ms / 0 / 0 | 1 / 36.705ms |
| 켬 R1 | 67.5ms / 0 / 0 | 50ms / 0 / 0 | 1 / 38.211ms |
| 끔 RB | 112.5ms / 0 / 0 | 100ms / 0 / 0 | 5 / 43.327ms |
| 켬 R2 | 105ms / 0 / 0 | 70ms / 0 / 0 | 4 / 39.990ms |

첫 끔→켬→끔에서는 PC PLC가 켠 구간에 더 많았으나 노트북은 반대였다. 반대 순서에서는 양쪽 모두 끈 구간이 더 많았다. **계측 영향0도, 계측이 공백의 단독 원인이라는 결론도 채택하지 않는다.** 끈 상태에서도 공백이 재현됐고, 최초250ms 사건을 평상시 발생률로 일반화하지 않는다.

## 같은 패킷으로 확인한 간격 증가

SSRC·RTP 타임스탬프·wire 순번으로 Tx/Rx를 대응하고 송신 API의 별도 앱 프레임 순번도 확인했다. 아래는 모두 인접한 송신 앱 프레임이다.

| 방향 / 조건 | 송신 API 간격 | 송신 Npcap Tx 간격 | 수신 Npcap Rx 간격 | 수신 콜백 간격 |
|---|---:|---:|---:|---:|
| 노트북→PC / 최초 | 10.988ms | 11.077ms | 250.231ms | 250.261ms |
| 노트북→PC / 켬 B | 4.597ms | 4.661ms | 60.396ms | 60.387ms |
| 노트북→PC / 켬 R1 | 5.157ms | 5.259ms | 38.247ms | 38.211ms |
| 노트북→PC / 켬 R2 | 10.291ms | 10.375ms | 39.990ms | 39.990ms |
| PC→노트북 / 켬 R1 | 9.938ms | 9.965ms | 45.659ms | 45.607ms |

이 사건의 큰 간격 증가는 **송신 소프트웨어 Tx 뒤→수신 소프트웨어 Rx 앞**에 있었다. Npcap Tx는 하드웨어 송신 완료가 아니고 Rx는 전파 도착 시각이 아니다. NIC 하위 드라이버·펌웨어·무선·AP/메시·수신 드라이버는 이 자료만으로 분리되지 않는다. 각 호스트 내부의 패킷 간격만 비교했으며 pcap epoch와 앱 QPC 또는 다른 호스트 절대 시각을 직접 빼지 않았다. Tx→Rx 간격 증가는 절대 편도/입→귀 지연이 아니다.

모든 PLC를 위 큰 공백 사건으로 설명하지 않는다. private 시각 대응 탐색에서는 작은 사건 하나가 수신 소프트웨어 관측 뒤의 처리/스케줄링과 겹칠 가능성도 남았다. 이는 같은 호스트 Npcap/QPC의 일정한 속도·원점 차이를 가정한 인과 경계 분석이며, 독립 검증된 물리 시각이 아니다. 단일 사건으로 SDK/버퍼 알고리즘을 고치거나 전체 끊김을 네트워크로 단정하지 않았다.

## 분석 도구 변경

`native/TransportProbe/Analysis/analyze_tx_rx_intervals.py`의 `load_pcap`과 `compare`에 Npcap Tx 입력을 추가했다. 원래 Pktmon raw-QPC 입력은 유지한다. Npcap 입력에서는 앱 QPC와 epoch를 빼는 API→Tx 절대값을 출력하지 않는다. 각 시계 원점을 독립적으로 바꿔도 간격 결과가 같고, 방향/포트·Decimal 정밀도·누락 열·중복/역순/축출 거부를 자체 검사했다.

```powershell
python ./native/TransportProbe/Analysis/analyze_tx_rx_intervals.py --self-test
python ./native/TransportProbe/Analysis/analyze_tx_rx_intervals.py --npcap-tx SENDER.json RECEIVER.json TX-RTP.csv RX-RTP.csv OUTPUT.json
```

제품의 프레임·큐·SDK나 기본값은 변경하지 않았다. 따라서 빌드 통과를 새로운 지연 개선 근거로 제시하지 않는다.

## 경로 대조와 복구

PC의 기존 Ethernet과 이미 연결된 Wi-Fi를 통화별로 비교했다. 노트북 Wi-Fi·프레임·버퍼·양쪽 수집 조건은 고정했다. 모든 표본에서 요청한 로컬/상대 미디어 주소가 실제 선택 endpoint와 일치했다. NIC와 매체 경로가 함께 달라지므로 차이가 있어도 단일 드라이버/AP 원인으로 결론 내리지 않는다.

| PC 경로 | PC PLC / 출력 부족 / 재버퍼 | 노트북 PLC / 출력 부족 / 재버퍼 | PC 공백>30ms / 최대 | 노트북 공백>30ms / 최대 |
|---|---:|---:|---:|---:|
| Ethernet A1 | 85ms / 0 / 0 | 50ms / 0 / 0 | 1 / 43.575ms | 1 / 38.227ms |
| Wi-Fi B | 165ms / 13.69ms / 1 | 232.5ms / 0 / 0 | 3 / 51.066ms | 12 / 44.331ms |
| Ethernet A2 | 102.5ms / 0 / 0 | 107.5ms / 0 / 0 | 3 / 49.675ms | 2 / 45.667ms |
| Wi-Fi R1 | 160ms / 36.17ms / 2 | 232.5ms / 16.83ms / 1 | 3 / 40.606ms | 6 / 71.489ms |
| Ethernet RB | 512.5ms / 21.35ms / 2 | 245ms / 32.5ms / 2 | 1 / 40.004ms | 1 / 42.494ms |
| Wi-Fi R2 | 132.5ms / 9.5ms / 1 | 200ms / 0 / 0 | 5 / 56.413ms | 8 / 45.975ms |

6회의 상세 기록에서 양쪽 송신 trace와 수신/late는 각 캡처에 모두 유일하게 대응했다. 각 방향의 겹치는 API→콜백 구간 미관측은0이었다. Ethernet A2 통화 중 앞선 두 수집의 오프라인 tshark export를 PC에서 실행한 구간이 있어 완전히 조용한 호스트 조건으로 취급하지 않는다. 반대 순서 반복에서는 수집이 끝날 때까지 오프라인 분석을 실행하지 않았다.

첫 대조에서 Wi-Fi B는 양쪽 PLC가 많았고 유선 복귀 후 줄었지만, Ethernet도 공백이 남았다. Ethernet A1의 노트북→PC 사건은 Tx10.630ms→Rx43.534ms, Wi-Fi B는 Tx10.195ms→Rx51.000ms, Ethernet A2는 Tx5.696ms→Rx49.669ms였다. 해당 양끝은 모두 유일한 캡처와 인접 송신 앱 프레임으로 대응했다. 따라서 **PC의 Ethernet 한 경로에서만 재현되는 현상은 아니다.** 단일 환경의 짧은 순서 대조만으로 Wi-Fi의 보편적 열세나 특정 장치 결함을 확정하지 않는다.

반대 순서의 Ethernet RB는 오히려 PLC·부족이 증가했다. 이 회차의 큰 공백 상당수는 마지막30초 trace 밖에 있었다. 전체 수집을 따로 대응하니 노트북→PC Tx9.362ms→Rx80.671ms, PC→노트북 Tx9.877ms→Rx114.966ms 사건이 있었다. 이 양끝은 인접한 wire RTP 순번이며, trace 밖의 송신 API 시각을 만들어 붙이지 않았다. **한 경로로 바꾸면 문제가 해결된다는 결론은 기각**한다. 반복 구간을 더 선택해 유리한 결과를 찾는 방식은 채택하지 않았다.

## 전체 수집의 미관측과 진단 표기 수정

양쪽 수집10회·20방향의 전체 RTP 수집 수명에는 수신514,548개가 있었고 모두 송신 캡처와 유일하게 대응했다. 그러나 대응한 양끝 사이의 송신 캡처514,560개 중 **12개는 수신 캡처에서 관측되지 않았다**. 최초 PC→노트북8개와 Ethernet RB PC→노트북4개이며, 각각 연속4개 묶음이었다. 이들은 마지막30초 상세 trace 밖이다. 노트북의 당시 RTCP 보고도 각각8개·4개를 보고했다. 캡처 누락 가능성과 소프트웨어 Tx 이후 전송 실패/매체 손실 등을 물리적으로 분리한 것은 아니며 **물리 네트워크 손실 확정이나 전체 무손실 주장은 하지 않는다.**

전체 수집의30ms 초과 Rx 공백293건은 양끝 Tx/Rx가 모두 유일하게 대응했다. 290건은 wire 순번 차이1, 나머지3건은 위4개 미관측을 사이에 둔 순번 차이5였다. 간격 증가는18.508~239.154ms였고, 각 사건의 송신 Tx 간격은 최대20.560ms였다. 전체 수집 수명은 통화 전후도 포함하므로 이293건을 정확히60초 통화당 발생률이나 상세 trace의 PLC 건수와 동일하게 취급하지 않는다.

현재 고정 SDK 소스 `ReceptionReport.GetSample`은 `ReceptionReportSample.PacketsLost`에 누적 `expected - received`가 아니라 **`lost_interval`**을 넣는다. 따라서 뒤의 정상 구간 보고0은 앞선8개/4개 미관측을 반증하지 않는다. `CallForm`의 잘못된 **‘누적’ 표기를 ‘보고값’으로 수정**하고 `RtcpMetrics.Local`에 이 SDK 의미를 주석으로 남겼다. JSON 필드·카운터 계산·보안/미디어 경로는 유지했다. 과거 보고서의 마지막 RTCP ‘누적0’ 표현도 통화 전체 무손실 근거로 사용하면 안 된다.

13회·26개 호스트 trace의 PLC 기록797개를 재검산했다. 같은 SSRC·RTP 시각에 대해 trace 안에서 먼저 `queued` 입장한 기록은0이었다. 이것은 이미 입장한 정상 패킷을 잘못 무시한 반복 PLC의 관측 증거가 없다는 뜻이며, trace 시작 전 이력·미기록 패킷까지 정상으로 증명하지 않는다. 입장 잠금 대기 최대0.761ms, 잠금 안 작업 최대0.844ms였다. 앞서 남긴 작은 캡처 후 사건과 시간축 자체의 모든 가능성을 배제하지 않는다.

진단 UI 수정 후 `VoiceNative` Release `--no-restore -warnaserror` 빌드는 경고/오류0이었다. Python 분석 자체 검사도 통과했다. UI 문구·주석만 바뀌어 오디오 회귀·게임/외부 환경 재시험을 새로 수행한 것으로 표현하지 않는다.

## 채택·기각과 다음 경계

채택한 것은 양쪽 Npcap 간격 분석과 RTCP 손실 표기의 정확성 보완이다. 프레임/출력 여유 확대, SDK 재작성, 자동 경로 승격은 하지 않았다. 실제 입→귀 지연이 줄었다는 결과는 없다.

현재 공통으로 남는 범위는 노트북 Wi-Fi 하위 계층·무선/AP/메시 및 수신 측 소프트웨어 관측 이전이다. PC Ethernet 하나만의 문제나 송신 API 이후 SDK 처리만으로 위 사건을 설명하는 가설은 약해졌지만, 공통 OS/NDIS 지연까지 제거한 것은 아니다. 독립 AP/대체 NIC·직결 대조·신뢰할 수 있는 AP 재시도 통계·별도 무선 관측 없이 이 경계를 물리 부품 하나로 확정할 수 없다. 메인 공유기 직결 유선은 사용자 환경에서 불가하며 AP 신뢰 통계·무선 모니터 캡처·물리 송수신 시각은 **미측정**이다. 같은 경로의 횟수만 늘리거나 버퍼를 키워 원인 규명/해결로 표시하지 않는다.

추가 장비/연결이 준비되기 전의 소프트웨어 조사 후보는 소수의 캡처 뒤 마감 사건에 대한 동일 패킷 QPC와 스케줄링/GC/DPC 대응이다. 이것도 이미 늦게 수신된 큰 사건을 해결하는 시험으로 섞지 않는다. 이번에는 새로운 WPR 계측이나 장치/네트워크 설정 변경을 추가하지 않았다.

13회 통화의 양쪽 종료 코드는 모두0이었다.23개 캡처도 정상 종료0·강제 종료 없음·64MiB 상한 미도달·보고된 interface/pcap/dumpcap 드롭0이었다. 마지막 수신 캡처 전체의 긍정 대응과 수신 미관측12개를 별도로 제시했으며, 드롭 보고0만으로 완전 수집/무손실을 선언하지 않았다.

원본 캡처·fixture·수집/실행 스크립트·해시·정상 종료/복구 기록은 Git 제외 `native/.local/extreme-106`에 보존한다. 개인 주소·전체 패킷·자격 증명은 커밋하지 않는다. 기존 배포본은 그대로 유지한다.4개 배치의 양쪽 자체 캡처/컨트롤러는 정상 종료했고 임시 절전 방지 요청은 모두 해제했으며 노트북 기존 시험 파일은 원본 목록과 SHA256으로 복구 검증했다. 최종 두 호스트에 자체 dumpcap/TransportProbe 프로세스가 없고 원래 OS 경로가 유지됨을 읽기 확인했다.

기존 실행은 `./native/run.ps1`, 비교 후보는 `./native/run.ps1 -Experiment opus-adaptive`로 유지한다. 시험의 NIC 선택은 해당 소켓 종료와 함께 사라졌으므로 시스템 경로를 되돌리는 명령은 필요하지 않다. 기본 프레임·버퍼·SDK를 바꾸지 않아 미디어 동작 복귀용 설정도 추가하지 않았다. 현재 소스 수정은 미커밋 상태이며 이번 작업에서 커밋·푸시는 수행하지 않았다.
