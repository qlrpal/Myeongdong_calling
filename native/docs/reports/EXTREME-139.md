# EXTREME-139 — 입력 불연속 때 앱의 부분 PCM 폐기와 송신 전 간격 증가

2026-11-01 / 기존129–138 미커밋 작업 보존. **교정된 계측으로 자연 PLC를 포착하고, 그 구간에서 앱이 부분 PCM30ms를 버렸음을 확인했다.** 해당 사건의 송수신 간격 증가는 이미 송신 전단에 있었으며 모든 과거 PLC/누락의 공통 원인을 확정한 것은 아니다. 오디오 초기화 정책 자체와 기본 지연 설정은 유지했다.

## 조사 대상과 Windows 관측의 한계

138에서 노트북 입력 불연속은5/3회였지만 앱이 초기화한 부분 프레임 양은 집계하지 않았다. `WindowsAudioDevice`는 DataDiscontinuity 표시를 받으면 조립 중인 `captureFrameCount`를0으로 만드는 경로가 있다. 이때 남아 있던 PCM은 송신 큐 초과 폐기나 수신 PLC 카운터에 직접 포함되지 않는다.

Windows의 [GetBuffer 정의](https://learn.microsoft.com/en-us/windows/win32/api/audioclient/nf-audioclient-iaudiocaptureclient-getbuffer)에서 장치 위치는 패킷 첫 프레임의 스트림 상대 위치이며 QPC는100ns 단위다. [BufferFlags 정의](https://learn.microsoft.com/windows/win32/api/audioclient/ne-audioclient-_audclnt_bufferflags)에 따라 DataDiscontinuity/시각 오류에서 이전 장치 위치를 그대로 신뢰해 누락량을 산출하면 안 된다. 따라서 **앱이 직접 버린 샘플**과 **원시 장치 위치/QPC 변화**를 별도로 기록했다. 원시 위치 차이를 물리 수음 누락량이나 네트워크 손실로 합산하지 않는다.

## 실제 수정

- `Audio/CaptureContinuityTracker.cs`: 기존 오디오 잠금 안에서 패킷 메타데이터를 관측한다. 앱이 불연속 초기화로 버린 부분 PCM의 누적 샘플/시간, 비교 가능한 위치 불일치 수, 최근16개 사건/덮어쓰기를 보존한다. 위치·기대 위치·원시 차이·비교 가능 여부·QPC 간격을 구분한다. TimestampError는 비교 기준을 해제하고 새 기준점을 설정한다. 관측 중 힙 할당이나 별도 타이머/오디오 큐는 없다.
- `WindowsAudioDevice`: 기존 초기화를 실제 캡처 조립 잠금 안으로 모으고 폐기 직전 부분 샘플 수를 측정한다. 기존 불연속 처리·PCM 조립을 유지한다. 변환 청크가 여러 개여도 원래 네이티브 패킷은 한 번만 관측한다.
- `CallDiagnostics`/상세 진단 UI: `Microphone.CaptureContinuity`와 앱 초기화 폐기량을 표시한다. 기존 송신 큐 폐기와 구분한다. 일반 통화 조작 화면의 설정은 추가하지 않는다.
- 검사 두 곳이 비공개 `Capture` 시그니처에 리플렉션으로 의존하던 부분을 기존의 캡처 없는 합성 입력 진입점으로 변경했다. 실제 프레임 전환/SRTP 검사는 유지했다.

폐기 대신 무조건 이전 조각을 이어붙이거나 새 버퍼/패딩을 추가하는 변경은 하지 않았다. 장치 위치가 불연속인 상황에서 신선도·중복/누락·프레임 시간축을 함께 검증해야 하는 다음 후보로 남긴다.

## 계측 오류 발견과 교정

최초 실제 시험에서 PC의 NAudio 호환 입력 경로가 배치를 비운 뒤 **데이터 없는 알림**도 보내는 것을 관측했다. 새 계측이 이를 유효한 위치0 패킷처럼 취급해 사건 이력을 소진했다. 오디오 샘플이 없는 이 알림에는 유효한 GetBuffer 위치/시각이 없으므로, 플래그 없는 빈 알림은 기존 변환 경로처럼 처리하지 않고 관측 기준도 유지하도록 수정했다. 빈 알림 앞뒤 유효 패킷의 위치가 이어지는 회귀를 추가했다. 플래그 있는 빈 알림의 위치/시각은 미확정으로 취급한다.

초기 자료 `input-180`은 탐색 자료이며 정상 성능/연속성 합격의 근거로 사용하지 않는다. 특히 PC 입력 사건 분석은 `input-180-input-analysis.INVALID-empty-notifications.json`으로 분리했다. raw 원본·초기 바이너리·패킷 경계 관측은 삭제하지 않았다. `TRIAL-INDEX.json`에 지위를 명시한다. 이후 아래 결과는 **수정본 `input-corrected-180`**이다.

## 회귀 검증

`--capture-continuity-checks`는 위치가 이어져도 플래그가 있으면 이전 위치 비교를 신뢰하지 않는 것, 플래그 없는 위치 변화, 시각 오류 뒤 기준점, 빈 알림 무시, 최근16개 상한을 검사한다. 관측1만 회의 관리형 할당0을 확인했다. 실제 캡처 조립기로256샘플 부분 입력 뒤 불연속을 넣어 정확히256샘플을 초기화하고 이후 PCM이 기존 조립 정책과 동일한지 검사한다. 프레임 경계에서 불연속이 나면 폐기량0이어야 한다.

최초 전체 검증은 위 비공개 메서드 리플렉션 검사에서 실패해 진입점을 정리했다. `verify-final.log`와 빈 알림 교정 뒤 `verify-empty-fix.log`의 전체 `./native/verify.ps1 -NoRestore -Integration`을 통과했다. 경고/오류0 빌드, BuildTools·제품/UI·기존 오디오·복구·서버/실행기·실제 로컬 SRTP/가변 프레임/IPv6를 포함한다. 실패 로그 `verify.log`도 보존했다. 실제 기기 측정 중 전체 회귀를 동시에 실행하지 않았다.

## 자연 PLC의 양쪽 경계 대응

PC는 `playout-plc`, 노트북은 `remote-request`로 같은 사건 ID의 사전/사후 기록을 동결했다. 양쪽 상대 수락1, 사전/사후 모두 존재했다. PC 기록7197개/충돌 누락46, 노트북6263개/충돌 누락59였다. 누락0을 보장하지 않는다.

PC 첫 PLC는 약168.288초에 있었다. 첫 캡슐에는 RTP 시각을 보류한 PLC7개/합계20ms가 있으며, 기준선171초 부근의 나머지2.5ms는 첫 사건 뒤2초 상한 밖이라 경계 원본을 보존하지 않았다. 따라서 전체22.5ms를 모두 개별 대응했다고 표시하지 않는다.

캡슐의 PLC는 모두 해당 프레임을 나중에 인증 수신/입장했다. 서로 다른 PLC 보정이 같은 RTP 위치를 보류할 수 있으므로 중복 네트워크 패킷으로 세지 않는다. 고유한 송신 프레임5개를 다음과 같이 대응했다.

|---|---:|---:|---:|---:|
|A|0.079ms|16.401ms|16.391ms|3.357ms /2.074ms|
|B|0.054ms|14.923ms|14.990ms|1.399ms|
|C|0.045ms|14.903ms|14.892ms|0.415ms|
|D|0.064ms|16.559ms|16.542ms|4.637ms /1.966ms|
|E|0.052ms|15.304ms|15.356ms|0.787ms|

송신/수신 간격은 **같은 두 RTP 프레임**에 대한 각 호스트 내부 기간이다. 다른 PC 절대 시각의 차감이나 편도/입→귀 지연 계산이 아니다. 이 다섯 간격의 차이는약 −0.016~+0.066ms였으므로, 해당 구간의 간격 증가는 네트워크 통과 중 새로 크게 생긴 형태가 아니라 **이미 송신 쪽의 약15~16.6ms 간격**에 있었다. 고정 전송 지연이나 다른 사건의 네트워크 문제까지 배제하는 것은 아니다.

해당 프레임의 인코딩 기록은약0.094~0.205ms, 완성 후 송신 API까지는0.045~0.079ms였다. 송신 전단에서 이미30ms의 부분 PCM이 폐기됐고 첫 대응 프레임을 보낼 때까지는그중20ms가 폐기된 상태였다. **이번 캡슐은 입력 불연속 처리·프레임 조립 쪽의 기여를 직접 검토할 근거**다. 불연속 플래그 자체의 발생 이유와 모든 PLC가 이 정책 하나 때문이라는 결론은 아직 아니다.

## 별도로 남긴 최초 탐색 사건

빈 알림 계측이 남아 있던 최초 시험은 PC PLC30ms였고 첫 캡슐은 한10ms RTP 구간을 전진 보정했다. 해당 프레임의 송신 API 진입/반환은 있었으나 수신 인증·입장·SDK 후속 관측에는 없었다. 앞뒤 수신 RTP 순번이 하나 건너뛰고 RTCP의 해당 구간 누락 보고도1이었다. 진단 누락 카운터와 미계측 경계가 있어 물리 손실/SDK 인증 거부로 확정하지 않는다. 특히 이 탐색 자료를 대표적인 정상 성능으로 사용하지 않는다.

이 **미관측/전진 보정형**과 교정본의 **나중에 도착한 프레임/시각 보류형**을 하나의 원인으로 합치지 않는다. 전자는 소켓 전송/UDP 반환/SRTP 경계가 추가로 필요하고, 후자는 위 대응에서 송신 전단의 간격 증가를 이미 관측했다.

## 판단·복구·남은 시험

채택한 변경은 정확한 앱 폐기 집계·장치 위치의 신뢰 구분·상세 진단 표시·빈 알림 오탐 수정·기존 검사 진입점 정리다. **일반 통화의 지연 감소나 입력 초기화 정책 개선을 달성했다고 표시하지 않는다.** 현재 근거로는 수신 버퍼를 키우거나 장치 설정을 바꾸는 것보다, 동일한 캡처 사건을 재현해 부분 프레임 처리의 대체 정책을 검증하는 것이 다음 앱 개선 대상이다. 오래된 PCM을 보존해 지연을 늘리지 않는 조건과 실제 PCM 연속성/RTP 호환성을 함께 확인해야 한다.

실제 마이크 음향·청감·입→귀·게임·다인·외부/TURN·장기 통화·새 ETW/Npcap/무선 물리 시각은 이번에 미실시다. 합성 음성을 실제 장치 콜백에 공급했으며 캡처 내용의 음질을 검증한 것은 아니다. 경고 횟수의 환경별 차이나 장치 위치의 불확실성을 숨기지 않는다.

노트북 원본 DLL SHA256 `612914CFA7B0B871C2626C4C141E47FF8DB5FBF45370042A4F16304AFFC0A480`로 복구했고 자체 probe0, PC 종료 확인도probe0이었다. 운영 서버·기존 베타/dist·OS 라우팅/VPN·SSID·드라이버·장치·전원 계획 설정은 유지했다. 커밋·푸시는 하지 않았다.

최신 소스는 `./native/run.ps1`, 회귀는 `./native/verify.ps1 -NoRestore -Integration`, 새 검사만은 TransportProbe의 `--capture-continuity-checks`다. 진단 JSON의 `Microphone.CaptureContinuity`를 확인한다. 원본·초기/교정 빌드·실행/분석 스크립트는 Git 제외 `.local/extreme-139/`에 보존한다. `TRIAL-INDEX.json`, `input-corrected-180-input-analysis.json`, `input-corrected-180-capsule-analysis.json`, `input-corrected-180-causal-summary.json`, `input-corrected-plc-windows.json`, `verify-empty-fix.log`, `restoration.json`이 결과 입구다.
