# 극저지연 추가 비교: 재생 마감과 짧은 보간 유지

2026-10-21, `codex/extreme-latency`. 실제 PC/노트북·합성 음성·WASAPI 공유 모드·강제 TURN으로 비교했다. 시스템 장치 설정과 기존 배포본은 변경하지 않았다. 각 실기 시험은 15초, 카운터 증가는 약 14.8초의 첫/마지막 스냅샷 차이이며 준비 구간을 제외했다.

## 같은 도착 순서를 재현한 결과

`--extreme-replay INPUT OUTPUT`를 추가했다. 기록된 수신 큐 잠금 순서와 출력 요청 샘플 수를 그대로 사용하고, 같은 길이의 합성 페이로드를 공급한다. 초기 큐/디코더 상태는 재현할 수 없어 앞 2초와 끝 1초를 제외했다. 이후에도 초기 이력의 영향은 남을 수 있다.

이전 062 PC 수신 기록에서 여유 10ms/유지 없음은 도착→렌더 호출 중앙값 8.64ms, 부족 92ms, 보간 673ms였다. 여유 5ms/빈 큐 유지 2.5ms는 중앙값 8.46ms, 부족 50ms, 보간 720ms였다. 노트북 기록에서는 같은 두 조건의 중앙값이 13.61→7.99ms로 바뀌었지만 보간은 10→103ms로 늘었다. 살아남은 패킷의 지연만 낮게 보이는 효과를 피하기 위해 디코딩·폐기·늦은 패킷 수도 함께 출력한다.

큐 정리 문턱을 5/10ms 늦추는 후보도 비교했지만 잔여 큐가 커졌고 양방향에서 지연 우위를 확인하지 못해 해당 코드는 제거했다. 고정 여유만 0~2.5ms로 낮추는 방식은 PC 수신 보간이 수 초까지 늘었다.

## 최소 입력 주기 + 전용 폴링 (제거)

노트북의 1.33ms 최소 입력 주기를 이벤트 방식과 바쁜 폴링 방식으로 비교했다. PC의 조건은 고정했다.

| 노트북 입력 방식 | 불연속 증가 | 송신 RTP 시간 / 실제 추적 시간 | 프로세스 CPU 비용 |
| --- | --- | --- | --- |
| 이벤트 | 1963회 | 9.82초 / 15.26초 | 0.12코어 |
| 전용 폴링 | 1632회 | 11.17초 / 15.31초 | 1.05코어 |

폴링은 개선 폭에 비해 CPU 비용이 크고 정상 속도의 송신을 회복하지 못했다. 게임과 함께 쓸 기본 후보로 채택하지 않고 폴링 구현을 제거했다. 드라이버 내부 손실 원인까지 확정한 결과는 아니다. 입력 프리셋은 앞서 정한 약 5ms 기준을 유지한다.

## 실기 후보 비교

`opus-2.5-r5-hold`는 2.5ms Opus 패킷, 5ms 여유, 최대 2.5ms의 빈 큐 보간 유지다. 큐가 비었고 미래 패킷도 없을 때만 보간하면서 원래 RTP 시각을 보존한다. 미래 패킷이 있으면 실제 구멍으로 보고 일반 PLC로 시각을 진행한다. 렌더 스레드를 차단하지 않으며 전체 연속 PLC 10ms 상한을 공유한다. 보간을 삽입한 만큼 위상 지연이 생길 수 있다.

| 조건 | PC 도착→렌더 중앙값 / P95 | PC 부족 / 보간 | 노트북 도착→렌더 중앙값 / P95 | 노트북 부족 / 보간 |
| --- | --- | --- | --- | --- |
| Opus 2.5ms, 여유 10ms | 9.97 / 17.20ms | 224 / 370ms | 10.82 / 12.42ms | 160 / 113ms |
| 새 5ms 후보 1차 | 8.66 / 15.98ms | 40 / 638ms | 8.63 / 12.34ms | 50 / 403ms |
| 새 5ms 후보 2차 | 8.51 / 16.19ms | 106 / 833ms | 7.62 / 14.13ms | 65 / 420ms |
| PCM 2.5ms, 여유 10ms | 9.25 / 16.71ms | 39 / 520ms | 13.97 / 15.76ms | 30 / 40ms |

도착→렌더는 수신 큐에 진입한 시각부터 해당 패킷의 첫 PCM을 렌더 공급자에 넘긴 시각까지다. 실제 장치 출력·입력 지연, 네트워크 전송, 패킷 전체 재생 시간을 포함하지 않는다. 해당 구간에 실제 재생된 패킷만의 분포이며, 페이로드가 폐기되면 지연 분포에서 빠지므로 보간량과 함께 읽어야 한다. 시험을 순차 실행했으며 무선망 변동을 통제하지 않았다. 따라서 표는 전체 마이크→귀 지연 감소나 통계적으로 확정된 개선의 증거가 아니다.

5ms 후보는 이번 두 실행에서 재생된 패킷의 중앙값이 작았지만 보간량은 커졌다. 지연 우선 실험 옵션으로 제공하고 안정 기본값으로 승격하지 않는다. PCM 2.5ms는 Opus와 패킷 빈도를 맞춘 비교다. 수신 페이로드 비트레이트는 약 764~767kbps로 Opus의 약 66~68kbps보다 컸고, 전체 지연 우위는 입증하지 못했다.

## 반영한 코드와 사용법

- `LatencyExperiment.EmptyHoldMs`와 제한된 RTP 시각 유지 구현.
- 실제 구멍에서는 일반 PLC, 늦게 도착한 정상 패킷은 보존, 장기 공백에서는 재버퍼링하는 회귀 검사.
- UI/실행 프리셋 `opus-2.5-r5-hold`, `pcm-2.5-r10` 추가. 양쪽 같은 프리셋을 선택한다.
- 시험 도구에 프로세스 CPU 비용을 코어 단위로 기록. 1.0은 CPU 한 코어를 평균적으로 사용하는 양이다.
- 기록을 같은 조건에서 재현하는 `--extreme-replay` 추가.

실행 예: `./native/run.ps1 -Experiment opus-2.5-r5-hold`.

최종 검증: Release 빌드 경고·오류 0개, `verify.ps1 -NoRestore -Integration` 전체 통과. 신규 프리셋과 제한 보간 검사, 기존 통화/장치/코덱 회귀, 서버 8개 검사와 실제 로컬 WebRTC 통합 검사를 포함한다. 커밋·푸시와 배포본 교체는 하지 않았다.

원시 자료는 Git 제외 경로 `native/.local/extreme-063/`에 있다. `*-event.json`, `*-poll.json`은 폐기한 입력 방식 비교, `*-hold.json`/`*-hold2.json`은 새 후보 두 번의 실기, `*-r10.json`은 10ms 대조군, `*-pcm25.json`은 동일 패킷 빈도의 PCM 비교다. `*-hold-replay.json`과 `pc-new-replay.json`은 큐 재현 결과다. 처음의 `*-replay.json`은 제거한 큐 정리 문턱 비교 결과다.
