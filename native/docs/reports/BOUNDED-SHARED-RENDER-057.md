# 0.5.7 공유 출력 공급량 제한과 안전 복귀

2026-10-19. 게임과 함께 사용할 WASAPI 공유 이벤트 모드를 유지하면서, 엔드포인트 전체를 항상 채우는 출력 공급 정책을 개선했다. 독점 모드·ASIO·장치 형식 변경·게임 설정 변경·서버 변경은 하지 않았다.

## 구현

`SharedRenderPlayer`는 지원되는 float32 모노/스테레오 믹스 형식에서 `IAudioClient3` 공유 스트림과 장치가 허용하는 최소 주기를 사용한다. 정상 공급 목표는 `min(장치 버퍼 용량, 엔진 한 주기 + 5ms)`다. 이벤트마다 목표에서 현재 padding을 뺀 양만 읽어 공급한다. 별도 PCM 큐·주기 인코딩 타이머를 추가하지 않았다.44.1kHz 출력은 기존 WDL 변환을 유지하며 모노→스테레오를 적용한다.

첫 구현은 즉시 목표를 낮췄으나 실제 통화 시작 구간의 공급자 Read가 PC13.33ms·노트북21.20ms 걸린 사례에서 양쪽 모두 전체 버퍼로 안전 복귀했다. 조용한 무음 장치 시험만으로는 나타나지 않았던 초기 실제 디코딩 작업이다. 그 비용의 정확한 내부 원인을 모두 JIT로 확정하지는 않았다.

최종 구현은 시작 시 기존 전체 여유를 유지한다. 버퍼 소진 없이2초가 지나면 공급 목표를 낮춘다. 초기 소진은 안정화 시간을 다시 시작한다. 목표를 낮춘 뒤 한 번이라도 padding0을 관측하면 같은 스트림은 전체 용량으로 복귀하여 낮은 여유로 반복 실패하지 않는다. 새 스트림에서는 다시 초기 안정화를 수행한다. 공급자가 버퍼를 읽는 동안 장치 큐가 소진될 수도 있어, WASAPI lease를 Release하기 전에도 padding을 확인한다.

주기·형식 협상 또는 시작 실패에는 기존 NAudio 공유 플레이어로 복귀한다. 장치 해제 등 실행 중 오류는 기존 한 번 자동 출력 복구 경로로 전달한다. 시작·정지·해제는 lease 사용 스레드와 분리하며 중복 Play는 무해하게 처리한다. 물리 장치 재연결을 이번에 새로 시험한 것은 아니다.

## 기본값과 복귀

- 앱의 ‘재생: 저지연 우선’＋RTP 경로에서 활성화한다.
- ‘재생: 기존 방식’은 기존 NAudio 전체 공급 경로를 사용한다. 통화에서 나온 뒤 변경한다.
- 공유 저지연 요청을 끄면 기존 공유 출력 경로를 사용한다.
- 진단의 `Render`에 `BoundedActive`, `TargetPaddingMs`, `CapacityMs`, `EmptyEvents`, `SafetyFallbacks`를 저장하고 UI에도 표시한다.

`EmptyEvents`는 실제 장치 padding0의 관측 횟수다. 모든 물리 underrun을 검출하는 드라이버 카운터가 아니며, 청감상의 끊김 횟수와 같지 않다. RTP 큐 부족으로 채운 무음과도 별개다. `SafetyFallbacks`는 낮춘 목표에서 소진을 관측하여 전체 여유로 고정 복귀한 횟수다.

## 두 PC 실제 통화 비교

각 회차120초, 동일 코덱·RTP 정책·입력 후보를 사용했다. 기존 출력, 즉시 축소 후보, 초기 안정화 보완 후보를 차례로 시험했다. 회차 사이의 네트워크 상태는 동일 입력으로 통제하지 않았으므로 전체 끊김 차이를 출력 변경의 인과 효과로 주장하지 않는다. 통화 중 빌드·파일 회수는 하지 않았다.

| 장치 | 엔진 주기 | 전체 용량 | 보완 후보 목표 | 기존/후보 API padding P50 | 후보 장치 소진 / 안전 복귀 |
|---|---:|---:|---:|---:|---:|
| PC |10.15873ms |22.31293ms |15.17007ms |22.313 / 15.170ms |0 / 0 |
| 노트북 |10ms |22ms |15ms |22 / 15ms |1（시작 구간） / 0 |

후보는 양쪽 모두 끝까지 제한 공급을 유지했다. 장치 오류·출력 재시작·추적 유실은0이었다. 표의 API padding 분위수는 첫5개 진단과 마지막 진단을 제외했다. 이는 엔드포인트에 쌓인 양이며 실제 스피커까지의 지연이 아니다.

| 장치 | 수신→제출 P50/P95 기존→보완 후보 | RTP 부족 무음 기존→보완 후보 | PLC 기존→보완 후보 |
|---|---|---:|---:|
| PC |28.12/37.59 →26.40/35.24ms |882.54→968.73ms |450→390ms |
| 노트북 |28.24/39.61 →23.57/34.25ms |1022→1082ms |470→440ms |

RTP 부족 무음은 후보에서도 남았다. 이 비교로 네트워크 문제 해결이나 전체 안정성 개선을 주장하지 않는다.

API padding 차이인 PC 약7.14ms·노트북7ms를 그대로 입→귀 개선량으로 발표하지 않는다. 목표를 낮추는 전환 중에는 출력으로 읽어오는 양을 잠시 줄이므로 대기가 상위 RTP 큐로 옮겨갈 수도 있다. 기존 소비율 보정을 유지하지만 전체 효과는 같은 음성 신호의 물리 실측으로 별도 확인해야 한다.

## 강제 지연과 회귀 검사

양쪽 PC에서 기존 출력·후보·후보＋의도적인50ms 공급 지연을 각15초 실행했다. 기존과 정상 후보의 장치 padding0 관측은0, 강제 지연 후보는1회 관측 뒤 전체 용량으로 안전 복귀하고 계속 진행했다. 반복 Play·정지·해제도 통과했다. 최종판의50ms 지연은5초 뒤 주입하여 초기 안정화가 끝난 뒤 복귀하는지 검증했다.

빌드 경고0·오류0, 전체 회귀, 서버7개, 실제 WebRTC 통합 검사를 통과했다. 최초 제한 환경에서는 localhost 접속이 EACCES로 거절됐지만 네트워크 접근 권한을 적용한 동일 검사를 완료했다. 새로운 목표량·수명주기 순수 검사는 기본 `verify.ps1`에 포함했고, 실제 장치 시험은 자동으로 시작하지 않는다.

추가로 실제 `WindowsAudioDevice` 경로에서 양쪽 모두 출력 시작→수동 재시작→중복 시작→중복 Close를 검사했다. 출력 재시작1회, 장치 오류 없음, 정상 재생 상태를 확인했다. 이 검사는 마이크 없이 빈 수신 큐에 무음을 공급하며 장치를 물리적으로 뽑는 시험은 아니다.

## 0.5.7 기본 정책으로5분 부하 통화

최종 기본값 선택 경로를 사용해 양쪽 PC에서300초 양방향 통화를 실행했다. 각 장치에 독립적인 무음 공유 출력 스트림 하나와 CPU 작업자 하나（4ms 작업·6ms 휴식）를 함께 실행했다. 실제 게임 프로세스는 이 시점에 실행 중이 아니었으므로, 이를 몬스터 헌터 와일즈 부하를 그대로 재현한 시험이라고 부르지 않는다. 게임 설정을 바꾸거나 게임을 새로 실행하지 않았다.

| 항목 | PC | 노트북 |
|---|---:|---:|
| 버전·정책 |0.5.7 / LowLatency |0.5.7 / LowLatency |
| 실행 시간 |300초 |300초 |
| 출력 padding P50 / P95（시작5개 진단 제외）|15.170 /15.170ms |15 /15ms |
| 제한 공급 유지 |예 |예 |
| 장치 padding0 관측 / 안전 복귀 |0 /0 |0 /0 |
| 장치 오류 / 출력 재시작 |0 /0 |0 /0 |
| RTP 부족 무음 전체 |180.15ms |20ms |
| RTP 부족 무음 증가 시점 |첫 약1초 이내 |첫 약1초 이내 |
| PLC 전체 |290ms |180ms |

오류 없이 양쪽 검사가 끝났다. 시작 약1초 이후에는 RTP 부족 무음 누적값이 증가하지 않았으나 PLC는 계속 일부 발생했다. 따라서 “통화 전체 무음 부족0” 또는 “네트워크 손실 해결”이라고 요약하지 않는다. 부하 작업자·시험 통화·보조 공유 출력은 완료 후 종료했고 양쪽 시험 프로세스가 남지 않았음을 확인했다.

이번에 해결한 범위는 **공유 출력 버퍼 전체를 항상 채우던 고정 대기의 축소와 그 변경에 필요한 초기 안정화·실패 복귀**다. 물리 입→귀 지연과 긴 수신 공백의 원인은 별도 검증 대상이며, 이 변경만으로 전체 음성 지연 문제를 모두 해결했다고 주장하지 않는다.
