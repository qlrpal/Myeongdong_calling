# EXTREME-078 — 패킷 저장소 할당 감소와 송신 방식 대조

2026-10-22. 077의 전역 피어 잠금 제거에 이어, 제품 코드의 반복 할당을 줄이고 직접 송신을 전용 스레드와 비교했다. 집 AP/드라이버 설정 대조는 재개하지 않았다.

## 채택한 변경

1. `OutgoingAudio`를 불변 값 형식으로 바꿨다. 직접 송신에서도 프레임마다 생성하던 메타데이터 객체를 제거했다. RTP 순번·누락 표식·타임스탬프·큐의 최신 프레임 보존 동작은 유지한다.
2. 수신 패킷은 `ArrayPool<byte>`에서 임대한 저장소로 복사한다. 원본 RTP 배열을 그대로 보관하지 않아 호출자가 입력을 재사용해도 안전하다. 임대 배열의 용량과 실제 payload 길이를 구분하고 디코더에는 실제 길이만 전달한다. 디코딩 성공/실패·폐기·backlog 정리·SSRC 변경·타임스탬프 재동기화·suspend·dispose에서 반환한다. Opus 디코딩 이후에는 PCM/시각 메타데이터만 남고 반환된 압축 바이트를 참조하지 않는다.
3. 최대120ms로 제한된 큐를 정렬 트리에서 미리 확보한 작은 정렬 배열(`SortedList`)로 바꿨다. 최소1ms 패킷120개와 후보1개를 수용하는 초기 용량121이다. 트리 노드·Packet 객체와 LINQ overlap/first/reverse 탐색 할당을 제거했다. 입력 중복·중첩·재정렬·wrap·backlog 정책은 유지한다.
4. 캡처·송신·디코드의 선택적 진단 lambda를 별도 메서드로 옮겼다. 진단용 hash가 없는 정상 프레임에서 캡처된 지역 변수의 closure를 만들 필요가 없도록 했다. 진단 필드와 시각 정의는 유지한다.

송신 payload 자체는 기존 소유 배열을 유지한다. SIPSorcery의 송신 버퍼 수명과 비동기 소비를 입증하지 않은 상태에서 인코더 배열을 즉시 재사용하거나 풀에 반환하지 않는다. GC 모드·우선순위·프레임/수신 여유를 동시에 바꾸지 않았다.

## 할당 및 처리 미세 시험

새 CLI `--audio-hotpath-benchmark OUTPUT.json`은 사전 인코딩된 패킷을 사용한다. 각 모드에서2,000회 워밍업 뒤10,000회 Add+Read를3회 측정하며, 진단/clock correction을 끈 상태의 현재 스레드 할당량과 admission/playback 시각을 기록한다. 연속성·잘못된 패킷·PLC·underfill 조건도 확인한다. encoder/transport/device/OS 스케줄링을 포함하지 않는 국소 시험이다.

| 측정 범위 | 변경 전 | 변경 후 |
|---|---:|---:|
| 송신 프레임 메타데이터 생성+관측 | 136 B/packet | 0 B/packet |
| Opus2.5ms 수신+재생 | 4,464 B/packet | 3,944 B/packet |
| Opus5ms 수신+재생 | 9,744 B/packet | 9,200 B/packet |
| PCM1ms 수신+재생 | 336 B/packet | 0 B/packet |

같은 설정의3회 결과에서 각 할당량은 같았다. 풀은 워밍업 뒤 재사용된 조건이며 cold start나 풀 압력에서도 할당0이라는 보장은 아니다. Opus의 남은 값에는 디코더 내부 작업 등이 포함된다. 앱 전체가 무할당이거나 GC 정지가 제거됐다는 뜻은 아니다.

2.5ms admission P99는 변경 전3.0~4.1µs, 변경 후1.4~1.6µs였다. 5ms는2.8~3.0→1.4µs, PCM은0.7~1.0→0.2~0.3µs였다. 순차 미세 시험이며 OS 상태가 완전히 통제된 성능 보장은 아니다. playback P99는 실행별 변동이 커 일관된 개선으로 판정하지 않는다. **이 수치를 입→귀 ms 단축으로 환산하지 않는다.**

원시 자료는 Git 제외 `native/.local/extreme-078/before.json`, `after.json`, `after-final.json`. `after.json`은 중간 구현, `after-final.json`은 closure 분리까지 반영한 수신 저장소 결과다. 이후 송신 후보와 진단 필드를 추가했으나 해당 저장소 구현은 같다.

## 전용 송신 후보

`LatencyExperiment`의 선택적 `DedicatedSend`를 추가했다. 기본은 false이고 기존 프리셋의 직접 송신을 유지한다. 비교 도구의 JSON에서만 `InlineSend:false, DedicatedSend:true`로 선택한다. 두 값이 동시에 true면 거부한다.

전용 sender는 bounded channel을 AutoResetEvent로 깨우며, 한 번 깨어나면 남은 항목을 처리한다. 폴링·전역 타이머 해상도 변경·무제한 큐를 사용하지 않는다. MMCSS Pro Audio 등록 성공 여부, 송신 모드·큐 용량·worker 오류는 Sender 진단에 기록한다. 종료는 캡처 정지 뒤 stop→worker 완료→핸들 해제 순서다. 기존 Task.Run 송신 모드도 유지한다.

초기 실제 캡처 시험에서 한 프레임 큐는 잘못된 대조 조건이었다. 한5ms대 장치 콜백에2~3개의2.5ms 프레임이 들어오는데, worker가 깨어나기 전 형제 프레임을 버렸다. 해당 자료를 보존하고 채택하지 않았다. 후보는 입력 EnginePeriod/FrameMs의 올림값으로 큐 용량을 정하며 상한16프레임을 유지하도록 수정했다. 이는 시작 전 고정 용량이며 추가 재생 대기 목표가 아니다. 실제 콜백이 보고 주기보다 크거나 worker가 오래 멈추면 여전히 drop할 수 있어 무손실 보장은 아니다. 기존 직접 송신 프리셋은 바뀌지 않는다.

### 로컬 UDP 스케줄링 A/B/A

새 `--sender-scheduling-benchmark OUTPUT.json`은 같은 호스트의 loopback UDP로 직접→전용→직접을 비교한다. 각1,000프레임,2.5ms 절대 고해상도 waitable timer로 실제 약398.7~399.9pps를 만들었다. 합성 busy thread0개 및2개 조건을 순차 실행했다. 전역 타이머 설정은 바꾸지 않는다. Opus/SRTP/실제 장치/게임/RF는 제외한 시험이다.

| 조건 | 직접 A1 / 전용 / 직접 A2: 생산자 P99 | 같은 순서: 수신 전달 P99 |
|---|---:|---:|
| 합성 부하 없음 | 0.396 / 0.146 / 0.467ms | 0.642 / 0.923 / 0.634ms |
| 합성 busy2개 | 0.556 / 0.210 / 0.738ms | 1.106 / 1.111 / 0.878ms |

모든 단계1,000/1,000 송수신·drop/pending0, 전용 worker MMCSS 등록 성공. 전용 큐 대기 P99는0.094/0.096ms였다. 생산자 작업은 줄었지만 수신 전달 P99 개선은 확인되지 않았다. 따라서 **전용 송신으로 기본값을 교체하지 않는다.** 기존 `sender-scheduling.json`은 실제 약64pps인 Sleep 기반 예비 시험이므로400pps 결과와 섞지 않는다. 두 시험 모두 규칙적으로 생성되는 프레임이며 장치 버스트는 별도 실제 캡처 시험에서 확인한다.

## 검증 범위

- Release 정적 분석/빌드 경고0·오류0.
- 제품 회귀에 packet pool 추적기를 추가해 임대 배열의 더러운 여분 공간, 호출자의 즉시 입력 덮어쓰기, duplicate, decode 실패, trim, suspend/resume, SSRC/시각 변경, 중복 dispose의 버퍼 소유권을 검증했다.
- 전용 sender의 짧은 버스트, 제한 큐 drop, wake 합치기와 순서, 실행 중 종료, 반복 자원 해제, 예외 보고, 모드 충돌 거부·큐 용량 계산을 검증했다. 유휴 앱 엔진의 Sender 진단도 확인했다.
- 저장소 변경 뒤 `verify.ps1 -NoRestore -Integration -Stress` 전체 통과(`verify.log`). 송신 후보 추가 뒤 `verify.ps1 -NoRestore -Integration` 전체 통과(`verify-final.log`). 마지막 버스트 용량 보정 뒤 Release 빌드·제품 회귀도 재검증했다. 기존 정적/코덱/프레임/재정렬/PLC/복구/clock stress·서버8개·ICE/DTLS/SRTP/RTCP/재생 통합을 실패 없이 유지했다.

## 실제 앱 엔진·공유 장치 대조

같은 PC에서 엔진 프로세스2개, 실제 공유 캡처/출력, 합성 음성, 로컬 전용 시그널링 서버·호스트 직접 WebRTC로 각15초씩 실행했다. 파일의 `pc`/`laptop`은 기존 도구의 **역할 이름일 뿐 둘 다 같은 PC**다. 두 프로세스가 장치·CPU·OS를 공유하므로 서로 다른 사용자의 통화 대조와 같지 않다. 장치 설정/기본 장치는 변경하지 않았다. 합성 입력으로 실제 대화를 파일에 저장하지 않았다.

초기 한 프레임 전용 큐는 측정 창 송신 drop3,048/3,020개와 PLC7,570/7,602.5ms를 기록했다. 기능 도구 종료코드는0이었지만 성능/품질 실패다. 이 자료 `engine-dedicated-*.json`을 그대로 보존한다. 이후 입력 주기 기반 용량으로 보정해 **새 전체 A/B/A**를 실행했다. 실제 보고 캡처 주기는 양쪽 모두10ms였고 전용 용량은4였다. 5ms 주기가 실제로 적용됐다고 가정하지 않는다.

아래는 각 단계 첫/마지막 진단 스냅샷 사이 약14.57~14.93초의 증가량이다.

| 단계 | 송신 drop 증가량, 역할pc/laptop | 수신 underfill 증가량 | PLC 증가량 | 출력 장치 empty 증가량 |
|---|---:|---:|---:|---:|
| 직접 A1 | 0 / 0 | 74.42 / 35.23ms | 82.5 / 92.5ms | 0 / 0 |
| 전용 B, 용량4 | 0 / 0 | 0 / 0ms | 70 / 70ms | 0 / 0 |
| 직접 A2 | 0 / 0 | 303.40 / 293.69ms | 225 / 265ms | 1 / 0 |

전용B의 시작을 포함한 **누적 송신 drop은 양쪽6개**다. 측정 창 증가량0을 전체 실행 drop0이라고 표현하지 않는다. worker 오류 없음·MMCSS 성공·최종 pending0을 확인했다. 프로세스 CPU는 약0.084~0.097코어였다. 이 값은 시스템 전체 CPU 사용률이 아니다.

같은 호스트 QPC에서 SSRC+RTP timestamp를 대응하고, 공통 trace의 앞/뒤1초를 제외해 각 방향 약5,200~5,350개 송신을 비교했다. trace eviction0. 원시 분석은 `analyze-engine.py`, 결과 `engine-summary.json`이다.

- 직접 송신 encode-end→send-start P99는0.0038~0.0043ms, 전용은0.2218/0.2294ms였다. 전용 큐가 전달하는 추가 대기는 실제 존재한다.
- 송신 시작→상대 RTP 알림 P99는 직접A1 19.38/22.34ms, 전용16.50/15.62ms, 직접A2 72.78/73.40ms였다. 같은 PC의 로컬 경로에서도 알림까지 긴 꼬리가 발생했다. 이 구간은 송신 처리·소켓/OS·수신 스케줄링/콜백을 포함하며 RF/AP 지연으로 설명할 자료가 아니다. 반대로 이 별도 시험으로071/072의 게이트웨이 사건을 앱 원인으로 소급하지 않는다.
- 실제 재생 제출된 대응 패킷의 capture-frame 시각→상대 출력 제출 중앙값은 직접A1 38.46/38.59ms, 전용38.74/38.50ms, 직접A2 38.67/38.02ms였다. 전용이 중앙값을 일관되게 줄이지 않았다. 수신→제출 중앙값도 약20~21ms였다.
- 제출 대응은 송신 전체가 아니다. 예를 들어 역할pc→상대 방향은 A1 5,304송신 중5,262개, B5,340중5,313개, A2 5,239중5,060개가 정상 제출과 연결됐다. 미제출/늦음/폐기 표본을 제외한 지연 분포에는 생존 편향이 있으므로 underfill/PLC와 함께 판단한다. capture-frame QPC는 장치 보고 시각이며 물리 입→귀가 아니다.

전용B는 이 짧은 동시 장치 부하 시험에서 연속성이 좋아진 후보지만, 시작 drop과 추가 송신 대기가 있고 직접A1/A2 상태도 일정하지 않았다. **생산 기본값은 직접 송신 유지**, 전용은 후속 다중 피어/장시간 비교 옵션으로 남긴다. MMCSS/GC 설정을 더 강하게 바꾸면 해결된다고 추정하지 않는다. 실제 입력 주기와 버스트를 무시한 규칙적 패킷 시험만으로 송신기를 채택하지 않는 것이 이번 대조의 핵심이다.

모든 소유 엔진/시그널링 프로세스를 종료하고 입출력 장치 핸들을 해제했다. 최종 용량 보정 뒤 전체 회귀/통합 재검증은 `verify-burstcap.log`에 기록한다. 기존 `native/dist`, 원격 노트북/OCI, 공유기/전원/드라이버/시스템 라우팅 변경 및 git commit/push 없음.
