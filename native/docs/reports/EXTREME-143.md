# EXTREME-143 — 노트북 원본 복구 및 20ms 기준선 재시험

2026-11-02 / 기반 `5ce456b`와140~142 미커밋 변경 보존. 사용자가 노트북 복귀를 알린 뒤141의 복구 대기를 해소하고 중단됐던180초 기준선을 새 실행 ID로 재시험했다. 앱 오디오 코드는 변경하지 않았다.

## 가설·조건

141에서 전원/캡처 중단으로 확보하지 못한 정상20ms 기준선을 확인한다.140의 격리 바이너리와 동일한 SHA256 `36D9C78AF976DB2BABB02F301684153D14C3717A3208F4CE1A7623703A5A9B6B`를 양쪽에 사용했다. 이후 진단 도구 수정본을 동일 바이너리라고 섞지 않았다.

독립 두 PC, 같은 버디 LAN 유선 지정, 직접 UDP, native Opus LowDelay64/48kHz mono/10ms, 수신 여유20ms, 기존 출력 정책, 기준선180초,250ms 표본, 상세 baseline trace 끔, 기존 사건 기록 auto를 유지했다. 노트북 유선1Gbps·Wi-Fi disconnected를 확인했고 양쪽 바인딩/선택된 로컬·상대 endpoint가 지정 유선과 일치함을 모든 표본에서 검증했다. 운영 서버는 기존 신호 연결만 사용했다.

이번20ms 기준선에서는 기존 끊김이 재현되지 않았다.140의 별도10ms180초는 PC PLC2.5ms/렌더 소진1회였으나, 실행 날짜·전원 복귀·시작 위상 등이 같지 않고 이번에는 입력 불연속도0이다. 따라서 두 회차 차이만으로 수신 여유가 그 사건의 원인이었다고 확정하지 않는다. 기본20ms와 기존 자동 하한15ms를 유지하며,142의 모델 재현에서 실패한10~14ms 후보를 승격하지 않는다. 안정적인 평상시 지연 감소를 새로 확보한 결과는 아니다.
