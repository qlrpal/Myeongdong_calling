# EXTREME-082: 제어된 손실·묶음 도착 대조와 불필요한 큐 폐기 수정

2026-10-23. 친구 재시험 없이 가능한 합성 대조를 진행했다. 원본 진단·기존 dist·서버·OS 설정은 변경하지 않았다.

## 발견한 앱 동작

20ms 분량의 짧은 패킷이 한꺼번에 도착하는 경우, 소비 시점의 `요청 길이+짧은 여유`만 남기는 정리가 정상 오디오까지 버렸다. 큐 용량 계산도 장치 읽기 크기에만 기반해 도착 묶음을 충분히 수용하지 못했다. 결과적으로 실제 네트워크 손실 없이도 폐기와 PLC가 반복됐다.

친구 진단에는 입력 전달 간격 약20ms가 관측됐으므로 관련 가능한 앱 문제다. 그러나 초 단위 JSON에는 패킷별 시간/길이가 없어 친구 통화의 동일 원인이라고 확정하지 않는다. 그 자료를 그대로 재생했다고 주장하지 않는다.

## 수정

적응형 짧은 여유 프리셋에서 유효 패킷이 1ms 이내 간격으로 묶여 도착한 분량을 관측한다. 최대 보존량은 기존 실험 BacklogMs 범위로 제한하고, 최근 1초 창에서 갱신한다. 재생 정리·재시작 준비·유효 큐 용량이 이 묶음을 수용하게 했다. 이전 묶음은 시간창이 지나면 줄어들며 타임라인 초기화 때 제거한다. 진단 JSON에 `RecentArrivalBurstMs`를 추가했다.

모든 환경의 고정 여유를 늘린 변경은 아니다. 관측된 묶음이 기존 요청+여유보다 클 때만 정리 하한에 반영한다. 묶음이 큰 경로에서는 이전에 버리던 정상 샘플을 보존하는 만큼 대기와 연속성의 교환이 있다. 그 상한은 측정/구성 범위에 제한된다. 기존 기본 모드와 고정 여유 실험 모드의 큐 경계는 유지한다.

일부 기존 검사에는 가상 RTP 시간과 실제 CPU 루프 시각이 혼용돼 있었다. CPU가 빨라지면 긴 도착 묶음으로 잘못 추정되므로 해당 검사에 명시적 가상 도착 시각을 전달했다. 기존 성공 기준을 느슨하게 바꾸지 않았다.

## 재현 방법

```powershell
# 먼저 빌드/기본 검사
./native/verify.ps1 -NoRestore
./native/TransportProbe/bin/Release/net10.0-windows10.0.19041.0/TransportProbe.exe --adaptive-network-checks native/.local/reports/adaptive-network.json
# 기존 장시간 스트레스들과 함께 실행하려면
./native/verify.ps1 -NoRestore -Stress
```

각 조건은 독립된 120초 가상 통화다. 실제 Opus 페이로드와 제품 RTP 재생 버퍼·자동 정책을 사용하며 500ms 피드백 폴링과 100ms 피드백 전달을 모사한다. 고정2.5ms·고정5ms·자동 모드를 비교하고 별도의 강제 길이 전환 조건을 둔다. 네트워크 이상은 30~75초에 가하고, 마지막20초에 PLC/부족/폐기가 남지 않는지 검사한다. 정상,1% 손실,400ms 도착 정지 후 몰림,12ms 재정렬,7초간50% 손실,200ms 재생 중단,20ms 캡처 묶음,입력 주기 변경을 다룬다. uint RTP 순환도 포함한다.

여기서 고정2.5/5는 송신 프레임 길이를 고정한 것이고 수신 짧은 여유는 적응형이다. 해당 옵션을 바꾸는 합성 모드 이름이지 사용자 프리셋 이름이 아니다. 실제 음성·소켓·장치를 기록/재생하지 않는다. 단계별 시간 진행으로 외부망이나 실제 스케줄러를 재현한 것도 아니다.

## 수정 전후 결과

20ms 캡처 묶음,120초 합계:

| 송신 프레임 | PLC 이전→수정 | 복구 폐기 이전→수정 |
| --- | ---: | ---: |
| 고정2.5ms | 14997.5→0ms | 15007.5→10ms |
| 고정5ms | 60→0ms | 70.2→10ms |
| 자동 | 895→0ms | 905→10ms |

남은 10ms 폐기는 시작 시점의 오래된 큐 정리다. 이 세 경우 수정 후 부족은0이고 마지막20초의 PLC/부족/폐기는 모두0이었다. 정상10ms 묶음의 PLC/부족은 이전·이후 모두0,500ms 표본에서 본 큐 중앙값/P95는 모두5/5ms로 같았다. 이 값은 실제 입→귀 지연이 아니다.

400ms 도착 정지에서는 PLC·부족을 없앨 수 없었다. 예를 들어 고정2.5ms에서 합계PLC60ms·부족750ms가 남았으며 회복 후에는 지속되지 않았다.50% 손실 조건도 예상대로7초 동안 약3500ms PLC가 남았다. 자동 프레임이 모든 손실/재정렬에서 고정2.5ms보다 우월하지 않았다.12ms 재정렬 대조에서는 고정2.5ms PLC532.5ms,자동755ms였으므로 자동 모드를 보편적 최저 지연/최고 연속성으로 승격하지 않는다.

수정 전후 JSON과 로그는 Git 제외 `.local/extreme-082/`에 보존한다. 원본080 진단의 실제 패킷 흔적 재생은 자료 부족으로 불가능하며, 동일 패턴의 가설 대조와 구분한다.

## 검증 범위와 다음 실제 시험

기본 제품 검사에 무손실20ms 묶음의 PLC/부족0과 묶음 추정 초기화 회귀를 추가했다. 전체 회귀·서버8개·실제 캡처/SRTP 반복 전환·IPv4/IPv6 미디어 통합을 통과했다. 최종 입력 주기 전환과 추정치 만료 회귀까지 포함한 25개 대조(총50분 가상 미디어 시간)도 통과했다. 입력 주기가 10→20→10ms로 바뀌는 조건에는 순간PLC5ms가 남았지만 최종20초에는 모든 조건의 PLC/부족/폐기가0이었다. 최종 출력 시작 준비 조건 정합성 변경 뒤에는 빌드·극저지연·제품 회귀를 다시 확인했다. 제어된 시험과 기능 검사 통과가 친구 환경의 전체 해결이나 물리 지연 원인 확정을 뜻하지 않는다. 친구와 가능할 때 양쪽 최신 빌드로 재시험하고, 이상 시 나가기 전 양쪽 JSON을 보존한다.
