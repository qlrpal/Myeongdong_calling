# 지연 발생 위치와 수신 여유 최적화 시험

2026-10-20. 목표는 지연 우선, 품질 다음이다. Windows WASAPI 공유 모드, 개인 장치 효과 및 게임 소리와의 공존을 유지했다. 서버·방화벽·장치 설정은 변경하지 않았다.

## 확인한 발생 위치

이번에는 캡처 프레임에 합성 신호를 넣고, 동일 시작 패킷의 해시로 송신·수신·정상 디코딩·출력 제출을 확인했다. 양쪽 모두 Opus LowDelay64, 10ms 프레임, 표준 10ms 공유 입력, TURN 강제 연결이다. 80초씩 5회 통화했고, 양방향 각 회차 6/6개 신호가 유효했다. 전체 패킷 추적은 회차·방향당 약 8천 개다.

| 구간 | PC → 노트북 | 노트북 → PC |
| --- | --- | --- |
| 실제 입력 샘플 QPC → 프레임 완성 | 중앙값 약 19ms | 약 17–19ms |
| 인코딩 실행 | 약 0.02ms | 약 0.07–0.08ms |
| 송신 큐 대기 | 약 0.02ms | 약 0.04ms |
| 송신 API 실행 | 약 0.03ms | 약 0.16–0.18ms |
| 송신 API 완료 → 상대 복호화 후 수신 콜백 | 중앙값 범위 약 8–15ms | 약 9–14ms |
| 수신 콜백 → 출력 provider 제출, 20ms 여유 | 회차 중앙값 약 31–41ms | 약 31–39ms |
| 출력 provider 제출 → 디지털 루프백 신호 QPC | 회차 중앙값 약 123–133ms | 약 37–42ms |

입력 행은 실제 마이크의 시계와 프레임 수집 동작을 관찰한 값이다. 합성 신호 자체는 프레임 완성 후 삽입되므로 이 행을 실제 테스트 신호의 물리 입력 지연으로 해석하지 않는다. 출력 행은 각 신호의 제출→검출 차이다. 디코딩은 대부분 0.1ms 안팎 또는 그 이하였고, 별도의 긴 PCM 큐 대기는 관찰되지 않았다.

**큰 고정 대기가 남는 위치는 노트북의 출력 제출 이후다.** 반면 인코딩·송신 큐·디코딩 CPU 시간을 줄여 수십 ms를 얻을 근거는 없다. 수신→제출에는 줄일 수 있는 수십 ms의 대기가 있지만 출력 이후의 큰 구간을 제거하지는 못한다.

표는 회차별 별도 중앙값의 범위이며 합산하지 않는다. 이전 Stereo Mix 공통 경로의 약 180ms와 입력·시작점·검출 기준이 완전히 같지 않으므로, 이 표를 합쳐 정확히 180ms를 분해했다고 주장하지 않는다. 물리 입→귀 지연도 아니다.

PC 출력은 이번 기록에서 `Realtek HD Audio 2nd output`, 44.1kHz stereo float였다. 노트북은 Realtek 스피커 엔드포인트, 48kHz stereo float였다. 장치 기본값을 바꾸지 않았다.

## 네트워크 구간을 확인한 방법과 한계

별도 SSH 제어에서 40번씩 QPC 교환을 수행했다. 왕복 경로 대칭을 가정하지 않고 가장 좁은 오프셋 하한·상한을 보관했다. 각 교환 묶음의 최선 폭은 약 1.32/1.75/1.33ms, 세 묶음을 합친 외곽 폭은 약 3.25ms였다. 그 범위와 송수신 SSRC/RTP timestamp를 이용해 뒤 두 회차의 동일 패킷을 맞췄다.

이 범위를 시험 사이에 사용하려면 호스트 재시작이 없고 시계 오프셋이 관측 외곽 밖으로 벗어나지 않았다는 조건이 필요하다. 이 조건을 수학적으로 보장하는 정밀 동기화 장치를 사용한 것은 아니다. 따라서 단방향 구간을 보정 조건이 있는 범위로 보고하며 RTT/2를 실측값으로 사용하지 않았다.

정상 중앙값은 약 8–15ms였지만, 특정 회차에서는 같은 패킷의 송신 완료→수신 콜백이 최대 약 193–196ms, 역방향 약 169–172ms까지 늘었다. 수신 패킷 간 공백도 약 169/187ms였다. 이 회차는 양쪽 앱 무음 채움 약 159/204ms를 기록했다. 이러한 변동은 출력 이후의 고정 대기와 별개다. 수신 큐를 무조건 낮추는 것으로 해결할 수 없다. 송신 API 완료와 복호화 후 콜백 사이에는 OS·네트워크·수신 스케줄링이 함께 포함되므로 순수 회선 전파 시간이라고 부르지 않는다.

## 20 → 10 → 20ms 여유 대조

각 회차 80초, 양쪽 동일 설정의 실제 TURN 통화였다. 시작 5초와 끝 1초를 제외한 전체 정상 재생 패킷의 수신→출력 제출 중앙값이다.

| 수신 장치 | 20ms A1 | 10ms B | 20ms A2 |
| --- | --- | --- | --- |
| PC | 35.34ms | 24.65ms | 39.18ms |
| 노트북 | 39.09ms | 21.33ms | 40.97ms |

| 수신 장치 | A1 PLC / 늦은 패킷 | B PLC / 늦은 패킷 | A2 PLC / 늦은 패킷 |
| --- | --- | --- | --- |
| PC | 170ms / 7개 | 110ms / 3개 | 150ms / 1개 |
| 노트북 | 120ms / 4개 | 170ms / 6개 | 160ms / 3개 |

이 세 회차의 앱 무음 채움과 재버퍼링은 양쪽 모두 0이었다. 10ms 후보는 제출 전 대기를 약 10–20ms 줄였지만, 노트북의 늦은 패킷은 늘었다. 출력 제출 이후의 큰 대기는 유지됐다. 순차 시험의 회차별 네트워크 차이가 있으므로 중앙값 차이 전부를 설정 하나의 인과 효과로 확정하지 않는다.

## 입력 정렬 후보

일부 기록에서 입력의 부분 프레임이 다음 콜백까지 기다리는 패턴이 있었다. 최초 인코딩 이전에만 시작 조각을 정렬하는 후보를 별도 시험했지만, 실제 조정한 샘플은 양쪽 모두 0개였다. 앞뒤 기준과 비교해 이 후보의 효과를 입증하지 못했다. 해당 회차의 수신 공백도 겹쳤으므로 설정 탓이나 개선으로 해석하지 않는다. 후보 코드와 전용 CLI를 제거했고 입력 동작은 변경하지 않았다.

## 연속 합성 음성 대조

같은 48kHz 모노 합성 음성을 양쪽에 반복 공급했다. 실제 캡처 시계는 유지하고 마이크 PCM만 교체했으며, 실제 발화나 장치 음질 평가가 아니다. 20/10/20ms를 회차당 120초씩 비교했다. 아래 큐 값은 시작 5개와 마지막 표본을 제외한 약 114개 표본의 중앙값이며, 나머지는 마지막 표본의 누적값이다.

| 수신 장치·회차 | 여유 | 큐 중앙값 | 무음 채움 | PLC 보완 | 늦은 패킷 | 재버퍼링 |
| --- | --- | --- | --- | --- | --- | --- |
| PC A1 | 20ms | 41.09ms | 277.81ms | 620ms | 33개 | 6회 |
| PC B | 10ms | 25.70ms | 118.58ms | 280ms | 12개 | 2회 |
| PC A2 | 20ms | 32.80ms | 186.79ms | 100ms | 1개 | 1회 |
| 노트북 A1 | 20ms | 40.06ms | 322.35ms | 710ms | 34개 | 6회 |
| 노트북 B | 10ms | 25.10ms | 155.92ms | 300ms | 13개 | 2회 |
| 노트북 A2 | 20ms | 31.39ms | 193.17ms | 150ms | 2개 | 1회 |

송신 대기 큐의 프레임 폐기는 여섯 기록 모두 0개였다. 최대 패킷 도착 공백은 A1 약 175ms, B 약 184/204ms, A2 약 292/293ms였다. A2가 최대 공백은 가장 컸지만 누적 PLC와 재버퍼링은 더 적었다. 최대 공백 하나나 큐 평균 하나로 전체 안정성을 판단하면 안 된다.

10ms는 큐를 낮췄지만 A1보다 일부 안정성 지표가 좋고 A2보다 나빴다. 네트워크 공백 횟수·시점이 회차마다 달라 안정성 차이를 수신 여유 하나의 효과로 분리하지 못했다. **10ms가 항상 더 불안정하다고 확정한 것도, 안정성을 검증했다고 판단한 것도 아니다.** 제품 공통 기본값은 20ms를 유지한다. 10ms 비교 경로는 진단 도구에만 남긴다.

## 변경과 판단

- 같은 패킷의 구간 추적, 별도 QPC 시계 교환, 실제 통화의 여유 비교 및 연속 음성 A/B/A 실행 도구를 추가했다. 시계·추적 누락·미완료 통화·해시 불일치가 있는 자료는 정상 지연으로 분석하지 않는다.
- 입력 정렬 후보는 실제 효과가 없어 제거했다. 제품 캡처·코덱·기본 수신 여유·출력 모드를 변경하지 않았다. 실증되지 않은 절감을 제품 개선으로 발표하지 않는다.
- 이번 결과는 고정 지연과 순간 공백을 구분한다. 정상 상태에서 큰 고정 구간은 노트북 출력 제출 이후다. 이전 DTS 개입 시험의 추가 대기 결과와도 방향이 일치하지만, 이번 자료로 해당 구간 전체를 DTS나 실제 DAC 지연으로 단정하지 않는다.
- 개인 장치 효과를 끄거나 독점 모드로 전환하는 최적화는 적용하지 않았다. 현재 남은 앱 측 후보는 약 10–20ms 수신 대기 절감이지만, 순간 공백 복구와 실제 음성 안정성의 검증을 더 요구한다.
- 게임을 실행한 부하 시험이나 물리 입→귀 측정은 이번 회차에서 하지 않았다. 연속 합성 음성과 단기 A/B/A만으로 게임 환경·외부망 전체의 안정성을 보장하지 않는다.

## 재현

```powershell
# 양쪽에서 같은 방, 서로 다른 pc/laptop 역할로 실행
TransportProbe.exe --stage-optimize https://qlrpal.ddns.net/ ROOM OUTPUT-call.json ROLE 20
TransportProbe.exe --reserve-speech-ab https://qlrpal.ddns.net/ PREFIX OUTPUT_DIRECTORY ROLE speech.wav
# 별도 제어 시계: SSH 대상·고정 host key·비밀번호는 일시 환경 변수로만 전달
TransportProbe.exe --measurement-clock CLOCK.json
python native/TransportProbe/Analysis/analyze_stage_optimization.py native/.local/stage-optimize-059 native/.local/stage-optimize-059/summary.json
```

원본은 Git 제외 경로 `native/.local/stage-optimize-059/`에 보관했다. 오디오 페이로드·원음·세션 토큰은 새 진단 기록에 저장하지 않았다. `align` 이름의 원본 회차는 제거된 입력 후보의 역사적 자료이며 실제 조정량 0개였다. 현재 재현 CLI는 제품의 기본 입력과 진단용 수신 여유 비교만 지원한다.

## 검증과 종료

최종 `native/verify.ps1 -NoRestore -Integration`을 통과했다. Release 빌드는 경고·오류 0개였고, 오디오 변환·코덱·타임라인·큐·시계/지연 진단 회귀, 서버 7개 테스트, 실제 로컬 ICE/DTLS/SRTP/RTCP 및 RTP 재생 통합 검사가 통과했다. 분석기의 빈/짝수 표본 요약과 미완료 추적 거절도 확인했다. `git diff --check`는 오류가 없었다.

양쪽 통화·진단 프로세스가 종료됐으며 전역 오디오·개인 장치·서버 설정 변경은 없다. Git 커밋·푸시·배포 ZIP 생성은 수행하지 않았다.
