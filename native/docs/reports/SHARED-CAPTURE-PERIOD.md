# 0.5.6 · WASAPI 공유 입력 주기 단축

2026-10-18. 게임과 통화를 함께 사용하는 조건에서 WASAPI 공유 모드를 유지하고 입력 전달 대기를 줄이는 첫 변경입니다. 독점 모드·ASIO·개인 장치 설정 변경은 사용하지 않습니다.

## 구현

기존 입력은 NAudio의 최소 공유 주기가 5ms보다 짧으면, 과거 최소 주기 입력의 오버플로 때문에 표준10ms 공유 입력으로 복귀했습니다. 라이브러리의 최소 주기 옵션 대신 약5ms를 직접 요청할 수 있는 `SharedCaptureRecorder`를 추가했습니다.

- `IAudioClient3.InitializeSharedAudioStream`을 EventCallback 플래그로 사용합니다. 장치 기본 형식이 기존48kHz 변환 경로에 맞는 경우에만 시도합니다.
- 요청 주기는5ms 이상, fundamental의 정수배, 장치 min/max 범위 안이며 기본 주기보다 짧아야 합니다. 노트북은256프레임/48kHz, 즉5.333ms를 선택했습니다.
- 초기화가 거절되거나 형식·주기가 맞지 않으면 기존 NAudio 공유 입력을 사용합니다. 스트림 시작 실패도 같은 형식을 보존한 표준 공유 입력으로 복귀합니다.
- 입력 전용 MTA 스레드와 MMCSS Audio 작업을 사용하고, WASAPI 버퍼는 콜백 종료 때까지 lease로 관리합니다. 추가 타이머·프레임 큐는 만들지 않았습니다. 정지 시 스레드가 끝난 뒤 COM·이벤트 자원을 해제합니다.
- ‘짧은 공유 입력 주기 우선’을 통화 밖에서 끌 수 있습니다. 출력 정책은 바꾸지 않습니다. 장치가 지원하지 않는 경우 짧은 주기를 강제하지 않습니다.

이 선택 규칙은 [Microsoft의 공유 스트림 주기 계약](https://learn.microsoft.com/en-us/windows/win32/api/audioclient/nf-audioclient-iaudioclient3-initializesharedaudiostream)을 따릅니다. 기존 NAudio3 공개 API로 특정 중간 주기를 지정할 수 없어 캡처 어댑터만 추가했으며 출력·Opus·RTP 재생 정책은 유지했습니다.

## 장치 단독·공존 검사

각 장치에서 기존 입력, 짧은 주기, 짧은 주기+무음 공유 출력+한 부분 CPU 작업을12초씩 실행하고 처음2초를 제외했습니다. 음성은 저장하지 않았습니다. 부분 CPU 작업은 한 작업자가 약5ms 실행/5ms 휴식하는 방식이며 실제 게임은 아닙니다.

- PC의 fifine 입력은10ms 미만을 지원하지 않아 세 경우 모두 기존10ms 경로를 사용했습니다. 입력 불연속은 모두0이었습니다.
- 노트북은5.333ms를 사용했습니다. 단독 짧은 주기 첫 시험은 입력 불연속1회, 공유 출력·CPU 공존 시험은0회였습니다. 이 한 번의 불연속을 없었던 것으로 처리하지 않습니다.
- 공유 출력은 별도 앱 스트림에 해당하는 무음 출력입니다. 실제 게임·GPU 부하·모든 드라이버의 안정성까지 증명하지 않습니다.

## 실제 두 PC 통화 비교

각 모드120초, 같은 0.5.5 재생 정책·Opus10ms·직접 연결로 비교했습니다. 기존→후보 순서이며, 통화 중 별도 빌드·파일 회수·부하 검사는 하지 않았습니다. 추적은 방 참가 전부터 시작했습니다. 표는 각 송신 측에서 시작5초 이후·끝1초 이전 프레임의 같은 시계로 계산했습니다.

| 송신 측·입력 모드 | 실제 경로 | 첫 샘플→인코딩 시작 P50/P95 | 첫 샘플→송신 완료 P50/P95 |
|---|---|---:|---:|
| PC · 기존 |10ms |19.17 / 19.31ms |19.40 / 19.63ms |
| PC · 후보 |미지원→10ms 복귀 |19.17 / 19.31ms |19.38 / 19.58ms |
| 노트북 · 기존 |표준 공유10ms |19.04 / 19.95ms |19.71 / 20.79ms |
| 노트북 · 후보 |5.333ms 공유 |16.00 / 21.77ms |16.53 / 22.48ms |

노트북은 인코딩 시작 중앙값이 약3.05ms 빨라졌지만 P95는 약1.82ms 늘었습니다. 콜백만 빨라지는지 확인하지 않고10ms 프레임 조립까지 포함했습니다. 후보의 첫 콜백 중앙값은 약5.99ms였지만 이를 전체 캡처 지연으로 표현하지 않습니다. 다른 구간의 분위수를 더해 전체 지연을 계산하지 않습니다.

선택한 구간에서 두 장치·두 모드 모두 입력 불연속과 시각 오류는0이었습니다. 후보 회차의 수신 PLC는 PC150ms·노트북80ms, 무음 부족은 양쪽0ms였습니다. 기존 회차는 PC320ms·노트북310ms PLC와 각각5.00/16.52ms 무음 부족이 있었지만, 회차별 네트워크 조건이 달라 이 차이를 입력 변경의 인과 효과로 주장하지 않습니다.

이 시험은 코덱 선행 대기·상대 재생·장치 출력·음향 전달을 포함한 입→귀 전체 지연이 아닙니다. 테스트 실행 파일은 버전 표기 변경 전0.5.5 작업 빌드였으며, 입력 후보는 보고서의 `intermediateCapture`로 구분했습니다.

## 검증과 현재 판단

경고0·오류0 빌드, 기존 회귀·서버7개·실제 WebRTC 통합 검사를 통과했습니다. 주기 반올림·min/max·기본 주기보다 느려지지 않는 조건·10ms 복귀를 검사했습니다. PC는 실제 미지원 복귀, 노트북은 실제 지원 경로를 확인했습니다.

짧은 공유 입력을 지원하는 장치에 사용하는 것으로 구현했으며, 전체 환경의 최저 지연을 확정한 것은 아닙니다. 정상적인 입력에서도 P95가 늘 수 있어 사용자가 입력 주기 단축만 끌 수 있게 했습니다. 최초 단독 검사 불연속1회와 실제 게임 부하 검증 미완료는 남은 한계입니다. 기존 배포 ZIP은 이번 작업에서 다시 만들지 않았습니다.

```powershell
./native/run.ps1
./native/verify.ps1 -NoRestore -Integration

# 명시적 마이크 검사: 무음 공유 출력과 제한된 CPU 작업 포함
./native/TransportProbe/bin/Release/net10.0-windows10.0.19041.0/TransportProbe.exe --capture-period-device OUTPUT.json
```

입력 원본 음성은 저장하지 않았습니다. 장치 검사·두 PC 추적·분석 JSON은 Git 제외 경로 `native/.local/capture-period-056/`에 보존합니다.
