# 재생 기한·시작 위상·공백 뒤 회복 조사 · 2026-10-17

단순히 목표를 20ms로 낮추는 대신, 빈 큐에서 한 번 기다리는 후보와 공백 뒤 오래된 큐를 정리하는 후보를 구현했습니다. 모두 검증 도구에서만 선택하며 앱 기본 설정·배포 파일·서버는 유지합니다.

## 원인 범위와 측정 보완

이전의 별도 작업 없는 고정 목표 시험에서 노트북의 늦은 패킷 84개는 모두 빈 큐에서 해당 RTP 시각을 PLC로 넘긴 뒤 도착했습니다. PLC 결정→도착 중앙값은 3.393ms, P95는 11.050ms였습니다. 이는 앱이 패킷을 기다릴 기한을 놓친 사례이며, 물리 출력 기한이나 네트워크 지연의 직접 원인을 측정한 값은 아닙니다.

이전 8개 자료 중 7개는 첫 버퍼 관측에서 이미 앞선 입력이 쌓여 있었습니다. 첫 읽기 전 큐가 30~60ms이거나 첫 10ms 패킷을 넣은 직후 큐가 약 38~39ms였습니다. 누락된 초기 큐·디코더·소비율 상태 때문에 차가운 시작으로 재생한 결과를 실제 시작 상태와 동일하다고 볼 수 없습니다. 읽기 기록의 `PlayoutStarted`는 읽기 **후** 상태이므로 이것만으로 초기 상태 누락을 판단하지 않았습니다. 기존 자료의 재생 결과는 같은 입력에 대한 후보 비교로만 사용합니다.

자동 추적을 방 참가 전부터 시작하도록 바꿨습니다. 180초 기록 한도 내에서 연결이 55초를 넘으면 실패 처리하고, 연결 후 약 120초를 측정합니다. 첫 입력·출력 요청과 초기 버퍼를 포함하며, 종료 후에는 상대의 마지막 표본을 위해 2초간 통화를 유지합니다.

## 추가한 도구와 후보

- `analyze_playout_deadlines.py`: 같은 수신 측 시계로 늦은 도착을 앞선 PLC 결정과 연결합니다. 이미 재생한 패킷의 중복·관측되지 않은 결정은 따로 셉니다.
- `--playout-replay INPUT OUTPUT`: 원래 버퍼 잠금 순서·RTP 시각·출력 요청 크기를 동일하게 재현합니다. 실제 음성 대신 10ms Opus 무음을 사용합니다. 같은 정책의 판정 수를 실제 기록과 대조할 수 있습니다.
- `transient`: 고정 목표 20ms에서 큐가 완전히 비는 에피소드마다 한 번 10ms PLC를 넣되 RTP 시각을 넘기지 않습니다. 패킷이 늦게 도착해도 재생할 자리를 남깁니다. 목표 여유를 계속 올리지 않으며, 뒤 패킷이 이미 큐에 있으면 기존 손실 PLC를 적용합니다. 실제 손실인데 뒤 패킷도 아직 오지 않았다면 한 번 기다릴 수 있습니다.
- `fresh`: 위 후보에 최신 큐로 재시작하는 정책을 더합니다. 재버퍼링 뒤 현재 출력 요청+목표 여유를 유지할 만큼만 최신 패킷을 남깁니다. 최초 시작에는 적용하지 않습니다. 건너뛴 음성은 `RecoveryDiscardedPackets`·`RecoveryDiscardedMs`로 별도 기록합니다.

10ms 보류는 실제 음성이 아니라 PLC입니다. 연속 PLC 60ms 상한에 포함하며, 무한히 기다리지 않습니다. 파형·음질 동등성은 검증하지 않았습니다.

## 시작부터 기록한 실제 비교

PC 유선 ↔ 노트북 Wi-Fi, LAN 직접 연결입니다. Opus 48kHz 모노 10ms, 적응 목표 끔, WASAPI 저지연 요청과 장치 설정을 유지했습니다. 각 회차 약 120초이며, 회차 중 파일 전송·빌드·별도 검사를 하지 않았습니다. 두 회차 종료 뒤 자료를 회수했습니다.

다음은 시작 후 60초부터 종료 1초 전까지의 수신 콜백→디코딩입니다. PLC 등은 이 구간의 약 1초 표본 차이입니다. 입→귀 전체 지연이 아닙니다.

| 수신 측·정책 | P50 / P95 | PLC / 늦은 패킷 | 재버퍼링 / 무음 부족 |
|---|---:|---:|---:|
| PC · 기존 | 35.15 / 41.73ms | 0ms / 0개 | 0 / 0ms |
| PC · 한 번 보류 | 29.70 / 75.92ms | 150ms / 10개 | 1 / 33.58ms |
| 노트북 · 기존 | 29.35 / 31.15ms | 10ms / 1개 | 0 / 0ms |
| 노트북 · 한 번 보류 | 24.40 / 34.52ms | 90ms / 5개 | 0 / 0ms |

회차별 네트워크 조건이 달랐습니다. 기존 회차의 후반 최대 수신 간격은 PC 40.90ms·노트북 41.50ms, 보류 회차는 PC 133.55ms·노트북 77.47ms였습니다. 순차 실측의 차이를 정책의 인과 효과로 단정하지 않습니다.

## 같은 기록에서 원인 분리

새 실제 자료 6개는 각 원래 정책으로 재생했을 때 전체 디코딩 수·PLC 수·보류 시간·늦은 패킷 수가 모두 실제 기록과 일치했습니다. 첫 관측은 빈 큐 읽기 또는 첫 10ms 패킷이었습니다. 오디오 내용과 실제 장치 출력이 일치한다는 뜻은 아닙니다. 재생 지연은 버퍼 진입→디코딩이 일어난 출력 요청 시각으로 계산하며 실제 디코딩 함수 진입 시각과 미세한 차이가 있습니다.

### 비교적 안정적인 PC 도착 기록

후반 구간의 같은 입력을 재생했습니다.

| 정책 | 진입→재생 요청 P50 / P95 | PLC / 늦은 패킷 |
|---|---:|---:|
| 기존 목표 학습 | 35.14 / 41.73ms | 0ms / 0개 |
| 고정 목표 | 25.17 / 31.72ms | 20ms / 2개 |
| 고정 목표+한 번 보류 | 26.72 / 34.52ms | 10ms / 0개 |

낮은 목표가 대기를 줄이고, 한 번 보류가 일부 늦은 도착을 받아들이는 대신 PLC 10ms를 삽입하는 절충을 확인했습니다. 노트북의 안정 기록은 기존 29.34ms와 후보 29.36ms로 중앙값 차이가 거의 없었습니다. 모든 수신 측에서 지연이 줄어드는 것은 아닙니다.

긴 공백 뒤 이미 쌓인 과거 음성을 재생하면서 꼬리 지연이 남았습니다. 동일한 입력에서 재시작 정책만 바꾸면 P95가 낮아지지만, 음성 50ms를 실제로 생략합니다. 따라서 손실 없는 개선으로 표현하지 않습니다. 네트워크의 공백 자체는 여전히 남고 재버퍼링도 1회입니다.

## 최신 큐 재시작 후보의 실제 통화

00:25:42~00:27:47 KST에 추가로 약 120초 통화했습니다. 후반 구간의 PC 수신→디코딩 P50/P95는 29.33/40.36ms, 노트북은 32.84/41.71ms였습니다. PLC는 PC 190ms·늦은 패킷 13개, 노트북 60ms·늦은 패킷 0개였습니다. PC는 후반 재버퍼링 1회가 있었으며, 전체 회차에서 회복을 위해 PC 음성 90ms·노트북 음성 30ms를 의도적으로 생략했습니다.

이 회차의 같은 PC 도착 기록을 재생하면, 보류만 적용한 P95 85.09ms가 최신 큐 재시작을 추가했을 때 40.36ms가 됩니다. PLC 190ms·늦은 패킷 13개는 같습니다. 한편 노트북은 같은 입력에서 기존 정책 중앙값 31.68ms가 후보 32.83ms보다 낮았습니다. 따라서 모든 환경에서 더 빠르다고 보장하지 않습니다.

**기본값은 유지합니다.** 짧은 지연에는 한 번의 보류, 긴 공백 뒤에는 최신 큐 재시작이 도움이 되는 사례를 확인했지만 실제 손실·음성 생략·지연 사이의 절충이 남습니다. 다음 검증은 같은 입력에서 보류 횟수와 생략량을 제한하면서 장시간 통화·주관적 음질까지 확인하는 것입니다.

## 검증 범위와 사용법

- 경고·오류 없는 빌드, 기존 회귀와 서버 7개, 실제 ICE/DTLS/SRTP·RTCP 통합 검사를 통과했습니다.
- 72조건×3정책, 총 216개 가상 검사에서 출력 크기 5/10/20/40ms, 시작 위상 0/3/7ms, ±200ppm 클록 차이, 30ms 정지 유무를 비교했습니다. 규칙적인 입력은 세 정책 모두 PLC·부족 없이 진행했습니다.
- 짧은 지연 패킷을 보존하는지, 뒤 패킷이 있는 손실은 기존처럼 넘기는지, 긴 공백은 60ms PLC에서 재버퍼링하는지 검사했습니다. 회복 시 60ms를 생략하고 20ms 큐를 유지하는 합성 사례와 최초 시작을 정리하지 않는 사례도 검사했습니다.
- 잘린 자료·다른 프레임 길이·잘못된 입력·0 길이 출력·순서가 모호한 시각·원본 덮어쓰기는 재생 도구에서 거부합니다.

```powershell
./native/verify.ps1 -NoRestore -Integration -Stress

# 각 PC에서 같은 방, 같은 모드; 역할은 pc / laptop
# MODE: learned, fixed, transient, fresh
./native/TransportProbe/bin/Release/net10.0-windows10.0.19041.0/TransportProbe.exe --playout-target-probe https://qlrpal.ddns.net/ UNIQUE_ROOM OUTPUT.json pc fresh

./native/TransportProbe/bin/Release/net10.0-windows10.0.19041.0/TransportProbe.exe --playout-replay INPUT.json OUTPUT.json
python native/TransportProbe/Analysis/analyze_playout_deadlines.py SUMMARY.json PC.json LAPTOP.json
```
