# EXTREME-086: 시계 편차 보정 A/B와 혼합 패킷 용량 수정

2026-10-23. 지연 우선이라는 목적에 맞춰 기존 모드를 대조군으로 두고 큐 대기·PLC·폐기를 함께 평가했다. 원본 진단·dist·서버·OS 설정은 유지했다. 실제 친구 환경 전체 해결 여부는 미확정이다.

## 채택1: 실제 패킷 단위에 맞는 큐 용량

새 `forced-transitions-488` 대조에서2.5→5→10→5ms 전환과488샘플 출력 요청을 조합했다. 기존 용량 계산은 과거 최솟값인PLC 단위2.5ms에 의존하고,출력 위상 보호 여유를 용량에 반영하지 않았다. 마지막5ms 전환 뒤 시작에 필요한 정상 패킷 묶음을 수용하지 못해 정리·재시작이 반복됐다.

용량 계산에 현재 실제 패킷 길이와PhaseReserve를 반영했다. 설정 여유를 일괄 증가시키는 방식이 아니며 요청·패킷 반올림 분량을 수용한다. 수정 전300초 합성에서 공급 부족약210012.83ms였던 조건이 수정 후0ms였다. 새 기본 회귀는488샘플 요청과2.5→10→5ms 전환 후 초기1초를 제외한 공급 부족 증가0을 검사한다. 실제083의 동일 원인 확정이 아니라 재현 가능한 앱 문제의 수정이다.

## 채택2: 제한된 RTP 시계 추정

큐 높이를 더 민감하게 추종하는 후보는 폐기·부족을 늘려 제거했다. 최종 변경은 원격RTP 진행량과 로컬 요청 샘플 수의 기울기를 고정 크기320점 저장소로 추정한다. 약100ms마다 관측하고1초마다 회귀하며 최소12초 관측이 필요하다. 호스트 간 절대 시각을 비교하지 않고 발진기 자체를 측정했다고 표현하지 않는다. 피팅 잔차10ms RMS 초과 또는 추정 기울기 차이0.3% 초과를 거부하고,추가 속도 편향은±1000ppm으로 제한한다. 기존 전체 속도 보정 안전 범위는 유지한다.

과도한 일반화를 막기 위해 실제 적용 조건을 제한했다.

- `FineClock:true`인 적응형 짧은 여유Opus 실험.
- 최근 패킷2.5ms이며 최근1초의 출력 요청 크기가 안정적이고,도착 묶음보다 크면서 정확한 배수가 아닌 조건.
- 부족·PLC·정리 이후 최소5초가 지났고 추정 편차 절댓값100ppm 이상.

조건이 맞지 않으면 새 편향을0으로 둔다.5/10ms 패킷이나 가변 출력에는 이번 후보를 일반 적용하지 않았다. 원격RTP 타임라인 초기화 때 추정기를 초기화한다. 진단의 `RtpClockBiasPpm`은 추정치이고 실제 적용 보정량은 `RateCorrectionPpm`을 함께 확인한다. `RtpClockFitReady`는 피팅 준비 상태이지 적용 조건 전체의 충족을 뜻하지 않는다.

`opus-adaptive`, `opus-auto-frames`에 FineClock을 켰다. 기본 실행·기존 안정 모드·별도5ms 대조 프리셋은 유지한다. 실행 명령은 바뀌지 않는다.

## 시계 보정만의 A/B

양쪽 모두 패킷 용량 수정을 적용한 상태에서FineClock false/true를 비교했다.각50개 조건·각300초다.약10.17ms 출력,2.5ms 송신/자동 모드의 결과:

| 조건 | 기준→채택 |
| --- | ---: |
| -200ppm·PLC 합계 |60→5ms|
| +200ppm·복구 폐기 합계 |69.5→17ms|
| -200ppm·큐 중앙값/P95 |11.271/18.292→11.646/18.833ms|
| +200ppm·큐 중앙값/P95 |13.667/20.500→13.792/20.938ms|
| 정상10ms·큐 중앙값/P95 |5/5→5/5ms|

PLC 감소와 맞바꾼 큐 P95 차이는 최대약0.55ms였다. 따라서 모든 조건에서 큐 대기까지 정확히 감소했다고 주장하지 않는다. 이는500ms 표본의 소프트웨어 큐 통계이며 실제 입→귀 측정이 아니다. 고정 버퍼를 늘린 결과와도 구분한다.

50개 전 조건에서 선언된 회귀 기준을 통과했다.가변 출력±500ppm은 이번 추가 보정을 적용하지 않아085에서 기록한 소량의PLC/폐기가 남는다.자동 프레임 전환도 모든 재정렬 조건에서 고정2.5ms보다 우월하지 않아 기본 실행으로 승격하지 않는다.지연과 연속성을 함께 평가한다는 기존 원칙을 유지한다.
