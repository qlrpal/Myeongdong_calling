# EXTREME-149 — 중단 후 복구·검사기 실장치 검증

2026-11-03 · `codex/extreme-latency` / HEAD `e8a140b` 기반. 아래는 재개 후 실제 결과다. 새 지연 제어 후보를 채택한 작업이 아니라 검사 도구의 검증과 남은 품질 범위 확인이다.

## 구조·실제 변경

제품은10ms/native Opus LowDelay64/고정 수신20ms/WASAPI 공유 모드·직접 우선/TURN 대체를 유지한다. 실제 출력 주기5ms 이상에서 추가 여유3ms, 그 미만5ms와 장치 용량 상한을 적용하는 기존144 정책도 유지한다. 기각한 PI/일회성 정착/5ms 후보는 활성 소스에서 제거된 상태다.

- `PairFunctionalProbe.RunAsync`: 최대3600초,300초 초과1Hz baseline 표본,2~60초 명시적 정착과 전후 진단을 지원한다. 일반 앱의 시작 지연을 늘리는 설정이 아니다.
- `Runner/pair-checks.mjs`, `check-runner.mjs`: `--warmup-seconds`를 검증해 자식 프로세스에만 전달한다. 부모 환경을 바꾸지 않는다. 보고서 병합/동일 프레임 분석은 한쪽만 있거나 다른 비교 메타데이터를 거부한다.
- `RenderPresentationProbe`: 출력 소진 또는 공급 중 소진이 있으면 장치 시계 대응을 거부한다. 정상 시계만으로 소진 이후 PCM 인덱스 대응을 신뢰하지 않는다.
- `WarmupTransferChecks`:48조건의 기존 워밍업/처음부터 낮은 패딩 재고 산술을 제공한다. 원하는 초기 패딩 대조는 제품 정책으로 채택하지 않았다.
- `TwoHostGroupProbe.RunAsync`, `Program`: 기존 실험 프리셋 그룹 명령과 별개로 기본10ms/수신20ms 명령을 추가했다. 매 표본에서 실제 정책을 확인하며 빌드·음원·호스트 식별자 해시를 남긴다.
- `analyze_group_probe.py`: 기존 첫10초 제외 지연/품질과 전체 저장 표본 구간 품질·입력/앱 부분PCM 폐기를 분리한다. 과거 미측정 항목은null로 남긴다.

## 빌드·회귀·실제1:1

`verify.ps1 -NoRestore -Integration -Stress` 전체가 경고/오류0으로 통과했다. 로컬 실제UDP/SRTP·가변 Opus 프레임·IPv6·서버/실행기·제품/UI·오디오/복구/측정 회귀 및 워밍업48조건을 포함한다. 의도적 손실/지연 교란 검사는 각 검사 기준의 bounds/progress 합격이며 PLC0이나 실제 환경 무끊김 합격이 아니다. Python 분석13개와 그룹 분석 자체 검사도 통과했다.

새 실행기로 두PC 직접45초·음소거·재참가·정리를 완료했다. 부모 환경의 정착59초보다 명령줄2초가 우선 적용된 것을 양쪽 보고서로 확인했다. 실제 출력 주기는 PC2.667ms/노트북10ms, 목표 패딩5.833/13ms였다. 품질 카운터의 최종 전체 판정은 각 summary 원본에 보존한다.

## 판정과 미해결

채택한 것은 검사 도구·보고서 신뢰성 보완이다. 새 제품 지연 제어/프레임·버퍼 기본값은 추가하지 않았다. 기존3ms 출력 정책을 유지하되 전체 환경의 안정화나 새로운 물리 입→귀 단축은 선언하지 않는다.

남은 문제는 집중 다인 부하의 PC 출력 마감 실패, 일부PLC·송신 큐 폐기, 노트북 입력 불연속/앱 부분PCM폐기다. 관리형 할당은 크지만 SDK/진단/렌더/전송 중 어느 경로가 얼마를 차지하는지 상위 스택이 미계측이다. 이전100에서 기각한 전용 송신을 그대로 기본값으로 바꾸지 않는다. 후속 비교를 한다면 같은 정상10ms·같은 큐 정책에서 송신 스케줄링만 분리하고, 할당도 먼저 프로파일링한다. 단일 출력 구조의 비교 역시 같은 프레임/여유에서 별도로 해야 한다.

148의 원래TURN A2는 여전히 실패 회차다. 보고서 회수와 원본 복구는 완료했지만 원인 확정·동일 연속 A/B/A 완료로 바꾸지 않는다. 실제 게임·물리 입→귀·외부 친구/독립 회선·독립6대PC·물리 장치 탈착은 미실시다.
