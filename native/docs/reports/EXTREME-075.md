# EXTREME-075 — 두 AP의 실제 2.4GHz 대조

## 가설·승인·준비

073의 대역 교란을 줄이기 위해 사용자가 핫스팟을 2.4GHz로 변경했다. 새 검색으로 SSID의 실제 2.4GHz 채널 1·WPA3-Personal을 확인했다. 기존 AP는 2.4GHz 채널 5·WPA-Personal이다. 074의 추가 5GHz 대조는 실행하지 않는다. 사용자가 연결 전환을 자율 진행하도록 허용한 기존 AP→핫스팟→기존 AP 각 180초 범위에서 실제 대역을 확인해 새로 측정한다.

073 A2도 사용자의 핫스팟 대역 변경과 겹쳐 주변 RF 조건이 고정되지 않았다. 이를 새 A1로 재활용하지 않고 전체 3단계를 새 출력에 측정한다. AP 전환 시 Windows DHCP/IP 자동 변경만 사용하며 source/interface를 각 단계 다시 확인한다. 휴대폰 단계에서 오래된 홈 IP가 남아 있으면 측정을 시작하지 않는다. 실제 2.4GHz가 아니면 중단·복구한다.

예상 관측과 배제 범위는 073과 같다. 대역은 맞췄지만 보안·채널·RSSI·연결 상태 초기화·응답 구현은 여전히 다르다. 두 AP는 같은 장소의 무선 매체·주변 간섭과 PC/NIC를 공유한다. 따라서 핫스팟에서도 지연되면 기존 AP 통과가 필수 조건이라는 설명은 약해지나 PC 하드웨어 단독 확정은 아니다. 핫스팟에서 개선되더라도 AP 펌웨어 고장으로 확정하지 않는다.

## 측정

073과 같은 두 NIC 고정 source/IP_UNICAST_IF, 게이트웨이 CHAOS DNS·ICMP 5Hz·OCI/공개 STUN·자체 echo·자체 OCI 제한 부하를 사용한다. 각 180초 교집합의 첫 5초·끝 2초를 제외한다. 분석은 분포·미응답·초과 빈도와 동시 이더넷 대조를 함께 기록한다. 서로 다른 RCode/응답 구현과 DNS 내부 전달 가능성을 구분하며 ICMP를 음성 지연으로 바꾸지 않는다.

PC에서 변경하는 변수는 승인된 AP 접속뿐이다. 보안·드라이버·전원·공유기·라우팅 수동 수정·배포본 변경은 없다. 원래 메인 2.4GHz 프로필/BSSID/IP로 복구하고 고급 속성 전후 동일 및 시험 프로세스 종료를 확인한다. 원시 자료/개인 스크립트는 Git 제외 `native/.local/extreme-075/`에 보존한다.

## 결과

세 단계 각 180초를 완료했다. 실제 연결은 A1/A2가 메인 AP의 채널 5·WPA-Personal, B가 핫스팟 채널 1·WPA3-Personal이었다. 같은 Realtek 8852CE, source/interface 20을 유지했고 B의 DHCP 주소는 10.37.0.172, 게이트웨이는 10.37.0.215였다. A1/A2는 .31→.254다. RSSI는 A1 약 −51 / B −32 / A2 −50dBm으로 신호와 보안까지 동일한 시험은 아니다.

| Wi-Fi 경로 | 게이트웨이 UDP P50 / P95 / 최대 | UDP >30ms / 응답 | 게이트웨이 ICMP P50 / P95 / 최대 | ICMP >30ms / 응답 |
|---|---:|---:|---:|---:|
| A1 메인 AP 2.4GHz | 1.17 / 8.95 / 69.46ms | 35 / 5,574 | 1.54 / 8.78 / 35.02ms | 4 / 854 |
| B 핫스팟 2.4GHz | 3.49 / 19.64 / 100.23ms | 114 / 5,606 | 2.66 / 17.46 / 62.06ms | 9 / 854 |
| A2 메인 AP 2.4GHz | 1.16 / 10.22 / 125.03ms | 84 / 5,565 | 1.44 / 8.52 / 83.68ms | 8 / 854 |

표의 Wi-Fi DNS/ICMP는 세 단계 모두 분석 창 송신에 응답이 대응됐다. 이는 부하 스트림까지 모든 패킷이 무손실이라는 뜻은 아니다. 이더넷 A2의 로컬 DNS는 5,553건 중 5,549건만 대응됐다. 미응답을 숨기거나 ICMP 무손실로 DNS 손실을 대체하지 않는다. 자체 echo는 무선 왕복이 아니며 이번 단계별 Wi-Fi 최대는 0.51 / 0.69 / 4.37ms였다.

## 같은 시각의 경로 대조

대표 B의 ICMP 순번 220, QPC 120422.730758:

- 핫스팟 게이트웨이 ICMP 62.06ms와 독립 DNS 62.04ms, OCI 77.69ms가 같은 송신 시각 ±50ms 창에서 관측됐다.
- 같은 PC 이더넷은 게이트웨이 ICMP 3.91ms / DNS 1.70ms / OCI 11.38ms였고, Wi-Fi 자체 echo는 0.16ms였다.
- 따라서 이 사건은 특정 DNS 응답 처리만이나 PC 전체 정지만으로 설명하기 어렵다. 홈 공유기를 IP 경로로 거치지 않는 핫스팟에서도 로컬 지연이 발생했다.

B의 DNS 최대 100.23ms 사건(QPC 120552.358458)은 같은 창의 OCI 142.48ms, 이더넷 DNS 1.70ms / OCI 10.49ms와 대응했다. 해당 창에는 Wi-Fi ICMP 송신 표본이 없어 ICMP도 100ms였다고 추정하지 않는다. 반대로 A2 DNS 최대 125.03ms 창의 Wi-Fi ICMP는 0.94ms였다. 서로 다른 패킷의 송신 시각이 ±50ms 안에 있다는 이유로 모든 프로토콜이 항상 같은 장애를 경험했다고 주장하지 않는다.

이더넷 A2에서도 DNS 최대 114.76ms / OCI 238.96ms / ICMP 103.11ms가 각각 관측됐다. 서로의 최대값 시각이 동일하다는 뜻은 아니다. 이들을 Wi-Fi 단독 사건과 섞지 않으며, 모든 지연이 Realtek Wi-Fi 하나에서 생긴다고 판정하지 않는다. 자세한 패킷별 창은 `episodes.json`, 전체 분포와 미응답은 `summary.json`에 보존했다.

## 판정과 한계

핫스팟으로 바꿔 로컬 대기가 사라지고 원복하면 다시 나타나는 개선 패턴은 확인되지 않았다. 이번 조건에서 B의 로컬 P95와 초과 빈도는 A보다 오히려 높았지만, 이것을 휴대폰 AP 하드웨어의 성능 순위로 일반화하지 않는다. DNS 응답은 A의 NOTIMP(4)와 B의 NOERROR(0)로 다르고, ICMP 응답 구현·보안·RSSI·주변 간섭도 다르다. 특히 AP 두 개는 같은 위치의 RF 환경을 공유한다.

확정할 수 있는 범위는 **홈 공유기를 통과하지 않는 별도 AP 경로에서도 로컬 지연이 재현됐다**는 것이다. 홈 AP 단독 원인 설명은 약해졌다. 남은 후보는 PC의 공통 무선 NIC/드라이버/펌웨어, 공통 무선 환경, 또는 두 AP 각각의 대기다. 이번에는 NIC/DPC를 동시 기록하지 않았으므로 071/072의 소프트웨어 경계 측정을 새 사건에 소급 적용하지 않는다. 앱/Opus/WebRTC 없는 대조이며 전체 음성 지연이나 통화 연속성 판정이 아니다. **최종 물리 원인 규명 완료가 아니다.**

외부 OCI 중앙값은 A1 10.20 / B 41.78 / A2 10.13ms였다. B의 이동통신망이 달라 외부 RTT를 AP 효과로 계산하지 않았다. 각 180초·한 차례 A/B/A와 실제 관측 부하의 제한도 남는다. 통계 표본을 독립 장애 횟수로 취급하지 않는다.

## 복구·검증·다음 조건

- 최종 결과 오류 없음·`restored=true`. 원래 메인 2.4GHz의 동일 BSSID / .31로 복구했고, 고급 속성 전후 동일을 확인했다. 073도 동일하게 복구됐다. 실제 BSSID는 로컬 원본에 보존한다.
- 양 실험의 모든 native source와 선택 interface 주소 일치, 모든 stream reader 오류 없음 확인. 분석기에서 Windows 기본 인코딩으로 한국어 이더넷 label을 읽지 못한 검증 시도는 UTF-8 명시로 다시 검증했다. 성능 시험 실패와 섞지 않는다.
- TransportProbe 실행 없음, 고정 시험 포트 없음, WPR 기록 없음 확인. 앱·배포본·공유기·보안·전원·라우팅 수동 변경 없음. 휴대폰의 2.4GHz 선택은 사용자가 직접 한 설정이며 임의로 5GHz로 되돌리지 않는다.
- 남은 NIC 구분에는 다른 클라이언트/다른 어댑터가 필요하다. 기존 노트북 SSH는 접근 가능하고 메인 2.4GHz·핫스팟 프로필도 저장돼 있었다. 읽기 전용 CIM 조회에서 Intel Wi-Fi 6 AX201 160MHz / ifIndex13 / .30을 확인했다. 다만 `WlanQueryInterface`가 Windows 위치 권한 때문에 오류 5로 현재 AP 조회를 거부했다. 이 권한이나 새 AP 연결을 임의 변경하지 않았다. 사용자에게 원래 SSID 확인 후 메인2.4GHz 연결 확인을 요청했다. 다음 동시 대조는 실제 노트북 연결 AP를 사용자 확인 또는 승인된 방법으로 검증한 후 진행한다. 다른 PC 비교는 동일 PC의 NIC만 교체하는 엄밀한 대조와는 구분한다.
