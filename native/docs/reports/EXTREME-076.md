# EXTREME-076 — 같은 메인 AP의 Realtek·Intel 동시 대조

## 가설과 승인 범위

075에서 휴대폰 AP에서도 PC의 로컬 지연이 나타났다. 이번에는 같은 메인 2.4GHz AP에서 PC Realtek 8852CE와 노트북 Intel AX201을 동시에 관측한다. Realtek 전용 현상인지, 다른 클라이언트에서도 나타나는지 확인하는 대조다. 사용자가 노트북의 `main-2g-profile` 연결 완료를 확인했고, 시험 후 원래 `original-mesh-profile` 복구를 승인했다.

예상 관측: PC만 지연되면 PC 클라이언트 분기 후보가 강해지고, 두 클라이언트가 함께 지연되면 공통 AP/무선 환경 후보가 강해진다. 다만 본체·위치·OS·드라이버가 함께 다르므로 같은 PC의 NIC만 교체하는 단일 변수 인과 시험은 아니다. 어느 결과도 특정 NIC 고장이나 AP 큐를 확정하지 않는다.

## 방법과 실제 유효 시간

- 같은 GatewayProbe 바이너리로 명시적 source/IP_UNICAST_IF의 게이트웨이 UDP CHAOS DNS·자체 nonce ICMP를 기록했다. PC Wi-Fi `.31`/20, 노트북 `.30`/13, PC Ethernet `.88`/23. Ethernet은 버디와 무선 백홀을 거치는 경로이며 직결 유선이 아니다.
- 별도 TransportProbe의 자체 echo·OCI/외부 STUN·제한 부하를 함께 실행했다. 자체 echo는 LAN 왕복이 아니다. 부하 요청 400Hz는 실제 속도 보장이 아니며 공통 구간 실제 약335~336pps였다. 세 경로 부하가 함께 있는 조건이므로 무부하 일반 성능으로 확대하지 않는다.
- 모든 경로의 source/interface 일치, 수신 reader 오류 없음, 대응 응답 중복 없음 확인. GatewayProbe Release 빌드 경고/오류 0. 사전 fixture에서 잘못된 DNS 질문·clock nonce 거부와 정상 응답·ICMP 왕복을 검증했다.
- 첫 PC `paired` 실행 동안 노트북의 여러 줄 명령 전달이 완료되지 않았다. 이 자료는 예비/비동시 실행으로 보존하고 동시 대조에 사용하지 않았다. 노트북 스크립트를 파일로 다시 전달한 뒤 노트북 `paired`와 PC `paired2`가 각각 180초 측정됐다.
- 시작 오차 때문에 **180초 전체 동시 시험은 달성하지 못했다.** 실제 자료 교집합의 앞5초·뒤2초를 제외한 **138.5289초**만 아래 표에 사용했다. PC QPC 분석 창은122837.445346~122975.974230이다. 노트북은18:59:09, PC는18:59:30에 결과가 생성됐다. 결과 회수 전송은 노트북 시험 종료 뒤여서 공통 분석 창에 포함되지 않는다.

서로 다른 QPC 원점을 직접 빼지 않았다. UDP 네 시각 교환에서 `remoteSent-localReceived ≤ offset ≤ remoteReceived-localSent`를 구하고, 가까운 ±10초 교환 중 폭이 가장 작은 표본으로 대응했다. 대칭 지연을 가정하지 않는다. 보고서에 저장한10초 간격 대표 표본의 반폭은0.871~1.088ms, 중앙 offset 변화는 약1.14ms였다. 이 반폭은 **교환 시각의 범위**이며 다른 시각까지의 엄밀한 드리프트 상한은 아니다. 패킷별 교차 비교는 약±50ms 창과 추정 오차를 사용하고 정밀 단방향 지연이나 물리 송수신 시각으로 해석하지 않는다. PC clock 전체725/890 응답에는 노트북 종료 후 구간이 섞여 있으므로 이를 공통 구간 손실률로 사용하지 않는다.

- QPC122866.546776 부근: PC DNS51.35 / OCI58.89ms, 노트북 DNS43.21 / OCI53.00ms. PC 자체echo0.20 / 노트북0.45ms, 버디 경로 DNS21.43 / OCI27.74ms였다. 두 Wi-Fi 클라이언트에서 같은 창에 대기가 나타났다. 같은 창 ICMP는 PC4.35 / 노트북3.58ms라서 모든 패킷이 같은 지연을 겪었다고 주장하지 않는다.

## 배제 범위와 남은 한계

**Realtek 전용 결함 하나로 모든 로컬 지연을 설명하는 가설은 약해졌다.** 다른 Intel 클라이언트에서도 로컬 지연이 있었고 공통 창도 관측됐다. 반대로 두 클라이언트가 항상 같이 지연된 것은 아니어서 AP 전체 정지 하나로 모든 사건을 설명하지도 못한다. 앱/코덱/오디오 큐 없는 합성 시험이므로 음성 처리만의 문제로 설명할 수 없다.

이번 새 사건에는 Pktmon/DPC/ISR 캡처가 없어 071/072의 소프트웨어 NIC 경계 귀속을 소급하지 않는다. AP 신뢰 가능한 재전송·채널 점유·큐 통계는 **측정 불가**, 물리 RF 송수신 시각도 없다. 절전 서비스 주기·무선 경쟁/재시도·클라이언트 큐·AP 큐 중 직접 원인은 아직 확정하지 못했다. 핫스팟 대조075와 이번 교차 클라이언트 대조를 합쳐도 공통 RF 환경과 장치별 독립 대기를 물리적으로 분리한 것은 아니다.

다음 인과 대조에는 같은 PC에서 다른 물리 Wi-Fi 어댑터를 쓰거나, 신뢰 가능한 모니터링 장비/AP의 MAC 재시도·절전·큐 계측이 필요하다. 같은 ping/기존 무효 설정 대조를 반복해 이 한계를 해결했다고 주장하지 않는다. 신규 장비·채널·절전 설정 대조는 구체적인 변수·반증 조건·복구안과 별도 승인 후 진행한다. 직결 유선은 불가능하므로 재요청하지 않는다.

## 종료와 복구

PC 진단 성공 종료, 원래 메인2.4GHz BSSID/channel5 유지, GatewayProbe/TransportProbe 및 고정 시험 포트 없음 확인. 노트북의 측정 자체는 성공했고 reader 오류가 없었지만, 자동 복구는 Windows 위치 권한 제한 `WlanGetAvailableNetworkList` 오류5로 거부됐다. 이 실패는 `paired-result.json`에 그대로 보존했다. 위치 권한을 변경하거나 우회하지 않았다.

사용자가 원래 메시로 수동 복구했다고 확인했다. 이후 SSH 재접속으로 WLAN8001 **record4791 / 2026-10-22T10:01:06.3167129Z**의 ProfileName/SSID `original-mesh-profile`를 확인했다. 노트북 시험 프로세스와42420/42600~42603 포트도 없었다. 연결 이벤트는 SSID 복구 근거이며 보호된 BSSID 실시간 조회를 대신한 물리 AP 확정 자료는 아니다.

공유기·드라이버·전원·보안·시스템 라우팅·제품 음성 코드·`native/dist` 변경 없음. Git commit/push 없음. 최종 원인 규명 또는 안정판 승격 판정이 아니다.
