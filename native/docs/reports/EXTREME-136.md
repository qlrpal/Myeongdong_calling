# EXTREME-136 — ASIX 유선 기준선과 PC 경로 A/B/A

2026-11-01 / 기반 HEAD `baadb47`와 기존129–135 소스 변경. 사용자 제공 USB 유선랜·케이블을 사용해 **실제 독립 두 Windows PC의 동일 버디 LAN측 유선 기준선**을 확보했다. 제품 코드/정책 변경, 커밋·푸시·릴리즈는 하지 않았다.

## 연결과 가설

노트북 ASIX 어댑터는1Gbps Up, Intel Wi-Fi는Disconnected였다. 노트북에서 읽은 현재 ASIX 드라이버는3.22.3.0이며 시험 중 드라이버를 바꾸지 않았다. 앞서 채팅에 제시된1.18.19.1128과 같은 호스트/시점의 값이라고 가정하지 않는다. PC 이더넷도1Gbps, PC Wi-Fi는 이미 연결된 메인 AP의5GHz/channel161/802.11ax였다. 사용자가 두 랜선을 **같은 메시 버디의 LAN 포트**에 연결했다고 확인했다.

가설은 PC의 기존 Wi-Fi 경로를 제외하면 이번 통화의 왕복/도착 변동과 PLC가 낮아지는지다. A1/A2는 양쪽 유선, B는 노트북 유선을 유지하고 PC 시험 소켓만 이미 연결된 Wi-Fi 주소로 지정했다. OS 라우팅·VPN·SSID·장치/전원·드라이버·AP 설정을 바꾸지 않았다. 모든 기준선 표본의 실제 후보 양쪽 끝점과 소켓 인터페이스를 검증해 유선/무선 주소가 선택됐으며 Tailscale 주소가 미디어에 선택되지 않았음을 확인했다.

이 대조는 **PC 경로 전체의 대조**다. PC Wi-Fi→메인 AP→버디와 버디 LAN측 경로는 물리 경로도 달라지므로 Wi-Fi 칩셋/무선/백홀/AP 중 하나만 바뀐 시험으로 해석하지 않는다. 버디 내부의 실제 전달/무선 프레임 시각은 측정하지 않았다. 메인 공유기 직결 시험이나 모든 하위 구간의 물리 분리 완료라고 표시하지 않는다.

## 실제 통화 조건

최신135 블록 PCM 경로, 기본 수정 SDK `udp1-turn1-rtp0`, 네이티브 Opus LowDelay64/48kHz mono/10ms, 수신 여유20ms, 기존 상대별 WASAPI 공유 출력으로 고정했다. 같은 앱/검사기/합성 입력 해시, 각45초 기준선의 상세 기록과 양쪽6기능/입퇴장·재참가·정리를 완료했다. 세 실행의 별도 pair merge도 모두pass였다. 합성 음성을 실제 캡처 콜백에서 공급한 시험이며 물리 마이크 음향·청감·입→귀 측정은 아니다.

실제 캡처 주기 PC10ms/노트북5.333ms, 출력 주기2.667/10ms, 목표 패딩5.833/15ms, 출력 용량5.833/22ms는 세 실행에서 같았다. 앱 DLL SHA256은 `E0FCAE384EE5B2D964FA697395D6D46610B9A2495F8FB60B40E499691132F5BD`, 검사기 `6F57B7EB941CF68E4B5442631867089D78DB0174DFA5D295394D1F3EA1A011AD`로 양쪽 일치했다.135의 코드 최적화 전/후 성능 대조가 아니므로 이번 결과로 그 처리 비용 감소율을 실제 기기에서 재입증했다고 하지 않는다.

모두 기준선의 재버퍼·송신 폐기·출력 부족/소진·안전 출력 전환·늦은 패킷·중복·유효성 거부0이었다. PLC는 정상 창을 고르지 않은 첫/마지막 진단 표본의 차이다. 노트북 A1의 캡처 불연속2회는 별도 남은 관측이며 무손실/무오류 전체 합격이라고 숨기지 않는다.

RTT는250ms마다 반복된 같은 값을 독립 보고로 세지 않았다. 보고 나이가 감소한 새 값만 취하고 보고 시각이 기준선 시작10초 이후인 것의 중앙값이다. 해당 표본 수는 PC7/7/6개, 노트북6/7/7개로 작다. RTT는 왕복과 RTCP 처리/시각 오차를 포함하며 입→귀 지연이 아니다.

**초기 큰 RTCP 값도 존재했다.** 전체 기준선 최대는 PC33.995/34.647/33.805ms, 노트북9.464/6.396/9.931ms다. 이 중 유선 PC의 큰 값은 시작 직후 첫 보고에 있었으며 전체 음성 콜백 최대와 같지 않았다. 원인을 새 NIC나 무선으로 특정하지 않는다. 안정 구간만 보여 초기 사건을 없었던 것으로 취급하지 않는다. 전체 콜백 간격에는 정상 창 제외를 적용하지 않았다.

같은 프레임의 송신 호스트 첫 샘플→API와 수신 호스트 인증 콜백→첫 PCM 공급 기간의 샘플 가중 합은 PC→노트북42.410/48.181/46.558ms, 역방향43.531/43.892/43.087ms였다. **전송/SDK와 실제 장치 출력이 빠진 내부 기간 합**이며 입→귀 지연이 아니다. 같은 유선 A1/A2에도 시작/렌더 위상 차이가 있어 약4ms 차이가 남는다. 이 수치 차이를 전부 무선 편도 지연 또는135 코드의 이득으로 해석하지 않는다.

## 오디오를 제외한 유선 UDP

통화와 결과 전송이 끝난 뒤 양쪽 유선 주소/인터페이스를 지정하고 각각64바이트·100pps·60초의 기존 `--udp-bound` 도구를 실행했다. 오디오/코덱/WebRTC를 사용하지 않는 독립 프로세스다. 송신 시간/순번과 반대편 수신 순번을 연결하고 다른 PC의 절대 QPC를 빼지 않는다. 아래는 각 송신 시작5~57초의5200개 순번이며 시작/종료 경계를 제외한다. 시작 뒤 첫 수 초에 앞선 통화 결과 분석도 있었으므로 이 구간은 정상 UDP 분포에서 제외했다.

| 방향 | 분석 구간 송신/대응 | 미관측 | 수신 간격 P95/P99/최대 | 같은 순번 쌍 수신 간격−송신 간격 최대 |
|---|---:|---:|---:|---:|
| PC→노트북 |5200 /5200|0|10.512 /10.739 /17.028ms|3.442ms|
| 노트북→PC |5200 /5200|0|10.499 /10.660 /26.827ms|16.811ms|

중복 식별자·순서 역전·잘못된 헤더/상대·오버플로는 관측되지 않았다.20ms 초과 수신 간격은0/2개,50ms 초과는양쪽0개였다. 도구는 모니터 모드나 물리 NIC 시각을 사용하지 않으므로16.811ms 증가를 네트워크만의 대기나 ASIX 내부 큐로 특정할 수 없다. 송신 API 이후와 수신 프로세스 처리까지가 섞인 관측이다. 이는 왕복 echo 측정도 아니다. 왕복 표는 위 실제 통화의 RTCP다.

전체 원본에서는 PC6000/노트북6000개 송신, 반대 수신은6000/5995개였다. 빠진 노트북 송신은 시작 경계 순번0~4였다. 동시 프로세스 시작을 보장하지 않았으므로 이를 물리 네트워크 손실로 확정하거나 전체6000개 무손실로 표시하지 않는다. 분석 구간에서만 미관측0이다.

## 결론과 남은 범위

현재 유선 구성으로 두 실제 Windows 앱의 직접 통화·재참가·진단을 검증할 수 있다. 이번 한 A/B/A에서 유선 대조의 RTT/큰 도착 간격/PLC가 PC Wi-Fi 경로보다 낮게 관측돼 유선 기준선의 가치가 확인됐다. **기존 집 환경의 모든 사건·다른 회선·친구/TURN 사건의 원인 규명을 완료한 것은 아니다.** 이번 Wi-Fi도50ms 초과 큰 사건은 없었으므로 과거100ms급 사건의 직접 재현 대조가 아니다.

유선에서도 일부 순수 UDP 간격 증가와 캡처/초기 RTCP 사건은 남았다. 반대로 버퍼를 줄여도 반드시 안전하다는 근거로 쓰지 않는다. 제품 기본값은 바꾸지 않는다. 다음 작업은 이 유선 구성을 앱 검증 기준선으로 유지하고, 필요할 때 같은 조건에서 후보 하나를 대조한다. 현재 결과만으로 모니터 모드 장비의 즉시 추가 구매를 요구하지 않는다.

게임·외부 사용자·TURN·다인·장시간·물리 입→귀·새 동시 Npcap/ETW/무선 캡처·버디 내부 전달/재전송 시각은 이번에 미실시다. 사용자가 Wi-Fi에 다시 연결하도록 요구하지 않았다. 노트북 Wi-Fi는 사용자가 준비한Disconnected 상태를 유지했다.

## 후속 원본 분석: 현재 남은 문제

사용자 요청으로 새 통화/설정 변경 없이 원본을 추가 분석했다. 첫 유선 노트북의 캡처 불연속 증가는 기준선32.853~33.108초와43.619~43.877초의 각 진단 표본 사이에 있었다. 초기 장치 준비에만 발생한 것으로 설명할 수 없다. 주변 캡처 콜백 최대 간격13.991/14.144ms, 콜백 자체 최대 실행0.134/0.147ms였다. 해당 주변 송신의 장치 보고 첫 샘플 간격 최대14.053/14.120ms에 대해 RTP 전진은480샘플(10ms), 송신 API 간격은1.939/1.833ms였다. 장치 시각/부분 프레임 초기화/실제 누락을 아직 분리하지 않았으므로 차이4ms를 실제 잃은 음성량으로 확정하지 않는다. 다만 입력 불연속과 RTP 수신 PLC는 다른 경계이며 PLC0만으로 원본 음성이 연속이었다고 판정하면 안 된다. 두 번째 유선에는 불연속 증가가 없었다.

평상시 단계의 중앙값은 두 유선 회차에서 PC 장치 보고 첫 샘플→송신 API19.107/19.116ms, 노트북20.161/18.691ms였다. PC 프레임 조립은약0.004ms, 노트북은10.489/9.772ms이며 각 개별 분포의 중앙값은 합산하지 않는다. 수신 입장→첫 PCM 공급은 PC23.177/24.382ms, 노트북20.722/24.386ms다. 반면 인코딩 중앙값은 PC0.049/0.052ms·노트북0.103/0.094ms, 송신 큐 중앙값은0.021~0.045ms였다. 정상 지연 개선의 우선 검토 대상은 작은 코덱/큐 비용보다 캡처/프레임 위상과 수신·렌더 대기다. 설정값을 무조건 낮추거나 전체 장치/음향 지연으로 치환하지 않는다.

현재 남은 항목은 (1) 위 정상 대기와 실행 간 위상 차이, (2) 간헐적 입력 불연속의 의미/앱 처리, (3) 유선 순수 UDP의 일부 수신 간격 증가, (4) 경로와 관계없이 초기 RTCP 보고가 크게 나오는 이유다. 실제 게임/장시간/물리 입→귀/외부·TURN·다인은 여전히 별도 검증 범위다. 유선 기준선으로 앱 측 후보를 먼저 대조하고, 과거 무선 물리 조사 전체를 다시 반복하지 않는다.

## 정리·복구·재현

노트북 시험 폴더의 원본을 먼저 보관하고 동일 빌드로 잠시 배치했다. 배치 후 콘솔 인코딩 출력이 실패했으나 원본을 다시 덮어쓰지 않고 배치/백업 해시를 직접 확인해 준비를 마쳤다. 최종 원본 DLL SHA256 `612914CFA7B0B871C2626C4C141E47FF8DB5FBF45370042A4F16304AFFC0A480` 일치를 검증해 복구했고 자체 활성 probe0이었다. 양쪽 유선 NIC의 종료 시점 discard/error 카운터는0이었다. 이것을 물리/무선 무손실의 증거로 확대하지 않는다. 노트북 비활성 Wi-Fi의 누적 출력 오류3은 시험 전 자료가 없어 이번 사건으로 귀속하지 않는다.

원본 JSON·격리 빌드·실행/분석/복구 스크립트는 Git 제외 `.local/extreme-136/`에 보존했다. `comparison.json`, `wired-udp-analysis.json`, 세 `*-result.json`/`*-merge.log`, `restoration.json`을 결과 입구로 사용한다. 원본에는 개인 주소/장치/닉네임이 있으므로 커밋하지 않는다. 기준 앱은135에서 검증한 빌드와 동일해 전체 정적/로컬 회귀를 다시 반복하지 않았고 이번 실제 두 PC 시험을 추가했다.

재현은 [두 PC 검사](../PAIR-CHECKS.md)와 [평상시 단계 분석](../STEADY-PIPELINE-MEASUREMENT.md)의 같은 빌드·각45초·수신 여유20ms·기존 출력으로 수행한다. A는 양쪽 유선 주소, B는 노트북 유선을 유지하고 PC의 기존 연결 Wi-Fi 주소만 시험 프로세스에 지정한다. 새 연결/OS 경로 변경을 자동화하지 않는다. 실제 선택된 후보/인터페이스와 기능 병합을 확인한 다음 결과를 비교한다.
