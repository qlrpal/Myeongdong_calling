# EXTREME-135 — PCM 시계 보정 루프의 동일 출력 최적화

2026-11-01 / 기반 HEAD `baadb47`. 기존129–134 미커밋 변경을 보존했다. **수신 Read의 처리 비용 감소를 확인해 채택했다. 물리 입→귀 지연이나 고정 대기 수 ms 감소를 입증한 변경은 아니다.**

## 현재 구조와 수정 이유

134에서 프레임 축소·시계 허용 폭 축소는 양방향 개선 근거가 없어 제외했다. 기존 RAW 캡처·최소 장치 주기 실험도 반복하지 않았다. 이번에는 수신 버퍼에서 PCM 샘플 하나를 출력할 때마다 반복하던 디코더 준비·프레임 진단·시계 모드 분기를 **이미 디코딩한 PCM 블록의 경계**로 옮겼다. 버퍼 크기·타이머·주기·소비율 제어를 바꾸지 않고 실시간 작업량만 줄이는 가설이다.

`RtpOpusPlayoutBuffer.Read`는 기존과 같은 시점에 다음 프레임을 디코딩/PLC하고 첫 실제 소비 직전에 프레임을 제출한다. 새 `PcmClockInterpolator.Render`는 현재 PCM 블록 안에서만 원래 인과적 선형 보간을 계산한다. 위상·이전/현재 샘플·페이드 상태를 보존하고, 보정률1/위상1/페이드 없음일 때는 원래 한 샘플 지연을 그대로 보존하는 블록 복사를 사용한다. 다음 프레임의 선행 디코딩이나 새 PCM 큐는 없다. Windows little-endian PCM16 출력의 기존 바이트 순서를 유지한다. 시계 보정을 끈 경로는 변경하지 않았다.

## 검증 설계

`PcmClockInterpolatorChecks`는 원래 샘플 점화식을 독립 참조로 두고 입력0/1/2/120/256/480샘플, 출력0/1/128/480샘플, 보정률0.998/1/1.01, 위상0/0.37/1/1.8, 페이드0/48/240의864조합을 비교한다. 출력 PCM과 소비/공급 수·모든 보간 상태가 일치해야 한다. 워밍업 뒤 보간 함수1만 호출의 관리형 할당0도 확인한다. 기존 `verify.ps1`의 기본 검사 목록에 넣었다.

전체 RTP 버퍼는 `RenderLoopComparison`으로 검증한다. 네이티브 Opus LowDelay64, 프레임2.5/5/10ms, 요청128/256/480샘플, 송신 시계 −200/0/+200ppm, 정상/교란 두 조건의54개 조합이다. 각 조합은30초 **합성 미디어 시간**이며 교란은 결정적인 도착 묶음·누락·중복·소스 변경을 포함하고 RTP 랩도 통과한다. 실제 기기/망/게임/실시간 장기 통화 시험으로 표시하지 않는다.

같은 검사 코드를 기존/후보의 별도 바이너리에서 실행했다. 1차 탐색 뒤 기존→후보→기존을 세 차례 반복했다. 모든 실행의54조건에서 출력 전체 PCM SHA256과 디코딩/PLC 음성시간·늦은/중복/무효·재버퍼·재동기화·소스 변경·폐기·소비/요청/부족·최종 큐·보정률이 기존과 동일했다. **기존 교란에서 있던 PLC를 없앴다는 뜻은 아니다.** 전체 반복486조건의 동등성이다. 재생 함수의 누적 경과만 측정하며 패킷 생성·입장·출력 해시·직렬화는 시간 구간 밖이다. 다른 OS 작업의 선점은 이 경과에 포함될 수 있다.

## 함께 수정한 분석 오류

134 분석기의 `PipelineRead.PlcFrames`는 누적값이 아니라 **그 읽기에서 발생한 PLC 개수**였다. 이전 읽기보다 증가한 경우만 제외하면 연속 PLC 읽기를 놓칠 수 있어, 현재 읽기의 값이 양수인 모든 구간을 제외하도록 수정하고 연속1/1/2/1 회귀를 추가했다. Python 분석 검사8개를 통과했다.134의 양쪽 시계 폭3회와 프레임3회를 원본에서 재계산했으며 제외 구간 수 일부는 늘었지만 표에 실은 단계 분포와 같은 프레임 양쪽 기간 합·기각 결론은 바뀌지 않았다. 수정 계산은 `*-analysis-corrected.json`으로 원본과 함께 보존한다.

## 채택·유지·미실시

동일 PCM/동일 상태와 반복 처리 비용 감소를 근거로 블록 처리 경로를 기본 구현에 채택했다. 별도 제품 토글이나 후보 목록을 추가하지 않았다. WASAPI 공유 모드·프레임·수신 여유·시계 제어 법칙·출력 패딩·직접/TURN·SDK·네트워크/장치/전원 설정은 유지했다. 노트북/OCI에 접근하거나 설치·설정을 변경하지 않았다. 기존 dist·베타 ZIP·공개 릴리즈는 다시 만들지 않았고 커밋/푸시는 하지 않았다.

물리 입→귀 지연, 실제 두 PC 통화, 친구/다인/TURN/게임, 장시간 장치 출력 마감과 게임 프레임타임은 이번 변경으로 **미실시**다. 기존 통합 시험은 아래 검증 기록처럼 별도로 구분한다.

## 최종 회귀 기록

경고0/오류0 빌드와 BuildTools58검사, SDK 식별, 기본 오디오/복구/제품/UI 검사·서버 구문 검사를 통과했다. 최초 `verify.ps1 -NoRestore -Integration`은 서버 검사 한 개의 `fetch`가 임시 포트를 `bad port`로 거부하면서 중단됐다. 서버 코드 변경 없이 그 검사 묶음만 재실행해8/8 통과했다. 따라서 최초 전체 명령이 한 번에 통과했다고 표시하지 않는다.

이어서 실행기12검사와 LAN·10ms RTCP는 통과했다. RTP 재생 통합은 새 PCM 루프에 진입하기 전 RTCP RTT/수신 손실 보고 대기20초에서 실패했다. 원인을 최적화 또는 단순 네트워크 문제로 확정하지 않았다. 해당 검사 한 차례 재실행과 미실시 가변 프레임/IPv6를 이어 실행해 모두 통과했다. 가변 SRTP2.5/5/10ms·RTP 랩·제어된 누락/재정렬/중복을 기존 통합으로 확인했다. 실패 로그 `verify-final.log`/`verify-remaining.log`와 완료 로그 `verify-integration-retry.log`를 함께 보존한다. **최종적으로 각 구성 검사는 통과했지만 최초 실행의 두 실패는 남은 시험 불안정성으로 기록한다.**
