# 0.5.6 게임 공존 공유 입력 시험

2026-10-18, 사용자가 실행한 Monster Hunter Wilds와 PC·노트북 WebRTC 통화를 함께 실행했다. 게임 설정은 변경하지 않았다. 게임 프로세스 PID 24640은 시험 전과 두 번째 회차 도중 유지됐고 CPU 누적 시간이 증가했다. 실제 플레이 장면·프레임률·게임 소리의 청감은 자동 확인하지 않았으므로 모든 게임 부하에 대한 보증은 아니다.

동일 0.5.6 빌드로 표준 입력 → 짧은 공유 입력 순서, 각 120초씩 시험했다. 게임은 PC에서 실행했고 노트북은 통화 상대였다. 기존 저지연 공유 출력·Opus 10ms·20ms 재생 목표를 유지했다. 시험 중 빌드·파일 전송은 하지 않았다. 원본 음성은 저장하지 않았다.

## 입력 결과

첫 5초와 마지막 1초를 제외하고 송신 측의 동일 시계에서 계산했다. 아래 값은 **첫 입력 샘플 → 인코딩 시작**이며 입→귀 전체 지연이 아니다.

| 송신 장치 | 표준 P50 / P95 | 짧은 입력 우선 P50 / P95 | 실제 후보 입력 |
|---|---:|---:|---|
| 게임 PC |21.33 / 21.90ms |19.29 / 19.43ms |미지원 → 10ms 복귀 |
| 노트북 |18.70 / 20.19ms |15.59 / 21.02ms |5.333ms 공유 |

노트북 중앙값은 약 3.12ms 감소했지만 P95는 약 0.83ms 증가했다. PC는 두 회차 모두 10ms 경로이므로 회차 간 감소를 짧은 입력 구현의 효과라고 주장할 수 없다. 게임 부하와 네트워크 조건을 고정한 무작위 교차 시험은 아니다.

네 기록 모두 오류·추적 유실은 0이었다. 워밍업 이후 입력 불연속 0, 입력 시각 오류 0, 입력·출력 장치 오류 없음. 짧은 입력의 시작·중지와 PC의 미지원 복귀가 실제 통화에서 동작했다.

## 수신 재생 결과

아래 값은 각 수신 장치의 전체 회차 누적값이다. PLC는 누락 프레임 보완, 복구 폐기는 지연을 줄이려고 오래된 음성을 버린 양이다. 두 값을 원래 네트워크 패킷 손실률로 해석하지 않는다.

| 수신 장치·회차 | 무음 부족 | PLC | 복구 폐기 | 재버퍼 횟수 |
|---|---:|---:|---:|---:|
| PC · 표준 |30.90ms |150ms |40ms |1 |
| PC · 짧은 입력 우선 |0ms |140ms |20ms |0 |
| 노트북 · 표준 |31.69ms |140ms |80ms |1 |
| 노트북 · 짧은 입력 우선 |122ms |230ms |140ms |2 |

특히 두 번째 회차 노트북 수신에는 버퍼 부족이 남았다. 양쪽 입력의 불연속이 없다는 사실만으로 이 수신 문제의 원인을 입력·네트워크·출력 중 하나로 확정할 수 없다. 전체 게임 공존 안정화 완료로 표시하지 않는다.

### 후속 시각 대조: 시작 구간과 통화 중간을 분리

기존 네 기록을 추가 분석했다. 짧은 입력 회차 노트북의 122ms 부족은 첫 진단 시점 2ms에서 약 1초 뒤 122ms로 증가한 뒤 끝까지 늘지 않았다. 원시 재생 요청에서도 부족은 재생 요청 추적 시작 후 0.163–0.413초에 집중됐다. 이 회차 수신 콜백에는 시작 직후 244.19ms·140.02ms 공백이 있었다. 따라서 앞의 누적값을 통화 중 지속적인 끊김으로 읽으면 안 된다. PC 후보 회차의 누적 부족은 0ms다. 최초 재생 대기에서 `ProvidedSamples=0`인 요청은 있을 수 있으므로 원시 요청 부족을 그대로 사용자 통화 중 언더런으로 집계하지 않는다.

표준 회차의 양쪽 약 31ms 부족은 시작 약 66초 뒤 발생했다. 각 수신 시계 안에서 부족 직전부터 복구까지의 기록을 비교했다.

| 수신 측 | 수신 콜백 최대 공백 | 같은 RTP 경계의 상대 송신 완료 간격 | 주변 출력 요청 최대 간격 | 재생 잠금 최대 대기 |
|---|---:|---:|---:|---:|
| PC |131.03ms |17.09ms |10.28ms |0.0013ms |
| 노트북 |131.42ms |20.03ms |11.62ms |0.0016ms |

RTP SSRC·timestamp로 두 끝의 패킷을 대응시켰다. 표의 송신 간격은 대응하는 경계 패킷 간 송신 완료 시간 차이며 모든 중간 패킷의 정상 수신을 보장하지 않는다. 기기 시계를 직접 빼거나 단방향 전송 지연을 산출하지 않았다. 두 수신 공백이 같은 표준 회차의 비슷한 위치에 있지만 시계 동기화로 동시성을 입증한 것은 아니다.

해당 주변 0.5초 전–복구 0.1초 후에서 수신 버퍼 호출 최대 소요는 PC 0.052ms·노트북 0.009ms였다. 출력 요청은 계속 들어왔고, 큐가 소진된 뒤 PLC 최대 구간을 거쳐 무음 부족으로 이어졌다. 같은 131ms 정지가 입력 조립·상대 송신 완료·출력 요청·재생 잠금에는 나타나지 않았다. **이 중간 사건은 송신 완료 기록 이후부터 복호화된 수신 콜백 이전 구간이 우선 조사 대상**이다. 송신 API 완료는 물리 송신 시각이 아니며, NIC·Wi-Fi/AP·OS UDP 전달·복호화/스케줄링 중 어느 하나인지는 이 기록으로 구분할 수 없다.

분석 코드는 Git 제외 경로의 `underfill.py`, `match-gaps.py`이며, 부족 주변 상세 기록은 `underfill-analysis.json`이다. 이번 분석은 기존 기록만 사용했고 추가 마이크·게임 시험은 실행하지 않았다.

## 판단과 다음 작업

### 시작 조건 검토 결과

시작 조건은 압축 음성 합계가 `목표 예비량 + 현재 출력 요청량` 이상인 경우에만 첫 재생을 허용한다. 목표는 20ms이며 10ms 패킷 단위로 채워진다. 예컨대 출력 요청이 22ms이면 최소 42ms가 필요하고 실제로는 50ms 이상이 쌓여야 한다. 10ms보다 조금 큰 출력 요청은 약 30.2ms가 필요하므로 보통 40ms 이상에서 시작한다. 단순히 첫 패킷 하나를 받았다고 재생하지 않는다. 단, 이는 전체 패킷 양에 대한 조건이며 RTP의 모든 구간이 연속한다는 보장은 아니다.

| 수신 장치·회차 | 첫 재생 직전 큐 | 첫 출력 요청 | 첫 요청에 제공한 음성 | 첫 요청 PLC |
|---|---:|---:|---:|---:|
| PC · 표준 |50ms |10.15ms |10.15ms |0 |
| PC · 짧은 입력 우선 |120ms |10.17ms |10.17ms |0 |
| 노트북 · 표준 |110ms |22ms |22ms |0 |
| 노트북 · 짧은 입력 우선 |110ms |22ms |22ms |0 |

문제의 노트북 후보 회차는 첫 재생 전 25개 패킷이 도착했고, 120ms 상한에 따른 기존 큐 정리를 거쳐 110ms가 남았다. 첫 요청은 정상적으로 채웠다. 이후 시작 직후의 긴 수신 공백을 겪으며 큐 소진·PLC·재버퍼로 진행했다. 따라서 이번 사례는 시작 시 예비량 부족 때문에 즉시 실패한 경우가 아니다. 통화 시작 후 공백을 미리 예측하여 제거할 수 있다는 근거도 없다.

양쪽 송신의 각 첫 1초 기록에서 최대 송신 완료 간격은 16.21–21.56ms였고, 최대 송신 큐 대기는 0.58–7.36ms였다. 이 구간에 수신 측의 140–244ms 공백과 같은 크기의 송신 정지는 없었다. 이 결과 또한 송신 이후→수신 콜백 이전 구간을 우선 대상으로 보는 근거이며, 실제 NIC 전송 시각이나 물리 경로의 원인을 확정하지 않는다.

**결정:** 시작 목표 20ms와 현재 PLC 상한을 유지한다. 시작 대기나 PLC 상한을 늘려 공백을 가리는 변경은 하지 않는다. 첫 재생에 과거 음성이 110–120ms까지 쌓이는 별도의 지연 문제도 보이지만, 이를 덜어내면 후속 공백에 대한 여유가 줄어든다. 즉시 폐기 정책을 추가하지 않고 같은 입력을 사용한 재현 비교를 거친 뒤 판단한다. 이번 작업은 기록 분석·보고서 보완이며 제품 재생 코드는 변경하지 않았다. 분석 요약은 로컬 `startup-analysis.json`에 보관했다.

짧은 공유 입력은 지원 장치에서 중앙 지연을 줄이지만 느린 구간까지 개선하지는 않았다. 입력만 끌 수 있는 복귀 옵션을 유지한다. 기존 추적 대조에서는 통화 중간의 수신 공백과 시작 직후의 수신 공백을 확인했다. 시작 조건 검토는 완료했으며, 다음 비교 대상은 첫 재생에 쌓인 과거 음성을 줄일 때의 지연·복구 절충이다. 긴 중간 수신 공백은 송신 완료→수신 콜백 사이 문제로 별도 취급한다. 일정한 지연이 늘어나는 일괄 버퍼 확대는 이번 결과로 정당화되지 않는다.

원본 메타데이터·분석 스크립트는 Git 제외 경로 `native/.local/game-capture-056/`에 보관한다. 실행 프로세스는 시험 종료 후 자동 종료했다. 게임은 종료하지 않았다.
