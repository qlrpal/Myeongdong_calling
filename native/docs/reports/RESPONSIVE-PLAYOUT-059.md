# 자동 저지연 수신 정책 구현과 비교

2026-10-20. 개인 장치 효과와 출력 지연 조사는 이번 작업 범위에서 제외하고, 앱의 수신 대기와 공백 뒤 복구를 대상으로 삼았다. WASAPI 공유 모드와 Opus LowDelay64를 유지했다.

## 구현

재생 선택에 **자동 저지연 (시험)**을 추가했다. 기본 선택은 기존 고정 20ms 저지연 정책이다. 통화에서 나간 상태에서 새 방식을 선택할 수 있다.

- 시작과 재버퍼링 뒤에는 20ms 여유로 시작한다.
- 정상 재생이 이어지면 첫 6초 후부터 초당 1ms씩 최소 15ms까지 줄인다. PLC나 무음 채움이 발생한 시간은 정상 구간으로 계산하지 않는다.
- 빈 큐와 반복 지연 도착에 반응해 최대 30ms 범위에서 여유를 확보한다. RTP timestamp 차이를 빼서 실제 누락 구간을 지터로 잘못 계산하지 않는 기존 방식을 유지한다.
- 목표를 낮춰도 실제 큐가 오래 남지 않도록 소비율 제어의 허용 구간을 5→2.5ms, 피드백 계수를 0.1→0.25로 조정했다. 기존 소비율 안전 범위인 -0.2%~+1%는 유지한다. 하드웨어 클록 오차를 측정하거나 교정했다는 의미는 아니다.
- 연속 PLC 60ms 제한, 재시작 시 최신 예비 큐만 유지하는 기존 정책, 폐기량·무음 채움·PLC·보류량 카운터를 유지한다. 새 정책을 위해 음성을 강제로 더 버리는 동작은 추가하지 않았다.

## 같은 수신 기록 비교

이전 80초 통화의 8개 수신 기록을 그대로 재생했다. 모든 후보가 동일한 패킷 추가 순서와 장치 읽기 크기를 사용한다. 합성 10ms Opus 무음으로 재생하므로 실제 발화의 주관적 품질 시험은 아니다. 시작 5초와 끝 1초를 제외한 수신→디코딩/재생 호출 중앙값이다.

| 수신 기록 | 고정 20ms | 자동 15–30ms | PLC 증가량 |
| --- | --- | --- | --- |
| PC A1 | 35.3ms | 27.2ms | 40ms |
| 노트북 A1 | 38.9ms | 29.5ms | 50ms |
| PC A2 | 39.1ms | 33.2ms | 90ms |
| 노트북 A2 | 40.8ms | 35.4ms | 110ms |
| PC 공백 회차 | 34.7ms | 28.8ms | 30ms |
| 노트북 공백 회차 | 36.9ms | 31.6ms | 40ms |
| PC 복귀 회차 | 31.2ms | 22.0ms | 50ms |
| 노트북 복귀 회차 | 30.4ms | 29.1ms | 60ms |

약 1–9ms의 중앙값 감소가 있었지만 PLC 보완은 늘었다. 보완 중에는 뒤늦은 패킷을 살리기 위해 RTP 위치를 보류하는 PLC도 포함된다. 이를 전부 실제 패킷 손실이나 무음 끊김으로 부르지 않는다. P95는 8개 중 7개 기록에서 낮아졌고, PC 공백 회차에서는 약 50.7→56.9ms로 높아졌다.

정상 기록의 무음 채움과 재버퍼링은 두 방식 모두 0이었다. 공백 기록에서는 양쪽 모두 재버퍼링 3회였고, 무음 채움은 PC 약 159.2→156.2ms, 노트북 약 204.4→196.4ms였다. 이 작은 차이를 전체 네트워크 공백 해결로 발표하지 않는다.

## 제외한 후보

공백 뒤 20ms 이상의 PLC와 과도한 큐가 함께 있을 때 오래된 음성을 추가로 정리하는 후보는 일부 기록에서 PLC·늦은 패킷을 늘렸다. 예를 들어 노트북 A1은 약 30ms를 추가 폐기했지만 PLC가 120→170ms로 늘고 중앙값 이득도 거의 없었다. 후보 코드를 제거했다.

최소 10ms와 더 빠른 소비율 제어를 조합한 후보는 약 6–15ms를 줄였으나, 기록당 PLC가 대략 100ms 이상 추가되는 경우가 많았다. 최종 선택은 최소 15ms와 완만한 제어이며, 이 역시 선택 가능한 시험 모드로 제공한다.

## 실제 통화 대조

두 PC에서 같은 합성 음성을 반복 공급하며 기준→자동 저지연→기준의 순서로 회차당 120초씩 TURN 통화를 진행했다. 표준 10ms 공유 입력을 사용하고, 캡처 시계·인코딩·네트워크·실제 출력 요청 크기는 유지했다. 이 시험은 물리 마이크 음질이나 입→귀 지연 시험이 아니다.

첫 실행은 진단 추적 시작 누락으로 기준 회차 종료 시 불완전 추적 오류를 반환했다. 이 기록은 성능 비교에서 제외했고, 수정 후 별도 `live2` 경로로 재실행했다. 미완료 추적을 성공 자료로 사용하지 않는 검사가 해당 누락을 검출했다.

최종 세 회차는 양쪽 모두 오류·추적 누락 없이 완료했다. 시작 5초와 끝 1초를 제외한 패킷의 수신→출력 제출 분포다.

| 수신 장치·회차 | 중앙값 | P95 | PLC 전체 / 보류 PLC | 늦은 패킷 |
| --- | --- | --- | --- | --- |
| PC 기준 A1 | 29.03ms | 40.08ms | 50 / 40ms | 1개 |
| PC 자동 B | 23.05ms | 40.77ms | 150 / 140ms | 1개 |
| PC 기준 A2 | 27.52ms | 39.76ms | 40 / 30ms | 1개 |
| 노트북 기준 A1 | 23.09ms | 34.08ms | 60 / 40ms | 2개 |
| 노트북 자동 B | 26.01ms | 39.41ms | 140 / 130ms | 1개 |
| 노트북 기준 A2 | 27.32ms | 38.61ms | 70 / 40ms | 3개 |

여섯 기록 모두 앱 무음 채움 0ms, 재버퍼링 0회, 송신 큐 프레임 폐기 0개였다. 자동 회차의 실제 목표 여유는 양쪽 모두 15–25ms 범위였다. 최대 30ms 경계는 독립 검사에서 확인했다.

PC에서는 중앙값이 앞뒤 기준보다 약 4.5–6ms 낮았지만 P95는 개선되지 않았다. 노트북은 앞뒤 기준 사이 값으로 일관된 지연 감소를 확인하지 못했다. 노트북 A1은 출력 버퍼 소진 후 22ms 안전 복귀가 있었고 B/A2는 15ms 제한 공급을 유지했으므로 출력 상태 차이도 있다. 순차 회차의 네트워크 변동 때문에 모든 차이를 정책 하나에 귀속하지 않는다.

자동 모드의 PLC 증가는 대부분 RTP 위치를 전진시키지 않는 보류였다. 예를 들어 PC 자동은 150ms 중 140ms가 보류였고, 기준 A1은 50ms 중 40ms였다. 이를 실제 손실률 증가로 환산하지 않는다. 그러나 보류 중에는 합성 보완 음성을 재생하므로 주관적 음질 영향이 없다고 주장하지도 않는다.

따라서 **앱에서 선택 가능한 시험 모드로 제공하고 기본값은 바꾸지 않는다.** 180ms 전체나 물리 입→귀 지연을 이만큼 줄였다고 발표하지 않는다. 다음 검증은 같은 방식의 게임 부하·외부망·실제 발화 품질이며, 출력 장치 효과를 변경하는 작업은 하지 않았다.

## 자료와 재현

원본은 Git 제외 경로 `native/.local/recovery-policy-059/`에 있다. 초기 후보는 루트 및 `v2`, 최종 절충안의 재생 비교는 `v3`, 유효한 실제 통화 대조는 `live2`에 보관한다. 실패한 첫 실행은 `live`에 별도로 남겼다.

```powershell
TransportProbe.exe --recovery-policy-test OUTPUT.json
TransportProbe.exe --recovery-policy-replay INPUT-call.json OUTPUT.json
# 양쪽에서 같은 방 접두사, pc/laptop 역할로 실행
TransportProbe.exe --responsive-speech-ab https://qlrpal.ddns.net/ PREFIX OUTPUT_DIRECTORY ROLE speech.wav
python native/TransportProbe/Analysis/analyze_latency_budget.py DIRECTORY SUMMARY.json
```

출력 제출 이후의 장치 지연·물리 입→귀 지연 감소로 이 수치를 바꾸어 해석하지 않는다. 실제 게임 부하·외부망의 장시간 사용 및 발화 품질 검증 없이 새 방식을 기본값으로 바꾸지 않는다.

## 검증과 종료

최종 `native/verify.ps1 -NoRestore -Integration`을 통과했다. 빌드 경고·오류 0개, 새 정책 선택과 기존 적응 방식의 충돌 거절, 예비 여유 상하한·재시작·정상 구간 판단·소비율 안전 범위 검사, 기존 오디오·코덱·RTP 회귀, 서버 7개 테스트와 실제 로컬 WebRTC/RTCP/RTP 통합 검사를 통과했다.

추가한 동일 사건 합성 비교는 프레임 10/20ms, 장치 읽기 10/22ms, 정상·순서 변경·60–400ms 공백의 80개 조합이다. 정상 구간은 무음 채움·PLC가 없었다. 80ms 공백의 합산 무음 채움은 줄었지만, 일부 더 큰 공백에서는 네 장치/프레임 조합 합계가 기존보다 약 6.5ms 늘었다. 큰 네트워크 공백을 새 정책이 해결한다는 근거로 사용하지 않는다.

`git diff --check`를 통과했고 양쪽 시험 프로세스는 모두 종료했다. 개인 장치·서버 설정은 변경하지 않았다. 새 실행 파일은 Release 빌드 경로에 있으며, 배포 ZIP과 Git 커밋·푸시는 만들지 않았다.

2026-10-21의 후속 [게임 부하 비교](GAME-RESPONSIVE-059.md)에서는 정상 기록의 대기 감소와 PLC 증가를 확인했고, 첫 기준 회차의 심한 수신 공백을 자동 정책도 완전히 복구하지 못했다. 자동 모드를 기본값으로 채택하지 않았다.
