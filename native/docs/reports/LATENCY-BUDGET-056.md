# 0.5.6 지연 예산과 다음 개선 대상

2026-10-19. 게임 공존 시험의 기존 네 기록과 현재 코드를 대조했다. 추가 통화·마이크·게임 시험은 실행하지 않았다. 목표는 지연 우선, 품질 다음이며 게임 소리와 공존하는 WASAPI 공유 모드를 유지한다.

## 직접 확인한 구간

아래는 각 장치 자신의 시계에서 구한 P50 / P95(ms)다. 송신은 첫5초·끝1초, 수신은 첫 수신 이후5초·끝1초를 제외했다. 표준과 후보는 다른 회차여서 행 사이 차이를 입력 변경의 인과 효과로 단정하지 않는다. 후보 입력은 노트북5.333ms, PC 미지원→10ms 복귀다.

‘수신→제출’에는 디코딩 실행이 포함되며, 디코딩 행을 다시 더하지 않는다. 개별 구간의 분위수도 더하지 않는다. 서로 다른 장치의 시각 차이를 계산하지 않았다. 수신 지연 분포는 실제 재생된 패킷만 포함하므로 늦어 폐기한 패킷과 PLC는 별도로 평가해야 한다.

## 코드상 대기 구조

- 앱은 48kHz 모노480샘플, 10ms 프레임을 완성한 뒤 인코딩한다. 추가 주기 타이머는 없다. 첫 샘플 기준 프레임 완성 시간에는 프레임 자체를 모으는 시간과 WASAPI 전달 대기가 겹쳐 포함된다. 여기에 다시10ms를 더하지 않는다. 마지막 샘플이나 평균 샘플 기준 지연과도 다르다.
- 노트북 후보의 첫 샘플→첫 콜백은 P50 5.579ms, 첫 콜백→프레임 완성은 P50 11.117ms였다. 각각의 P50 합은 전체 P50과 같지 않다. 짧은 장치 주기가10ms 프레임 완성 주기와 맞지 않아 부분 프레임을 다음 콜백까지 기다릴 수 있다.
- 송신 큐는 최대3프레임이며 오래된 프레임을 버리는 제한 큐다. 정상 구간 실제 대기는 수십 마이크로초여서 지금 가장 큰 절감 대상은 아니다.
- 재생은 출력 요청에 따라 디코딩하며 별도40ms PCM 큐를 중첩하지 않는다. 저지연 정책의 예비 목표는20ms, 실제 요청은 PC 약10.167ms·노트북10ms다. 목표20ms가 패킷별 실제 대기20ms를 보장하지는 않는다.
- 코덱은 이번 기록에서 Baseline이다. 명시적 LowDelay64/96 프로필은 이미 선택 가능하지만 기본값은 아니다. Baseline의 `LookaheadMs`는 null이므로 보고서에서 특정 선행 대기 값을 확정하지 않는다. 인코딩 CPU 시간과 코덱 선행 대기는 서로 다른 값이다.
- 출력은 `WasapiPlayerBuilder.WithSharedMode().WithEventSync()`이며 저지연을 우선 요청한다. PC 출력 장치 형식은44.1kHz여서48kHz 음성을 WDL로 변환한다. 게임이나 장치 설정을 바꾸지 않는다.

## 우선순위 결정

1. **다음 구현 검토 대상은 WASAPI 공유 출력의 실제 버퍼·주기·프리필 구조다.** 약22ms API 보고값이 어떤 대기를 표현하는지 라이브러리 구현부터 확인하고, 지원 주기를 유지하면서 불필요한 프리필이 있는지 조사한다. 요청값40ms가 그대로 실제40ms 지연이라는 가정으로 설정을 바꾸지 않는다.44.1kHz 경로의 변환 버퍼도 함께 확인한다.
2. 출력에 제거할 불필요한 대기가 없다면10ms 프레임과 캡처 콜백의 정렬을 다음 대상으로 삼는다.5ms 프레임은 인코더·RTP timestamp·수신 검증·PLC가10ms를 전제하므로 단일 상수 변경으로 적용하지 않는다. 장치가10ms 단위로만 전달한다면 프레임 축소만으로 같은 절감이 생기는 것도 아니다.
3. CPU 인코딩 최적화와 송신 큐 교체는 후순위다. 이미 대부분1ms 미만이므로 큰 구조 변경의 근거가 약하다.

20ms 재생 목표를 낮추거나 시작 버퍼를 일괄 덜어내는 변경은 현재까지 끊김·의도 폐기 증가 위험이 확인되어 보류했다.131–244ms 수신 공백은 별도의 경로 문제이며 정상 지연을 늘려 숨기지 않는다. 이후 후보는 실제 공유 모드 유지, 같은 입력 비교, 게임 공존, P95·PLC·무음 부족·의도 폐기를 함께 확인해 적용한다.
