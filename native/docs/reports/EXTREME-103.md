# EXTREME-103 · 콜백 앞 공백의 소프트웨어 패킷 관측

2026-10-26 / `codex/extreme-latency`. EXTREME-102에서 남은 콜백 앞 경계만 조사했다. 제품 앱·SDK·코덱·프레임·버퍼·장치 주기·우선순위를 바꾸지 않았다. 변경한 공개 코드는 오프라인 분석 도구뿐이다.

## 목적과 판단 범위

같은 RTP 패킷 쌍의 수신 콜백 간격과 OS 쪽 캡처 간격을 비교한다. 긴 공백이 소프트웨어 캡처에도 이미 있으면 그 뒤 앱 콜백까지의 처리만으로 공백이 생긴 것은 아니다. 반대로 캡처 간격은 짧은데 콜백 간격만 크면 캡처 이후 배달/깨우기·SDK 구간이 후보가 된다.

캡처는 NDIS 계층의 소프트웨어 관측이다. 실제 NIC 하드웨어 도착·무선 전파·AP 내부 시각이 아니다. 입→귀 지연도 아니다. **이번 조사는 끊김 원인 범위를 줄이는 시험이며 제품 수정이나 해결 완료 선언이 아니다.**

## 먼저 제외한 관측

- I1: SSH 주소와 ICE 미디어 주소가 같다고 가정해 필터를 설정했다. 실제 미디어 주소가 달라 대상 RTP를 수집하지 못했다. 실패한 수집으로 보존하고 지연 판단에서 제외했다.
- I2: 확인한 미디어 주소로 Pktmon의 NIC 수집을 다시 수행했다. ETW 이벤트 손실0이었지만 앱 수신12026개 중 정확한 RTP 정체성이 대응한 것은4060개(33.76%)뿐이었다. 해당 trace의 late14개는 하나도 대응하지 않았다. 모든 큰 콜백 공백의 양끝도 대응하지 못했다. **부분 표본의 짧은 NIC→콜백 값으로 문제 패킷의 원인을 판정하지 않았다.**

이벤트 손실0과 패킷별 수집 완전성은 다르다. 기존의 불완전한 Pktmon NIC 수집을 같은 조건으로 더 반복하지 않고, 이미 설치돼 있던 Npcap의 독립 관측으로 전환했다. 새 드라이버는 설치하지 않았다.

## Npcap과 Pktmon 동시 관측 I3

같은 앱 빌드·직접 UDP·`opus-adaptive`·네이티브 Opus로 실제 두 PC60초 시험을 수행했다. 실제 PC 미디어 주소에 해당하는 Ethernet 인터페이스를 확인했다. Npcap은 비 promiscuous 모드, 합성 시험 상대의 UDP만, 패킷 앞128바이트, 최대100초/64MiB로 제한했다. Pktmon도 자체 필터/세션만 사용했다.

Npcap 종료는0, 강제 종료 없음, 수집52132개, 인터페이스/pcap/dumpcap/flushed 드롭은 보고상0이었다. 마지막30초 앱 수신12030개를 SSRC·RTP 타임스탬프·wire 순번·수신 UDP 포트로 모두 유일하게 대응했다. late279개도 모두 대응했다. 이는 앱에 관측된 프레임에 대한 완전한 대응이지, SDK 이전 손실이나 전체 통화 무손실의 증명은 아니다.

| 비교 | 결과 |
|---|---:|
| 30ms 초과 콜백 공백 | 49건 |
| 캡처에서 같은 양끝 패킷이 대응한 공백 | 49/49건 |
| 최대 콜백 공백 | 112.458ms |
| 그 사건의 Npcap 관측 간격 | 112.367ms |
| 그 사건의 캡처 이후 간격 증가 | 0.092ms |
| 49건의 캡처 이후 간격 증가 최솟값/최댓값 | −0.019 / 0.137ms |

49건 중45건은 공백 끝 패킷이 late였고4건은 late가 아니었다. 긴 간격 자체가 항상 같은 재생 결과를 만든다는 뜻은 아니다. 해당 사건군의 수십~100ms 공백은 **Npcap 소프트웨어 관측에도 이미 존재**했다. 관측 이후의 SDK/버퍼 처리에서 이 크기의 간격이 새로 증가했다는 결과는 아니다.

단, I3의 전체 진단 구간 PC PLC는977.5ms, 출력 부족167.02ms로 이전 반복보다 많았다. 계측 영향과 시점별 환경 변동을 분리하지 않고 이 수치만으로 코드 악화나 관측 무해성을 선언하지 않는다. 이를 확인하기 위한 대조는 아래와 같다.

## 시각을 처리한 방식

Npcap의 `host_hiprec_unsynced`를 사용했다. 공식 문서는 이 타입을 성능 카운터 기반의 단조 시각으로 설명하며, 시스템 시각과 차이가 날 수 있다고 명시한다. [Npcap 공식 API 문서](https://npcap.com/guide/npcap-api.html).

분석에서는 pcap의 epoch 시각을 앱 QPC에서 직접 빼지 않았다. 같은 두 패킷의 캡처 간격과 앱 콜백 간격을 각각 계산한 뒤 비교했다. 두 시간원의 진행률이 비교 가능하다는 가정은 남는다. 음수 차이는 따라잡기/관측 지점 차이를 숨기지 않도록 그대로 보존했다. 이 값은 절대 NIC→콜백 지연이 아니라 **간격의 증가량**이다.

오프라인 도구 `analyze_deadline_event.py --capture-intervals`는 수신 포트와 완전한 RTP 식별자로 연결하고 중복/누락된 양끝은 정확한 대응으로 취급하지 않는다. 시각 원점을 바꿔도 결과가 같고, 중복·누락을 거부하는 자체 검사를 통과했다. 원본은 변경하지 않는다.

```powershell
python ./native/TransportProbe/Analysis/analyze_deadline_event.py --self-test
python ./native/TransportProbe/Analysis/analyze_deadline_event.py --capture-intervals RECEIVE.json PCAP-RTP.csv RESULT.json
```

PCAP-RTP.csv는 동일 인터페이스 캡처를 `tshark -n`으로 읽고 실제 로컬 UDP 포트를 RTP로 해석해 생성한다. 필요한 열은 `frame.time_epoch, udp.dstport, rtp.ssrc, rtp.timestamp, rtp.seq`다. RTP version2/PT111만 사용했다. 원본 prefix·전체 진단은 Git 제외다.

## 관측 도구 영향 대조

제품/모드/경로/60초·앱 자체 마지막30초 trace는 고정하고, 추가 패킷 캡처 끔 A1 → Npcap만 켬 B → 끔 A2 순서로 수행했다. B에는 Pktmon을 켜지 않았다. 제품 지연 설정 A/B가 아니라 **계측의 영향 대조**다. 모든 앱 종료 코드는0, trace 축출은0이었다.

| 조건 / 수신 측 | 진단 구간 PLC | 출력 부족 | 마지막30초 30ms 초과 콜백 공백 / 최대 |
|---|---:|---:|---:|
| A1 끔 / PC | 460ms | 520.83ms | 9건 / 240.073ms |
| B Npcap / PC | 367.5ms | 375.08ms | 8건 / 138.662ms |
| A2 끔 / PC | 785ms | 894.27ms | 8건 / 201.430ms |
| A1 끔 / 노트북 | 417.5ms | 157.52ms | 9건 / 82.694ms |
| B Npcap / 노트북 | 162.5ms | 40ms | 3건 / 47.896ms |
| A2 끔 / 노트북 | 590ms | 660ms | 6건 / 51.786ms |

캡처를 꺼도 더 큰 공백이 재현됐고, B에서만 악화되는 패턴은 아니었다. 한 차례 대조·변동이 큰 환경이므로 **계측 영향0 또는 동등성의 통계적 증명은 아니다.** I3와 B 사이의 품질 차이도 두 관측기의 상호작용인지 시간대 변동인지 확정하지 않는다.

B의 Npcap은 정상 종료0/강제 종료 없음, 드롭 보고0이었다. 마지막30초 수신12014개와 late61개를 모두 유일하게 대응했다. 30ms 초과8개 공백의 모든 양끝도 대응했고, 캡처 이후 간격 증가 범위는−0.089~+0.094ms였다.

### Npcap만 켠 시험의 가장 큰 사건

| 같은 두 RTP 프레임의 간격 | 값 |
|---|---:|
| 송신 노트북의 API 시작 간격 | 10.344ms |
| PC Npcap 소프트웨어 수신 관측 간격 | 138.751ms |
| PC 수신 RTP 콜백 간격 | 138.662ms |
| 해당 송신 API 실행시간 | 0.094ms |

해당 프레임은 송신 앱 순번도 인접했다. B의8개 큰 공백 모두 정확한 송신 프레임 쌍을 연결했으며 송신 API 간격은5.159~10.487ms였다. I3의49개도 모두 연결했고 송신 API 간격 최대는11.152ms였다. **이 사건들의 큰 간격 증가는 송신 API와 PC Npcap 소프트웨어 수신 관측 사이에 있다.** 수신 캡처 이후 SDK/버퍼가 수십~100ms를 새로 누적한 설명과는 맞지 않는다.

이는 송신 소켓/OS·드라이버, 전송 경로, 수신 NIC/드라이버의 캡처 이전 구간을 포함한다. 송신 API 반환이 물리 송신 완료를 보장하지 않으므로 물리 네트워크만의 문제라고 단정하지 않는다. 일정한 SDK 지연이나 다른 출력 부족 사건까지 배제한 결론도 아니다.

다음 한 경계는 같은 사건의 **송신 측 소프트웨어 Tx 관측**이다. 송신 API 간격→송신 Tx 간격→수신 소프트웨어 Rx 간격을 같은 RTP 쌍으로 비교하면, 큰 변동이 송신 OS/드라이버 쪽에서 이미 생겼는지 그 이후 구간인지 더 나눌 수 있다. 다른 튜닝은 계속 보류한다.

## 미해결과 복구 원칙

- 아직 송신 측 소켓/드라이버·NIC/무선·메시/AP·수신 드라이버의 물리적 구분은 없다.
- 49건의 간격 비교는 모든 PLC·출력 부족·재버퍼 사건의 원인 판정이 아니다. 일정한 처리 지연의 크기까지 배제하지 않는다.
- 캡처 자체가 다른 시점의 관측과 동일한 환경을 보장하지 않는다. 실제 게임·외부 사용자 시험이나 입→귀 지연 측정을 대신하지 않는다.
- 제품 동작 수정·수신 여유 확대·단일 출력 믹서·기타 최적화는 채택하지 않았다.
- 각 수집은 기존 Pktmon 세션·필터가 있으면 중단하도록 했고, 소유한 세션/필터/프로세스만 종료한다. Npcap은 제한 시간 정상 종료를 확인한다. 노트북 시험 파일은 기존 목록으로 원복·SHA256 검증한다. 공유기·라우팅·NIC 고급 속성·기존 배포본은 변경하지 않는다.

원본·실패한 수집·수집 스크립트·정상 종료/복구 결과는 ignored `native/.local/extreme-103`에 보존한다.

최종 복구 확인: I2/I3의 자체 Pktmon 세션·필터는 모두 제거되어 idle/필터 없음으로 돌아왔다. I3와 B의 Npcap 프로세스는 제한 시간에 정상 종료했다. 노트북 시험 파일 복구·원본 SHA256 검증을 마쳤다. 기존 사용자 미커밋 변경과100~102의 수정은 보존했다.
