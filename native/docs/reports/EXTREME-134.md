# EXTREME-134 — 평상시 소프트웨어 대기 분해와 두 후보 기각

2026-11-01 / 기반 HEAD `baadb47`, 기존129–133 미커밋 변경을 보존했다. **이번 시험에서 제품 기본값으로 채택할 지연 감소를 입증하지 못했다.** 효과가 불분명한 시계 제어·5ms 정상 경로 후보는 제거했다. 재사용 가능한 오프라인 분석과 읽기 전용 진단만 남긴다.

## 구조와 조사 전환

네트워크의 간헐적 큰 공백은131–133의 관측 한계까지 보존하고 같은 조사를 반복하지 않았다. 이번에는 실제 캡처 → 프레임 조립/인코딩 → 기존 송신 큐 → 상대별 송신 API, 인증 RTP 콜백 → 상대별 RTP 버퍼/디코딩 → PCM 공급의 **평상시 호스트 내부 대기**를 분리했다. 기존 상대별 WASAPI 공유 출력, 직접 연결, native Opus LowDelay64, 수신 여유20ms를 유지했다. SDK는 기본 수정판 `udp1-turn1-rtp0`이며 별도 경계 진단 SDK를 사용하지 않았다.

PC 입력/출력은 USB 마이크/Realtek 헤드폰, 노트북은 내장 Realtek 입력/출력이다. 예전 Sound Blaster 출력 측정과 합쳐 하나의 장치 지연으로 표현하지 않는다. 실제 입력 주기 PC10ms/노트북5.333ms, 출력 주기2.667/10ms, 출력 목표 패딩5.833/15ms, 용량5.833/22ms였다. 요청 주기와 실제 주기를 구분한다. 장치·전원·드라이버·라우팅·SSID·공유기 설정은 변경하지 않았다.

## 측정과 해석

실제 두 PC에서 같은 합성 입력을 실제 캡처 콜백에 공급했다. 마이크의 물리 음향을 검증한 시험은 아니다. 각 기준선45초, 장치/미디어 준비2초 후 상세 기록을 시작했다. 분석은 첫10초와 마지막0.25초를 제외한다. 수신 간격30ms 초과·PLC 증가·시작 전/짧은 읽기 주변 ±250ms를 수신 단계 분포에서 제외하고, 캡처 간격30ms 초과/콜백 실행10ms 초과는 송신 단계에서 별도로 제외한다. **품질 카운터는 이런 정상 창 필터를 적용하지 않은 기준선 첫/마지막 진단 표본의 차이**다. 첫/마지막 표본 사이만 보므로 기준선의 모든 순간을 완전 포괄한다는 뜻은 아니다.

`analyze_steady_pipeline.py`는 같은 호스트 시각만 사용한다. `analyze_paired_software.py`는 SSRC/타임스탬프로 같은 프레임을 연결하여 송신 호스트의 장치 보고 첫 샘플→송신 API 기간과 수신 호스트의 인증 콜백→첫 PCM 공급 기간을 더한다. 서로 다른 PC의 절대 시각을 빼거나 두 중앙값을 더하지 않는다. 짧은 프레임을 두 배로 세지 않도록 샘플 수로 평균을 가중하고 대응 수/음성시간을 표시한다.

**이 합은 입→귀 지연이 아니다.** 송신 API부터 인증 콜백 사이의 SDK/전송, 장치에 공급된 뒤 실제 출력, 음향과 코덱의 내용상 지연은 빠져 있다. 프레임 첫 샘플과 렌더 읽기 단위에 따른 양자화도 남는다. 정상 재생된 프레임만 대응하는 생존 편향과 제외 비율을 숨기지 않는다. 프레임 분할만으로 첫 샘플 나이가 작아지는 현상을 전체 지연 이득으로 해석하지 않는다. 상세 기록은 잠금/객체 할당을 포함하는 선택적 계측이며 기본 앱 비용과 같지 않다.

## 후보1: 시계 보정 상단 허용 폭 축소

가설:20ms 목표 주변의5ms 허용 폭 때문에 큐가 약25ms에 머문다면 상단만2.5ms로 좁혀 평상시 대기를 줄일 수 있다. 하단까지 좁힌 최초 합성 후보는 일부 음수 시계 편차에서 오히려 큐가 늘어 먼저 기각했다. 실제 Opus,128/256/480 샘플 읽기, 시계 편차 −200/0/+200ppm, 지터 유무의36조건/18쌍 오프라인 비교 후 상단만 축소한 후보를 실제 A/B/A로 시험했다.
