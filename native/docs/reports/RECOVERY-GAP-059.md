# 0.5.9 수신 공백 복구 후보 비교

2026-10-20 KST, 핫스팟 시험에서 관측한160–400ms급 수신 공백을 참고해 결정적인 합성 도착 스케줄을 만들었다. 현재 방식과 두 후보를96개 조합으로 비교했다. 일부 조건에서 오래된 음성의 재생을 줄였지만 무음 부족과 폐기가 늘었고, 모든 조건에서 복구가 빨라지지는 않았다. **제품 기본값은 유지하며 후보는 진단에서만 선택한다.** 외부망 개선 완료로 판정하지 않는다.

## 현재 동작에서 확인한 부분

현재 재버퍼 이후 시작 조건은 패킷 총량이 `20ms 예비량 + 이번 출력 요청량` 이상인지 확인하고, 과거 패킷을 정리해 새로 시작한다. 이 총량은 RTP 시각의 연속성을 보장하지 않는다. 중간이 비어 있는 패킷 여러 개가 한꺼번에 도착하면 시작 직후 다시PLC를 실행하거나 과거 음성을 재생할 수 있다.

이는 코드에서 확인하고 합성 입력으로 재현한 동작이다. 기존 핫스팟 파일에는 패킷별 도착 순서와 재생 요청 추적이 없어, 실제9회 재버퍼가 이 이유로 발생했다고 확정한 것은 아니다.

## 비교 방식

- `current`: 현재 고정20ms·60ms 연속PLC 한계·10ms 일시 보완·최신 패킷 재시작.
- `continuous-tail`: 재시작 시 가장 최신의 연속된 RTP 구간이 예비량과 출력 요청량을 채울 때까지 기다림.
- `bounded-tail`: 같은 연속 구간 조건을 사용하되 추가 대기는 출력 요청1회만 허용. 여전히 불충분하면 기존 방식으로 복귀해 무기한 대기를 막음.

정상 도착, 짧은 순서 뒤바뀜,160/220/400ms 지연 후 묶음 도착,160/400ms 지연 후 일부 패킷 추가 지연,400ms 영구 손실의8가지 스케줄을 사용했다. Opus10/20ms 패킷과10/22ms 출력 요청을 교차하고3개 정책을 비교해96회다. 각 회차 가상12초, 정상 전송 지연20ms,4초 부근에 한 번의 장애를 넣었다. 같은 조건의 세 정책은 완전히 같은 도착·출력 요청 이벤트를 사용한다.

실제 LowDelay64로 만든 합성 단음 패킷을 표준 디코더로 복호화했다. 이는 음질이나 합성 발화 청감 시험이 아니다. 음성 기기와 실제 네트워크는 사용하지 않았다. 약1초 간격 핫스팟 진단을 정확한 패킷 재생 데이터로 둔갑시키지 않았다.

## 대표 결과: 10ms 패킷·10ms 출력 요청

‘음성 나이’는 생성 PCM의 RTP 기준 시각부터 가상 출력 요청까지의 경과다. 물리 입→귀 지연이나 출력 장치 지연이 아니다. 정상 조건 중앙값은 세 정책 모두40ms였다.

| 조건·정책 | 부족 합계 | PLC | 오래된 음성 폐기 | 공백 종료 후1초 내 음성 나이P95 | 최신 음성 첫 복귀 |
|---|---:|---:|---:|---:|---:|
| 400ms 묶음 · 현재 |320ms |60ms |20ms |80ms |관측1초 내 없음 |
| 400ms 묶음 · 제한 대기 |330ms |60ms |40ms |40ms |10ms |
| 400ms + 일부 추가 지연 · 현재 |320ms |100ms |30ms |140ms |90ms |
| 400ms + 일부 추가 지연 · 무제한 연속 대기 |340ms |60ms |60ms |40ms |20ms |
| 400ms + 일부 추가 지연 · 제한 대기 |330ms |70ms |50ms |50ms |10ms |
| 160ms + 일부 추가 지연 · 현재 |90ms |70ms |40ms |50ms |10ms |
| 160ms + 일부 추가 지연 · 제한 대기 |100ms |60ms |50ms |40ms |20ms |

최신 음성 복귀는 출력된 프레임의 나이가 장애 전 중앙값+패킷1개 이하로 처음 돌아온 시점이다. ‘없음’은1초 관측 창 안에 이 조건을 만족하지 않았다는 뜻이며 영구적으로 복구되지 않았다는 의미가 아니다. 첫 프레임의 복귀가 이후 모든 프레임의 신선도를 보장하지 않으므로P95도 함께 기록한다.

표의400ms 일부 추가 지연에서는 제한 대기가 복귀를90→10ms로 줄였지만 부족10ms·폐기20ms를 추가했다. 반대로160ms 사례에서는 복귀가10→20ms로 늦어졌다.22ms 출력 요청 조건에서도 개선이 항상 나타나지는 않았다. 첫 후보처럼 계속 연속 구간을 기다리면 손실이 반복되는 경로에서 기다림이 길어질 위험도 있다.

세 정책 모두 정상·짧은 순서 뒤바뀜 조건에서 부족·PLC·재버퍼0이었다. 이 조건들의 측정 결과는 모드 이름을 제외하면 일치했다. 모든 스케줄에서 중간 큐120ms 상한과60ms 연속PLC 한계를 검사했다.96회는 독립적인 실환경 통계 표본이 아닌 결정적인 입력 조합이다. 코드 검사 통과가 후보의 성능 우위를 뜻하지는 않는다.

## 결정

지연 우선 목표에서는 공백 후 과거 음성을 오래 듣는 문제도 줄여야 한다. 그러나 이번 후보는 무음 부족·폐기와 절충하며, 작은 공백에서 복구를 늦추기도 한다. 평상시 고정 버퍼 확대는 하지 않았지만 이것만으로 채택하기에는 근거가 부족하다. 현재 앱 기본값과 기존 시험 실행 패키지는 바꾸지 않았다. 후보는 `RtpOpusPlayoutBuffer`의 기본false 진단 옵션으로만 남긴다.

다음 비교에서는 출력 요청 위상, 단발이 아닌 반복 공백, 실측 패킷별 추적을 추가해야 한다. 우선 파편화된 큐에서 어느 음성을 폐기할지와 추가 대기의 허용 조건을 검토한다. 네트워크 공백 자체의 제거와 앱 복구 개선은 별개다. 실제 통화 경로에서의 후보 검증·핫스팟 재시험·청감 검증은 아직 수행하지 않았다.
