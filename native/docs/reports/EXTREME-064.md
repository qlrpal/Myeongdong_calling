# 대체 후보 검증: 출력 1ms 여유와 짧은 적응형 재생

2026-10-21, `codex/extreme-latency`. 목표는 지연 우선의 기존 모드 대체 후보를 찾는 것이다. 실제 PC/노트북의 공유 WASAPI 입력·출력과 합성 음성을 사용한다. 물리적 마이크·이어폰 지연을 개선하거나 시스템 장치 설정을 변경하지 않았다. 게임 부하는 별도로 통제하지 않았다.

## 변경

- 최소 출력에 엔진 주기 외 1ms만 추가하는 `OutputHeadroomMs` 지원. 기존 안정 모드의 5ms 여유보다 작다.
- 2.5ms Opus와 짧은 적응 여유, 1ms 출력 여유를 사용하는 `opus-adaptive` 추가. 1차는 5~15ms, 2차는 5~20ms 범위다. 낮은 여유에서 시작하고, 도착 마감 압력/빈 큐에서만 짧은 단위로 늘리며, 충분히 조용한 재생 후 1ms/초씩 하한으로 돌아온다.
- 긴 공백 후 재시작은 설정된 최대 여유를 사용한다. 커진 여유가 큐 상한과 재생 시점 정리에도 반영되도록 수정했다. 이전 하한을 계속 사용하면 재시작에 필요한 큐를 쌓기도 전에 버리는 문제가 생길 수 있어 회귀 검사를 추가했다.
- 수신 Opus 길이를 로컬 인코더 길이와 분리했다. 같은 새 빌드의 기존 10ms 모드와 짧은 모드를 혼용할 수 있도록 검증 중이다. 이미 배포된 예전 바이너리의 짧은 패킷 수신 능력을 바꾸는 것은 아니므로 양쪽 최신 빌드를 사용한다. PCM과 Opus 혼용은 지원하지 않는다.
- 실험 큐의 비상 정리로 버린 오디오도 별도 폐기 카운터에 포함한다.
- 최대 600초 시험 지원. 전체 스냅샷/카운터를 유지하면서 원시 패킷 기록은 마지막 최대 30초로 제한해 기록 누락을 방지한다.
- `--qualification-summary DIRECTORY OUTPUT`로 같은 기준과 실패 이유를 재현한다. 실제 직접/TURN 경로, 송신 분량, 누락·보간·폐기·큐 증가와 장치 오류를 함께 본다.

## 검증 기준과 해석

지연 우선의 잠정적인 정상 환경 기준이다. 전체 제품/모든 네트워크의 기본값 승격을 자동 결정하지 않는다.

- 첫/마지막 스냅샷 구간에서 출력 요청 대비 부족 ≤0.3%, 부족+보간 ≤1%, 별도 폐기 ≤1%.
- 연결/장치 오류·장치 재시작·출력 버퍼 빈 이벤트·송신 큐 누락·잘못된 RTP 패킷 0회.
- 송신 RTP 오디오 분량이 실제 시간의 99~101%, 마지막/첫 1/3 구간의 초과 큐(실제 큐−실제 목표 여유) 중앙값 증가 ≤10ms. 목표 여유를 의도적으로 올리는 적응 동작과 제어되지 않는 누적을 구분한다. 원래 큐 증가량도 별도로 기록한다.
- 시도한 직접/TURN 경로와 실제 선택 경로 일치, 패킷 기록 누락 0회.
- 입력 불연속 플래그는 별도 `strictCapturePass`로 기록한다. 플래그 자체만으로 앱 재생 실패로 판정하지 않으며, 송신 분량과 재생 연속성 기준은 그대로 적용한다.

도착→렌더 수치는 재생된 패킷의 수신 큐 진입→렌더 공급 시각이다. 물리적 출력이나 전체 마이크→귀 지연이 아니다. 폐기된 패킷은 이 지연 분포에서 빠지므로 보간/폐기와 함께 해석한다. 장시간 시험의 지연 분포는 마지막 기록 구간이고, 부족/보간 비율은 전체 측정 구간이다.

보간에는 실제 패킷 유실뿐 아니라 늦게 도착할 정상 패킷을 보존하기 위한 짧은 타임스탬프 유지도 포함된다. 누적 보간 시간을 같은 길이의 연속 무음이나 RTCP 패킷 유실로 해석하면 안 된다. 실제 부족으로 만든 무음은 별도 카운터다.

## 고정 후보 비교 (완료)

직접 연결·TURN에서 각각 안정 모드→10ms/출력1ms→5ms/출력1ms→안정 모드를 30초씩 실행했다. 기본 모드도 제품과 같은 약 5ms 기준 입력 선택을 사용하도록 시험 도구를 바로잡았다. 이전 062/063의 기본 모드와 입력 조건이 다를 수 있다.

직접 연결의 안정 모드 도착→렌더 중앙값은 약 25~33ms, 10ms/출력1ms 후보는 약 12~16ms였다. 출력 버퍼 빈 이벤트는 모두 0회였다. 고정 5ms 후보는 양쪽 부족/보간이 크게 증가하여 대체 후보에서 제외했다.

고정 10ms/출력1ms 후보도 양 경로에서 각 5분 검증했다. 직접 연결 부족은 PC 1782ms/노트북 1171ms, TURN 부족은 PC 1396ms/노트북 1090ms로 부족 비율 0.3% 기준을 넘었다. 연결·유효 데이터 전송 PASS만으로 대체 준비 완료라고 판단하지 않았다.

일부 짧은 비교에는 결과 회수 SSH 트래픽이 겹쳤을 수 있다. 장시간 연속 시험 중에는 대용량 결과 회수와 빌드를 피했다. 실행 순서와 다른 프로세스/무선망 상태까지 통제한 실험은 아니다.

## 적응형 1차 (15ms 상한, 장시간 TURN 불합격)

5ms/10ms 하한 적응 후보를 직접 연결·TURN에서 각각 60초씩 비교했다. 모두 잠정 연속성 기준을 통과했다. 지연 우선으로 5ms 하한을 선택해 장시간 검증을 진행한다.

5ms 하한의 60초 비교에서 도착→렌더 중앙값은 PC 직접/TURN 약 13.7/13.6ms, 노트북 약 13.5/8.0ms였다. 5ms는 하한이며 실제 목표 여유 중앙값은 PC 13~14.5ms, 노트북 7.5~11ms로 환경에 따라 늘었다.

5분 직접 연결에서 적응형 부족은 PC 423ms/노트북 381ms로 고정 10ms 후보보다 줄었다. 보간은 각각 565ms/2330ms였다. 전체 합산 비율은 약 0.33%/0.91%다. 그러나 5분 TURN에서는 부족 PC 2023ms/노트북 1758ms, 보간 1468ms/2493ms로 전체 합산 약 1.16%/1.42%여서 기본값으로 채택하지 않았다.

## 적응형 2차 (20ms 복구 상한, 완료)

평상시 하한은 5ms로 유지하고 복구 상한을 20ms로, 연속 PLC 한도를 10→30ms로 변경했다. 짧은 공백마다 재버퍼링을 반복하며 만드는 추가 무음을 줄이려는 변경이다. 고정 20/30ms 지연을 계속 추가하는 동작은 아니다. 기존 모드의 PLC 한도 60ms보다 작다.

혼합 모드에서는 수신 패킷 길이로 PLC 단위를 정하고 그 길이만큼만 적응 보류를 예약하도록 수정했다. 긴 상대 패킷을 로컬 2.5ms 길이로 잘게 손실 처리하면 도착한 정상 패킷을 불필요하게 버릴 수 있었다. 10ms 이상을 보내는 상대는 별도 수신 여유 하한을 복구 상한까지 올리는 호환 정책을 추가했다. 다른 짧은 패킷 상대와 로컬 송신의 짧은 프레임에는 영향을 주지 않는다.

직접 연결 5분, 안정 모드 TURN 5분, 새 후보 TURN 5분을 순차 실행했다. 마지막 혼합 수신 수정 후 양방향 역할을 바꿔 직접 연결/TURN 혼합 모드 각 30초와 동일 모드 TURN 60초도 재검증했다. 잘못된 RTP 패킷과 송신 큐 누락은 없었고, 혼합 모드의 과도한 부족/보간 문제는 해소됐다. 노트북 출력 소진 1회 관측은 별도로 남는다.

측정 콜백의 배열 증설을 피하도록 원시 기록 큐를 미리 할당한 최신 빌드에서도 TURN 5분을 다시 수행했다. 해당 변경으로 소진 관측이 없어지지는 않았다. 기존/새 모드의 소진 관측 시점은 기록 시작 시점과 일치하지 않았으므로 기록 큐 증설이 원인이라고 주장하지 않는다.

| 5분 조건 | PC 부족 / 보간 | 노트북 부족 / 보간 | PC / 노트북 출력 소진 | 도착→렌더 중앙값 PC / 노트북 |
| --- | --- | --- | --- | --- |
| 기존 모드 TURN 대조 | 0 / 290ms | 0 / 160ms | 0 / 1회 | 35.10 / 34.49ms |
| 새 후보 직접 연결 | 46.06 / 695ms | 2.50 / 2120ms | 0 / 0회 | 15.32 / 16.43ms |
| 새 후보 TURN 1차 | 92.08 / 977.50ms | 57.50 / 2247.50ms | 0 / 1회 | 14.40 / 19.23ms |
| 최신 빌드 TURN 재검증 | 59.19 / 715ms | 39.73 / 1560ms | 0 / 1회 | 14.39 / 15.70ms |

최신 TURN의 부족 비율은 PC 0.0197%/노트북 0.0133%, 보간 비율은 0.2385%/0.5207%, 별도 폐기는 0.1681%/0.4547%였다. 입력 분량은 실제 시간과 거의 같았고 입력 불연속 증가·송신 누락·잘못된 패킷·장치 재시작은 0회였다. 목표 여유를 뺀 초과 큐 중앙값 증가도 없었다. 실제 목표 여유 중앙값/P95는 PC 18/20ms, 노트북 16/20ms였다. 5ms 하한이 이 환경의 지속적인 실제 여유라는 뜻은 아니다.

## 판정과 사용

현재 두 PC의 1:1 환경에서는 **지연 우선의 교체용 프로필로 `opus-adaptive`를 제공**한다. 최신 TURN 수신→렌더 중앙값은 기존 대조보다 PC 약 20.7ms, 노트북 약 18.8ms 작게 관측됐다. 출력 목표는 약 15ms에서 약 11ms로 줄었으며 보간량은 늘었다. 무선망/다른 프로세스를 완전히 통제한 동시 비교가 아니므로 모든 환경에서 같은 감소를 보장하지 않는다.

엄격한 `continuityPass`는 출력 소진 0회를 요구하므로 노트북 TURN은 **FAIL을 유지**한다. `sourceRtpQueuePass`는 출력 소진 조건을 별도로 떼어 보여 주며 양쪽 최신 시험에서 통과한다. 노트북의 기존 모드도 5분에 소진 1회가 있어 관측 횟수는 같지만, 원인이 동일하거나 항상 가청 끊김이라는 뜻은 아니다. 이를 숨기거나 모든 항목 PASS로 바꾸지 않았다.

기존 기본값·안정 브랜치·배포본을 자동 교체하지 않았다. 양쪽 최신 빌드에서 `./native/run.ps1 -Experiment opus-adaptive`로 사용한다. 되돌리기는 `-Experiment baseline`이다. 게임 부하·다자 통화·실제 먼 지역 친구 환경의 기본값 승격은 아직 검증 범위 밖이다. 물리적 입→귀 지연 감소도 이번 결과로 확정하지 않는다.

## 보조 시계 분석

TURN 1차의 종료 근처 시계 교환 폭은 약 2.016ms였다. 마지막 5초의 재생된 패킷을 짝지어 보고, 교환 시점 이후/이전의 상대 시계 드리프트가 200ppm 이내라는 추가 가정으로 여유를 넓히면, 캡처 API 시각→상대 렌더 공급 중앙값의 조건부 참고 범위는 PC→노트북 약 40.3~47.2ms, 노트북→PC 약 29.1~36.1ms였다. 교정과 패킷 시각 차이는 최대 약 15초다. 이는 가정에 따른 범위이며 마이크 앞단·렌더 공급 후의 실제 장치 재생·귀 도달 시간을 포함하지 않는다. 주 판정은 이 보조 분석에 의존하지 않는다.

## 최종 검증과 남은 범위

Release 빌드 경고·오류 0개, `verify.ps1 -NoRestore -Integration` 전체 통과. 짧은/기존 Opus 혼합, PLC 단위/상한, 적응 여유 복구/감소, 최초 출력 요청 전 큐 보존, 순서/랩/손실/장치 복구와 기존 서버·실제 로컬 WebRTC 회귀를 포함한다. 원시 기록은 빌드 식별자와 함께 보존했다.

가장 엄격한 장치 소진 0회 조건은 남아 있다. 다음 검증은 이를 같은 하드웨어의 기존 모드와 비교하면서 게임 부하·다자 환경으로 넓히는 것이다. 더 많은 고정 여유를 항상 추가하여 지연을 높이는 변경은 하지 않았다. 커밋·푸시와 배포본 교체는 하지 않았다.

원시 결과와 `qualification-summary.json`은 Git 제외 경로 `native/.local/extreme-064/`에 있다. `*-long-*`는 고정 10ms의 5분 시험, `*-adaptive-long-*`는 적응형의 5분 시험이다. `*-mixed-*`는 새 빌드의 기존/적응형 모드 혼합 비교다. 빌드별 변경을 구분하기 위해 후속 보고서에는 엔진 모듈 빌드 식별자도 기록한다.
# 후속 정정

이 보고서의 자동 실기 도구는 명시적인 미디어 인터페이스를 전달하지 않아 OS 자동 경로를 사용했다. 따라서 ‘직접 연결’은 ICE 경로 구분이며 물리 LAN 고정을 검증했다는 뜻이 아니다. 후속 [EXTREME-067](EXTREME-067.md)에서 노트북의 겹친 Tailscale 경로를 확인하고 인터페이스 지정 대조를 추가했다. 이전 큐/처리 시각 관측은 해당 실행 조건의 값으로 보존하며, 순수 LAN의 보편적 성능으로 확대하지 않는다.
