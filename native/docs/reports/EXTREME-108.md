# EXTREME-108 · 종료 오류 격리와 세션 복구 수명

2026-10-27 / `codex/extreme-latency`. 기존106/107 미커밋 작업을 보존하고 통화 오류·정리·재연결과 안내를 보완했다. 프레임·버퍼·코덱·기본 출력 선택·수정 SDK·시스템 라우팅은 바꾸지 않았다. 노트북·OCI 작업은 하지 않았다.

## 확인한 문제

기존 `LeaveAsync`는 입력 정지, 송신 완료 대기, 상대 종료 중 하나가 예외를 내면 뒤의 자원/세션 정리를 건너뛸 수 있었다. 상대 종료 내부의 `finally`에서 다른 오류가 발생하면 원래 오류가 가려질 수도 있었다. 창 종료 역시 설정 저장/세션 종료 실패가 엔진 해제를 막을 수 있었다.

세션 제어에는 참가가 부분적으로 실패한 뒤 정리, 재시도 소진 후 정리, 동시에 들어온 참가/퇴장/Dispose의 완료 수명, 알림 콜백 예외에 대한 보호가 부족했다. 퇴장 실패 안내를 성공 문구로 덮고 장치 변경 후 자동 재참가를 이어가는 UI 경로도 있었다.

이전 신호 스트림의 오류가 예약한 비동기 정리는 어느 세션의 작업인지 확인하지 않았다. 이전 통화를 정리한 뒤 새 통화를 시작해도 오래된 작업이 늦게 실행되면 새 통화를 닫을 수 있는 코드 경로였다. 실제 발생률을 측정한 것이 아니라 코드에서 찾은 수명 경쟁이며, 이번에 제어된 지연 콜백으로 검증했다.

## 변경한 코드

- `CallCleanup`: 독립 정리 단계를 모두 시도한 뒤 단계와 원래 예외를 모아 `CallCleanupException`으로 반환한다. 사용자 메시지는 단계/조치만 표시하고 내부 원인은 `InnerExceptions`에 보존한다. 한 실패로 다음 단계가 생략되거나 원래 오류가 뒤의 예외에 가려지지 않게 했다.
- `WebRtcCallEngine.LeaveCoreAsync/ClosePeerAsync`: 마이크·송신 큐/스레드·코덱·모든 상대·공통 출력·측정 캡처·취소 자원 정리를 각각 시도한다. `DisposeAsync`에서는 정리 실패에도 HTTP 클라이언트 해제를 수행한다. 참가 실패와 그 뒤 정리 실패가 함께 발생하면 둘 다 보존한다.
- `ReadEvents/CleanupAfterEventFailureAsync`: 스트림이 시작한 세션 객체를 고정하고, 같은 세션이 아직 현재 통화일 때만 정리한다. 이전 작업이 새 통화를 닫지 않는다. 백그라운드 정리 오류도 관찰해 알린다.
- 서버 퇴장 알림은 로컬 정리 시도 뒤 캡처한 이전 서버로 전송하며3초 제한을 둔다. SSE 종료로 이미 삭제된 세션의401/404는 중복 퇴장으로 취급한다. 알림 실패는 로컬 정리 오류와 구분한다. **장치/API 정지까지 포함한 전체 종료3초 보장은 아니다.**
- `CallSession`: 작업 수를 잠금 아래 추적하고 제어 게이트 해제까지 기다린 뒤 Dispose한다. 중복 참가/복구를 막고, 퇴장은 재시도 의도를 즉시 취소한다. 동시에 요청한 Dispose는 같은 완료/오류 작업을 기다린다. 부분 참가 실패·최종 복구 실패·대기 함수 오류에도 정리를 시도한다.
- `CallNotifications`: 상태 관찰자 하나가 예외를 내도 다른 관찰자와 정리가 진행된다. 임의로 오래 막히는 외부 콜백까지 격리하는 비동기 실행기는 아니다.
- `CleanupError`: 정리 오류를 진단에 남긴다. 정리 실패 후 자동 복구는 새 마이크/연결을 열지 않고 중단한다. 사용자에게 진단 저장/앱 재시작을 안내하며, 명시적인 새 참가 시 이전 경고를 초기화한다.
- `CallForm/CallForm.Product`: 참가/출력/서버/정리 오류 안내를 구분하고 종료 실패를 성공 문구로 덮지 않는다. 장치 변경 후 자동 재참가는 종료 성공 시에만 진행한다. 창을 닫을 때 설정 저장이나 통화 제어 오류가 있어도 다른 정리와 엔진 Dispose를 계속 시도한다.
- `SharedCaptureRecorder/SharedRenderPlayer/WindowsAudioDevice`: 정지 예외가 있어도 정지 이벤트/스레드 종료와 나머지 해제를 시도한다. 클라이언트와 장치·대기 이벤트 해제를 분리하고 입력/출력 양쪽 오류도 모은다. 작업 스레드가 살아 있는 경우 네이티브 클라이언트를 먼저 해제하지 않는다. 출력 재시작이나 초기화 실패의 정리에서도 기존 오류와 후속 정리 오류를 보존한다.

정리 API가 예외를 내거나 네이티브 코드에서 영구 정지한 상황에 대해 OS 자원이 반드시 해제됐다고 보장하는 것은 아니다. 본 변경의 보장은 **독립적인 나머지 정리 시도, 실패 보존/안내, 새 자동 통화 차단**이다. 관리형 진단에서 참조가 비어 있다는 것만으로 OS 핸들 전체 해제를 판정하지 않는다.

## 장치 없는 실패 주입 검사

`CallLifecycleChecks`를 제품 회귀에 포함했다.

- 정지와 해제 단계 각각 예외 발생 → 뒤 단계 실행, 원래 오류2개 보존.
- 일부 자원을 만든 뒤 참가 실패 → 퇴장 호출, 의도/작업 상태 정상 종료.
- 상태 관찰자 예외 → 다른 관찰자 통지와 정리 계속.
- 동시 복구 요청30개 → 활성 대기 루프 하나, 퇴장으로 취소 후 재참가 없음.
- 참가 중 중복 참가, 퇴장과 동시 Dispose → 참가 하나·공유 완료 작업·종료 뒤 작업 없음.
- 연결 시작 알림 중 퇴장 → 실제 Join을 시작하지 않음.
- 최종 재시도 실패·대기 함수의 예상 밖 오류 → 부분 자원 정리, busy/의도 해제.
- 정리 오류 또는 기록된 정리 경고 → 자동 재연결 중단, 마이크 재개 없음.
- 종료 오류 안내 유지와 이후 명시적 참가, 장치/서버별 안내 분류.

이는 가짜 엔진/정리 동작을 사용하는 제어 수명 검사다. 마이크·네트워크 품질을 측정한 것이 아니다.

## 실제 단일 PC 장애 검사

`CallLifecycleProbe`와 localhost 전용 `Fixtures/lifecycle-server.mjs`를 추가했다. 운영 서버에는 새 경로나 설정을 추가하지 않았다. 서버 fixture는 설정503, 실제 SSE 연결 종료, 퇴장 응답 정지를 제공하며 URL/세션 토큰을 기록하지 않는다.

실제 공유 입력/출력·native Opus·10ms·직접 WebRTC 엔진3개에 합성 음성을 사용했다. 상대 볼륨은0.01이었다. 기존 출력과 공통 출력에서 다음 검사를 수행했다.

| 검사 | 확인 내용 |
|---|---|
| 여러 정리 오류 | 마이크/첫 상대/공통 출력의 실제 정리 뒤 오류 주입. 두 상대 모두 정리 시도, 나머지 단계 진행, 관리형 통화 상태 비움 |
| 정리 경고 | 진단 경고와 자동 복구 중단, 새 마이크를 자동으로 열지 않음 |
| 다른 상대 계속 통화 | 대상 퇴장 뒤 남은 두 엔진의 디코딩 수가 증가 |
| 새 참가 | 실패 후 명시적 퇴장/재참가 성공, 이전 경고 초기화 |
| 오래된 정리 작업 | 이전 세션의 정리 콜백을 보관하고 새 통화 뒤 실행 → 새 통화 유지 |
| 잘못된 입력/출력 선택 | 존재하지 않는 endpoint를 이 엔진에만 지정 → 올바른 안내와 정리. Windows 기본 장치는 변경하지 않음 |
| 서버503 | 참가 전 실패를 서버 안내로 분류, 자원 정리 |
| 실제 신호 연결 종료 | 서버가 SSE를 실제 종료 → 세 세션 모두 새 연결로 복구 |
| 퇴장 응답 정지 | 로컬 정리를 먼저 진행하고 알림 대기를 약3초에 종료 |

정리 오류는 **실제 해당 정리 작업이 반환한 뒤** 주입했다. 실제 네이티브 해제 전 영구 실패/정지가 있어도 OS 자원이 해제됨을 증명하는 시험이 아니다. 가상 검사의 정지 실패→다음 해제 실행과 실제 엔진의 후속 단계 진행을 구분한다.

오래된 정리 시험 역시 실제 네트워크에서 경쟁 발생률을 측정한 것이 아니라, 생산 코드와 같은 세션 검사 경로에 오래된 콜백을 제어해 전달한 것이다. 별도의 SSE 종료 시험은 실제 localhost 연결 종료/재연결을 사용했다.

## 그룹 회귀와 남은 연결 문제

초기6엔진 공통 출력 회귀는2·3·6명, 출력 재시작, 음소거, 퇴장/재참가, 혼자 남기와 새 통화를 통과했다. 후속 빌드의 같은 엄격한 검사에서는 three 단계에서 한 로컬 ICE 연결의 `disconnected`가 관측돼 **실패**했다. 그 관측 직후 약0.1초 뒤 정리를 시작했으므로 끊김 지속시간/자연 복구 여부는 판정하지 않았다. 출력 오류·디코더 오류가 확인된 사건은 아니며 정확한 원인은 미확정이다.

실패 원본을 보존하고 같은 조건의 별도 새 프로세스에서 한 차례 재시험했다. 재시험은 전체 단계를 통과했다. **재시험 통과로 최초 실패를 삭제하거나 모든 환경의 연결 안정화를 선언하지 않는다.** 이 제어 수명 변경을 현재/기존 ICE 공백의 해결로 표현하지 않는다. 아직 집 네트워크/SDK·OS 경계 조사와 독립 환경 검증이 남아 있다.

## 최종 검사 결과

최종 소스 빌드는 경고0·오류0이며 `CallLifecycleChecks`를 통과했다. 실제 장치의 기존/공통 출력은 각각 장애 검사10개를 통과했다. 퇴장 응답을 멈춘 시험의 완료 시간은 각각3.010/3.022초였다. 이는 서버 알림 대기 제한을 확인한 값이며 네이티브 장치 종료의 최악 시간을 보장하지 않는다.

최종 `verify.ps1 -NoRestore -Integration`도 종료 코드0이었다. 정적 분석·제품/서버 회귀·IPv4/IPv6 WebRTC·SRTP/RTCP·가변 프레임 검사를 통과했다. 27초 미디어 시간의 제어된 pull 검사에서 PLC/부족0이었지만 실제 장치·네트워크 장시간 무손실을 뜻하지 않는다. `git diff --check`도 통과했다.

오디오 어댑터 정리 보완 후 그룹 회귀도2·3·6명, 출력 재시작, 음소거, 퇴장/재참가 등 전체 단계를 통과했다. 마지막 클라이언트/장치 해제 오류 수집 변경 후에는 두 출력 모드의 장애 검사를 다시 수행했다. 앞서 기록한 ICE 끊김1회는 미해결 이력으로 유지한다.

최종 실제 장치 시험의 전용 서버·시험 프로세스가 남지 않았음을 확인했다. 입력4개·출력4개와 기본 입력/출력 선택은 시험 전후 동일하다. 원본은 `native/.local/extreme-108/complete`와 `release-final`에 보존했다.

## 실행·재현·복귀

```powershell
./native/verify.ps1 -NoRestore -Integration
./native/TransportProbe/bin/Release/net10.0-windows10.0.19041.0/TransportProbe.exe --call-lifecycle-checks
node ./native/TransportProbe/Fixtures/lifecycle-server.mjs
# 위 서버가 표시한 localhost 포트와 합성 음성 fixture를 사용한다.
# TransportProbe.exe --call-lifecycle-integration http://127.0.0.1:PORT/ REPORT.json SPEECH.wav false
# 마지막 false를 true로 바꾸면 공통 출력으로 검사한다.
```

오류 보완은 기존 실행에 적용된다. 공통 출력 후보는 계속 `run.ps1 -SharedOutput`으로만 선택하고, 옵션을 생략하면 기존 출력이다. 프레임/버퍼를 조절해 검사 결과를 맞추지 않았다. 기존 dist·사용자 진단은 변경하지 않았고 소스는 미커밋 상태다.

원본 JSON·단계 로그·바이너리 해시·초기/후속 검사·그룹 실패 및 재시험은 Git 제외 `native/.local/extreme-108`에 보존한다. 독립 PC·외부망/TURN·실제 게임 부하·물리 장치 뽑기/재삽입·GUI 버튼 자동화·물리 입→귀 지연은 이번 검사에 포함하지 않았다. 전체 앱 완성이나 지연 감소 ms를 선언하지 않는다.
