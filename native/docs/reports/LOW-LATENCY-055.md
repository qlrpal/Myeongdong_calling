# 0.5.5 · 저지연 기본 정책 적용

목표는 Windows 음성 통화의 지연 감소이며 음질이 두 번째입니다. 이번 변경은 진단 확장 대신, 앞서 비교한 재생 정책을 실제 앱 기본값으로 적용합니다. 개인 마이크·이어폰 설정과 OCI 서버는 변경하지 않았습니다.

## 적용한 동작

앱의 ‘재생: 저지연 우선’을 기본으로 선택합니다.

- 소비율 보정 목표를 20ms로 고정합니다. 시작 큐가 많다고 30ms를 정상 목표로 학습하지 않습니다.
- 빈 큐 에피소드마다 한 번 10ms PLC를 삽입하고 RTP 시각은 남겨 두어, 짧게 늦은 패킷을 받아들입니다. 뒤 패킷이 이미 있으면 일반 손실 PLC를 사용합니다.
- 긴 공백 뒤 재시작할 때 현재 출력 요청+목표 여유를 유지할 만큼 최신 패킷을 남깁니다. 생략한 음성은 ‘지연 회복을 위해 생략한 음성’으로 표시합니다.
- PLC 60ms 연속 상한·앱 큐 120ms 상한·소비율 보정 상하한은 유지합니다.

통화에서 나온 뒤 ‘재생: 기존 방식’을 고르면 이전 동작으로 되돌릴 수 있습니다. 지터 적응20~40ms는 기존 방식에서만 선택할 수 있어, 검증하지 않은 조합을 기본에 섞지 않습니다. JSON의 `PlaybackPolicy`에도 선택 정책을 기록합니다. 도구의 개별 실험 플래그는 `experimental`로 구분합니다.

정책 선정의 근거는 [같은 도착 기록의 재생 비교](PLAYOUT-DEADLINE-RECOVERY.md)입니다. 안정적인 PC 기록에서는 대기가 줄었고, 공백 뒤에는 최신 큐 재시작이 꼬리 지연을 줄였습니다. 모든 환경에서 지연이나 음질이 더 좋아진다는 보장은 없습니다. 이 문서는 해당 보고서에서 기본값을 유지했던 판단 이후의 적용 기록입니다.

## 앱과 같은 정책으로 5분 연속 통화

2026-10-17 00:38:13~00:43:17 KST, PC 유선 ↔ 노트북 Wi-Fi, 직접 연결입니다. 별도 파일 전송·빌드·검사를 끝낸 뒤 앱과 같은 `SetPlayoutPolicy(LowLatency)` 경로로 실행했습니다. 진단음·루프백 측정은 끄고 메타데이터만 수집했습니다.

재생 큐 통계는 시작 5초 이후 약 1초 간격 진단 표본이며, 앞선 추적의 수신→디코딩 시간과 다른 지표입니다. 장치 버퍼와 캡처를 포함한 물리 입→귀 지연이 아닙니다. 누락된 시작·끝 패킷을 네트워크 손실로 계산하지 않았습니다.

시험 전에 정한 내부 판정 기준은 연결 유지, 무음 부족0.1% 이하, PLC1% 이하, 회복 생략1% 이하, 표본 큐 P50≤40ms·P95≤60ms입니다. 양쪽 모두 통과했습니다. 이 기준은 주관적 음질이나 제품 전체의 보편적 성능 보증이 아닙니다. 이번에는 재버퍼링이 없어 최신 큐 생략이 실행되지 않았으며, 해당 경로는 앞선 실제 공백 자료·재생 비교와 합성 검사로 확인했습니다.

## 검증·배포와 다음 작업

경고0·오류0 빌드, 기존 회귀·서버7개·실제 WebRTC 통합, 기존17조건 부하, 216개 가상 비교가 통과했습니다. 새 정책 선택·기존 방식 복귀·적응 모드 충돌·잘못된 정책 거부도 검사했습니다. 처음에는 실행 중 검사 도구와 재빌드가 겹쳐 파일 잠금이 발생했고, 종료 후 재빌드·회귀를 정상 완료했습니다.

`./native/build.ps1 -NoRestore -Package`로 `native/dist/`와 `native/dist.zip`을 갱신합니다. 이전 패키지와 진단 파일은 빌드 스크립트가 `.local/archive/build-*`에 보존합니다. 원본5분 보고서·시험 전 기준·판정 결과는 Git 제외 경로 `.local/playout-release-055/`에 있습니다.

다음 개발은 캡처 전달 지연 약17~19ms 중 앱이 줄일 수 있는 부분에 집중합니다. 추가 진단은 변경 전후를 판단하는 데 필요한 만큼만 사용합니다. 실제 대화의 주관적 음질과 원거리/TURN 장시간 통화 검증은 남아 있으며, 이번 시험으로 전체 통화 지연의 절대값을 확정하지 않습니다.
