# 일반 통화 합성 발화 비교

2026-10-21. 게임 부하 시험을 제외하고 PC·노트북에서 고정 20ms → 자동 저지연 → 고정 20ms 순서로 각 120초씩 양방향 통화했다. 합계 6분이며 각 회차 사이 연결 준비 시간은 별도다.

## 결론

자동 회차는 수신→출력 제출 중앙값 PC 20.24ms, 노트북 20.85ms였고 측정 구간의 추가 무음·재버퍼링은 양쪽 0이었다. 마지막 고정 회차는 30.02/28.17ms였으며 역시 추가 무음·재버퍼링이 없었다. 두 정책 모두 이 짧은 관측에서 지속적인 큐 누적은 보이지 않았다.

첫 고정 회차에서는 게임 없이도 양쪽에 공백이 발생했다. 자동 모드가 공백 원인을 제거했다고 해석하지 않는다. 동일 입력 기록 재생에서도 자동 모드는 중앙 지연을 줄이는 대신 일부 기록의 PLC를 늘렸다. 기본 고정 20ms와 자동 시험 모드를 유지한다.

## 방법과 범위

- 최신 코드, Opus LowDelay64 / 48kHz 모노 / 10ms, 표준 공유 입력, RAW 우선 WASAPI 공유 이벤트 출력, 양쪽 TURN 강제 경로.
- 기존 Windows TTS 합성 발화 약 32.4초를 반복했다. 실제 캡처와 프레임 조립 후 인코딩 직전에 PCM만 교체한다. 실제 마이크 음질·잡음 제거와 사람이 말한 음성은 검증하지 않는다. 마이크 원음·수신 음성을 저장하지 않았다.
- 양쪽 6개 결과 모두 오류 없이 종료했고 파이프라인 기록 퇴거는 0이다. 출력 오류·출력 재시작·유효하지 않은 패킷은 0이다.
- 처음 비동기 시작 시험과 첫 예약 시작 시험은 무효 처리했다. 노트북 시스템 시계가 PC보다 약 13.65초 빠른 사실을 SSH 왕복으로 확인했다(측정 범위 13.46–13.83초). 노트북 예약 시각을 14초 보정해 재시험했고 세 회차 모두 완료했다. 시스템 시계 설정은 바꾸지 않았다. 이 동기화 정밀도로 편도 네트워크 지연을 계산하지 않는다.
- 연결 준비 후 예약 시각까지 대기하고 파이프라인 기록을 시작했다. 누적 무음·PLC·재버퍼링·폐기량은 첫 진단 표본을 빼서 준비 구간을 제외했다. 지연 통계는 기록의 시작 5초와 끝 1초를 제외한다. 전체 입→귀 지연이 아니다.

## 동일 기록 대조

6개 기록마다 동일 도착 순서와 장치 요청 크기로 고정/자동 및 기존/반복 공백 복구를 각각 재생했다. 합성 Opus 무음을 사용하는 냉시작 반사실 시험이며 초기 디코더·큐 이력을 완전히 복원하지 못한다. 청감·물리 지연 검증이 아니다.

- 마지막 고정 PC 기록의 중앙값은 고정 29.35ms → 자동 25.80ms, PLC는 70→130ms였다.
- 마지막 고정 노트북 기록은 28.01→22.98ms, PLC는 60→120ms였다. 양쪽 무음·재버퍼링은 계속 0이었다.
- 첫 고정 PC 기록의 무음은 146.79→143.06ms, 노트북은 155.73→154.94ms였다. 큰 공백을 해결한 수준은 아니다.
- 새 반복 공백 복구는 실시간 자동 회차 및 6개 재생 기록 모두 활성화 0회였다. 이전 자동 모드와 무음·PLC·재버퍼링 수치가 같았다. 이번 기록으로 새 복구 기능의 효과를 추가 입증하지는 못했다. 조건을 충족했던 기존 기록과 통제된 장치 검증은 [복구 보고서](GAP-RESTART-059.md)에 있다.

## 검증과 정리

시험 도구에 양쪽 예약 시작 옵션 `--scheduled-responsive-speech-ab`를 추가했다. 늦거나 2분 이상 먼 시작 요청은 실패 처리하며 제품 통화 코드는 바꾸지 않았다. 예약값은 각 호스트의 시스템 시계에 맞게 별도 보정해야 한다.

빌드 경고·오류 0, 전체 정적 분석·회귀·서버 7개 및 실제 로컬 WebRTC/DTLS/SRTP·RTCP 통합 검사 통과. `git diff --check` 통과. 시험 후 양쪽 음성 시험 프로세스 잔류 0을 확인했다. 게임·장치 효과·음량·OS 시계·서버 설정 변경은 없다.
