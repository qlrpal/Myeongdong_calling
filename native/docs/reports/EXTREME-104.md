# EXTREME-104 · 송신 Tx 경계와 실제 VPN 경로

2026-10-27 / `codex/extreme-latency`. EXTREME-103의 다음 단계인 송신 API→소프트웨어 Tx→PC 소프트웨어 Rx를 조사했다. 제품 앱·SDK·코덱·버퍼·프레임 기본값은 수정하지 않았다. 공개 코드 변경은 분석기의 명시적 raw IPv4 입력 지원뿐이다.

## 현재 경로에서 새로 확인한 사실

노트북에서 PC 주소를 대상으로 `Find-NetRoute`를 읽었을 때, 선택된 출발 주소·인터페이스는 **Tailscale**이었다. 집 LAN과 같은 `/24` 경로를 Tailscale이 제공하고 있었다. 실제 Wi-Fi 주소와 PC에서 보이는 음성 출발 주소도 달랐다. 읽기 조회와 실제 통화 진단을 함께 보존했다.

따라서 이 시험의 WebRTC **직접 UDP**는 TURN을 사용하지 않는다는 뜻이며, OS 아래 VPN/서브넷 경로까지 통과하지 않는다는 뜻이 아니다. 이 점을 기존의 물리 Wi-Fi 조사와 구분해야 한다. 현재 경로 관측을 과거 모든 시험 시점으로 소급하지 않는다.

## 초기 수집에서 배제한 것

- 초기 원격 스크립트는 PowerShell 실행 정책 때문에 시작되지 않았다. 그다음 분리 실행은 SSH 실행 세션이 끝나며 하위 프로세스가 유지되지 않았다. 준비 신호가 없었으므로 두 시도에서 통화 시험을 시작하지 않았다. PC의 제한 캡처는 자동 종료됐고 시험 파일은 복구했다.
- 원격 스크립트는 SSH 실행 채널을 끝까지 유지하고, 해당 PowerShell 프로세스에만 실행 옵션을 지정했다. 시스템 실행 정책을 변경하지 않았다.
- 첫 실제60초 수집은 노트북 Wi-Fi와 해당 TCP/IP 지점만 선택했다. RTP는 보이지 않고 일부 ICE 확인 패킷만 보였다. 이를 패킷 손실로 단정하지 않았다. OS 경로 조회로 실제 RTP가 Tailscale 경로임을 확인한 후 관측 지점을 맞췄다.

## 실제 경로의 Tx 수집

같은 제품 바이너리·`opus-adaptive`·네이티브 Opus·1:1 직접 UDP60초를 유지했다. PC는 기존 Npcap 수신, 노트북은 기존 Pktmon에서 Wi-Fi/TCPIP 및 Tailscale/TCPIP의 네 지점만 수집했다. 새 드라이버·프로그램은 설치하지 않았다. UDP 대상·128바이트 prefix·시간/파일 크기 상한을 적용했다.

노트북 Tailscale 지점은 Pktmon의 `PacketType=IP`로 기록됐다. 기존 분석기는 Ethernet/Wi-Fi 형식만 지원했으므로, 명시적으로 IP라고 선언된 이벤트에 한해서만 IPv4 헤더 시작을0으로 해석하도록 보완했다. MAC 주소 첫 비트만 보고 raw IP라고 추측하지 않는다. 기존 형식·truncation·IPv4 options·fragment 거부와 raw IP 검사를 통과했다.

| 송신 지점 | 관측된 소스 trace 프레임 | API 시작→Tx 관측 중앙값 / p95 / 최대 |
|---|---:|---:|
| Tailscale 가상 어댑터 | 7345 / 12012 | 0.050 / 0.200 / 6.800ms |
| Tailscale의 TCP/IP 지점 | 7345 / 12012 | 0.048 / 0.193 / 6.796ms |

**송신 수집은 불완전하다.** 전체 프레임 부재나 전체 통화 무손실을 판정하지 않는다. 다만 아래 두 공백의 양끝 프레임은 송신 API·두 Tx 지점·PC Rx·콜백에서 모두 같은 RTP 식별자로 정확히 연결됐다. 선택 사건의 두 Tx 지점은 각 패킷당 단일 시각 관측이었다.

| 사건 | 송신 API 간격 | Tailscale Tx 간격 | PC Rx 관측 간격 | PC 콜백 간격 |
|---|---:|---:|---:|---:|
| E1 | 11.014ms | 11.125ms | 43.514ms | 43.484ms |
| E2 | 11.419ms | 11.553ms | 43.341ms | 43.381ms |

이 두 사건의 간격은 **Tailscale 가상 Tx 뒤→PC 소프트웨어 Rx 이전**에서 약32.390/31.788ms 더 벌어졌다. 송신 API→가상 Tx 이전이나 PC 캡처 이후 콜백에서 이 크기의 간격이 새로 생긴 결과와 맞지 않는다. 불완전한 수집에서 양끝이 보이지 않는 다른 사건에는 결론을 확장하지 않는다.

각 호스트/관측기의 같은 두 패킷 간격만 비교했다. 서로 다른 PC의 절대 시각을 빼지 않았다. 이 값은 편도 지연도 물리 무선 송수신 시간도 아니다. 가상 Tx 뒤에는 Tailscale 처리·암호화·물리 송신 드라이버·VPN 전송/서브넷 중계·수신 드라이버가 포함될 수 있다. 아직 이 중 정확한 하위 원인을 특정하지 않았다.

## 통화별 인터페이스 선택 대조

다음 대조는 OS 자동 A1 → 시험 통화 소켓만 Wi-Fi로 선택 B → OS 자동 A2다. 시스템 VPN·전역 라우팅·공유기 설정을 바꾸지 않는다. 기존 `MediaInterfaceSelection.Apply`는 통화 소켓에 `IP_UNICAST_IF`를 지정하고 선택 주소로 바인딩하는 기능이며 시스템 경로 변경 명령을 호출하지 않는다.

모든 단계는 같은 제품 빌드·코덱·프레임·버퍼·60초 조건이었다. PC는 OS 자동을 유지하고 노트북의 시험 소켓 선택만 바꿨다. 추가 패킷 캡처는 켜지 않고 동일한 앱 상세 trace만 유지했다. 기본 OS 자동 모드를 Wi-Fi로 강제 변경하거나 사용자의 VPN을 끄지 않았다.

실제 경로 검증: A1/A2에서는 PC가 보는 미디어 출발 주소가 노트북 Wi-Fi 주소와 달랐고, B에서는 노트북 Wi-Fi 주소와 같았다. B의 요청 인터페이스도 보고서에 기록됐다. 시험 뒤 OS 선택 경로는 원래 Tailscale로 유지됐다. 통화별 소켓 선택은 해당 시험 엔진 종료와 함께 끝났다.

| 조건 / 수신 측 | PLC 증가 | 출력 부족 | RTCP RTT 중앙값 / 최대 |
|---|---:|---:|---:|
| A1 OS 자동 / PC | 107.5ms | 11.98ms | 9.716 / 62.229ms |
| B 통화별 Wi-Fi / PC | 72.5ms | 0ms | 2.581 / 3.524ms |
| A2 OS 자동 / PC | 92.5ms | 14.81ms | 9.468 / 121.766ms |
| A1 OS 자동 / 노트북 | 145ms | 22.5ms | 9.296 / 77.293ms |
| B 통화별 Wi-Fi / 노트북 | 162.5ms | 12.5ms | 2.395 / 6.364ms |
| A2 OS 자동 / 노트북 | 172.5ms | 52.42ms | 8.915 / 19.641ms |

진단 구간은 약59.5~59.9초다. RTT는 최근10초 이내 보고를 사용하고 보고 나이가 다시 작아지는 시점의 새 보고만 골랐다(방향·단계별10~13개). 반복 표본을 독립된 수백 개 보고로 계산하지 않았다. RTCP RTT는 네트워크/프로토콜 왕복 지표이며 입→귀 지연이 아니다. 이를2로 나누어 물리 편도 지연으로 제시하지 않는다.

이번 대조에서는 경로 선택에 따라 RTT 중앙값이 약7ms 달라지고 자동 경로로 돌아가면 다시 증가했다. 한 차례 A/B/A이므로 모든 시점/환경의 개선 폭이나 통계적 동등성을 보장하지 않는다. 노트북의 PLC는 B에서도162.5ms였고 A1보다 많았다. **경로 변경으로 통화 연속성 문제가 해결됐다는 결과는 아니다.**

### Wi-Fi 선택 후 남은 사건

B의 마지막30초 trace에서 큰 공백은 방향별 한 건이었다. 같은 프레임 쌍의 송신 API 간격도 연결했다.

| 방향 | 송신 API 간격 | 수신 콜백 간격 |
|---|---:|---:|
| PC→노트북 | 9.977ms | 57.008ms |
| 노트북→PC | 0.187ms | 35.960ms |

VPN 경유를 피한 통화에서도 콜백 앞 공백이 남았다. 이 B 단계에는 패킷 캡처가 없으므로 물리 Wi-Fi Tx/Rx의 어느 쪽에서 벌어졌는지 더 분해하지 않는다. 다음에는 **이 통화별 Wi-Fi 경로를 고정한 상태**에서 송신 Wi-Fi 소프트웨어 Tx와 수신 관측을 연결한다. 이미 기각한 전원·스캔·qWAVE 조정을 반복하지 않는다.

## 한계와 보존

- 현재의 OS 경로를 확인한 결과이지, 모든 과거 Wi-Fi 스파이크의 원인 판정이 아니다.
- 가상 송신 경계는 물리 NIC 송신 완료를 의미하지 않는다. VPN 내부의 어디에서 대기가 생겼는지 분리되지 않았다.
- 다른 출력 부족·PLC 사건, 외부 사용자·게임 부하·물리 입→귀 지연을 이 결과로 설명하지 않는다.
- SDK/Opus/출력 정책 튜닝·기본 경로 자동 우회 등 제품 변경은 하지 않았다.
- 원본·원격 수집 스크립트·실패한 시작·종료/복구 기록은 ignored `native/.local/extreme-104`에 보존한다. 개인 IP·VPN 피어 정보·패킷 prefix는 커밋하지 않는다.

최종 복구: 정상 수집의 자체 Pktmon 세션·필터를 종료/제거하고 idle·필터 없음으로 확인했다. PC Npcap은 정상 종료0/강제 종료 없음, 보고된 드롭0이었다. 노트북 시험 파일은 기존 복구 목록으로 원복하고 원본 SHA256을 검증했다. 양쪽 시험 프로세스는 종료했다. OS 경로와 지속 실행 정책은 원래 상태를 유지했고 기존 dist·서버·사용자 미커밋 변경을 보존했다.
