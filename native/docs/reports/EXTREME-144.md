# EXTREME-144 — 출력 장치 시계로 평상시 대기 대조

2026-11-02~03 / 기반 `5ce456b`와140~143 미커밋 변경 보존. 간헐적 네트워크/렌더 공백 원인 조사는 이번 최우선 과제에서 제외하고, 수신 여유20ms를 유지한 출력 상시 대기 감소를 검증한다. 물리 입→귀 달성을 선언하는 시험이 아니다.

## 근거와 측정 경계

134의5ms 프레임/시계 상단 허용 폭,140~142의 낮은 수신 여유 후보는 반복하지 않았다. 출력의 엔진 주기 외 추가 여유5ms 중2ms를 줄이는 가설이다. 기존 최소 출력 프리셋처럼 프레임·수신 여유·MMCSS·워치독을 함께 변경하지 않는다.

142에서 디지털 루프백 파형은 검출됐지만 캡처 QPC가 신뢰 조건을 통과하지 못했다. 이를 완화하지 않고 별도 장치 검사에서 실제 렌더 PCM의 샘플 위치를 저장하고 IAudioClock 위치/주파수/QPC와 대응했다. [Microsoft GetPosition 정의](https://learn.microsoft.com/en-us/windows/win32/api/audioclient/nf-audioclient-iaudioclock-getposition)에 맞춰 위치를 주파수로 나눠 스트림 상대 초로 변환하고100ns QPC와 연결한다. 물리 DAC/음향 시각으로 확대하지 않는다.

새 검사 `--render-presentation-device OUTPUT.json`은 실제 WASAPI 공유/RAW GameChat 출력, native Opus LowDelay64,10ms 패킷,20ms 고정 수신 여유를 사용한다. 수신 입장 시각부터 렌더 PCM에서 검출된 신호의 장치 시계 시각까지를 같은 PC에서 측정한다. PCM 참조는 미리 디코딩한 파형이어서 코덱 내용상 lookahead를 제외한다. 마이크/입력·실시간 인코딩·네트워크·물리 귀는 포함하지 않는다. PCM은 제한된 임시 메모리에만 두고 파일에는 저장하지 않는다.

시계 관측의 단조성·일정 주파수·유한 호출 시각·최대5ms 호출·미래 QPC/오래된 QPC·실제 제출 샘플 경계·전체 진행률을 검사한다. 신호 위치 양옆100ms 이내 관측으로만 보간하고 관측 범위 밖은 외삽하지 않는다. 신뢰 가능한 신호10개 이상인 timing complete와 끊김 기준 continuityPassed를 구분한다. complete만으로 개선/안정성을 판정하지 않는다.

기본 실행에는 observer가 없으며 새 PCM 복사/시계 호출은 검사 도구를 명시적으로 설치했을 때만 발생한다. 검사 오버헤드는 모든 대조에 존재하므로 일반 앱의 CPU/할당 수치라고 표현하지 않는다.

## 장치 대조

각 PC에서5→3→5ms 출력 추가 여유를32초씩 비교했다. 최초 탐색은 프로세스 시작에 상대적인 송출이어서 위상 차이가 남았다. 초기 결과를 폐기/덮어쓰지 않고, 후속으로 장치 시계 원점+1초에 송출을 정렬한 별도 세 회차를 실행했다. 각 회차14개 신호가 모두 대응됐고 PLC/재버퍼/출력 소진/PCM 부족은0이었다. P95는14표본의 nearest-rank라 최대값과 같다.

| 장치 / 입장→장치 시계 중앙값·P95 | 기존5ms A1 | 후보3ms | 기존5ms A2 |
|---|---:|---:|---:|
| PC, 위상 정렬 |29.970 /30.232ms|29.974 /30.135ms|29.980 /29.993ms|
| 노트북, 위상 정렬 |59.961 /61.348ms|58.243 /60.379ms|59.941 /61.169ms|

노트북 중앙값은 인접 두 대조보다1.698~1.718ms 낮고P95는0.790~0.969ms 낮았다. PC에서는 일관된 이득이 없었다. PC 출력은 실제2.667ms 주기/용량5.833ms라5ms 추가 여유도 용량에 막혀 실제 목표가5.833ms다.3ms 후보 목표는5.667ms로 줄어드는 양 자체가 작았다. 노트북은10ms 주기/용량22ms이며 목표15→13ms로 줄었다. 따라서 후보를 실제 출력 주기5ms 이상에만 적용하고 짧은 주기 장치의 기존 정책은 유지하는 것으로 좁혔다.

최초 탐색 중앙값은 PC28.977→30.995→29.960ms, 노트북63.388→56.802→57.311ms였다. 그 차이를2ms 설정 축소의 효과로 그대로 사용하지 않는다. 위상 정렬 시험과 초기 탐색의 결과를 섞지 않는다.

## 구현

- `SharedRenderPlayer.ChooseTarget`: 검증 후보는 출력 주기5ms 이상일 때 엔진 한 주기+3ms, 그 미만은 기존 한 주기+5ms이며 장치 용량을 넘지 않는다. 초기 전체 패딩,2초 정착, 소진 시 전체 용량 복귀/고정 정책은 유지한다.
- `IRenderProbe`, `ConfigureProbe`, `WindowsAudioDevice.ConfigureRenderProbe`: 장치 검사 전용 PCM/clock observer이며 시작 전 bounded 출력에만 설치된다. 제품 UI나 설정 파일에 실험 토글을 추가하지 않는다.
- `RenderPresentationProbe`: 위상 정렬된 대조, 시계 신뢰/보간·PCM 채널 변환·기존 출력 생명주기 거부 회귀를 제공한다. `verify.ps1`에 자체 검사를 추가한다.
- `RenderDeviceChecks`:5ms 경계·짧은 주기 보존·장치 용량 상한·44.1kHz 반올림을 검사한다.

## 채택·한계·복구

장치 시계 위상 대조의 노트북 측 약1.7ms 감소와 observer 없는 두 PC A/B/A의 연속성 유지를 근거로 **주기5ms 이상인 bounded 공유 출력의 추가 여유3ms를 개발 소스 기본값으로 채택**한다. PC처럼 짧은 주기의 기존5ms 추가 여유와 호환 출력·실험 minimal 출력은 유지한다. 수신20ms/자동 하한15ms, Opus/프레임·입력 주기·SDK·보안·MMCSS·스케줄링 정책은 변경하지 않았다.

이 이득은 시험 노트북의 수신 입장→렌더 장치 시계 구간이다. 모든 장치에서1.7ms 또는 입→귀 전체가1.7ms 줄었다는 보장은 아니다. 실제 게임 부하·다인·강제 TURN/외부 친구·독립 다른 장치·장시간·물리 입→귀와 청감은 이번 후보에서 미실시다. 해당 조건의 품질 합격이나 새 안정판 전체 대체로 표현하지 않는다.

노트북 장치 대조2회와 실제 통화3회 모두 원본 시험 폴더를 매회 복구하고 원본 VoiceNative.dll SHA256 `612914CFA7B0B871C2626C4C141E47FF8DB5FBF45370042A4F16304AFFC0A480` 일치 및 해당 검사 프로세스0을 확인했다. 운영 배포본/베타 ZIP/서버·장치·전원·드라이버·네트워크 설정은 유지했다. 커밋·푸시·릴리즈하지 않았다.

Git 제외 원본은 `native/.local/extreme-144/`의 `presentation-summary.json`, `call-comparison.json`, 기준/후보 빌드와 로그, `extreme-144-aligned/`, `extreme-144-call-a1/b/a2/`의 참가자 원본·설정·해시·복구 상태에 보존한다.

## 실행과 기존 경로

기본 실행은 `./native/run.ps1`이며 장치 주기로 자동 선택한다. 별도 설정 변경이 필요하지 않다. 장치 비교 도구는 다음과 같다.

```powershell
./native/TransportProbe/bin/Release/net10.0-windows10.0.19041.0/TransportProbe.exe --render-presentation-checks
./native/TransportProbe/bin/Release/net10.0-windows10.0.19041.0/TransportProbe.exe --render-presentation-device NEW-REPORT.json
```

장치 검사는 합성 소리가 재생되며 기존 보고서를 덮어쓰지 않는다. 검사 종료 뒤 observer는 남지 않는다. 새 소스에서 `-Experiment baseline`은 이번 출력 목표 변경을 해제하지 않는다. 기존 정책으로 실행하려면 변경하지 않은 기존 공개 베타/배포본을 사용한다. 소스의 정확한 정책 복귀는 `ChooseTarget`의 추가 여유를 이전처럼 항상 `.005`초로 되돌리고 관련 경계 회귀 기대값을 함께 되돌린 뒤 재검증하는 것이다. 다른 미커밋 변경 전체를 버리는 방식은 사용하지 않는다.


## 최종 검증

기존 observer 경로 추가 후와 조건부3ms 채택 후 각각 `./native/verify.ps1 -NoRestore -Integration`을 통과했다. 최종 경고/오류0 빌드, 시계/PCM 자체 검사, 목표 경계, 기존 Opus/재생/복구/사건/UI/서버/실행기 회귀, 실제 로컬 SRTP·가변 프레임·IPv6를 포함한다. 최종 출력 app DLL 해시가 실제 두 PC B 회차 후보와 같음을 확인했다. 이는 물리 입→귀/게임/외부망 합격을 뜻하지 않는다. 최초 빌드는 WindowsAudioDevice를 IDisposable로 가정해 실패했고 명시적인 Close/finally 정리로 수정한 뒤 재빌드했다. 초기 실패 로그도 보존한다.
