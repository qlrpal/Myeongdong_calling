# 0.5.9 모바일 핫스팟 외부망 시험

2026-10-20 KST, 사용자가 PC 집 인터넷·노트북 모바일 핫스팟 조건에서 자동 경로와 TURN 강제 경로를 각각300초 실행했다. 양쪽의 두 회차가 정상 종료했고, 자동 회차는 직접 연결, 강제 회차는 TURN 중계로 기록됐다. 연결성은 확인했지만 버퍼 부족·재버퍼가 있어 외부망 통화 안정화 완료로 판정하지 않는다.

## 조건과 유효성

- 0.5.9, Opus LowDelay64·48kHz 모노·10ms, 고정20ms 예비량, RAW 우선 공유/이벤트 출력.
- 양쪽 약32.4초 합성 발화 반복. 송신 페이로드 속도 진단 표본 중앙값64.51–64.57kbps. 실제 마이크 원음 저장 없음.
- 자동 회차01:22–01:27, TURN 회차01:28–01:33. 각 기기 파일의300초 시험에서 진단 표본298개, 첫·마지막 표본 간 약299.4초.
- 자동 회차 양쪽 모든 표본의 경로는 직접 연결, TURN 강제 회차 모든 표본은 TURN 중계였다. 핫스팟 전환은 사용자 수행 조건이며 모뎀·기지국·무선 품질을 별도로 추적하지 않았다.
- 시험 후 노트북이 LAN으로 돌아온 뒤 SSH로 JSON·로그를 회수했다. 두 장치의 시계는 동기화 검증하지 않았으므로 시각을 직접 빼서 단방향 지연을 계산하지 않았다. 게임 부하 유지 여부도 이번 자료로 확인하지 않았다.

## 사건 위치와 큐 변화

직접 회차PC의 부족은 첫 진단 후 약109–112초에199.42ms까지 증가했고, 약197초에205.60ms, 약217초에491.52ms가 됐다. 최대399.64ms 수신 간격은 약217초 표본에서 처음 관측돼 같은 진단 구간의285.92ms 부족 증가와 대응한다. 노트북 직접 회차의 부족은 약109–112초에 집중됐다. 두 장치의 비슷한 상대 시각만으로 정확한 동시 사건을 입증하지 않는다.

TURN 회차PC의 부족 증가는 약158초·277초·291초에 관측됐다. 최대211.79ms 수신 간격은 약291초 표본에서 처음 관측됐다. 노트북TURN 회차는PLC로 처리했고 재버퍼·부족으로 넘어가지 않았다.

첫5개 표본 제외 수신 큐 중앙값/P95는 직접PC36.65/55.40ms, 직접노트북39.08/58.52ms, TURN PC37.31/55.75ms, TURN 노트북44.73/59.77ms였다. 시작 쪽 표본5–59와마지막60개 중앙값은 각각35.88→39.68ms,37.71→36.67ms,39.15→36.65ms,49.06→45.02ms였다. 장시간 계속 쌓이는 큐보다는 짧은 공백과 재생 복구가 주요 문제로 보인다. 진단은 약1초 간격이라 모든 순간의 큐 상한은 입증하지 않는다.

PC 입력 불연속은 양쪽 회차 모두 첫·마지막1회로 증가하지 않았다. 노트북은 직접3→5회(약11초·20초),TURN4→5회(약73초)였다. 입력 시각 오류는모두0, 캡처 콜백 간격 최대 관측값은15.25–18.94ms였다. 수백ms 수신 공백을 입력 캡처나 출력 장치 오류만으로 설명할 근거는 이번 자료에 없다. 송신 큐의 관측 대기도 같은 크기로 늘지 않았다. 다만 실제 NIC 송신·수신 시각과 복호화 전후 추적이 없어 모바일망·핫스팟·OS 전달·수신 스케줄링을 구분할 수 없다.

## 판단과 다음 단계

1. 포트포워딩 없이 서로 다른 인터넷 연결에서 직접 통화와TURN 강제 통화가 모두 작동했다.
2. 이번TURN 회차의RTT 중앙값은 직접 회차보다 약4–5ms 높았고 부족·재버퍼는 적었다. 시간과 모바일망 상태를 고정하지 않은 단회 비교이므로TURN이 일반적으로 더 안정적이거나 더 빠르다는 결론은 내리지 않는다.
3. 현재20ms 예비량과60ms 연속PLC 한계로는160–400ms급 도착 공백을 모두 숨길 수 없다. 이를 위해 수백ms 고정 버퍼를 추가하면 지연 우선 목표와 충돌한다. 기본 버퍼를 일괄 확대하지 않는다.
4. 다음 앱 개선 대상은 긴 수신 공백 뒤의 재버퍼·오래된 음성 폐기·회복 시간이다. 먼저 재현 입력에서 기존정책과후보정책의 부족·폐기·복구 지연을 비교하고, 평상시 지연을 늘리지 않는 변경만 검토한다. 원래의 네트워크 공백 자체를 이 정책으로 제거했다고 표현하지 않는다. 실제 공백 원인 분리가 필요하면 송수신경계 추적을 별도 수행한다.

이번 시험은 전체 입→귀 실측이 아니다. RTT에API 버퍼를 단순 합산해 최종 지연으로 발표하지 않는다. 같은 장소의 모바일망 시험이므로 원거리 친구와의 실제 경로도 별도 조건이다.
