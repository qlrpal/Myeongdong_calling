# 노트북 출력 지연 원인 확인: DTS endpoint 효과

2026-10-19. 사용자가 ‘노트북 오디오는 원래대로 복구한다면 어떠한 수정도 허용’한다고 승인한 뒤 수행한 대조다. **노트북에서 관측한 큰 고정 출력 대기의 상당 부분은 DTS endpoint 효과 경로에 따른 것으로 확인했다.** 시험 후 효과 등록값을 복구했고, 복구 후 원래 지연이 돌아오는 것까지 확인했다.

이는 노트북의 특정 Windows 출력 구성에 대한 결과다. 과거 네트워크의 순간 공백·무선 문제까지 DTS로 설명하지 않는다. 수치는 디지털 경로이며 물리 입→귀 지연은 아니다.

## 무엇을 바꿨나

대상은 실제 기본 출력 장치에 등록된 다음 endpoint 효과였다.

- 클래스: `DTS_EFX_APO Class`, `dtsapo64.dll`.
- CLSID: `{599C2638-CC15-4FFE-B16A-9246260D2DF7}`.
- 해당 장치 `FxProperties`의 EFX 목록 `…{d04e05a6-594b-4fb6-a80d-01af5eed7d1d},15`에서 이 항목 하나만 임시 제외했다.
- Realtek EFX 등록과 나머지 SFX/MFX 등록, 샘플 형식·코덱·RTP 정책은 유지했다.

전체 효과 키와 변경할 값의 존재 여부·형식·순서를 먼저 백업했다. 보호된 키의 소유권·ACL을 수정하지 않고, 한시적인 SYSTEM 작업의 백업/복구 권한으로 해당 값만 변경했다. 독립적인6분 복구 예약과 `finally` 복구를 함께 두었다.

효과 체인을 확실히 새로 구성하도록 각 회차 전에 Windows Audio와 Audio Endpoint Builder를 같은 순서로 다시 열었다. 기존→DTS EFX 제외→기존 복구의 A/B/A이며, 시험 동안 일시적으로 다른 앱의 오디오도 영향을 받을 수 있는 장치 전체 변경이었다. 제품의 기본 동작으로 추가하지 않았다.

## 직접 WASAPI 대조

RTP·코덱·재생 큐·리샘플러를 제외하고 장치 기본 float 형식으로 합성 신호를 직접 공급했다. NAudio 캡처와 자동 포맷 변환도 제외한 native loopback 회차를 아래 주요 비교로 삼았다.

| 장치 상태 | 장치 시계→루프백 QPC 중앙값 | 장치 시계→콜백 중앙값 | 유효 신호 |
|---|---:|---:|---:|
| 기존 A1 |80.06ms |100.21ms |6/6 |
| DTS EFX만 제외 B |12.23ms |29.20ms |6/6 |
| 원래 체인 복구 A2 |80.09ms |100.76ms |6/6 |

공통 신호별로 A1/A2 평균과 B를 비교한 QPC 차이 감소의 중앙값은67.85ms였다. 장치 주기480프레임/48kHz, 용량1056프레임, 시계 주파수384000units/s는 모두 같았다. 해당 회차의 장치 버퍼 소진은0회였다.

따라서 ‘장치에 DTS가 등록돼 있으니 의심된다’는 수준을 넘어, **DTS EFX 등록을 제외하면 대기가 줄고 복구하면 돌아오는 개입 결과**를 얻었다. 다만 장치 시계와 루프백의 절대 시각을 물리 DAC/스피커 시각으로 바꾸어 해석하지 않는다. DTS 내부의 어떤 알고리즘이 몇 프레임을 보유하는지까지 분석한 것은 아니다.

## 우리 앱 수신·재생 경로 대조

같은 DTS A/B/A를 실제 `WindowsAudioDevice`·Opus 디코딩·RTP 재생 큐·RAW/GameChat 공유 출력에서 반복했다. 각 장치 상태에서20/10/20ms 수신 여유를 비교했으며, 아래 주요 표는 **각 상태의 마지막20ms 회차**다. 세 회차 모두 RAW 활성, 출력 목표15ms/용량22ms를 유지해 초기 회차의 안전 복귀 차이를 피했다.

| 장치 상태 | 패킷 추가→제출 중앙값 | 제출→루프백 콜백 중앙값 | 패킷 추가→루프백 콜백 중앙값 |
|---|---:|---:|---:|
| 기존 A1 |20.84ms |134.86ms |155.78ms |
| DTS EFX 제외 B |29.76ms |65.05ms |94.57ms |
| 원래 체인 복구 A2 |20.59ms |135.75ms |156.53ms |

모든 회차14/14개 신호가 유효했고, 이 주요20ms 회차들의 PLC·앱 무음 채움은0ms였다. 공통14개 신호별 A1/A2 평균과 B의 전체 지연 차이 중앙값은59.44ms였다. 전체 회차 중앙값 차이는 약61~62ms로 통계 정의가 다르다. 각 열도 같은 신호에서 따로 구한 중앙값이므로 열끼리 더해 전체 중앙값을 만들지 않는다.

B에서는 제출 전 대기가 오히려 더 컸지만 전체 수신 경로는 빨라졌다. 출력 쪽에서 줄인 대기가 전부 앱 큐로 이동했을 뿐이라는 설명과 맞지 않는다. 직접 장치 대조에서 약68ms, 앱 전체 수신 대조에서 약60ms의 차이가 난 것은 측정 구간·큐 위상·콜백 묶음이 다르기 때문이다. 두 개선량을 합산하지 않는다.

추가10ms 회차는 복구 상태에서 PLC20ms를 기록했다. 수신 여유10ms를 제품 기본값으로 적용하지 않았고20ms를 유지했다. 첫 기존20ms 회차에는 출력 안전 복귀1회가 있었으므로, 세 상태 모두 동일 제한 공급을 유지한 마지막20ms 회차를 주요 비교로 명시했다. 유리한 숫자만 선택한 전체 평균으로 발표하지 않는다.

## 원상 복구 확인

1. 원래 DTS·Realtek EFX 목록의 값·형식·순서를 복구했다. 원래 없던 SysFx 해제 값은 다시 존재하지 않는 상태로 복구했다.
2. 최초 변경 전 전체 효과 키 export와 최종 export를 값 단위로 대조했다. **영구 설정 차이는0개**였다. 파일 전체 해시는 달랐지만 차이는 vendor `Volatile` 하위의 실행 중 재생성된 값에 한정됐다. 실행 캐시를 과거 상태로 덮어쓰지는 않았다.
3. Windows Audio·Audio Endpoint Builder는 Running/Automatic으로 확인했다. 서비스 재시작 영향 점검에서 중지된 자동 시작 Realtek 서비스를 발견해 다시 실행했고 시작 유형은 유지했다. 수동 시작 종속 서비스는 중지 상태를 유지했다. 종속 서비스별 시험 전 실행 상태를 별도로 기록하지 못했으므로 개별 런타임 상태가 모두 이전과 동일하다고 주장하지 않는다.
4. Realtek 서비스 실행 후 마지막 native 대조의 QPC 차이는79.68/80.08/79.95ms, 각6/6개 신호였다. 원래 DTS 출력 경로가 다시 적용된 것을 확인했다.
5. 임시 예약 작업0개, 통화·진단 프로세스0개를 확인했다. 서비스 시작 유형·드라이버·장치 기본 형식·사용자 음량은 변경하지 않았다.

**현재 노트북은 DTS가 다시 적용되는 원래 효과 설정이다.** 약95ms는 DTS를 임시 제외했을 때의 디지털 수신 경로 관측값이며, 현재 제품의 영구 개선 성능이나 전체 통화 지연으로 발표하지 않는다.

## 앞선 실패·음성 결과의 해석

- 첫 보호 키 쓰기는 거부돼 설정이 바뀌지 않았다. 변경 전 중단된 실행은 근거에서 제외했다.
- 첫 SysFx 해제 값 비교는 Audiosrv만 재시작했고 지연 변화가 없었다. 이후 DTS 대조와 서비스 재구성 조건이 다르므로, Windows 설정 화면의 모든 ‘향상 기능 끄기’ 방법이 효과 없다고 일반화하지 않는다.
- 스트림 효과 API의 목록이 비어 있던 것과 별도 미초기화 APO가 지연0을 반환한 것은 endpoint 효과가 없다는 증거가 아니었다. 이번 등록 체인 개입 결과를 우선한다.
- 음향 시험은 검출에 실패했으므로 입→귀 지연으로 사용하지 않는다. 이번 개입으로 확인한 것은 Windows 디지털 출력 경로에서 DTS EFX가 만드는 큰 추가 대기다.

## 프로젝트에 대한 의미

WebRTC·TURN·Opus를 교체해야 해결되는 종류의 큰 대기는 아니었다. 현재 RAW 요청만으로도 이 장치의 DTS endpoint 효과를 우회하지 못했다. 다음 최적화 판단은 앱이 관리하는 대기와 장치 효과 대기를 구분해서 해야 한다. 사용자 장치의 효과 등록을 자동 삭제하는 기능을 제품에 넣지 않았다.

원본과 자동 복구 기록은 Git 제외 경로 `native/.local/output-clock-058/`에 있다. 주요 native 원본은 `dts-trial-022802/`, 앱 수신 대조는 `receive-trial-023042/`, 최종 복구 확인은 `restoration-final.json`·`restoration-semantic.json`이다. 서버·배포 ZIP·앱 기본 정책은 변경하지 않았다.
