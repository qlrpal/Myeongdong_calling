## 수정 전 발견

같은 최신 커밋 빌드를 실제 PC/노트북에 준비하고, 수동 상세 추적 없이 자동 기록만 켠 직접/TURN 각60초 시험을 실행했다. 별도 SSH 제어 프로세스가 RunId로 검증한 자체 노트북 시험 프로세스만100ms 정지하고 finally에서 즉시 재개했다. 요청100ms이며 실제 정지 시간이 정확히100ms라는 보장은 없다. 두 시험의 기능 검사는 통과했지만 **직접 시험 노트북의 로그 검증은 실패**했다.

원인은 자동 기록의 워밍업 기준이 참가 준비 시점이었던 것이다. 연결 준비에2초 이상 걸리면 상대가 연결되기도 전에 캡처 초기화 공백이 첫 사건으로 동결될 수 있었다. 실패 자료의 노트북은 capture-gap으로792개를 보존했지만 캡처/프레임 생성/송신 dequeue만 있었고 상대별 송신 API·수신 콜백·입장·재생·렌더가 없었다. 인위적 통화 정체가 나중에 발생해도 기록이 이미 동결돼 원인 분석에 쓸 수 없었다. 이전128의 성공만으로 이 초기화 순서 문제를 배제할 수 없었다.

## 수정

- `IncidentRecorder.Reset(at, armTriggers:false)`로 통화 준비 시 배경 기록은 시작하되 자동 트리거는 대기한다.
- `WebRtcCallEngine`은 **인증 후 콜백에서 협상된 오디오 페이로드 형식**을 처음 수신할 때 `ArmTriggers`를 호출한다. 원시 RTP/UDP 헤더로 활성화하지 않는다.
- 그 첫 수신 시각부터2초를 제외한다. 후속 패킷은 최초 활성화 시각을 미루지 않는다. 연결 전 장치 문제는 기존 오류/카운터/배경 기록으로 확인한다.
- `TriggerArmedAt`을 JSON에 추가하고 UI 대기 상태·측정 한계·사용 가이드를 갱신했다. 프레임·큐·음성 버퍼·전송 정책은 바꾸지 않았다.
- 연결 전100초가 지나도 조기 동결되지 않고, 첫 수신 뒤 워밍업과 재호출 시각 고정·실제 후속 트리거가 동작하는 회귀를 추가했다.
