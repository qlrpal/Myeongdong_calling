# EXTREME-131 — 선택적 소켓·UDP·SRTP 경계 대응

2026-10-31 / 기준 `baadb47`에 미커밋129/130을 보존했다. 이번 작업은 로그의 빈 경계를 채우는 진단 구현과 실제 두 PC 검증이다. 지연 최적화 성공이나 기존 문제 해결을 선언하지 않는다.

## 구조와 조사 대상

기본 기록은 프레임 생성→상대별 송신 API→인증된 RTP 콜백→입장/읽기/렌더를 연결하지만, 소켓 호출·UDP 반환·SRTP 거부는 관측하지 못했다. 이전106의 NIC 소프트웨어 경계 시험은 반복하지 않았다. 이번에는 같은 패킷으로 SDK 안의 대기를 구분하는 데 집중했다.

## 수정

- `sdk-diagnostics/prepare.py`: 기존 수정 SDK 캐시/소스 해시를 확인하고 별도 `.local/sdk-boundary-<GUID>`에 복제한다. 고정 앵커에만 소켓 요청/완료 관측, UDP 반환, SRTP 전후 계측을 삽입한다. 기본 캐시·배포본·일반 bin은 교체하지 않는다.
- `sdk-diagnostics/BoundaryProbe.cs`: 최대64,000개/120초, 값 형식·TryEnter 순환 메타데이터다. 평문 Opus PT111 헤더를 TURN 포장 안에서도 식별한다. 인증 전 헤더를 미디어 상태 갱신에 사용하지 않는다. 패킷 내용/음성/키/토큰/상대 주소는 보관하지 않는다. 활성 송신에는 완료 콜백 연결용 SendToken 할당이 추가된다.
- `TransportProbe/Diagnostics/SdkBoundarySession.cs`와 `Program`: 별도 SDK에만 존재하는 API를 반사로 연결한다. 로컬 실제 WebRTC/파서/상한/SRTP 회귀 명령을 추가했다. 일반 SDK에 활성화를 요청하면 명시적으로 실패한다.
- `PairFunctionalProbe`: 프로세스 한정 `MYEONGDONG_TEST_SDK_BOUNDARY=1`을 양쪽 핸드셰이크에 포함한다. 참가 전 시작, 첫 사건 동결/기준선 종료/실패 때 정지하고 오디오 정리 후 JSON으로 내보낸다. 기본은 꺼짐이다.
- `Analysis/analyze_sdk_boundaries.py`: 앱 프레임 식별과 RTP 순번을 구분해 연결한다. 같은 호스트 QPC 구간과 같은 패킷 쌍의 양쪽 간격 차이만 계산한다. 기록 누락/거부/중복/공백을 별도 표시한다. 독립 시계 원점과 창 밖 패킷을 다루는 회귀 검사를 추가했다.

분석 중 누락 식별자를 defaultdict에 조회하면서 빈 항목이 생겨 중복 수가 음수가 되는 표시 오류를 발견해 수정하고 회귀 검사로 보강했다. 패킷 자체의 중복이나 SDK 오류가 아니었다.

## 비교 조건

독립 Windows PC/노트북, 실제 공유 캡처/출력·합성 PCM 대체, 같은 앱/검사 바이너리·10ms Opus·20ms 수신 여유·상대별 기존 출력이다. 직접 연결 계측 끔→켬→끔 각60초, 강제 TURN 계측 켬60초와 각 실행의 음소거/입퇴장/재참가/정리를 수행했다. 새 방/RunId를 썼고 게임 부하는 가하지 않았다. 장치·전원 계획·시스템 라우팅·공유기 설정은 바꾸지 않았다.

진단 SDK `10.0.17+myeongdong.2.boundary1`, SHA256 `89F9E5716CAC53B7B32884A0C5C39F02503B56FE2C1A3D24A9372BEFACBF9A95`다. 기본 SDK는 `10.0.17+myeongdong.2`, SHA256 `F997C495945FABFC00C47C2C63C75330BD8BDD2C6F795F70EA3111D1A0503376`로 그대로다. 기존 ProductionPatched 필드는 기본 보안 패치 표식을 확인하는 것이므로 진단 빌드 판별은 informational version·DiagnosticOnly·manifest를 함께 본다.

## 계측 비용과 한계

직접 A1/B/A2 CPU는 PC0.0387/0.0405/0.0408코어, 노트북0.1144/0.0797/0.1003코어였다. 할당은 PC77.86/78.29/78.01MB, 노트북77.87/78.10/77.89MB였다. GC 정지는 PC8.25/7.07/8.75ms, 노트북25.88/12.91/20.73ms였다. B의 SDK 수집은60초 전체 활성, A2의 자동 앱 기록은 자연 사건으로 약74%에서 동결됐다. 할당 증가·순서/자연 변동이 있으므로 비용0이나 성능 개선으로 해석하지 않는다. A는 진단 SDK 내부 기록을 끈 비교이며, 계측 분기 자체가 없는 기본 SDK와 완전히 같지는 않다.

TURN 상세 수집은 자연 사건 동결로 약48% 구간에서 멈췄다. TURN A/B/A는 하지 않았으므로 TURN의 PLC를 계측 때문에 늘었다/늘지 않았다고 인과 판정하지 않는다. 기록 후 정리/기능 검사는 계속 수행했다.

EndReceiveFrom/ReceiveFrom 반환은 OS 도착 시간이 아니라 수신 코드가 실행되어 반환한 시각이다. 소켓 완료도 콜백 스케줄링을 포함한다. 따라서 송신 OS/드라이버, 무선·메시/AP, OCI TURN 경로/서버, 수신 OS/드라이버/콜백 대기를 물리적으로 분리하지 못했다. 이번에는 Npcap/ETW를 새로 수집하지 않았다. 이전106의 경계를 이번 동일 패킷 관측으로 대신 주장하지 않는다.

실제 게임 부하·3/6인·장시간·다른 회선·외부 친구·물리 입→귀·802.11 모니터/AP 내부 시각 측정은 미실시다. 첫 사건 캡슐 밖의 모든 원인을 배제하지 않는다.
