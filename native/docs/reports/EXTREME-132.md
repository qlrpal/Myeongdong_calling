## 방법

- 실제 독립 Windows PC와 노트북을 기존 OCI TURN UDP로 연결했다. 같은10ms Opus·20ms 수신 여유·기존 상대별 WASAPI 공유 출력·합성 PCM 대체를 유지했다. 통화 소켓만 기존 LAN 주소를 지정했다. 게임 부하·개인 마이크/이어폰 최적화는 하지 않았다.
- 세 실행 각각 기준선60초와 음소거/퇴장/재참가/종료를 검사했다. PC/노트북의 실제 NIC GUID·IP와 OCI STUN 응답으로 현재 공인 주소를 확인했다. 별도 관리자 확인창은 필요하지 않았다.
- 양쪽 Npcap은 OCI 주소의 UDP3478만 비 promiscuous·snaplen128·125초·16MiB 상한으로 수집했다. `host_hiprec_unsynced`를 사용했다. 서버 ens3는 자체 집 공인 주소의 UDP3478만 snaplen128·125초·100,000패킷 상한으로 캡처했다. 서버 timeout 종료124는 예상한 제한 종료이며 tcpdump 통계와 pcap 유효성을 별도 확인했다.
- 모두 자체 시험의 제한된 원시 암호화 prefix/STUN 메타데이터 캡처다. 음성 평문을 저장하지 않지만 원시 파일을 순수 메타데이터 로그로 표현하지 않는다. 로컬 `.local/extreme-132/` 및 노트북 고유 시험 폴더에만 보존하며 Git 제외다. 서버 원본은 SSH stdout으로 로컬 파일에 받아 서버 캡처 파일을 남기지 않았다.
- SSRC·RTP 타임스탬프·wire 순번으로 같은 패킷을 연결했다. 캡처의 절대 epoch와 앱 QPC 또는 서로 다른 호스트 절대 시각을 직접 빼지 않는다. 각 경계의 같은 패킷 쌍 간격을 비교하고, 서버 관측 체류만 같은 서버 시계에서 직접 계산했다.

## 판정과 남은 범위

이번에 대응한 큰 사건들은 수신 SDK/앱 전달이나 TURN 내부 체류보다 **송신 측 소프트웨어 NIC 관측↔OCI 서버 인터페이스 관측↔수신 측 소프트웨어 NIC 관측** 사이에서 주된 간격 증가가 나타났다. 업로드 쪽과 다운로드 쪽 사례가 모두 있다.

이것은 인터넷 회선만의 확정이 아니다. 각 중간 구간에는 NIC 하위 드라이버/펌웨어·무선/AP/메시·NAT/통신사/인터넷·OCI 가상화/하위 네트워크가 포함될 수 있다. Npcap/ens3는 물리 송수신 시각이 아니며 캡처 이후 큐도 존재할 수 있다. AP 내부 기록/모니터 모드 RF/메인 직결 유선 관측은 이번에 확보하지 않았다. 071~076의 로컬 증거와 양립하지만 서로 다른 사건을 같은 원인으로 확정하지 않는다.

다른 회선/독립 사용자·게임·3/6인·장시간·물리 입→귀 측정·캡처 영향 A/B/A는 미실시다. 이미106에서 캡처 꺼짐에도 공백이 재현됐지만 이번 캡처 영향0을 증명하지는 않는다. 추가 버퍼 축소나 네트워크 설정 변경을 해결책으로 채택하지 않았다.
