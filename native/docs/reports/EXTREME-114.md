# EXTREME-114 — 공개 서버 도달성과 두 PC 직접/TURN 회귀

한국 시각2026-10-28, `codex/extreme-latency`, HEAD `78ef68a`와109–113 미커밋 소스의 기존 Release 바이너리를 사용했다. 제품 알고리즘·기본값·기존 dist는 변경하지 않았다.

## 가설과 접속 확인

113의 공개 HTTP 실패가 OCI 서비스 중단인지, 주소/경로 문제인지 분리했다. PC와 OCI 양쪽 DNS 조회에서 공개 도메인은 OCI의 공인 주소와 다른 주소로 해석됐다. 일반 도메인 HTTPS health는 TCP 연결 시간 초과였다. 반면 OCI SSH는 성공했고 실제 서비스명 `voice-native`, `nginx`, `coturn`은 모두 active/running이었다. OCI 내부 HTTP health와 `curl --resolve`로 OCI에 연결하면서 원래 도메인의 TLS 인증서를 검증한 외부 HTTPS health는 HTTP200이었다.

따라서 현재 도메인의 주소와 OCI 배포 위치 불일치가 확인됐다. DNS를 OCI로 고친 뒤의 일반 앱 성공까지 입증한 것은 아니다. 초기 조회에서 사용한 `native-signaling`이라는 서비스명은 실제 unit명이 아니므로 그 inactive 결과를 서버 중단 증거로 사용하지 않았다. DNS·방화벽·라우팅·서버 설정은 변경하지 않았다.

## 시험 전용 접속과 한계

PC의127.0.0.1 임시 HTTP 프록시가 OCI HTTPS로 요청을 전달한다. 연결 주소만 OCI로 지정하고 hostname/SNI 및 인증서 검증은 원래 도메인을 유지한다. 노트북은 인증 SSH의127.0.0.1 역방향 포워딩으로 같은 프록시에 접속한다. 세션 토큰·TURN 비밀값·요청 URL은 로그에 기록하지 않는다.

TURN 설정도 같은 도메인을 사용하므로 시험 응답 안에서만 TURN UDP 주소의 hostname을 OCI IP로 대체했다. 임시 인증 정보와 UDP3478은 그대로 유지했다. 운영 설정이나 클라이언트 기본값의 수정이 아니다. 음성은 이 HTTP/SSH 프록시를 통하지 않으며 직접 시험은 LAN UDP, 강제 중계는 실제 OCI TURN UDP다. 일반 사용자의 공개 URL 검증을 대체하지 않는다.

실제 PC와 노트북, 합성 음성 입력 교체, WASAPI 공유 장치, 기본10ms·네이티브 Opus·수신 여유20ms·기존 출력, 통화별 LAN 지정 조건이다. 각 baseline은30초이며 전달·음소거/해제·양쪽 퇴장/재참가·종료의6검사를 수행한다. 게임 부하·물리 입→귀·독립 외부 회선·장시간 품질 시험은 아니다.

## 결과

- 첫 프록시 시도는 Node DNS callback 형식 오류로 HTTP502에 실패했다. 시험 도구의 오류로 분리하고 callback을 수정한 뒤 새 ID로 전체를 실행했다. 제품 실패나 음성 후보 비교에 사용하지 않았다.
- 직접 연결 첫 실행: 양방향 baseline·음소거/해제·PC 재참가는 양쪽 성공했다. 노트북 재참가 중 HTTP `ResponseEnded`가 발생해 노트북은 요청 실패, PC는 상대 연결/디코딩 대기 시간 초과로 전체 실패했다. 시험 프록시·HTTP 연결·네트워크·운영 서버 중 어느 경계인지 미분리이며 앱 오디오 결함으로 단정하지 않는다.
- 강제 TURN: 양쪽6검사 및 보고서 병합을 통과했다. baseline의 PLC 오디오 시간은 PC20ms/약0.067%, 노트북7.5ms/약0.025%였다. 양쪽 늦은 폐기·재버퍼·PCM 부족·렌더 empty·송신 폐기는0이었다. 노트북 캡처 불연속2회는 별도 남아 있다. 새 RTCP RTT 중앙값은 약22–23ms이며 입→귀 지연이 아니다.
- 직접 연결 반복: 동일한 프록시 구현·빌드·설정의 새 RunId에서 양쪽6검사 및 병합을 통과했다.30초 baseline의 PLC·늦은 폐기·재버퍼·캡처 불연속은 양쪽0이었다. 첫 실행의 HTTP 실패는 재현되지 않았지만 해결됐다고 선언하거나 성공 반복으로 원래 실패를 덮지 않는다.

같은 PC 쌍의 직접/중계 연결 기능 확인이며 가정 밖 친구 환경의 품질을 보장하지 않는다. 짧은 표본을 장기 끊김 발생률로 일반화하지 않는다. 별도 Node 검사도 함께 실행했으므로 이번 CPU/GC 값으로 최적화 우위를 판단하지 않는다.

11개 Node 도구 회귀 검사는 모두 통과했다. 제품 소스·바이너리는 바꾸지 않아 이번에는 전체 빌드/Integration을 반복하지 않았다. 시험 후 자체 TransportProbe·임시 프록시·노트북 격리 프로세스 잔류0을 확인했고 인증 SSH 포워딩을 해제했다. 운영 DNS·서버·VPN·OS 라우팅·방화벽·장치 기본값과 기존 dist는 변경하지 않았다. 공개 도메인 주소 문제는 미해결로 남긴다.

## 원본·재현

Git 제외 `native/.local/extreme-114/connectivity-results.json`과 `initial-analysis.json`에 양쪽 원본 위치·병합 결과가 있다. `invalid-proxy-results.json`은 프록시 구현 오류 시도의 위치 기록으로 정식 결과가 아니다. 후속 직접 반복은 `direct-repeat` 하위의 별도 실행으로 보존한다. 사용자 네트워크 주소·비밀값은 이 문서에 싣지 않는다.

일반 재현은 [두 PC 가이드](../PAIR-CHECKS.md)의 `-Route direct/relay -ObserveSeconds 30 -ReserveMs 20 -MediaAddress LOCAL_IP -NoBuild`를 양쪽에 같은 RunId와 반대 역할로 실행한다. 운영 도메인 도달성이 정상이어야 한다. 이번 임시 우회는 개발용 시험이며 제품 실행법에 기본으로 추가하지 않는다.
