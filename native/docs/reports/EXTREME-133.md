# EXTREME-133 — 추가 장비 없는 제한 부하·무선 관측 대조

2026-11-01 / `codex/extreme-latency`, HEAD `baadb47`와 미커밋129~132를 보존했다. 추가 하드웨어 구매/교체 없이 가능한 관측에 한정한다. 이 문서는 이번 임시 도구의 오류 자료와 수정 후 유효 자료를 구분한다.

## 가설과 변경 범위

1. 업로드 또는 다운로드가 현재 로컬 분기의 대기를 가역적으로 변화시키는가?
2. 게이트웨이와 OCI가 함께 늦을 때 다른 NIC와 측정 루프도 함께 늦는가?
3. 큰 왕복 중 얼마가 소프트웨어 NIC Tx/Rx 사이에 있고 앱/소켓의 잔여 관측은 얼마인가?
4. 현재 권한과 드라이버가 추가 ETW 또는 모니터 모드 관측을 제공하는가?

기존 스캔·MCC·qWAVE·보안/무선 모드 설정 대조와072의 단일 DPC 실행시간 검사는 반복하지 않는다. OS 경로·Tailscale·SSID·AP·드라이버·전원·오디오 설정·배포본을 바꾸지 않는다. 측정용 소켓/SSH 프록시에만 source와 IP_UNICAST_IF를 지정한다.

## 시험 방법

- PC의 기존 이더넷(메시 버디 경유)과 메인2.4GHz Wi-Fi를 동시에 관측한다. 이더넷을 메인 직결 유선으로 표현하지 않는다.
- 각 NIC에서 로컬 게이트웨이의 비재귀 CHAOS TXT DNS와 OCI coturn의 nonce STUN Binding을 송수신하고, 별도127.0.0.1 UDP 자체 echo를 함께 기록한다. 자체 echo는 무선/실제 LAN 왕복이 아니다.
- 한 시리즈는 기준선→업로드→기준선→다운로드→기준선 각30초다. 각 단계 양끝3초를 제외한다. 판정 창은 송신 시각 기준이며 늦은 응답의 도착 단계로 옮기지 않는다.
- 자체 OCI SSH에만1,500,000bytes/s(12Mbps)로 제한한다. 한 부하 단계는약45MB·30초이며 서버 명령은45초 상한, 연결/keepalive도 제한한다. 회선 용량·포화를 측정한 시험은 아니다. 단순 속도 제한을 SQM/bufferbloat 확정이나 배제 근거로 사용하지 않는다.
- UDP 요청 목표 주기는20ms이나 실제 Windows 대기/스케줄링 때문에 정확한50pps를 보장하지 않는다. 응답 수·송신 간격·실제 요청 빈도를 보고한다. 자체 echo가 작다는 것만으로 장시간 스레드 정지를 제외하지 않고 송신 진행과 다른 NIC 응답도 함께 확인한다.
- 선택한 시리즈에서만 시험용 UDP 두 포트를 Npcap 비 promiscuous·96바이트·180초·8MiB 상한으로 기록한다. 같은 nonce/순번의 왕복 시간을 동일 호스트 캡처 시계로 계산하고 앱 단조 시계의 왕복 **기간**과 비교한다. epoch와 단조 시각 원점은 직접 빼지 않는다.

## 먼저 발견한 임시 검사 도구 오류 — 원인 판정에서 제외

초기 Python 수집기의 수신 처리와 timeout 정리에서 송신 카운터와 같은 `seq` 변수를 재할당했다. 늦은 응답이 송신 카운터를 되돌려 식별자를 재사용할 수 있었다. 기존 `ethernet`/`wifi`/`wifi-repeat`/`wifi-confirm` 네 자료에 중복 식별자가 각각3924/1711/121/87개 있었고, 이 자료로 계산했던227ms 사건·업로드 P95 급증 등 수치는 **원인 판정에서 철회**한다. 수신 버퍼/드라이버/무선의 중복 증거로 사용하지 않는다.

초기 캡처의 앱 미대응89개도 실제 관측 누락이 아니라2 Tx/2 Rx의 모호한 재사용 식별자였다. 이를 물리 손실이나 Npcap 결함으로 해석하지 않는다. 첫 수정 검토에서 timeout 루프의 재할당도 발견해 `fixed-wifi-a`를 자체 프로세스 트리만 종료하고 폐기했다. 성능 결과로 인정하지 않는다.

송신 순번은 독립 `itertools.count`로 생성하고 수신/timeout 변수와 분리했다. 분석기는 lane/sequence 중복을 발견하면 오류로 거부하도록 추가했으며 실제 네 초기 자료가 모두 거부됨을 확인했다. 원본과 초기 계산 파일은 지우지 않고 `.local/extreme-133/INVALID-INITIAL-TRIALS.json`·`invalid-trial-audit.json`으로 무효를 표시했다. 이 임시 도구는133에서 새로 작성한 것이며131/132의 C# TransportProbe/SDK 기록과 별개다.

## 새로 사용 가능한 관측의 한계

- 현재 실행 토큰은 Windows 관리자가 아니다. 고유 Voice133 WPR 시작은 프로필 검증 뒤0x80070005 접근 거부로 끝났다. 세션이 시작되지 않았고 UAC를 띄우거나 사용자를 기다리지 않았다. 최초 filemode 누락 검증 실패도 별도 보존하며 측정 결과로 사용하지 않는다.
- PC Realtek과 노트북 Intel의 WlanHelper 지원 모드 조회는 모두 `managed`만 반환했다. 현재 드라이버가 모니터 모드를 제공한다는 근거가 없어 전환을 시도하지 않았다. 하드웨어의 영구적 지원 불가나 다른 OS의 지원 여부까지 판정하지 않는다.
- 일반 어댑터 error/discard0을802.11 재전송0으로 사용하지 않는다. AP의 재전송/채널 점유/내부 큐와 U-APSD 서비스 시각은 새로 측정하지 못했다.
- 부분 수집된 OCI vmstat174개 초 표본은 CPU user+system 최대6%, idle 최소92%, steal 최대1%였다. 초기 Ethernet 예비 시험 일부와 겹치는 보조 자료이며 모든 시리즈/사건의 서버 CPU를 배제하지 않는다.

## 도구와 재현 자료

`Analysis/analyze_directional_load.py`는 단조 시각의 송신 구간·양끝 제외·RTT/timeout/실제 송신 빈도·전후 기준선을 계산한다. `analyze_probe_capture.py`는 고유 nonce/순번과 같은 호스트 캡처 왕복을 연결하고 모호한 대응은 거부한다. 각 분석기에 순번 재사용·창 경계·독립 시계 원점·중복 관측 거부 회귀를 추가했다. 제품/SDK 오디오 실행 경로는 수정하지 않았다.

## 수정 후 유효한 Wi-Fi 반복 결과

`valid-wifi-a`/`valid-wifi-b`는 같은 수정 도구·같은 캡처·같은 부하/연결 조건으로 새로 실행했다. 두 자료 모두 분석기의 lane/sequence 유일성 검사를 통과했다. 앱의 Wi-Fi 응답은 캡처 Tx/Rx에 모두 유일하게 대응했고 미대응/모호한 식별자는0이었다. Npcap은 각각20,964/20,940패킷, 보고된 드롭0이었다. 대응 DNS 응답5241/5235개는 모두rcode4(NOTIMP)였다. 비재귀 로컬 질문의 응답을 외부 인터넷 왕복으로 해석하지 않는다.

| 시리즈 / P95 | A1 | 업로드 | A2 | 다운로드 | A3 |
|---|---:|---:|---:|---:|---:|
| Wi-Fi A 게이트웨이 |16.06ms|15.61ms|15.33ms|9.89ms|14.95ms|
| Wi-Fi A OCI |46.12ms|24.50ms|47.53ms|20.43ms|47.73ms|
| Wi-Fi B 게이트웨이 |17.11ms|15.17ms|14.18ms|11.62ms|15.75ms|
| Wi-Fi B OCI |48.46ms|24.34ms|46.79ms|21.38ms|47.77ms|

실제 전송은 업로드 약11.99Mbps, 다운로드 약11.83Mbps였다. 각 업로드는 수신 측 byte 수45,023,232와 일치하고 정상 종료했다. 분석 창의 모든 lane timeout/send error는0이었다. UDP 실제 요청 빈도는약33pps로 목표50pps와 다르며, 이 값을 음성100pps 환경에 그대로 일반화하지 않는다.

유효 반복에서는 초기 무효 자료의 업로드 악화가 재현되지 않았다. 업로드가 항상 지연을 만든다는 결론은 기각한다. 다운로드 시 Wi-Fi의 로컬/외부 P95가 양쪽 전후 기준선보다 낮아졌고 두 시리즈에서 같은 방향이었다. 그러나 순차 짧은 대조·미통제 주변 RF·포화 미검증의 한계가 있다. 업로드와 다운로드의 TCP/ACK/스케줄링 패턴도 다르다. **U-APSD·절전·재전송·특정 큐 하나를 원인으로 확정하거나 유지 트래픽을 앱 해결책으로 채택하지 않는다.**

## 같은 로컬 요청의 관측 경계

Wi-Fi B의 sequence4169는 A3 기준선에서 다음과 같았다.

| 같은 송신 주기의 관측 | 왕복 |
|---|---:|
| Wi-Fi 게이트웨이 앱 RTT |78.6788ms|
| 같은 DNS 요청의 Npcap Tx→Rx |78.6260ms|
| 두 왕복 기간의 잔여 |0.0528ms|
| Wi-Fi OCI |83.1316ms|
| 이더넷 게이트웨이 대조 |1.8185ms|
| 이더넷 OCI 대조 |9.8893ms|
| 자체 echo |0.0365ms|

이 사건은 인터넷만의 문제나 프로세스 전체 정지 하나로 설명하기 어렵고 로컬 Wi-Fi 분기 후보를 강화한다. 해당 요청의 큰 왕복은 이미 소프트웨어 NIC 관측 사이에 있었다. 양옆 주기의 송신도 계속됐으며 자체 echo 하나만으로 스케줄링을 배제한 것은 아니다. NIC 하위 드라이버/펌웨어·무선 매체·AP 처리/큐·하위 수신 전달 중 어디인지는 여전히 미분리다.

분석 창에서 대응된 전체 Wi-Fi 요청의 앱 RTT−캡처 RTT 최대는 A0.4092/B0.6624ms였다. 캡처 게이트웨이 왕복 최대는62.293/78.626ms였다. 이는 같은 호스트의 두 **기간** 비교이며 Tx 하드웨어 완료·전파 시각 또는 입→귀 지연이 아니다. SDK/음성 앱을 사용하지 않은 UDP 대조이므로131/132와 같은 원인이나 음성 통화 개선을 입증한 것은 아니다.

## 유효한 이더넷 부하 대조

`valid-ethernet`도 수정된 동일 식별자 도구로 다시 실행했다. 이 시리즈에는 Npcap을 추가하지 않았으며 Wi-Fi 두 시리즈와 계측 비용 A/B로 비교하지 않는다.

| P95 | A1 | 업로드 | A2 | 다운로드 | A3 |
|---|---:|---:|---:|---:|---:|
| 이더넷 게이트웨이 |3.80ms|3.35ms|3.62ms|3.33ms|3.52ms|
| 이더넷 OCI |13.11ms|13.65ms|13.13ms|13.62ms|13.22ms|

게이트웨이 최대는 업로드51.09ms, 기준선30.34/28.14/34.01ms, 다운로드33.09ms였다. 한 최대값만으로 부하 원인을 확정하지 않으며,12Mbps에서 일관된 P95 악화는 입증하지 못했다. 링크가 포화됐다고 검증하지 않았으므로 bufferbloat 가설 전체를 배제하지 않는다. 이더넷은 계속 메시 버디의 무선 백홀 경로다.

## 채택·기각·미실시

- **채택:** 분석기의 중복 식별자 거부·송신 시각 기준 구간·실제 요청 빈도·같은 호스트 왕복 기간 비교와 회귀 검사. 수정 후 유효 자료는 Wi-Fi A26,203개/B26,174개/이더넷26,169개이며 중복0, 분석 창 send error/timeout0이다.
- **기각:** 초기 자료의 수치·업로드가 항상 악화 원인이라는 해석·순번 중복을 NIC/무선 결함으로 보는 해석. 제품의 버퍼·프레임·우선순위·유지 트래픽·네트워크 설정 변경은 채택하지 않았다.
- **남은 추정:** 로컬 Wi-Fi 분기에서 대기하고 트래픽 패턴에 따라 전달이 달라지는 현상과 일치한다. NIC/드라이버/펌웨어의 절전·묶음 처리·무선 경쟁/재시도·AP 스케줄링/큐는 여전히 직접 분리하지 못했다. 두 짧은 반복을 보편적 원인/완화 효과로 일반화하지 않는다.
- **미실시:** 관리자 ETW의 새로운 실행 대기 분석, 실제 무선 모니터 캡처, AP 내부 큐/재전송/절전 시각, 포화 검증, 실제 게임·음성 통화 동반 부하·독립 외부 사용자·물리 입→귀 지연. 노트북은 지원 모드 조회만 했고, 이번 RTT는 PC 두 NIC와 OCI의 시험이다.

## 종료 검증과 재개 기준

WLAN Operational 조회는 오류 없이0건이었다. 이것을 스캔/재시도/절전 없음의 증거로 사용하지 않는다. 무선 고급 속성 전후 차이0, 원래 SSID/채널 유지, WPR 비실행, 자체 Python/SSH 프록시·dumpcap0, 서버의 자체 제한 부하/관측 프로세스 없음 확인. 노트북의 연결·오디오·파일을 바꾸지 않았으므로 복구할 변경은 없었다. OS 라우팅·VPN·장치·전원·AP·드라이버·기존 dist·공개 릴리즈는 유지했고 커밋/푸시는 하지 않았다.

새 분석기 두 개의 회귀와 기존 SDK/캡처 체인 회귀를 통과했고 `git diff --check`도 통과했다. 이번 변경은 오프라인 분석/문서이며 앱 빌드·전체 verify Integration은 다시 실행하지 않았다. 제품 지연 감소나 근본 원인 해결로 표시하지 않는다.

추가 장비/새 관리자 권한 없이 같은 probe/캡처를 더 반복해도 현재 관측 한계를 해소한다고 보장할 수 없다. 이번 결과를 [네트워크 조사 기준](../NETWORK-INVESTIGATION.md)에 통합했고, 다음에는 새 관측 경계 또는 구체적 반증 조건이 생겼을 때만 해당 후보를 다시 시험한다. 개인 장치·드라이버 설정을 자동 변경하는 해결책은 넣지 않는다.

유효 원본/요약은 `.local/extreme-133/valid-{wifi-a,wifi-b,ethernet}/`, `valid-summary.json`, 캡처 검증은 각 `capture-analysis.json`, 종료 상태는 `final-state.json`, 지원/권한 한계는 `wlan-supported-modes.txt`, `laptop-supported-modes.txt`, `wpr-start.log`에 보존한다. 초기 무효 자료와 중단 자료도 보존하며 향후 분석 시 반드시 무효 표시를 먼저 확인한다.

2026-11-01 정합성 점검에서 초기 계산 파일6개는 해시를 유지한 채 `.INVALID.json`으로 이름을 분리했다. raw 원본은 변경하지 않았다. `.local/extreme-133/TRIAL-INDEX.json`을 자료 상태의 입구로 사용하며 `computed-quarantine.json`에 원래/현재 계산 파일 위치와 해시를 보존한다. 예전 `all-analysis.json`은 초기 무효4개만 담은 집계였으므로 현재 `all-analysis.INVALID.json`이며 최종 유효 집계로 사용하지 않는다.
