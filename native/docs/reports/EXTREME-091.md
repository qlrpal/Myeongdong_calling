# EXTREME-091 — 공백 이후 재시작 최적화 후보 반증

2026-10-25. 지연을 우선하되 효과가 작은 변경으로 PLC/폐기를 늘리지 않는 것을 기준으로 평가했다. 기존089의 PC/노트북 A/B/A 각 마지막30초 기록6개를 사용했다. 새로운 장치/드라이버/네트워크 설정 변경은 없었다.

## 1. 재시작 여유 축소

가설: 연속 PLC 뒤 재버퍼링에서 다시 모으는 여유를 줄이면 불필요한 복구 대기가 줄어든다.

기존 동작과 공백 재시작 목표5/10/15ms를 각 기록에 대조했다(총24회). 초기 시작은 유지하고, 비정수 장치 요청/입력 묶음 위상 보호 및 상대 긴 프레임 하한은 유지했다. 한 기록의 이득을 다른 기록의 악화와 숨겨 합격 처리하지 않았다.

각 재생의 앞2초·뒤1초를 제외한 구간 합계(약27초×6개, 서로 겹칠 수 있는 창이므로 독립 통화 시간으로 해석하지 않음):

|재시작 정책|PLC 합계 ms|출력 부족 합계 ms|회복 폐기 합계 ms|
|---|---:|---:|---:|
|기존|1062.50|192.85|401.48|
|5ms 후보|1217.50|212.52|461.56|
|10ms 후보|1192.50|215.15|454.12|
|15ms 후보|1102.50|190.19|412.98|

대부분 조건에서 PLC가 증가했다.5ms 후보의 특정 PC 기록에서는 큐 중앙값이 약0.52ms 줄었지만 PLC는35ms, 부족은8.5ms 늘었다.15ms 후보는 일부 기록에서 조금 나아졌지만 다른 기록의 PLC가 늘었고, 여섯 기록 전체의 큐 중앙값 개선도 일관되지 않았다. 지연 감소 이득이 작고 악화가 있어 채택하지 않았다.

## 2. 충분한 후속 패킷이 있을 때 빈 RTP 구간 생략

가설: 이미 충분한 후속 데이터가 있는데 누락 구간을 PLC로 출력하는 것이 불필요하게 복구 지연을 만들 수 있다.

현재 재생 위치의 패킷이 없고, 후속 RTP가30ms 이내이며, 출력 요청+현재 위상 보호 여유 이상으로 후속 데이터가 있을 때만 누락 시간축을 생략하는 후보를 만들었다. 생략 시간은 별도로 집계해 PLC 감소를 정상 음성 복원처럼 표시하지 않도록 했다. 기존/후보를6개 기록에서 대조했다(12회).

결과는 모두 생략0ms였고 주요 지표가 같았다. 이 기록들은 충분한 후속 데이터가 쌓인 상태에서 누락 구간 때문에 막힌 경우에 해당하지 않았다. 따라서 이 후보 역시 적용 근거가 없어서 제거했다. 모든 다른 환경에서도 효과가 없다는 뜻은 아니다.

## 한계

합성 Opus 페이로드와 실제 기록의 입장/읽기 잠금 순서·장치 요청 크기를 재생했다. 최초 큐 이력은 없으며 앞2초 제외만으로 이력 영향이 완전히 사라진다는 보장은 없다. 네트워크 지연 원인·실시간 OS 부하·장치 실행 타이밍·실제 음질/입→귀 지연을 재현하는 시험이 아니다. 후보의 실제 두 PC 배포는 하지 않았다. 재생에서 우위가 없으므로 동일 후보를 실제 통화로 반복하는 비용을 피했다.

## 코드·복구

두 후보의 제품 코드·실험 인수·시험 CLI는 모두 제거해 기존 동작으로 복구했다. 후보 소스 스냅샷·각각의 빌드 로그·36회 재생 결과는 Git 제외 `native/.local/extreme-091/`에 보존했다. 이미 구현한088의 시간창 수정과090의 양방향 마감 분석은 유지한다. 기존 배포본·서버·시스템 설정은 변경하지 않았다. 커밋/푸시는 하지 않았다.

지금까지의 증거로는 이 집 환경의 큰 대기를 앱의 재시작 여유만 줄여 해결하기 어렵다. 앱 대기 최소화와 수신 연속성 사이의 교환을 확인했고, 효과가 없는 튜닝을 제품에 추가하지 않았다. 다음 환경 원인 분리에는 같은 PC의 다른 어댑터 같은 새로운 독립 대조가 유의미하며, 기존 무효 설정/동일 진단을 반복하지 않는다.

복구 후 검증: Release 빌드 경고/오류0, 기존 관리형 회귀와 서버8개 검사 통과. 후보 인수·CLI·진단 필드가 실행 소스에 남지 않았음을 검색으로 확인했고 diff 공백 검사도 통과했다.
