# EXTREME-084: 정밀 출력 주기·가변 요청 재현과 선택적 패킷 대응

2026-10-23. [083](EXTREME-083.md)의 후속 작업. 원본 진단·dist·서버·OS 설정은 변경하지 않았다.

## 재현과 수정

기존25개 합성 대조는10ms 고정 출력 요청이었다.488샘플(약10.1667ms) 출력,10/20ms 교대 출력,약30% 주기 누락+12ms 재정렬 조합을 추가했다.2.5ms 시간 격자에서는 비정수 요청이 양자화되므로 정확한 다음 캡처·도착·출력·피드백 이벤트의 시각으로 진행하도록 도구를 바꿨다. 이 도구 개선과 제품 수정을 구분한다.

정밀 이벤트 시계에서도 손실 없는488샘플·교대 출력에서 정리/PLC가 반복됐다. 출력 요청 길이와 최근 도착 묶음의 위상이 맞지 않는데 여유를 너무 작게 유지하고,작은 출력 요청이 다음 큰 요청을 위한 큐까지 줄이는 문제가 재현됐다.

제품 수정은 적응형 짧은 여유 프리셋에 적용한다.최근 최대 출력 요청은 그 크기가 마지막 관측된 뒤1초간 유지하고,같은 크기가 반복되면 갱신한다.도착 묶음의 최대값도 같은 유지 방식으로 바꿔 창 경계마다 잠깐 작아지는 문제를 막았다.출력 요청이 도착 묶음보다 크고 배수가 아니면 위상 보호 여유를 도착 묶음 이상으로 두고 시계 보정 목표에도 같은 값을 적용한다.재생 시작 준비·정리·용량과 실제 요청을 맞춘다. RTP 재동기화 때도 이미 관측한 장치 요청 크기를 지우지 않는다.기존 고정 여유·짧은 재시작 모드의 동작은 유지한다.

이는 해당 조건에서 정상 샘플을 남기는 만큼 제한된 추가 대기를 허용하는 수정이다.모든 환경에서 무조건 더 짧은 지연이라는 뜻은 아니다.정상10ms 대조의 별도 고정 버퍼는 추가하지 않았다.

수정 전120초 대조에서는 고정2.5ms의488샘플 출력에 PLC497.5ms,10/20ms 교대 출력에 PLC10000ms가 발생했다.수정 후에는 반복이 사라졌다.488샘플 조건에는 초기 부족 약10.17ms,교대 출력에는 초기PLC5ms가 남았다.미래의 첫 큰 요청 크기는 미리 알 수 없으므로 초기5초 학습과 그 뒤의 연속성을 분리해 검사한다.새 출력 조건의 초기PLC/부족은 각각20ms 이내,학습 뒤 정상 조건의PLC/부족은0을 요구한다.기존25개 조건의 기준은 유지한다.

## 선택적 30초 패킷 기록

상세 진단·고급 설정의 `패킷 경로 기록 (30초)`를 누르면 기존 제한된 PipelineTrace를 시작한다.통화 중 양쪽에서 누르고 기록이 끝난 뒤 각자 `진단 저장`을 누른다.두 번째 클릭은 이전 기록을 초기화한다.누르지 않으면 패킷 기록은 비활성이다.출력 JSON의 `pipeline`에 포함되며 기록 중 저장하면 그 시점의 부분 기록이다.

음성/패킷 페이로드를 저장하지 않고 송신 앱 경계의SSRC/RTP 타임스탬프·프레임 샘플 수·앱 순서,수신 콜백의RTP sequence·페이로드 바이트 수와 입장 결과/샘플 수·재생 결과·앱 시각을 기록한다.기존 일반 진단의IP·닉네임 포함 조건은 유지된다.기록 자체의 제한된 할당/잠금 비용은 있으며 MaxRecorderMs/방출 기록 수를 확인한다.

```powershell
python native/TransportProbe/Analysis/analyze_packet_pair.py PC.json FRIEND.json output.json
python native/TransportProbe/Analysis/analyze_packet_pair.py FRIEND.json PC.json reverse.json
python native/TransportProbe/Analysis/analyze_packet_pair.py --self-test
```

분석은SSRC/타임스탬프가 양쪽에서 일치하는 첫/마지막 경계 안의 송신 API 기록을 대응한다.양끝 밖 기록은 시작/종료 시점 차이로 누락될 수 있어 제외한다.기록 방출이 있으면 누락 분류를 거부한다.요약 samples만 있는 과거JSON은 패킷 재구성이 불가능하므로 거부한다.일치한 패킷의길이 차이와 수신 기록에 나타나지 않는 내부 전송을 나눈다.

송신 Sequence는 앱 순서이며 실제RTP sequence가 아니다.송신 API 반환은NIC 발신 증거가 아니다.수신 기록에 없다고 물리 네트워크 손실로 확정하지 않는다.서로 다른PC의절대 시각을 빼서 단방향 지연을 계산하지 않는다.단일 네트워크 경로·피어 방향의 짧은 대조로 사용한다.

## RTT와 검증 한계

기존 UI는15초 넘은RTT에 이미 `[오래된 보고]`를 붙이고,합산 지연 모델에서도 오래된 값을 제외한다.이 동작을 확인했으며 새RTT를 측정한 것으로 바꾸지 않았다.083의약10분 전RTT는 현재값으로 사용할 수 없다.

Release 빌드 경고·오류0,전체 회귀·서버8개·IPv4/IPv6 및 실제 캡처/SRTP 경로와37개 제어 대조를 통과했다.최종 버튼 배치 뒤에도 빌드·제품·패킷 기록 회귀를 통과하고 진단 화면 렌더링에서 버튼 노출을 확인했다.분석 도구의 경계·순환·누락·기록 방출 거부 자체 검사도 통과했다.30% 누락+재정렬/488샘플 자동 모드의 마지막20초에는 폐기2.5ms가 남아,모든 조건에서 모든 카운터가0이라고 해석하면 안 된다.원본 통화의 동일 원인이 확정됐거나 친구 환경의 전체 끊김이 해결됐다는 판정은 아니다.실제 장치·게임·외부망의 스케줄링은 이번 가상 재현 범위 밖이다.원시 결과는 Git 제외 `.local/extreme-084/`에 보존한다.
