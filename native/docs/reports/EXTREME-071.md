2026-10-22 사용자가 인계 문서를 읽고 재개를 요청해 W 대조부터 진행했다. 지연 최우선·WASAPI 공유 모드 목표를 유지한다. 아직 최종 물리 원인이나 안정판 승격을 판정하지 않는다.

## W — 완료

같은 PC의 버디 5GHz 백홀 경유 이더넷(.88/23)과 메인 2.4GHz 직접 Wi-Fi(.31/20)에 각각 합성 UDP를 명시적으로 바인딩했다. 양쪽 모두 로컬 게이트웨이에 비재귀 CHAOS TXT NOTIMP 응답을 받는 별도 Python 대조와 OCI/외부 STUN을 함께 150초 기록했다. peer=source인 LAN 표시는 **자체 echo**이며 실제 LAN 왕복이 아니다. 교집합 시간에서 시작 5초·끝 2초를 제외했다. 공유기·무선·인증 설정 변경 없음.

## X — 완료: NIC 경계로 지연 구간 확인

다음은 NIC Tx/Rx와 앱 송수신 QPC를 같은 패킷으로 대응하는 대조다. 무관한 트래픽을 수집하지 않도록 진단 CLI에 고정 4포트 선택 `--path-isolation-ports`를 추가했다. 기존 CLI 기본 바인딩은 유지한다. 자체 echo 목적지도 새 포트에 맞췄고, 일부 포트 초기화 실패 시 이미 연 소켓을 해제한다.

합성 OCI/기준 STUN 6개 소켓과 고정 source port의 로컬 게이트웨이 UDP 2개 소켓만 NIC 경계에서 128바이트·64MiB·150초 제한으로 기록했다. 최초 UAC 취소 후 재실행은 성공했다. 기존 캡처·필터가 없음을 확인하고 시작했으며, 종료 후 Pktmon 실행 없음·필터 없음 확인. 공유기 설정·음성 녹음 없음.

| 경로 | OCI RTT 중앙값 / P95 / 최대 | 게이트웨이 UDP 중앙값 / P95 / 최대 |
|---|---:|---:|
| 버디 백홀 경유 이더넷 | 9.75 / 13.22 / 46.01ms | 1.38 / 3.49 / 30.55ms |
| 메인 2.4GHz Wi-Fi | 10.25 / 24.01 / 111.66ms | 1.25 / 15.72 / 98.77ms |

**동일 DNS 패킷의 엄밀한 대응:** Wi-Fi 로컬 게이트웨이 DNS sequence 4184를 source port·transaction ID·질문과 QPC로 대응했다.

| 관측 구간 | 시간 |
|---|---:|
| 앱 송신 → NIC Tx | 0.0418ms |
| NIC Tx → 게이트웨이 응답 NIC Rx | 98.6709ms |
| NIC Rx → 앱 수신 | 0.0558ms |
| 앱 전체 RTT | 98.7685ms |

Tx/Rx는 각 1회 관측으로 대응이 모호하지 않았다. QPC는 appSent=115791.1177037, Tx=115791.1177455, Rx=115791.2164164, appReceived=115791.2164722다. 같은 송신 시각 ±50ms에서 이더넷 게이트웨이 2.05ms / OCI 9.08ms, Wi-Fi OCI 111.66ms, 자체 echo 0.12ms였다.

이 사건의 약 98.67ms는 물리 Wi-Fi NIC의 송수신 관측 경계 사이에 있으며 앱 socket 처리나 상위 수신 처리 대기로 설명할 수 없다. 다만 하위 드라이버·NIC 장치·무선 구간·AP 내부 중 어디인지는 미확정이다. DPC/ISR는 이번에 수집하지 않았으며 Windows 전체나 모든 드라이버를 제외한다는 뜻은 아니다. 다른 대응된 DNS sequence 465도 전체 79.30ms 중 NIC 사이가 79.20ms였다.

ETL 3,916,776바이트, 154.28초, ETW lost=0. 다만 **패킷 관측률은 불완전**하며 Wi-Fi DNS 송신 4,858건 중 Rx 대응 2,348건, 양 경계 대응 1,751건이었다. lost=0은 모든 송수신이 기록됐다는 보장이 아니다. 위 결론은 대응된 실제 관측에 한하며 미관측 패킷의 경로나 111.66ms OCI 최대값의 NIC 내역은 추정하지 않는다. ETW MCP는 일반 이벤트를 읽었지만 패킷 디코더는 지원하지 않아 tracerpt raw QPC CSV를 검증해 직접 대응했다.

## AA — MCC 설정 대조 완료, 개선 채택 안 함

Realtek `MCCSup`의 원래 값 1(Enabled) → 0(Disabled) → 1 순서로 각 90초 비교했다. **A1/B/A2 모두 어댑터를 재시작**하고 같은 메인 2.4GHz AP·IP에 재연결한 뒤 5초 대기했다. 재시작 자체의 효과를 MCC 효과로 혼동하지 않도록 통제했다. 각 단계에 두 NIC의 자체 echo·OCI·외부 STUN·독립 게이트웨이 DNS를 동시에 기록했다. 각 단계 교집합 시작 5초·끝 2초 제외. 서버 패킷 캡처는 이번 대조에서 하지 않았다.

| 단계 | Wi-Fi 게이트웨이 P50 / P95 / 최대 | 게이트웨이 >30ms 건수 | Wi-Fi OCI P50 / P95 / 최대 | Ethernet 게이트웨이 P95 / 최대 |
|---|---:|---:|---:|---:|
| A1 활성화 | 1.04 / 9.74 / 48.28ms | 9 / 2,674 | 10.06 / 18.43 / 54.53ms | 3.31 / 24.41ms |
| B 비활성화 | 1.11 / 9.02 / 37.65ms | 8 / 2,673 | 10.06 / 17.77 / 47.49ms | 3.64 / 28.10ms |
| A2 활성화 복원 | 1.11 / 9.89 / 56.28ms | 16 / 2,676 | 10.07 / 18.29 / 52.98ms | 4.00 / 37.52ms |

분석 창의 두 NIC 게이트웨이·자체 echo·일반 OCI 송신은 모두 응답됐으며, 이는 부하 스트림까지 전부 무손실이라는 뜻은 아니다. MCC 비활성화에도 30ms 이상 대기가 남았다. P95 변화가 작고 각 단계 90초·단일 A/B/A이므로 효과를 확정할 수 없으며 **지연 해결책으로 채택하지 않았다**. A2에서도 원래 설정을 재시작해 복원했고 최종 결과 `restored=true`, 오류 없음. 원자료 `*-071aa-*`, `*-dns071aa-*`, `*-path071aa-*`, `summary071aa.json`.

앞선 Y/Z 시도는 실행 상태 확인을 잘못해 진단 프로세스가 겹쳤다. 고정 포트 충돌 및 어댑터 재시작 중 소켓 오류가 발생해 **결과 전부 폐기**했다. 둘 다 MCC=1 복구 확인 후 종료했고, AA는 서로 다른 고정 포트 42400..42403 / 42500..42503으로 실행했다. 실패한 시도를 환경 성능 저하 증거로 사용하지 않는다.
