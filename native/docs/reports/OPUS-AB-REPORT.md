# 두 PC Opus A/B/A 검사 보고서

2026-10-16 01:05~01:13 KST · 앱0.4.9 · 실제 PC와 노트북 SSH 자동 실행

## 결론

두 PC 양방향 통화6회차와 디지털 출력 루프백30회 검출을 완료했습니다. 모든 측정의 테스트 패킷을 같은 해시로 추적했습니다. 연결·장치 오류와 송신 큐 버림은 없었습니다.

**전용 저지연 모드의 코덱 선행 대기6.5→2.5ms는 확인됐지만, 전체 루프백 지연이 일관되게 줄었다고 입증하지 못했습니다.** 회차별 입력 대기·재생 큐 및 측정 불확실성이4ms 차이보다 큽니다. 기존 기본값을 유지하고 저지연64를 비교 옵션으로 둡니다.

## 조건과 방법

- 동일 공유기의 PC와 노트북, 모든 회차 실제 선택 경로는 직접 P2P. OCI는 연결 관리에 사용됐으며 이번 비교는 TURN 경로 시험이 아닙니다.
- 두 PC 모두 WASAPI 표준 공유 모드, 입력 요청10ms·출력 요청40ms 고정. 출력 장치 재시작0회, 장치명 변경 없음. 일부 시작 샘플의 현재 API 대기는 약30ms이고 이후40ms였습니다.40ms는 요청값/런타임 관측이며 물리 장치 지연의 보장값이 아닙니다.
- PC 입력: fifine Microphone / 출력: Realtek HD Audio 2nd output.
- 노트북 입력: Realtek 마이크 배열 / 출력: Realtek 스피커.
- Opus48kHz 모노10ms, 목표64kbps, 복잡도9, VBR, 동일 관리형 OpusEncoder.
- A1=VOIP64, B=Restricted Low Delay64, A2=VOIP64 복귀. 한 송신자만 모드를 바꾸고 상대는 VOIP64 고정. PC→노트북3회차 후 노트북→PC3회차.
- 연결 확인 후 회차당 약75초.15초부터10초 간격으로400ms 신호5회 전송. 음성 원본은 저장하지 않았습니다. 개인 장치의 볼륨/DSP 설정은 변경하지 않았습니다.

## 루프백 결과

아래 값은 **각 측정 범위 중심값의 중앙값**입니다. 실제 입→귀 지연이나 정확한 단일 편도 지연이 아닙니다. 회차별 시계 보정 범위 중앙값은 약30.3~31.3ms이며 별도 검출 여유±20ms가 포함됩니다. 중앙값은 이를 제거하지 못합니다.

| 송신→수신 | A1 VOIP64 | B 저지연64 | A2 VOIP64 | 검출/패킷 추적 |
|---|---:|---:|---:|---:|
| PC→노트북 |288.8ms|270.8ms|261.1ms|각5/5|
| 노트북→PC |113.2ms|143.8ms|132.6ms|각5/5|

PC→노트북에서 B는 A1보다18.0ms 낮지만, A2도 A1보다27.6ms 낮습니다. 노트북→PC에서는 B가 A1/A2보다 높습니다. 따라서 첫 A와 B만 비교해 모드 효과라고 결론 내릴 수 없습니다.

동일 패킷의 단계별 중앙값:

| 방향·구간 | A1 | B | A2 |
|---|---:|---:|---:|
| PC→노트북: 캡처 프레임→인코딩 시작 |21.2ms|19.1ms|19.1ms|
| PC→노트북: PCM 큐 대기 |52.7ms|31.4ms|33.3ms|
| PC→노트북: 출력 제출→루프백 검출 |208.2ms|209.2ms|208.7ms|
| 노트북→PC: 캡처 프레임→인코딩 시작 |17.9ms|32.0ms|16.6ms|
| 노트북→PC: PCM 큐 대기 |17.5ms|29.7ms|34.9ms|
| 노트북→PC: 출력 제출→루프백 검출 |65.4ms|66.4ms|77.4ms|

각 구간 중앙값의 합은 전체 중앙값과 같지 않습니다. 코덱 선행 대기도 이 표의 인코딩 CPU 시간과 다른 값입니다. 노트북 출력 이후에 잡히는 약200ms는 이전 결과와 유사하며 출력 드라이버/DSP, 루프백 수집 및 검출의 영향을 분리하지 못했습니다. 마이크·이어폰 같은 개인 환경의 단독 지연으로 단정하지 않습니다.

## 통화 안정성

모든 회차에서 RTCP 보고 수신 손실0%, 누적 수신 손실0, 관측 중복/순서 뒤바뀜0, 송신 큐 버림0이었습니다. 회차별 RTT 중앙값은 약2.3~4.3ms입니다. 두 보고서의 누적 송수신 수는 관측 시점이 달라 서로 같아야 하는 값이 아닙니다.

노트북 큐 정리는 모든 회차0입니다. 전체 합계는 PC 부족33회/399.7ms, 노트북2회/30.0ms입니다. PC의 최장 단일 부족 구간은95.1ms입니다. 시작 구간이나 불리한 회차를 제외하지 않은 누적값입니다. 안정 상태의 평균 큐 계산만 최초 수신500패킷까지 제외했습니다.

PC 평균 재생 큐는 회차별27.2~48.7ms, 노트북28.8~53.9ms였습니다. 이 변동과 순간 부족은 남은 개선 대상입니다. 보고 손실0%를 재생 끊김0으로 해석하지 않습니다.

시작 구간을 포함한 입력 불연속 카운터는 PC 회차별1~2회, 노트북1~6회였습니다. 관측된 최대 입력 콜백 간격은 PC22.3ms, 노트북82.9ms입니다. 요청한10ms 주기가 모든 콜백에서 지켜졌다고 가정할 수 없으며, 이 변동도 모드 비교에 영향을 줄 수 있습니다.

## 판단과 다음 작업

1. 저지연 모드는 실제 양방향 통화와 측정에서 동작했습니다. 기본값 변경을 정당화할 일관된 전체 지연 개선이나 실제 발화 음질 평가까지 확보한 것은 아닙니다.
2. 다음 구현은 RTP 시간축을 기준으로 한 수신 버퍼·늦은 패킷 처리·Opus PLC입니다. 큐를 무조건 줄이는 대신 안정적인 낮은 재생 대기를 목표로 합니다.
3. 출력/루프백 측정 구간 분리는 별도 과제로 남깁니다. 현재±20ms 검출 여유를 가진 방법으로4ms 개선을 정밀 입증할 수 없습니다.
4. 실제 발화의 청감 비교, 외부망·TURN 조건, CPU 부하 및 장시간 통화는 이번 결과 범위 밖입니다.

## 재현과 원본

동일 빌드를 두 PC에 복사한 뒤 각각 실행합니다. 같은 prefix를 사용하고 역할을 pc/laptop으로 나눕니다. 각 역할에서 자동6회차를 수행합니다.

```powershell
TransportProbe.exe --opus-ab-test https://qlrpal.ddns.net/ UNIQUE_PREFIX pc-report.json pc
TransportProbe.exe --opus-ab-test https://qlrpal.ddns.net/ UNIQUE_PREFIX laptop-report.json laptop
```

원본은 Git 제외 경로 `.local/reports/opus-ab-pc.json`, `opus-ab-laptop.json`, 요약은 `opus-ab-summary.json`에 보존했습니다. 노트북에도 `voice-auto-test/opus-ab-laptop.json`을 남겼습니다. 원본에는 후보 IP 등 연결 정보가 포함되며 음성 파일은 없습니다.
검사용 임시 노트북 방화벽 규칙은 제거했고 검사 프로세스는 종료했습니다. PC에서는 임시 규칙 추가가 권한 부족으로 적용되지 않았으며 기존 네트워크 설정으로 직접 연결됐습니다.
