# EXTREME-151 — 정상10ms의 송신 스케줄링 비교

2026-11-03 / `codex/extreme-latency`, HEAD `ab2833e` 위의 미커밋150 최적화를 보존하고 비교했다. 물리 입→귀 지연 감소를 미리 전제하지 않았다.

## 가설과 비교 범위

정상 제품은 캡처 콜백에서 인코딩/제한 큐 입장까지만 하고, `Task.Run`으로 시작한 단일 비동기 채널 소비자가 상대별 SRTP/API 송신을 수행한다. 패킷마다 `Task.Run`을 만드는 구조는 아니다.100에서 기각한 전용 후보는2.5ms 인라인과 비교하면서 큐 정책도 달랐다. 이번에는 정상10ms의 스레드풀 소비자와 전용 MMCSS Pro Audio 소비자만 비교했다.

동일 바이너리의 검사기 내부 옵션으로 큐 용량3·만료 제한 없음·10ms·native Opus LowDelay64·수신20ms·기존 상대별 WASAPI 공유 출력을 고정했다. 전용 후보의 기존 `DedicatedLimits`는 적용하지 않았다. MMCSS CRITICAL을 새로 켜지 않았으며, 기본 제품 호출은 기존 스레드풀 경로를 유지했다. 프레임/폐기/송신 시계축·암호화·수신/출력 정책은 바꾸지 않았다.

검사 경로는 방화벽 준비가 된 고정 Release 경로를 재사용했다. 임시 A/B 폴더의 실행 파일을 직접 시작하지 않았다. 같은PC6개 엔진·30개 수신/출력 스트림·실제 캡처/공유 출력과 로컬 WebRTC를 사용했다. 음성은 인코딩 전 합성 PCM으로 교체하고 상대별 볼륨을0.01로 설정했다. 독립6명/6대PC나 다른 회선 시험이 아니다.

## 실행과 지표

- 상세: 각30초 요청, 스레드풀→전용→스레드풀. 마지막5초에만 기존 bounded pipeline 기록을 켰다. 기록 양 끝250ms를 제외하고 동일 송신 프레임의5개 상대 API 기록이 완전한 경우만 지연 분포를 계산한다. 불완전 그룹과 evict 수를 별도로 확인한다.
- 저계측 유휴: 각90초 요청, 같은 A/B/A, 고빈도 pipeline 기록 끔.
- 저계측 CPU 경쟁: 작업 스레드8개/논리CPU12개를 유지한 채 각90초 요청 A/B/A. 준비 신호와 실제 프로세스 CPU 사용·정상 종료를 확인한다. 스레드의15ms 작업/5ms 휴식은 요청값이며 실제 사용량은 별도 결과를 사용한다. 게임·GPU·DPC 부하 시험은 아니다.
- 첫 저계측 결과의 회차 편차가 커서 같은 바이너리/설정으로 CPU 부하 전용→스레드풀→전용 각90초 역순 대조를 추가했다. 별도 회차로 보존하며 처음 A/B/A의 일부로 합치지 않는다.

송신 큐 입장→읽기, 인코딩 끝→마지막 상대 API 반환, 현재 캡처 핸들러 시작→마지막 API와 캡처 반환을 구분한다. API 반환은 소켓 송신 완료나 NIC/무선 전송 완료가 아니다. 장치 보고 첫 샘플 시각도 물리 수음 시각으로 해석하지 않는다. 모든 기간은 같은 호스트 단조 시계 안에서만 계산한다.

저계측의 `LastWaitMs`는500ms마다 뽑은 일부 프레임의 대기 표본이며 전체 프레임P95가 아니다. `MaxWaitMs`는 참가/준비를 포함한 수명 누적 최대이므로 정상 관측 창만의 최대와 구분한다. 짧은 상세 기록과 저계측 자원 결과를 섞어 전체 지연을 만들지 않는다.

품질은 저장 첫/마지막 표본 사이의 PLC 오디오 시간·늦음/재버퍼·출력 소진/안전 복귀·송신 폐기/만료·입력 불연속/앱 부분PCM폐기를 본다.30개 수신 스트림과6개 캡처/송신 세션 합계를 단일 사용자의 횟수로 바꾸지 않는다. 기능·종료 성공과 품질 무오류 판정은 별개다.

## 결과와 채택 판정

12회 모두 기능/종료를 완료했다. 비교 표본마다 정상10ms·실험 프리셋 없음·큐3·만료 제한 없음·직접 연결·수신20ms를 확인했고, 전용 회차의 MMCSS 활성도 확인했다. 실제 캡처10ms/출력2.667ms/목표 패딩5.833ms였다.

### 최종 판정과 실제 변경

정상10ms 전용 송신의 **기본값 승격을 기각**했다. 작은 내부 큐 대기 감소는 확인했지만 전체 송신 꼬리/연속성·자원 이득이 충분하지 않다. 비교용 `DiagnosticDedicatedSender`, `VOICE_TEST_SENDER*`, 임시 상세 기록 분기를 활성 소스에서 모두 제거했다. 원래 실험 프리셋에 이미 있던 전용 송신 구현은 변경하지 않았다. 일반 앱 `WebRtcCallEngine`에는 이번 송신 비교의 최종 diff가 없다.

채택한 것은 `LocalGroupOutputProbe.Window`의 판정 보완이다. 기존에는 PLC/소진이 있어도 연결·디코딩·정리 조건을 통과하면 일반 PASS만 출력했다. 새 `resources[].qualityCounters`에 저장 첫/마지막 사이의 PLC·공급 부족·늦음/중복/무효/재버퍼·출력 소진/안전 복귀·송신 폐기/만료·입력 불연속/시각 오류·앱 부분PCM폐기·공유 믹서 클리핑을 따로 집계한다. `qualityCountersClear`와 `QUALITY` 로그로 기능 성공과 구분한다.

선택된 카운터가 모두 관측되고0일 때만 true, 관측된 사건이 있으면 false다. 필요한 렌더 카운터가 없으면0으로 채우지 않고 null로 표시하며, 다른 사건이 없다면 전체 카운터 판정도 null이다. 일부 출력이 미측정이어도 다른 출력의 관측 사건을 숨기지 않는다. 이 판정도 청감/입→귀 지연·장시간 품질 보장이 아니다. 집계는 창 종료 후 한 번만 수행해 기본 패킷/캡처 경로에 새 기록·할당을 추가하지 않았다.150의 진단 정렬 최적화는 그대로 유지했다.

첫 검증 스크립트는 공유 출력의 상대별 렌더 필드가 null일 것으로 잘못 예상해 assertion에서 실패했다. 실제 코드를 확인하니 `WindowsAudioDevice.Snapshot`은 공통 출력의 렌더 카운터를 각 상대에 전달하고 있었다. 이를 단순 합산하면 같은 사건을 상대 수만큼 세므로, `LocalGroupQuality.RenderCounters`로 공유 모드에서는 엔진당 한 번만 집계하도록 수정했다. `renderCoverage`에 소유 출력/측정 수와 관측 합계를 남긴다. 새 `GroupQualityChecks`는 공통2출력의 델타7을35로 중복 집계하지 않는지, 별도10출력에서는35가 맞는지, 부분 미측정/관측 사건4 보존과 빈 출력 범위를 검사한다. `ProductChecks`/전체 verify에 연결했다. 잘못된 검증 스크립트와 최초 보고서는 덮어쓰지 않고 보존했다.

최종 `verify.ps1 -NoRestore -Integration`은 경고/오류0으로 통과했다. 제품/그룹 카운터 회귀·서버/실행기·실제 UDP/SRTP·가변 프레임·IPv6 통합을 포함한다. 수정 후 상대별30출력/공유6출력의 실제30초 요청을 각각 완료했고, 새 필드의 출력 수30/6·측정 수30/6과 개별 품질 카운터/판정의 일치를 검사했다. 이 두 확인 회차의 저장 품질 델타는 모두0, 판정true였다. 앞선90초/CPU 비교의 실패 카운터를 이 짧은 성공으로 덮어쓰지 않는다.

최종 일반 앱 DLL SHA-256 `36D1B24465BA7BF4EE24BB8E27C5D430D6F4E14F8B9230FBD8D507E8C4848808`은150 보존 bin과 일치했다. 최종 소유 CPU 작업/검사기/로컬 fixture 서버 잔존0을 확인하고 임시 실행 유지 요청을 해제했다. 기존 앱 실행/배포 설정을 바꿔 남겨두지 않았다.

## 원본·복구

원본 보고서, 실행/분석 스크립트, 단계별 바이너리·음원 해시와 비교용 소스/동결 bin은 Git 제외 `.local/extreme-153`, 역순 대조는 `.local/extreme-154`에 보존한다. 비교 bin을 재사용하려면 실행 중인 검사기가 없는 상태에서 원본을 백업하고 고정 허용 경로에 전체 bin을 임시 배치한다. 해당 동결 도구만 `VOICE_TEST_SENDER=queued/dedicated`, `VOICE_TEST_SENDER_TRACE=1/0`을 인식하며 최종 제품/검사기에는 이 옵션이 없다. 종료 후 원본을 해시 복구한다. 일반 실행은 `./native/run.ps1`, 회귀는 `./native/verify.ps1 -NoRestore -Integration`을 사용한다.

150의 채택된 진단 계산과 앞서 추가한 고정 검사 경로의 방화벽 준비를 보존한다. 운영 서버/노트북/배포본·장치/전원/라우팅/VPN 설정은 이번 비교에서 바꾸지 않았다. 실제 게임·독립PC/외부회선·물리 입→귀·장시간 검증은 별도 미실시다. 프레임·큐 정책·수신/출력 여유 기본값은 유지한다.
