# EXTREME-111 · VPN 경로 유지 상태의 통화별 LAN 선택 대조

2026-10-28 / `codex/extreme-latency`. 사용자가 승인한 자동→LAN 지정→자동 대조다. 109/110 미커밋 작업을 보존했다. Tailscale·Windows 경로·방화벽·공유기·기존 앱/배포본을 변경하지 않았다.

## 가설과 조건

두 PC의 상대 LAN 주소에 대한 `Find-NetRoute`는 모두 Tailscale의 LAN 서브넷 경로를 선택했다. ICE가 LAN 후보를 교환하더라도 OS 자동 소켓이 그 물리 LAN으로 송신한다고 단정할 수 없다. 이번 가설은 **자동 미디어 선택과 LAN 소켓 지정의 차이가 직접 연결 성공 여부를 바꾸는가**다. VPN 실행 자체·세부 패킷 폐기 지점·하위 드라이버 원인을 구분하는 시험은 아니다.

같은 빌드·합성 파형·LowLatency 정책·Opus10ms·기존 출력·직접 경로를 유지했다. A1/A2는 양쪽 OS 자동, B는 양쪽 통화 소켓만 각자의 실제 LAN 주소/인터페이스를 지정했다. 각 단계는 새 실행 ID와 새 시험 프로세스이며 실패 원본을 자동 재시도로 덮지 않았다. 참가·송수신/디코딩·음소거·각자의 퇴장/재참가·정리6검사를 사용했다. 어느 한 PC의 단독 영향, 소스 주소 바인딩과 UNICAST_IF의 개별 기여는 분리하지 않았다.

## 구현

- `test-pair.ps1 -MediaAddress`와 Node `--media-address`를 추가했다. 상대 주소가 아닌 실행 PC의 로컬 주소이며 생략하면 기존 자동 동작이다.
- `PairFunctionalProbe`는 기존 `SetMediaInterface`를 호출하고 요청/선택 인터페이스, 실패 단계, 정리 전 진단과 실제 UDP 소켓 바인딩·UNICAST_IF readback을 기록한다. 연결 후 및 각 재참가에서 지정 인덱스 일치를 요구한다. 잘못된 주소를 OS 자동으로 대체하지 않는다.
- `DiagnosticMediaBindings`/`MediaInterfaceSelection.ReadIndex`는 시험 코드에서만 호출하는 소켓 설정 읽기다. 제품의 RTP 경로나 송신 설정 기본값을 변경하지 않는다. readback은 소프트웨어 설정 관측이며 물리 NIC 송수신 시각이 아니다.
- 양쪽 로컬 주소는 서로 달라도 정상이다. 병합 결과에 각각 보존한다.
- TransportProbe 콘솔을 UTF-8로 명시해 Node가 보존하는 오류 로그도 한글로 읽을 수 있도록 했다. 무효 인터페이스 시험의 실패 코드·준비 단계·읽을 수 있는 한국어 오류를 확인했다.

## 검증 코드 오류의 분리

초기 A/B/A의 B에서는 실제 양쪽 ICE/DTLS가 연결됐으나, 새 readback 코드가 IPv4 GET 값까지 바이트 순서 변환해 정상 인덱스를 틀렸다고 판정했다. 노트북이 이 검사로 종료하면서 PC도 완료하지 못했다. **이 B는 유효한 기능 대조 결과로 채택하지 않는다.** 원본 `aba-results.json`과 보고서를 보존했다.

[Microsoft IPPROTO_IP 문서](https://learn.microsoft.com/en-us/windows/win32/winsock/ipproto-ip-socket-options)에 따라 IPv4 SET은 네트워크 순서, GET은 호스트 순서로 처리하도록 수정했다. 실제 Windows IPv4 UDP 소켓/루프백 인덱스의 SET→GET 일치 검사를 제품 회귀에 추가했다. 수정 후 같은 빌드로 새 A1/B/A2 전체를 수행했다. 초기 연결 성공을 재해석해 통과로 바꾸지 않았다.

## 수정 후 실제 두 PC 결과

| 단계 | PC | 노트북 | 양쪽 병합 |
|---|---|---|---|
| A1 OS 자동 | ICE failed, 연결/디코딩 대기 종료,6검사 시작 못함 | 동일 | fail |
| B 통화 소켓 LAN 지정 | 6/6 완료 | 6/6 완료 | pass |
| A2 OS 자동 | ICE failed, 연결/디코딩 대기 종료,6검사 시작 못함 | 동일 | fail |

B의 초기 연결과 두 번의 재참가 모두 실제 소켓 옵션을 읽어 PC Ethernet 인덱스23·노트북 Wi-Fi 인덱스14와 일치함을 확인했다. 구간 진단의 선택 경로는 직접 연결이었다. OS 선택 경로는 시험 전후 양쪽 모두 원래 Tailscale로 동일했다. 시험 소유 프로세스는 남지 않았고 노트북의 기본 입력/출력도 동일했다. 시스템 라우팅 복구 명령을 실행할 필요가 없었다. 시험 임시 폴더·원본은 보존했다.

이번 결과는 **현재 환경에서 미디어 경로 선택 모드가 직접 연결 성공을 바꾼다는 강한 근거**다. Tailscale이 제공한 겹치는 LAN 경로의 관여를 지지하지만 Tailscale 제품 결함, 어느 한 PC의 단독 원인, 정확히 어디서 ICE 확인 패킷이 버려졌는지를 확정한 것은 아니다. 성공한 B에서도 방화벽 설정은 같았으므로 새 실행 파일의 정확한 인바운드 규칙0개만으로 실패를 확정하는 설명은 부족하다. 전체 유효 방화벽 정책을 검증하거나 모든 방화벽 영향을 배제한 것은 아니다.

연결 실패 구간과 성공 구간의 비교이므로 지연 ms 감소를 계산하지 않는다. PLC/끊김 품질·게임·다른 회선·독립 다인 PC·장시간 유지·물리 입→귀 지연은 미실시다. OS 경로의 전후 조회는 전체 시간의 모든 경로 변화를 연속 감시한 기록도 아니다. 일반 앱의 자동 선택 기본값은 유지한다.

## 실행과 증거

상세 사용법은 [두 PC 검사 가이드](../PAIR-CHECKS.md)를 참고한다. 기존 통화 앱에도 `run.ps1 -MediaAddress LOCAL_LAN_IP` 옵션이 있으며 상대 PC는 그 PC의 주소를 사용한다. 해당 실행의 미디어 소켓에만 적용하고 종료하면 끝난다. 모든 사용자에게 VPN 우회를 강제하거나 주소를 하드코딩하지 않는다.

Git 제외 원본은 `native/.local/extreme-111`에 있다. `aba-corrected-results.json`은 세 단계 양쪽 보고서 위치, `aba-summary.json`은 단계·검사·소켓 관측 요약이다. B의 최종 병합은 `native/.local/pair-checks/2026-10-27T16-35-04.024Z-oLHai2/pair-summary.json`이다. 경로 시각은 UTC이며 한국 시각2026-10-28 시험이다. 경고0·오류0 빌드·제품 검사·7개 Node 테스트와 무효 주소/UTF-8 로그 검사를 완료했다. 최종 `verify.ps1 -NoRestore -Integration`도 종료 코드0으로 제품·서버·SDK·IPv4/IPv6 SRTP/RTCP·가변 프레임 회귀를 통과했다. `git diff --check`도 통과했다. 원본 로그는 `verify.log`에 보존했다.
