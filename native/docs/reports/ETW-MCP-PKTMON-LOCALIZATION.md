# ETW MCP 연동·Pktmon 합성 UDP 재시험

2026-10-16 KST, Native0.5.4 진단 도구. 연결된 `nijosmsft/etw-mcp`로 기존 ETL을 재분석하고 PC·노트북에서 합성 UDP120초와 Pktmon을 동시 수집했다.

## 결론

**일부 PC→노트북 지연은 노트북 Wi-Fi NIC의 첫 Pktmon 관측 지점부터 이미 존재했다. 그 이후 관측된 Windows 경로의 통과 시간은 짧았다.** 따라서 확인된 사례를 수신 상위 필터/소켓 처리의 긴 대기만으로 설명하기 어렵다. 관측 경계를 OS UDP 이벤트보다 NIC 쪽으로 조금 더 옮긴 결과다.

대표 순번4642에서 PC Realtek NIC 관측 송신 간격은9.016ms, 노트북 Intel NIC의 첫 관측 수신 간격은48.710ms였다. 해당 수신 패킷의 이후10개 관측 지점 통과 폭은0.093ms, 앱 수신 간격은48.870ms였다.

이것은 **간격 변동**이며 해당 패킷의 편도 지연48.710ms를 측정한 것이 아니다. NIC Pktmon 관측은 하드웨어 선로 시각이 아니므로 송수신 NIC/드라이버·펌웨어 큐, 무선/AP/공유기 처리 중 무엇인지는 아직 미확정이다.

Pktmon 관측을 모든 앱 패킷에 연결하지 못했다. PC→노트북의 긴 간격46개 중 수신 양 끝이 연결된 것은12개, 양쪽 호스트의 전후 패킷이 모두 연결된 것은5개다. 노트북→PC는 같은 수준으로 연결된 긴 간격이0개여서 이번 결과를 일반화하지 않는다.

## 실행과 수집 범위

| 항목 | PC | 노트북 |
|---|---|---|
| 시험 시작~완료 |23:30:20.24~23:32:46.02|23:30:19.07~23:32:45.21|
| UDP 송신 패킷 |12,343|12,348|
| Pktmon frame 이벤트160 |59,272|83,214|
| Pktmon ETL 크기 |1,080,594바이트|1,690,356바이트|
| network ETL 크기 |11,534,336바이트|3,145,728바이트|

- 이전 통화의 동일한 송신 시각·길이 계획을 합성 UDP로120초 재생했다. 오디오·마이크·스피커·Opus·WebRTC는 실행하지 않았다. WLAN 통계 조회도 껐다.
- 양쪽 OS UDP ETW145초, ICMP125초, Pktmon 약146초. Pktmon은 두 지정 LAN IP 사이 IPv4 UDP42000만 단일 필터로 허용했고 `--pkt-size 64`,64MiB 순환 상한을 사용했다. 전체 트래픽/전체 패킷 캡처는 실행하지 않았다.
- 프레임 헤더에는 MAC 및 Wi-Fi 주소 정보가 포함될 수 있다. 실제 음성·사용자 HTTP/SSH 트래픽은 대상이 아니며 원자료·캐시는 git 제외 `.local/etw-mcp-054`에 둔다. 공개 보고서에 프레임 주소를 복사하지 않았다.
- 캡처 전에 기존 Pktmon 세션과 필터가 비어 있음을 확인했다. 기존 항목이 있으면 변경 없이 중단하는 실행기를 사용했다. 시험 후 자신의 필터를 이름으로 제거하고 녹화를 종료했다.
- 전체 트래픽으로 이어질 수 있던 초기 관리자 실행은 자동 승인 검토에서 거부됐다. 읽기 전용 사전 확인과 명시적인 UDP·길이 제한으로 범위를 줄인 실행은 승인됐다. 한국어 상태 문구 차이로 중단된 준비 시도에는 패킷 수집이 없었으며 본 결과에서 제외했다. 본 시험 원본은 `results-rerun`이다.
- 네 ETL 모두 정상 종료·손실 이벤트0개, 상한 미만이다. 앱/ICMP/trace 종료코드0, 합성 기록 overflow/error 없음. 계획 hash·길이 순서·예정 시각·OS 송신 길이 histogram을 검증했다. 공통 내부 순번 범위의 누락·중복·역전0개다.
- 타이밍 수집 종료 후 ETL 변환과 MCP 분석을 실행했다. Pktmon 자체 계측은 실행 환경을 바꿀 수 있으며 이전 시험과 성능 A/B로 비교하지 않는다. 오디오·드라이버·절전·방화벽 설정 및 배포 패키지는 변경하지 않았다.

## MCP 기본 분석에서 발견한 한계

1. **기존 UDP 자료 인식:** 기존 `Microsoft-Windows-Kernel-Network` ETL을 MCP 기본 .NET 경로로 불러오면 generic events는 읽지만 전용 UDP dataset은0개로 표시됐다. 동일 원본에서 기존 raw-QPC 변환기는 해당 PID UDP24,339개를 읽었다. MCP의 “No UDP event data” 안내를 트래픽 부재로 해석하지 않는다. xperf 모드도 이 원본에 필요한 UDP 테이블을 제공하지 않았다.
2. **한국어 Pktmon 출력:** MCP 텍스트 파서는 Appearance/Direction/Component 등 영어 항목명을 요구했다. 한국어 원본에서는0개와 PCAPNG59,272/83,214개가 불일치했다. 원본을 보존하고 파생 텍스트 항목명만 정규화해 확인했다.
3. **Wi-Fi 프레임:** 설치된 전용 Pktmon 파서는 Ethernet만 선택해 노트북 WiFi frame 관측53,340개를 누락했다. 단순 항목명 정규화만으로 해결되지 않는다.
4. **고정된 구성 요소 경로:** 설치된 계층 그룹화는 예시 구성 요소 번호 경로를 사용했다. 이번 호스트의 실제 번호는 PC Realtek NIC203, 노트북 Intel NIC13 등으로 달라 PC도 전용 계층 분석에서 journey를 만들지 못했다.
5. **자동 경고의 의미:** 기존 스케줄링 ETL의 DPC 요약 경고는 전체 분포에 대한 도구 휴리스틱이다. 긴 수신 간격과 동시인 실행을 확인한 이전 분석을 뒤집거나 특정 드라이버 원인으로 사용하지 않았다. thread Waiting과 CPU runnable 대기도 구분해야 한다.

MCP 설치 소스나 전역 설정은 수정하지 않았다. `get_pktmon_layer_latency`가 이 환경에서 성공했다고 표시하지 않는다. MCP .NET sidecar가 정상적으로 추출한 **generic Pktmon 이벤트의 구조화된 필드와 raw QPC**를 별도 분석기로 대조했다.

## 원본 순번을 이용한 교차분석

`analyze_pktmon_replay.py`가 MCP 캐시의 event160에서 raw QPC, 실제 ComponentId/EdgeId, 헤더를 읽는다. Ethernet에서 시험 token·송신 역할·Little Endian 순번을 검증한다.64바이트로 잘린 Wi-Fi frame은 IP-ID·양 끝 IP·IP 길이가 **검증된 단 하나의 순번**에만 연결될 때 사용한다. 여러 순번에 연결되는 키는 제외하며 이번 자료에서는 모호성 제외0개였다. 무관한 트래픽이나 다른 역할 token이면 분석을 거부한다.

두 PC의 절대 시각은 빼지 않는다. 같은 순번의 전후 두 패킷에 대해 각 호스트 내부의 Pktmon 관측 **간격**을 비교한다. 실제 NIC 이름/드라이버와 번호는 해당 호스트에서 저장한 구성 요소 목록으로 확인했다.

| PC→노트북 순번 | PC 마지막 관측 간격 | 노트북 첫 관측 간격 | 노트북 해당 패킷 관측 통과 폭 | 앱 수신 간격 |
|---|---:|---:|---:|---:|
|3168|10.013ms|50.892ms|0.039ms|51.076ms|
|4751|10.018ms|49.243ms|0.024ms|49.157ms|
|4642|9.016ms|48.710ms|0.093ms|48.870ms|
|4539|3.990ms|46.415ms|0.125ms|46.534ms|
|4577|9.534ms|43.872ms|0.023ms|43.949ms|

표의 노트북 첫 관측 지점은 Intel AX201/Netwtw10.sys의 component13이다. PC의 마지막 관측은 packet별로 다르며 **4642의 전후 두 패킷만 여기서 모두 Realtek NIC203으로 확인**했다. 다른 행의 마지막 관측을 실제 NIC 송신 시각이라고 부르지 않는다.

수신 전후가 연결된12개는 모두 첫 관측 간격부터30ms를 넘었다. 양 끝이 모두 연결되지 않은 사례는 판정에서 빼고0ms로 채우지 않는다. 수신 NIC의 첫 관측 이전에서 이미 간격이 벌어졌다는 근거지만, NIC가 전파를 받은 정확한 시각이나 펌웨어 대기 시간을 제공하지 않는다.

### 부분 관측 범위

| 호스트에서 관측한 흐름 | 내부 분석 범위의 순번 그룹 | 여러 지점이 있는 그룹 | 여러 지점 통과 폭 P95 / 최대 |
|---|---:|---:|---:|
| PC에서 PC 송신 |5,708|3,759|0.021 / 0.073ms|
| PC에서 노트북 수신 |1,833|1,833|0.015 / 0.232ms|
| 노트북에서 PC 수신 |5,579|5,579|0.059 / 0.184ms|
| 노트북에서 노트북 송신 |2,672|2,672|0.041 / 0.077ms|

이 수치는 연결 가능한 Pktmon 관측의 통과 폭이다. 전체 앱 송수신 수보다 적고, 관측되지 않은 시간이나 경로까지 포함한 커널 전체 체류 시간이 아니다. 한 지점뿐인 그룹은 통과 시간0ms로 해석하지 않았다. **ETW 손실0개가 모든 패킷의 모든 지점 관측을 보장하지 않는다.** 왜 이 범위만 패킷별로 연결되는지는 추가 확인 대상이며 누락 구간을 추정으로 채우지 않았다.

## 다음 판단

확인된 일부 PC→노트북 사례에서는 수신 상위 필터/소켓이 수십 ms를 추가한 설명보다 **노트북 NIC 첫 관측 이전 구간**을 우선 조사할 근거가 생겼다. 그렇다고 Netwtw10.sys 자체의 결함이나 AP 재전송을 확정한 것은 아니다. 드라이버가 이벤트를 내보내기 전의 처리도 포함된다.

다음은 Pktmon 관측 연결 범위를 점검하고, 같은 사례에서 송신 NIC 마지막/수신 NIC 첫 관측을 더 많이 확보하는 것이다. 이후에도 경계 사이가 남으면 장치·무선/AP의 별도 통계가 필요하다. 원인 확인 없이 필터 드라이버를 끄거나 버퍼를 늘리지는 않는다.

분석기 자체 검사는 IP 헤더 위치·실제 시험의 순번 byte order·잘린 헤더·다른 역할 거부를 확인했다. 기존 OS 경계 분석과 순번 재생 검증도 재사용했다. 실제 자료를 재분석하고 diff 공백 검사를 수행했다. 재현 시 MCP Python 환경의 pandas/parquet 의존성이 필요하다. 각 MCP 호출 결과와 최초 실패·제한은 `.local/etw-mcp-054`에 보존한다.
