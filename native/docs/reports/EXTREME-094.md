# EXTREME-094 — SDK 수신 시작 보호와 실제 6인 A/B/A

2026-10-25~26. EXTREME-093에서 재현한 SIPSorcery10.0.17 수신 시작 경쟁을 별도 SDK 빌드로 수정·검증했다. **실제 통화에서도 동시 수신과 정체성 중복·미관측을 줄이는 효과를 확인했다. 전체 네트워크 지연·PLC 해결이나 기본 배포본 승격은 아니다.**

## 변경 범위

- 정확한 상류 커밋 `08c2ed0ad72c423ca06950dee2e842488a219884`를 내려받아 압축본과 `UdpReceiver.cs`의 SHA-256을 확인한다. 소스가 다르면 패치를 거부한다.
- 수정 B는 수신 상태의 확인·설정을 같은 잠금 안에서 수행한다. 비동기 요청 등록·버퍼 복사·패킷 핸들러는 잠금 밖에서 실행한다. APM 콜백이 동기 실행될 가능성을 고려했다. 기존 수신 완료/예외 처리·재시작 구조는 유지한다.
- A는 같은 빌드에서 기존 비동기화 시작 로직을 사용한다. 양쪽에 동일한 추가 계측을 적용한다. Task API 전환·버퍼 확대·코덱·재생 여유·시스템/공유기/라우팅 변경은 하지 않았다.
- 선택적 계측은 수신 시작/완료 ID, 동일 버퍼 객체 식별자, 미완료 IO 수, 핸들러·동기 drain을 포함한 소유권을 기록한다. 처음64개 중첩 시작 및 최대128개 관련 작업 수명만 보존한다. 패킷 내용은 기록하지 않는다.
- [시험 빌드 준비·실행 도구](../../sdk-experiment/README.md)를 추가했다. 공식 NuGet 참조·잠금 파일·`dist`는 유지한다. 수정 DLL은 `.local`의 별도 앱/프로브에만 넣는다. 정상 `native/run.ps1`에는 자동 적용되지 않는다.

## 실제 6인 A/B/A

PC와 노트북에 실제 공유 캡처/렌더 엔진을 각각3개 실행했다. 양쪽 LAN 주소를 명시하고 각90초,2.5ms 송신으로 원본→수정→원본을 비교했다. 별도의 경쟁 유발 스레드는 사용하지 않았다. 각 프로세스에서 환경 변수로 게이트를 선택하며 두 호스트 DLL 해시를 확인했다. OS 시계 차이는 약23초를 시험 예약에만 보정했고 시계 설정은 변경하지 않았다.

첫 검증은 Begin 등록 호출 전체를 잠그는 시험용 B로 수행했다. 원본 두 구간에서 실제 통화 중첩·중복/미관측이 재현됐고 B는30개 수신기 모두 중첩0, 마지막 기록 범위의 모든 방향 중복/미관측0이었다. 이 결과만으로 등록 호출에 잠금을 유지하는 구현을 채택하지 않았다.

최종 후보는 상태 확인/설정만 잠그도록 범위를 줄이고 **새 A/B/A를 다시 수행**했다. SDK DLL SHA-256은 `A5328E5671D0B97FBB3248B634DDD573C99B0E4F1CB8967CEEDD19B122CCD61D`다.

PLC는 초반10초 이후 해당 호스트 내부6개 수신 방향의 `ConcealedMs` 합계 / 관측 수신 시간 합계다. 네트워크 패킷 손실률이나 단일 사용자의 지연값이 아니다. B에서도0이 아니며, 표본1회의 A/B/A를 장기 발생률로 일반화하지 않는다.

최종 B의30개 수신기는 모두 최대 미완료 IO1개, 중첩0, 종료 시 미완료0이었다. 하지만 **호스트 간 방향은 B에서도62개가 채널 미관측**이었다. 이 구간에 정체성 중복은 없었다. B의 호스트 간 PLC도 PC 약0.798%, 노트북 약0.562%로 남았다. SDK 경쟁을 수정해도 네트워크·장치 스케줄링·마감 문제를 모두 없애는 것은 아니다.

## 해석과 배제 범위

SDK의 비원자적 수신 시작은 실제 통화의 정체성 중복·미관측을 만드는 원인 중 하나로 볼 근거를 얻었다. 동일 버퍼의 다중 미완료 작업, 원본에서의 재현, 수정에서의 소실, 원본 복귀 시 재현을 함께 관측했다. 집 무선망만으로 같은 호스트의 이 현상을 설명할 필요는 없다.

기존에 조사한 OS 송신~NIC 수신 사이의 외부 경로 대기 전체를 이 결함으로 설명하지 않는다. 입→귀 지연 감소량도 측정하지 않았다. 재생 여유를 늘리지 않고 불필요한 누락·PLC를 줄이는 수정이라는 점이 지연 우선 목표에 부합한다.

## 회귀와 남은 항목

- 최종 후보로 실제 OCI 강제 TURN120초: 양쪽 종료 코드0,119개 상태 표본 모두 TURN 경로, 송수신 지속 및 진단 trace 검사를 완료했다. PC 마지막 송신/수신15660/15649, 노트북15754/15753이었다. PLC·부족이 있어 품질 합격으로 해석하지 않는다. 초반에 진단 ZIP 전송이 겹쳐 조용한 네트워크 성능 비교도 아니다.
- 추가 수명 계측을 끈 제품 흐름 시험에서 음소거·상대 볼륨·강제 복구 후 재연결까지 진행했으나 마지막 기본 장치 재입장 단계는 ICE 실패로 완료하지 못했다. 같은 빌드의 원본 게이트도 강제 복구 단계에서 연결 대기 제한으로 실패했다. 원본에서도 남는 재연결 문제지만, 이 사실만으로 새 수정의 모든 회귀를 배제하지 않는다. 최초 실패를 보존한다.
- 수정 게이트의 제품 흐름 재시험(추가 계측 켬)도 강제 복구 단계에서 연결 대기 제한으로 실패했다. 최초 수정/원본/수정 재시험 실패 모두 보존한다. 수신 경쟁 수정만으로 TURN 재연결 문제까지 해결됐다고 볼 수 없어 기본 배포본 승격을 보류한다.
- 최종 짧은 잠금 후보로 노트북 순수 UDP 스트레스를 추가했다. SDK 게이트를 수정 모드로 고정하고 각20000개씩3구간을 실행했으며 모두 중복·미관측0, 최대 미완료 IO1개였다. 이는 앞선 원본/래퍼/원본 대조와 다른 추가 수정 후보 회귀다.
- `prepare.ps1`을 처음부터 실행해 다운로드·해시 검증·패치·SDK 및 정상 솔루션 빌드·분리된 앱 준비를 통과했다. 양쪽 빌드는 경고/오류0이었다. 새 준비 경로의 SDK 해시는 `8D69D41FB2AF735CE86D3D2F81433F458F58BC752633011A94B5355A1393E6EE`이며 최종 후보와 생성된 수신기 소스가 같음을 확인했다. 빌드 위치 등에 따른 바이너리 차이가 있어 별도 manifest를 보존한다. 중복 패치도 입력 수정 없이 거부됨을 확인했다.
- 정상 패키지의 `verify.ps1 -NoRestore -Integration` 전체가 통과했다. 정적 분석·관리형 회귀·서버8개·IPv4/IPv6 ICE/DTLS/SRTP/RTCP·프레임 전환·실제 SRTP 경계 fixture를 포함한다. 분석기 self-test 및 PowerShell 구문 검사도 통과했다.
- 새 준비 스크립트의 수정 SDK는 수명 계측을 끈 상태로 IPv4 RTCP·SRTP 재생·2.5/5/10ms 전환·27초 미디어 시간·통제된 경계 fixture·IPv6 RTCP 통합을 모두 통과했다. 이27초 검사는 결정적 pull이며 실제 장치/네트워크 장시간 품질 시험은 아니다. 정상/수정 fixture를 별도로 보존했다.

원본·요약·로그·예약 조건·각 SDK 소스/바이너리는 ignored `native/.local/extreme-094/`에 보존했다. `group-*`는 첫 등록 호출 잠금 대조, `claim-*`는 최종 짧은 잠금 대조다. 원본 그룹 진단을 삭제하거나 실패를 성공으로 대체하지 않는다. 시스템 설정 변경은 없었으며 시험 소켓·엔진은 종료 시 정리한다. 새 코드는 커밋·푸시하지 않았다.
