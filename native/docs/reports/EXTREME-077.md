# EXTREME-077 — 송신의 전역 피어 잠금 제거

2026-10-22. 집 네트워크의 물리 원인 조사는076 상태로 보류하고, 앱이 추가하는 대기를 줄이는 첫 단계로 송신 경로를 정리했다.

## 문제와 변경

기존 `DispatchFrame`은 전체 피어 사전 잠금을 잡은 상태로 연결 상태 조회·RTP 시각 계산·암호화/송신·진단 갱신을 수행했다. 피어 입장/퇴장과 진단 조회가 이 잠금을 공유했다. 실험 모드의 직접 송신에서는 캡처 호출 경로에도 이 대기가 전달될 수 있었다. 이것은 구조상 가능한 경합이며, 이번 변경만으로 기존 수십 ms 네트워크 사건의 원인이었다고 판정하지 않는다.

- 피어 입장·퇴장·전체 종료 때만 불변 배열을 새로 발행한다. 송신은 `Volatile.Read`로 배열을 읽으며 전역 사전 잠금과 프레임마다 목록 복사를 하지 않는다. 배열은 발행 후 수정하지 않는다.
- 피어마다 `AudioSendLifetime`으로 송신 진입/종료를 짧게 관리한다. 암호화·소켓 I/O 중에는 이 관리 잠금도 보유하지 않는다. 정상 송신마다 lease 객체를 만들지 않는다.
- 제거된 피어의 종료는 신규 송신을 거부하고, 이미 진입한 송신이 끝나기를 비동기로 기다린 뒤 연결·출력·디코더를 닫는다. 오래된 배열을 읽은 송신도 종료 진입 뒤에는 거부된다. 대기는 전역 피어 잠금 밖에서 수행한다.
- 송신 실패 상태 알림도 송신 수명 보호를 반환한 뒤 호출한다. 종료 시 연결 닫기가 실패해도 출력/디코더 해제를 시도한다.

기존 직접 송신/스레드풀 송신 선택, 프레임 길이, 패킷 순서·RTP 타임스탬프·누락 표식, 수신 여유, WASAPI/MMCSS 정책은 그대로다. 피어별 송신은 여전히 순차적이다. 한 피어의 느린 송신이 다음 피어를 늦출 가능성이나 캡처 콜백에서 송신하는 비용까지 해결한 것은 아니다. 이 수명 보호는 로컬 오디오 송신과 로컬 종료 사이를 보호하며 모든 수신/시그널링 콜백의 수명을 새로 보장하는 범용 장치가 아니다.

## 검증

- Release 정적 분석/빌드: 경고0·오류0.
- 새 제품 회귀: 진행 중 송신이 있을 때 종료 대기, 오래된 목록의 신규 진입 거부, 다른 피어 독립 진입, 반복 종료 요청, 복수 송신 배출, 예외 경로 반환 확인. 워밍업 후10,000회 수명 진입/반환의 현재 스레드 할당0바이트 확인. 전체 송신 경로가 무할당이라는 뜻은 아니다.
- 기존 극저지연 프리셋·2.5/5ms·혼합 상대·PLC/재정렬/버퍼·송신 큐·제품 재접속·코덱/복구 회귀 통과.
- 서버8개 회귀 통과. 최초 실행의7개 실패는 샌드박스 localhost `EACCES`였으며, 로컬 연결 권한으로 재실행해8/8 통과했다. 제품 코드를 변경해 이 오류를 숨기지 않았다.
- 로컬 UDP 양방향/종료, ICE·DTLS·SRTP·RTCP·진단 데이터 채널, 복호화 RTP→재생 통합 통과. 이 통합은 기존 프로토콜 시험이며 실제 UI 엔진의 다중 피어 입퇴장을 재현한 장시간 시험은 아니다.

`verify.ps1 -NoRestore -Integration`은 최초 서버 권한 오류에서 중단됐고, 이후 남은 서버/통합 단계는 별도로 완료했다. 따라서 단일 명령 전체 성공이라고 기록하지 않는다. 마지막 공백 정리 뒤 Release 빌드도 다시 통과했다.

## 판정과 다음 단계

안전한 피어 수명 관리와 전역 잠금 제거를 구현했다. **입→귀 지연 또는 P95/P99가 몇 ms 개선됐다는 성능 판정은 아직 없다.** 다음에는 같은 합성 입력·피어 수·네트워크 조건에서 직접 송신과 전용 송신 스레드를 비교하고, 캡처→송신 대기 및 송신 처리의 꼬리·누락·출력 연속성을 함께 평가한다. 단순히 새 스레드가 있다는 이유로 채택하지 않는다. 패킷 풀링은 비동기 전송과 버퍼 소유권을 확인한 뒤 별도 변경한다.

제품/시험 소스와 이 문서만 변경했다. 기존 `native/dist`, 노트북, OCI, 공유기/드라이버/시스템 라우팅은 변경하지 않았고 git commit/push는 하지 않았다.
