# EXTREME-141 — 수신 여유 대조 중단과 렌더 소진/PLC 분리

2026-11-02 / 기반 `5ce456b`와140 미커밋 변경 보존. 목표는140의10ms 후보와 같은180초 조건의20ms 대조, 그리고 렌더 소진과 PLC의 분리다. **새 지연 감소나10ms 안정판 승격을 달성한 시험이 아니다.**

## 가설·조건

수신 여유 축소가140의 두 사건을 만든 것인지, 입력/출력 공급 문제가 별도인지 확인한다. 정상 대조라면 같은 빌드·유선 지정·직접 UDP·48kHz mono·native Opus LowDelay64·10ms 프레임·출력·180초·상세 기록 끔/기존250ms 진단·자동 사건 기록을 유지하고 수신 여유만20ms로 바꾼다. 입력·출력 장치 설정/전원/라우팅/VPN/AP/서버를 변경하지 않는다.

새 대조에는140과 같은 앱 SHA256 `36D9C78AF976DB2BABB02F301684153D14C3717A3208F4CE1A7623703A5A9B6B`를 격리 복사해 사용했다. 최근 추가한 개발 CLI 빌드나 새 보고서 수정본을 섞어 같은 바이너리라고 표시하지 않는다. 노트북 원본 시험 폴더를 먼저 백업했다.

## 기존10ms 사건의 분리

140의 성공한 `ten-180` 원본을 새 오프라인 분석기로 재분석했다. 다음 시각은 PC의 baseline 첫 표본에 대한 로컬 상대 시각이며 다른 PC 시계와 빼지 않는다.

| 관측 | 결과 |
|---|---|
| 정확한 render-empty 기록 |14.5407초, wake 단계|
| 이전 관측 render-submit→소진 |12.758ms|
| 이전 submit 작업 경과 |0.0016ms|
| 이전 보고 장치 패딩 /그때 채운 음성 |3.1667ms /2.6667ms|
| 직전 RTP 버퍼 읽기 후 남은 소스 |21.4375ms, PLC0|
| 소진 다음 읽기 |약0.4947ms 뒤 기록, 큐25.6042ms, PLC0|
| 누적 렌더 wake 간격 최대 |12.0719ms, 해당 표본 TimeoutWakes0|
| 별도 PLC 증가 표본 구간 |28.9885~29.2418초,2.5ms|

해당 소진 주변에는 앱의 수신 소스가 남아 있고 앞뒤 읽기에 PLC가 없었다. **수신 큐가 비어 출력할 샘플을 못 만든 사건과 구분되는 출력 공급 공백의 근거**다. 더 큰 RTP 여유를 두는 것만으로 장치에 샘플을 전달하지 않은 시간을 해결한다고 가정하면 안 된다.

이 결과는 OS 스케줄러·이벤트 전달·드라이버·GC 중 정확한 원인을 구분하지 않는다. 이전 submit은 마지막 *관측*이며 기록 충돌4건이 있다. 장치 패딩은 이전 wake에서 읽은 값으로 현재 물리 출력 시각이 아니다. 누적 최대와 특정 사건이 동일한 경계를 재는 것도 아니다. 물리 입→귀 수치나 하드웨어 결함으로 표현하지 않는다.

나중의 PLC는 첫 사건 보존 창11.8934~16.5396초 밖이다. 그러므로 캡슐의 PLC 기록0을 전체180초 PLC0으로 읽거나, 뒤의2.5ms를 앞의 소진과 같은 원인으로 합치지 않는다. 이 PLC의 개별 RTP 마감 원인은 이번 원본만으로 확정할 수 없다.

## 새20ms 대조: 실패 자료로 보존

양쪽 연결·ready 뒤 관측 중, 노트북에서 마지막 프레임 나이676.8ms가 관측돼 `캡처 전달 정지` 검사에 실패했다. 전체 실행 약123초 시점이며 PC도 상대 퇴장으로 실패했다. 노트북 장치 오류 문자열은 없었으므로 명시적인 장치 분리 오류와 같다고 단정하지 않는다. 단순 수신 여유의 효과와 구분해야 한다.

PC 캡슐은 `playout-plc`, 노트북은 연결된 사건 ID의 `remote-request`였으며 둘 다 당시 `AfterTrigger` 스냅샷이다. PC 보존 기록에는 PLC 합계60ms가 있으나 이는 중단된 사건의 기록량으로, 성공한180초 품질 수치가 아니다.20ms면 항상 무끊김이라는 주장도 하지 않는다. 동등 조건의 성공한20ms180초 기준선이 없으므로10ms와의 정량 비교/원인 판정은 여전히 미완료다.

최초 도구는 Window 성공 끝에서만 `windows`에 표본을 넣어, 이번 실패 원본의 `windows`가 비었다. `failureDiagnostics`와 사건 캡슐/이벤트는 남아 있으나 실패 직전까지의250ms 표본을 되살릴 수는 없다. 실패 원본을 수정하거나0으로 채우지 않는다.

## 실제 수정

- `PairFunctionalProbe.Window`: 성공 여부와 무관하게 `finally`에서 관측 표본·실제 경과·자원·`completed`를 보존한다. 실패한 검사를 우회하거나 합격 체크를 추가하지 않는다. 중단 원인은 기존 최상위 오류/실패 진단에도 남긴다.
- `pair-observation.mjs`: 명시적으로 미완료인 baseline을 정상 비교에서 거부한다. 기존 성공 보고서의 필드 생략과는 호환된다.
- `Analysis/analyze_playout_failures.py`: 기존 단일 호스트 표본/캡슐만 사용해 렌더 소진과 PLC 카운터 변화 구간, 앞뒤 소스 상태, 캡슐의 관측 범위를 분리한다. 실패/미완료·시계 역행·카운터 초기화·상대 변경을 거부한다. 누락 기록으로 네트워크 손실이나 OS 원인을 만들지 않는다.
- Node/Python 회귀: 미완료 자료의 정상 승격 방지, 소스가 남은 소진과 뒤의 PLC 분리, 관측 부족/시계·카운터 오류를 검사한다.

앱의 프레임·수신 여유 기본값·출력 패딩·MMCSS/워치독·기본 SDK는 변경하지 않았다. 무작정 버퍼나 우선순위를 바꾸는 수정은 채택하지 않는다. 새 분석은 기본 실행에 고빈도 기록·할당을 추가하지 않는다.

## 복구·남은 작업

노트북 시험 프로세스는 실패 보고서를 작성하고 종료했지만 이후 SSH 핸드셰이크가 불안정해 원본 시험 폴더의 복구 확인이 아직 필요하다. 백업은 해당 시험 workspace 안에 보존돼 있다. 기존 제품 배포본·운영 서버는 건드리지 않았다. 별도 원격 인증/네트워크 설정을 바꿔 복구를 강행하지 않는다.

이후 사용자가 노트북 전원 꺼짐 가능성을 알려 [142의 PC 단독 검증](EXTREME-142.md)으로 전환했다. 이 설명만으로 앞선 캡처 중단 원인을 확정하지 않으며, 원격 복구 완료로 표시하지 않는다.

원본/격리 빌드·실패 시도·분석은 Git 제외 `native/.local/extreme-141/`에 보존한다. `control20-180-result.json`, `prior10-pc-failures.json`, `prior10-laptop-failures.json`, `state.json`, `restore.py`가 입구다. 원격 응답 회복 후 원본 해시 복구를 확인하고, 장치/경로가 같은 조건에서20ms180초를 새 실행 ID로 다시 측정해야 한다. 이후에만 두 여유의 연속성을 비교한다.

실제 게임·물리 입→귀·외부 친구/TURN·다인·무선/장치 물리 시각·이번 실패를 주입한 새 Window 보존 경로의 실제 두 PC 시험은 미실시다.

## 검증

소스 변경 후 전체 솔루션의 경고/오류0 빌드, Node 실행기/병합/관측12개, Python 분석 회귀12개와 `git diff --check`를 통과했다. 기존140의 성공한180초 원본으로 새 분석기의 실제 출력도 확인했다. 새 오디오 알고리즘은 없으므로 전체 오디오/서버 회귀를 다시 반복하지 않았으며, Window 실패 보존의 새 실행 경로를 실제 두 PC에서 재현했다고 주장하지 않는다. 실패한20ms 보고서는 정상 분석기가 거부하는 상태로 유지한다. 원격 복구는 기본/대기시간 확장 SSH와 Windows SSH 클라이언트에서 실패해 `restoration-pending.json`에 기록했다. 노트북의 기존 Tailscale 피어도 오프라인으로 관측됐으며 새 경로나 설정을 만들지 않았다. 커밋·푸시·릴리즈는 하지 않았다.
