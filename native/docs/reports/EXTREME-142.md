# EXTREME-142 — 노트북 없이 수신 여유 하한 검증과 루프백 판정 보완

2026-11-02 / 기존140–141 미커밋 변경 보존. 사용자가 노트북 전원 꺼짐 가능성을 알려 PC 단독 검증으로 전환했다. **낮은 수신 여유 후보를 기각하고 측정 합격 판정을 보완했으며, 제품의 평상시 지연 감소를 달성했다고 선언하지 않는다.**

## 가설과 재현 범위

기존 자동 저지연 정책의 여유 하한15ms를10~14ms로 낮추면 안정 구간 큐를 줄이면서 기존 연속성을 유지할 수 있는지 비교했다. 새 앱 정책을 먼저 적용하지 않고 실제 `RtpOpusPlayoutBuffer`에 기존 생성자 매개변수를 전달하는 검사로 구현했다. 기본20ms·자동 정책 하한15ms·프레임·출력·SDK·장치 설정은 유지했다.

140의 성공한20ms 상세 실행3회에서 양쪽 수신 기록6개를 사용했다. 각 기록의 admission/read **잠금 획득 시각**으로 상태 변경 순서를 구성하고, 합성10ms Opus 패킷으로 교체했다. 원래 PCM·SRTP·네트워크·CPU 경쟁·초기 큐/디코더 상태를 복원한 것은 아니다. 모든 정책은 같은 빈 상태에서 시작한다. 첫10초 또는 기록 절반 중 더 긴 구간 뒤의 큐를 비교하며, 마지막50ms는 잘린 기록 끝의 인위적 부족을 피하려고 제외한다. PLC/폐기/부족은 그 재현 전체를 집계한다.

렌더 위상0/2.5/5/7.5ms와 네 도착 조건을 사용했다. `recorded`는 원래 도착 패턴, `burst30`은5초마다30ms 묶음 도착, `burst30-once`는20초에 한 번30ms 묶음 도착, `loss10`은20초 부근10ms 패킷 하나의 생략이다. 위상 변경과 추가 교란은 합성 민감도 시험이며 실제로 그 장애가 모두 발생했다는 뜻이 아니다. 지연된 render read는 장치 underflow의 물리 모델이 아니다.

정책은 고정20/10ms, 기존 자동 하한15ms, 후보 자동 하한10/11/12/13/14ms의8개다. 다른 자동 정책 매개변수는 기존과 같이 시작20ms·상한30ms·quiet/hold/재시작/시계 보정을 유지했다.6기록×4위상×4조건×8정책 = **768개 결정적 재현**이다. 기존 `PlayoutReplay`의 장시간 구형 trace 입력/복구 정책 비교와 달리 새 도구는45초 pair 보고서의 위상·자동 하한 민감도를 비교한다.

## 결과와 기각

아래 큐 감소는 `recorded` 도착 패턴의4개 렌더 위상·6기록, 총24개 비교의 **샘플 가중 큐 평균 감소량 중앙값**이다. 실제 입→귀·실제 장치 출력 지연이 아니다. 연속성 악화는 PLC 시간·최대 연속 PLC·재버퍼·늦은 폐기·복구 폐기·공급 부족·trim 중 하나라도 기존 자동15ms보다 증가한 조건 수다.

| 자동 하한 후보 | 큐 감소 중앙값 | 기록 도착 패턴+위상24조건 중 악화 | 전체96조건 중 악화 |
|---|---:|---:|---:|
|10ms|4.948ms|4|27|
|11ms|3.961ms|4|27|
|12ms|2.972ms|4|26|
|13ms|1.985ms|4|26|
|14ms|0.995ms|3|21|

10ms 후보는 한 PC 기록의 원래 도착 패턴에서도4개 위상 모두 PLC가 기존0에서7.5~10ms로 증가했다. 따라서 일부 실행에서 큐가 줄었다는 이유만으로 하한을 낮추지 않는다. 고정10ms와 고정20ms 대조도 위상 포함 기록 패턴24조건 중10개, 전체96조건 중72개에서 같은 연속성 기준을 악화시켰다. 기존140의 짧은 유선 성공을 전 환경 무끊김으로 승격할 수 없다는 근거다.

**10~14ms 자동 하한 후보는 모두 기각했다.** 앱의 자동 정책 하한15ms와 일반 기본20ms는 유지한다. 후보는 검사 도구의 비교 매개변수이며 제품 실행 모드/프리셋으로 추가하지 않았다. 반복적인20~30ms 공백을 낮은 버퍼로 항상 흡수할 수 있다는 주장도 하지 않는다.

## PC 실제 출력 경로의 추가 대조

기존 `--render-reserve-path-device`를 이용해 같은 PC에서20→10→20ms를 실제 WASAPI 공유 출력/디지털 루프백으로 측정했다. 각32초이며, 기존 도구의 Baseline 코덱·미리 인코딩한 신호·decoded-pcm 기준을 세 실행 모두 유지했다.140의 native LowDelay64 양쪽 실시간 캡처와 절대 지연을 합쳐 비교하지 않는다. 실제 귀/DAC·마이크·네트워크·게임 시험도 아니다.

각 실행14/14개 파형 상관 검출은 성공했지만, 기존 native QPC 신뢰 조건을 통과한 표본은 **세 실행 모두0개**였다. 루프백 QPC가 콜백보다 약0.6~3.3ms 미래로 관측된 구간이 있었고, 선택된 마커는 모두 신뢰 조건을 만족하지 않았다. 원시 시각이 실제로 잘못됐는지 또는 루프백 시각의 특성인지는 이번에 확정하지 않았다. 기준을 느슨하게 해서 숫자를 만들지 않는다. `totalMs`는 이미 null이므로 raw `nativeQpcTotalMs`/`afterSubmitMs`를 출력·입→귀 지연으로 인용하지 않는다.

이때 기존 도구가 상관 검출 수만 보고 `complete=true`로 기록하는 모순을 발견했다. **`RenderLatencyProbe.RunAsync`는 이제 실행당 신뢰 가능한 timing 마커도10개 이상이어야 complete를 통과**한다. 파형 검출 수와 `trustedTimingMarkers`를 분리하고 불충족이면 실패로 종료한다. 타임스탬프 신뢰 검사 자체는 유지했다. 원본을 고치지 않고 `render-qualification-review.json`에 과거 원본의 기존 complete=true/교정 기준 qualified=false를 별도로 보존했다. 교정된 코드로 실제 장치 시험을 반복했다고 표시하지 않는다.

## 실제 변경·검증

- `Checks/RecordedReserveReplay.cs`, 검사기 CLI: 단일 수신자의10ms pair 상세 기록을 제한된 범위에서 재생한다. 입력과 출력 경로 동일,100MiB 초과, 미완료/유실 기록·다중 상대/SSRC·유효하지 않은 길이/시각·원래 기록의 모호한 admission/read 순서를 거부한다. 결과에 입력/앱/검사기 해시와 관측 한계를 보존한다.
- `--recorded-reserve-checks`: 일정한 소스의 두 렌더 주기/위상·RTP 랩에서 모든 비교 정책의 디코딩 진행과 PLC/부족/재버퍼/trim0을 확인한다. `verify.ps1`에 연결했다.
- `RenderLatencyProbe`: 파형 검출과 시각 신뢰를 분리해 위의 잘못된 완료 판정을 막았다. 앱 오디오 경로에는 변경이 없다.

최초 빌드는 Program의 패턴 변수 이름 충돌과 상수 배열 분석 규칙으로 실패해 새 변수명을 구분하고 배열을 정적으로 보관했다. 실패 로그를 보존했다. 이후 경고/오류0 빌드와 결정적 재현 자체 검사·기존 파형 상관 검사·pipeline/incident 검사에서 PCM 동일성·기록 상한·경합 무할당 조건을 통과했다. 전체768재현 결과는`v3` 자료다. 이후 최종 수정은 입력 상한/자체 검사 강화와 루프백 보고서 완료 조건이며 오디오 정책 변경은 아니다.

최종 빌드로 한 기록의128개 재현/80개 후보 비교를 다시 실행해v3와 결과가 완전히 같은지 확인했다. 기존 출력 파일을 덮어쓰려는 실행은 실패하고 파일이 그대로임도 검사했다. Node 실행기/병합/관측12개, Python 분석12개, `git diff --check`를 통과했다. 기존파일/원본과 같은 출력 경로는 새 도구가 거부한다. 실제 장치 루프백의 교정 후 재측정·노트북 시험은 이 회귀 합격에 포함하지 않는다.

## 재현·보존·남은 범위

```powershell
# 이미 빌드한 검사기에서 실행한다. 원본은 성공한45초 상세 pair participant.json이어야 한다.
./native/TransportProbe/bin/Release/net10.0-windows10.0.19041.0/TransportProbe.exe --recorded-reserve-checks
./native/TransportProbe/bin/Release/net10.0-windows10.0.19041.0/TransportProbe.exe --recorded-reserve-replay PARTICIPANT.json OUTPUT.json
```

원본·단계별 결과·실행기는 Git 제외 `native/.local/extreme-142/`에 보존했다. `results-v3.json`, 각`*-replay-v3.json`, `render-reserve-current.json`, `render-qualification-review.json`, 빌드 로그가 입구다. 초기32/64조건 자료는 탐색 단계로 구분하고 최종768조건 집계와 섞지 않는다. 큐 평균은 요청 샘플 수로 가중하며P95는 read별 분포다.

노트북 전원/SSH가 회복되면141의 백업 시험 폴더 복구와 같은 조건의 성공한20ms180초 대조를 먼저 확인해야 한다. 해당 복구를 완료했다고 표시하지 않는다. PC 시험 프로세스는 종료했고 배포본/서버·라우팅/VPN·장치/드라이버/전원 설정은 유지했다. 물리 입→귀·독립PC 재시험·실제 게임·외부/TURN·다인은 미실시다. 커밋·푸시·릴리즈는 하지 않았다.

후속: 노트북 복귀 후 원본 도구 복구 및 독립 두 PC20ms180초 재시험은 [EXTREME-143](EXTREME-143.md)에서 완료했다. 위 복구 대기/미실시는142 실행 당시의 상태다.
