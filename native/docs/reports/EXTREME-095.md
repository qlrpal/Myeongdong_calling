# EXTREME-095 — TURN 재연결 437과 UDP 포트 재사용 회피

2026-10-26.094에서 남은 TURN 재연결 실패를 조사했다. **실패 시 TURN Allocate의437 응답을 확보했고, 같은 포트 재사용으로 통제 재현했다. 앱의 새 연결 포트 선택을 수정하고 정상 종료 시 TURN 삭제 요청을 보내는 별도 SDK 후보를 추가했다.** 코덱·WASAPI·재생 대기값·서버 설정·라우팅은 변경하지 않았다.

## 원인 관측

프로브에 제한된 SDK ICE 구조화 로그를 추가했다. 단계·호스트 로컬 단조 시각·정적 메시지 템플릿·오류 코드·소켓 주소만 선택적으로 기록한다. SDK의 전체 메시지 formatter, 예외 본문, SDP, 인증 이름/비밀/nonce/트랜잭션 ID는 저장하지 않는다. 로그는2048개로 제한하며 누락을 표시한다. 비밀을 포함하는 formatter를 실행하지 않는 검사도 추가했다.

동일 후보로 최초 제품 흐름은 성공했지만 반복1회차의 노트북 재연결에서 Allocate437을3회 받은 뒤 SDK가 중계 후보 수집을 포기했다. PC는 자신의 TURN 할당에 성공했으나 상대 후보가 없어 약16초 뒤 ICE 실패, 제품 검사는40초 연결 대기 제한으로 실패했다. 이후 같은 계측의2·3회차는 성공했다. 최초 실패를 삭제하거나 재실행 성공으로 대체하지 않는다.

[RFC8656 §7.4](https://www.rfc-editor.org/rfc/rfc8656.html#section-7.4)는 Allocate437을 서버가 이미 사용 중으로 보는 연결 조합의 충돌로 설명하고, 다른 클라이언트 전송 주소로 재시도하도록 권고한다. 단순 Wi-Fi 차단이나 오디오 장치 문제로 볼 증거가 아니다. SDK 소스의 정상 Close에는 TURN 할당 삭제 요청이 없었다. 현재 서버는 coturn4.6.1-1build4이며 기존 시간대의 유효한 coturn 로그는 확보하지 못했다. 이 때문에 과거 모든 실패가437이었다고 소급 확정하지 않는다.

## 미디어 없는 실제 TURN 통제 시험

같은 클라이언트 IP/UDP 포트로 성공한 할당을 닫고 다시 요청했다. 최초 성공의 서버 관측 주소도 기록했다. 원본 종료 A1→삭제 요청 B→원본 종료 A2로 비교하며 모든 조건의 종료 후 간격을2초로 동일하게 뒀다. 새 seed는 명시적으로 다른 무작위 포트를 선택했다.

|조건|첫 할당|같은 포트 재할당|다른 포트 재시도|
|---|---|---|---|
|A1 원본 종료|성공|437 실패|성공|
|B 인증된 Refresh(0) 후 종료|성공|성공|불필요|
|A2 원본 종료|성공|437 실패|성공|

초기200ms 간격에서는 삭제 요청을 보낸 B도 즉시 재할당에 실패했다. 또 초기 시험의 새 seed에 OS 자동 포트를 사용하자 바로 직전에 닫은 시험 포트가 다시 선택돼 seed부터437로 실패했다. 이 실패도 보존했다. 따라서 **Bind(0)을 다시 호출했다는 사실은 새 TURN 연결 조합을 보장하지 않는다.**

coturn4.6.1의 [refresh 처리 소스](https://github.com/coturn/coturn/blob/4.6.1/src/server/ns_turn_server.c#L4208-L4217)는0수명을 최소1초 타이머로 처리한다. 삭제 요청은 전송 성공과 즉시 삭제 완료가 같지 않다.2초 간격은 통제 시험에만 사용했으며 앱 재연결에는 추가하지 않았다.

## 구현

1. **일반 앱 소스:** PeerConnection 구성 전에49152~65534의 짝수 UDP 포트를 암호학적 난수로 선택한다. 프로세스 내 활성 포트 및 닫은 뒤600초가 지나지 않은 포트를 제외하고 명시적으로 bind한다. 외부 프로세스와의 bind 충돌은 최대16회 안에서 다른 포트로 재시도한다. 활성 포트는 긴 통화 중 만료시키지 않으며, 세대가 다른 과거 종료가 새 소유권을 해제하지 못한다. 포워딩·OS 라우팅·방화벽 규칙 변경은 없다.
2. **별도 SDK 후보:** 정확한 상류 소스 해시를 확인하는 `patch_turn_release.py`를 추가했다. UDP TURN 할당이 있는 정상 종료에서 소켓을 닫기 전에 인증된 Refresh(LIFETIME0)를 새 트랜잭션으로 보낸다. 종료 송신의 socket timeout은100ms로 제한한다. 응답 확인·삭제 완료를 보장하지 않는 best effort이며 TCP/TLS에는 적용하지 않는다. 일반 NuGet 패키지에는 자동 반영하지 않는다.
3. **진단 문구:** 강제 TURN 실패에 직접 연결/방화벽 차단으로 단정하는 문구를 표시하지 않도록 수정했다.
4. 제품 시험에 OS 자동 포트를 쓰는 대조 CLI, 단계별 SDK 로그와 실패 직전 스냅샷을 추가했다. 새 분석기는 모든 단계에서 실제 송신/수신/디코딩 카운터 증가까지 확인한다. 연결 상태만으로 미디어 통과를 판정하지 않는다.

포트 관리는 연결 구성/종료에만 관여하며 캡처·인코딩·송신·재생 루프에는 잠금이나 대기를 추가하지 않는다.600초는 현재 SDK의 TURN 요청 수명에 맞춘 프로세스 내 보존 기간이다. 프로세스 재시작·다른 NAT 클라이언트의 매핑 재사용·비정상 종료까지 전역으로 보장하는 것은 아니다.

## 실제 두 PC 제품 흐름

수신 경쟁 게이트는 수정 상태로 고정했다. TURN 삭제 기능은 끈 채 같은 빌드에서 OS 자동 포트 A1→새 포트 B→OS 자동 포트 A2를 비교했다. 양쪽 종료 코드는 A1 실패, B 성공, A2 성공이었다. 간헐적 문제라 이1회 A/B/A만으로 장기 개선율이나 원본 복귀 시 필수 재현을 주장하지 않는다.

이어 새 포트 선택과 UDP 종료 삭제를 결합한 조건으로 두 PC에서3회 연속 제품 흐름을 통과했다. 매회 초기 연결, 실제 PCM 음소거/해제, 상대 볼륨, 강제 복구 후 연결, 기본 장치 재입장, 명시적 종료를 포함한다. PC의 후처리에서는 매회8개 피어/단계 구간의 송수신·디코딩 증가와 TURN 경로를 확인했다. 실제 재생 장치를 사용하지만 물리 입→귀 지연이나 주관 음질 시험은 아니다.

노트북 후처리도 매회8개 미디어 구간을 통과했다. 양쪽3회, 총48개 피어/단계 구간에서 송신·수신·디코딩 증가를 확인했고, 각 회차의437 기록은 양쪽 모두0이었다.

## 최종 검증과 보존

- 수정 후보로 두 호스트6인90초 연결·디코딩·종료 정리를 통과했다.30개 수신기에서 미완료 IO 중첩이 없었고, 마지막5초의 양끝 일치 기록을 비교한30방향 모두 채널 중복·미관측0이었다. 전체 통화의 무손실·무PLC나6대 독립PC 검증을 뜻하지 않는다.
- 최종 명시 포트 통제 시험은 PC와 노트북 모두 위 표의8단계 결과를 재현했다. 초기에 다른 포트 재시도를 다시 Bind(0)에 맡겼던 노트북 시험은 앞서 사용한58748을 재선택해 실패했다. 마지막 도구는 seed와 재시도 모두 명시적 미사용 포트를 선택하도록 고쳤다. 이 진단 도구 수정과 중간 실패도 보존한다.
- `prepare.ps1`로 두 SDK 패치와 앱 빌드를 처음부터 재현했다. 최종 솔루션 빌드 경고/오류0, 포트 소유권/동시성·민감 로그 배제 검사 통과. 정상 패키지의 `verify.ps1 -NoRestore -Integration` 전체가 정적 분석·관리형·서버8개·IPv4/IPv6 ICE/DTLS/SRTP/RTCP·가변 프레임·경계 fixture를 통과했다.
- 준비 스크립트의 결합 SDK 후보도 계측을 끈 상태로 IPv4 RTCP·SRTP 재생·2.5/5/10ms·27초 결정적 미디어 pull·경계 fixture·IPv6 RTCP 통합을 통과했다. 이후의 변경은 통제 도구의 새 포트 선택 수정이며 다시 빌드·양쪽 실제 통제 시험을 수행했다. 앱과 SDK 코드는 그대로다.
- 실제 제품/그룹 시험의 SDK SHA-256은 `3236C12B229CA5EC517083E20F18EC7AD856B9EA2340CEAFBCC8D8B5FB20AE4B`, TransportProbe 해시는 `DF5B18857E1F5D1803C71B060D9BD1F5987A747685B5868B5923917FB4B12E34`였다. 최종 도구 수정 전후를 구분한다. 새 준비 경로의 SDK는 별도 manifest에 소스/바이너리 해시를 보존했다.
- 원본은 ignored `.local/extreme-095/` 및 노트북 임시 시험 폴더에 남긴다. `ports-*`는 삭제 기능을 끈 포트 A/B/A, `post-*`는 결합 조건3회, `group-*`는6인, `lifecycle-*`는 미디어 없는 통제 시험이다. 실패를 성공으로 덮어쓰지 않았다. 시험 엔진은 양쪽 모두 종료했고 노트북 시험 셸의 환경 변수를 제거했다.

## 범위와 배포

포트 선택 수정은 일반 앱 코드에 적용했다. SDK 수신 시작 보호·UDP 종료 삭제는 여전히 [분리된 시험 SDK 준비 도구](../../sdk-experiment/README.md)로 제공한다. 기본 NuGet 참조와 기존 `dist`는 변경하지 않았고 새 안정판 태그도 만들지 않았다. 새 코드의 커밋·푸시는 하지 않았다.

이 변경은 연결 실패를 예방하는 수정이다.094의 남은 호스트 간 지터·PLC, 과거 집 무선 경로의 대기, 모든 NAT 환경의437 자동 복구가 해결됐다는 뜻은 아니다. 서버 인증·방화벽·포트 범위·공유기 설정을 임의로 변경하지 않았으므로 복구할 시스템 설정은 없다.
