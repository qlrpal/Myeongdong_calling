# Mumble·네이티브 공통 신호 비교 — 0.5.9

2026-10-20 KST, 사용자가 준비한 집 PC·노트북의 Mumble 통화와 우리 앱을 같은 외부 측정기로 비교했다. **이번 설정·짧은 합성 신호에서는 Mumble이 더 짧게 측정되지는 않았다.** 다만 이는 PC 마이크 캡처 기준→노트북 디지털 루프백 검출 구간이며, 앱 내부 지연만의 비교나 물리 입→귀 측정이 아니다. Mumble 일반 성능·최저 지연을 대표하는 수치로 사용하지 않는다.

## 준비 및 경로

PC Mumble UI에서 `begemi`, `begemi-laptop`의 같은Root 접속을 확인했다. 서버는 OCI의64738포트,1.5.517이었다. PC 설정은WASAPI 공유 입력·출력,72kbps,10ms 패킷,저지연 Opus 허용,기본 지터10ms,출력 지연 설정10ms였다. 원래 입력 처리는 음성 감지,Speex 잡음 억제(-30dB),혼합Speex 에코 제거,최대 증폭36.17이었다. 이 설정값들을 합산해 실제 지연으로 간주하지 않았다. UI의서버UDP 평균11.6ms도 두 클라이언트 음성 경로나 입→귀 지연이 아니다.

우리 앱은0.5.9 기본LowDelay64·10ms·20ms 수신 예비량을 유지하고,동일OCI의TURN 중계를 강제했다. 양쪽 통화 진단에서TURN 경로를 확인했다. 같은 서버 호스트를 거치지만Mumble과TURN의 프로토콜·처리·포트는 다르므로 완전히 같은 네트워크 경로를 입증한 것은 아니다.

PC의 시스템 기본 출력은 이어폰이었다. 초기 신호가 이어폰에서 들렸다는 사용자 확인 후,시스템 기본 출력을 바꾸지 않고 측정 신호만Sound Blaster GS3에 지정했다. 스피커→마이크 배치를 유지했다. 공통 기준 마이크는fifine이며,시험 후 오디오 세션 메타데이터에서Mumble도fifine 입력을 사용 중임을 확인했다.

노트북 측정기는기본Multimedia 출력인Realtek 스피커 엔드포인트의 디지털 루프백을 사용했다. 우리 앱의수신 장치도해당엔드포인트였다. 노트북Mumble의실제출력세션·세부오디오설정은 별도로 검증하지 못했으며,기본출력선택과신호검출을 바탕으로 비교했다. 노트북의기존DTS 효과는 변경하지 않았다.

## 공통 측정기

1. PC GS3에서400ms 유성음 형태의합성신호를 재생한다.
2. PC 실제마이크캡처에서신호가 검출된시각을공통기준으로삼는다. 스피커재생명령→스피커→공기→기준마이크까지의시간을 앱지연에더하지않는다.
3. 통화앱을 거친노트북출력을디지털루프백에서검출한다.
4. 매신호직전SSH로12회시각왕복을교환하고가장좁은단조시계오프셋범위를사용한다. 시각정보만전송하며SSH로음성을운반하지않는다.

양쪽검출기는같은harmonic detector를사용한다.20ms 구간을처리하고연속2개구간일치로검출한다. 보고된구간은시계오프셋범위만반영한다. 검출20ms 양자화·신호왜곡·장치QPC 특성의오차전체를포함하는신뢰구간이아니다. 범위중점을통계요약에사용했으며각회차8회다.6개미만검출은실패로처리한다.

원음과수신음성은파일에저장하지않았다. 합성파형과캡처샘플은일시메모리에서만다룬다. 실제마이크음량이나EQ를수정하지않았다. 짧은음절의검출지연에는VAD 시작과신호처리의영향이들어갈수있어,지속발화의동일파형위치전달지연으로곧장일반화하지않는다.

## 네이티브 역방향에서 발견한 별도 문제

PC→노트북의측정방향은60초통화진단에서부족0ms·재버퍼0회·PLC20ms였다. 반면반대방향인노트북→PC는부족6252.77ms·재버퍼97회·PLC10920ms였다. 통화가정상종료됐다는것만으로양방향안정성을통과시킬수없다.

노트북마이크는5.333ms 공유캡처를사용했고최종입력불연속2369회,송신4792프레임이었다. PC는송신5959프레임·입력불연속1회였다. 두기기표본구간이완전히같지않아개수차이를그대로네트워크손실로계산하지않는다. 노트북입력불연속이빈번하고PC수신보고누적손실은0이어서,다음우선조사는복구버퍼확대보다**Mumble이함께실행된조건의짧은공유캡처와10ms 캡처대조**다. 공유주기충돌·드라이버·처리원인을현재자료만으로확정하지않는다. 이문제때문에이번시험을게임공존또는전체통화안정화완료로표시하지않는다.

## 제외 회차 및 복구

- 초기UDP 제어두회차는시각교정응답실패로제외했다. 현재관련프로그램수신차단규칙이관측됐으며규칙을변경하지않고SSH 제어로전환했다. 규칙이모든UDP 실패의유일원인이라고추적입증한것은아니다.
- 이어폰으로출력한SSH 회차는노트북검출0/8로제외했다.
- Mumble 음소거해제동작이사용자입력감지로실행되지않은중간회차는2/8만검출돼제외했다. 상태를재확인해원래송신을복구하고A2를새로실행했다.
- 진단초안은미검출을실행오류로반영하지못했지만,유효회차전6/8 기준과실패종료를추가했다. 초기파일의error가null이어도미검출값을지연통계에넣지않았다.
- PC Mumble을음성감지·Speex(-30dB)·혼합Speex 에코제거로복구하고,원래음소거알림선택및마이크음소거해제를화면에서확인했다. 증폭36.17·72kbps·10ms·저지연허용도복구화면에서확인했다. 출력설정은변경하지않았다.
- 시스템기본장치·볼륨·방화벽·노트북DTS는변경하지않았다. 양쪽측정프로세스잔류0을확인했고Mumble은실행상태로남겼다.

## 코드와 검증

진단전용 `--crossapp-send`, `--crossapp-receive`, `--crossapp-call`을추가했다. 마지막옵션은60초실제마이크TURN 통화다. SSH 비밀번호·대상·호스트키는일시환경변수로제공하며소스나결과에저장하지않는다. 자동접속원격작업폴더는현재격리시험폴더를전제로한다. 신호출력엔드포인트는진단환경변수로선택한다. 제품UI·기본오디오정책은바꾸지않았다.
