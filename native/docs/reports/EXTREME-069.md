# 극저지연 검증 069 — 두 수신 경로의 공통 변동

작성: 2026-10-22. 분기: `codex/extreme-latency`.

서버에서 보낸 패킷과 두 PC의 수신 기록을 대응하니, 큰 지연 변동이 유선 PC와 Wi-Fi 노트북에 함께 나타났다. 노트북 Wi-Fi만의 문제라는 설명은 충분하지 않다. 다만 OCI 가상 NIC·외부망·집 공유기 중 하나를 원인으로 확정하지 않았다. 이번에는 음성 알고리즘이나 버퍼를 변경하지 않았다.

후속 070의 실제 배선 확인: PC의 이더넷은 메인 공유기가 아닌 메시 버디에 연결되어 있고, 버디→메인 공유기는 5GHz 무선 백홀이다. 따라서 이 보고서의 ‘유선 PC’는 호스트의 첫 인터페이스 설명이며 무선 전체를 우회한 독립 대조가 아니다. 공통 변동만으로 메시 백홀을 배제하거나 WAN만의 문제로 한정하지 않는다.

## 패킷별 공통 변동

`analyze_shared_downlink.py`는 각 수신 스트림의 RTP SSRC·타임스탬프·순번을 서버 발신 pcap에 대응한다. 수신 시각 차이에서 발신 시각 차이를 빼고 스트림별 최솟값을 기준으로 상대 변동을 계산한다. 서로 다른 PC의 시각을 직접 빼지 않는다. 시계 속도 오차는 교정하지 않았으며 절대 단방향 지연이나 마이크→귀 지연이 아니다.

| 자료 | 공통 관측 길이 | 20ms 이상인 100ms 구간: 하나 이상 / 양쪽 | 양쪽 공통 묶음 | 상대 변동 최대 PC / 노트북 |
|---|---:|---:|---:|---:|
| 068 저장 자료 재분석 | 29.665초 | 15 / 14 | 8 | 237.66 / 213.24ms |
| 이번 069 | 29.560초 | 2 / 2 | 1 | 37.70 / 32.93ms |

분석 범위의 서버 패킷 대응률은 두 자료 모두 양쪽 100%다. 인접 구간은 독립 장애 횟수가 아니며 묶음은 빈 구간 하나까지 합친다. 서버 소프트웨어 발신 캡처는 실제 물리 송신보다 앞선다. 두 스트림의 공통 변동은 공통 경로를 조사할 근거이며 특정 장비의 고장 증명은 아니다.

## 새 120초 TURN 시험

068과 같은 2.5ms Opus·적응 예비량 5–20ms·공유 WASAPI 설정과 같은 VoiceNative DLL을 사용했다. PC와 노트북의 물리 미디어 주소를 명시하고 실제 TURN 경로를 확인했다. 시험 중 빌드와 대용량 파일 복사는 하지 않았다.

| 수신 기기 | 버퍼 부족 | PLC 보완 | 초기 포함 출력 소진 | 수신 등록→렌더 중앙값 | 명목 연속성 |
|---|---:|---:|---:|---:|---|
| PC | 0.036% | 0.290% | 0회 | 15.08ms | 통과 |
| 노트북 | 0.042% | 0.295% | 0회 | 13.03ms | 통과 |

양쪽 strictCapturePass도 통과했다. 렌더 중앙값은 제한된 패킷 추적 범위의 앱 내부 구간이며 전체 통화 지연이 아니다. 이번 시험은 장시간 기준 295초보다 짧다. 시간대와 회선 상태가 다르므로 이전 TURN 실패가 코드 변경으로 해결됐다고 주장하거나 기본 설정 승격 근거로 사용하지 않는다. [068 장시간 실패](EXTREME-068.md)는 유효하게 남는다.

## 서버와 ICMP 대조

서버에서 165초 동안 200ms 간격으로 825회 관측했다. 관측 시점의 fq_codel backlog·qlen 최대는 0, drop 증가도 0이었다. 조회 오류는 없었다. CPU 평균 사용률 약 3.01%, steal 평균 0.45%·최대 5.13%였다. 관측 사이 순간 큐나 OCI 호스트·가상 NIC 이후 구간을 배제하는 자료는 아니다.

서버 pcap은 201,026패킷, 커널 드롭 0으로 종료했다. 합성 시험의 UDP 헤더와 페이로드 앞부분을 최대 128바이트 보존했으며 복호화하지 않았다. 원본은 Git 제외 경로에 둔다.

추가한 `--path-control TARGET GATEWAY SECONDS OUTPUT`은 목적지·게이트웨이·루프백을 각각 최대 초당 5회 조회한다. 기존 고빈도 명령은 유지하고 새 명령에서는 Sleep(1) 스케줄링 제어 스레드를 실행하지 않는다. ICMP 자체도 관측 영향을 줄 수 있다.

PC의 인터넷/게이트웨이 RTT 최대는 31/19ms, 노트북은 36/409ms였다. 루프백 RTT는 모두 0ms, 응답 실패는 없었다. 노트북 게이트웨이의 409ms를 음성 지연으로 해석하지 않는다. ICMP 처리 우선순위와 응답 동작이 UDP와 다르며 최대값만으로 동시 원인을 확정할 수 없다. OCI의 ICMP 무응답은 이 시험의 음성 패킷 손실로 계산하지 않았다.

후속 070 확인: 노트북에서 게이트웨이 172.30.1.254의 OS 경로는 Tailscale(index 24), 인터넷 1.1.1.1은 Wi-Fi(index 13)였다. 이 ICMP 명령은 미디어 인터페이스를 지정하지 않으므로 게이트웨이 결과를 물리 Wi-Fi·공유기의 대조로 사용하지 않는다. 음성 및 서버 RTP 개별 대응 결과에는 이 ICMP 값을 사용하지 않았다.

## 적용과 다음 단계

추가한 것은 공통 변동 분석기와 저빈도 경로 대조 명령이다. Python 자체 검증(시계 오프셋 불변성·공통 변동·한쪽만 변하는 대조), 1초 루프백 명령 검증, Release 빌드가 통과했다. 음성 처리 변경이 없으므로 068의 전체 회귀 검증 결과와 구분한다.

불필요한 앱 버퍼 증설은 하지 않는다. 남은 조사는 OCI 발신 이후 공통 경로를 서로 다른 회선/서버 경로와 비교하는 방향이다. 기존 모바일 핫스팟 시험은 버전·프레임·예비량이 달라 현재 설정의 직접 대조로 쓰지 않는다. 게임 부하와 물리 장치 지연 시험은 이번 범위 밖이다.

원본과 집계: `native/.local/extreme-069/`. 기존 배포본·시스템 라우팅·오디오 장치·서버 큐 설정은 변경하지 않았다. 커밋·푸시는 하지 않았다.
