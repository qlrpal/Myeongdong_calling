# EXTREME-096 — 수정 SDK의 일반 빌드·실행·배포 연결

2026-10-26 / `codex/extreme-latency`

## 변경과 목적

094/095에서 검증한 수신 시작 상태 보호와 UDP TURN 정상 종료 시 인증된 Refresh(0)를 일반 빌드에 연결했다. 정상 실행에 실험 환경 변수나 DLL 수동 교체가 필요하지 않다. 기존 `dist`는 자동으로 덮어쓰지 않았으므로 새 소스로 다시 빌드해야 한다.

상류 SIPSorcery10.0.17의 고정 커밋 `08c2ed0ad72c423ca06950dee2e842488a219884`와 소스 해시를 확인하고, 두 수정만 적용해 빌드한다. 수신 상태 확인·설정만 잠그며 비동기 요청 등록과 패킷 핸들러는 잠금 밖이다. 종료 삭제는 UDP best effort이며 ACK나 즉시 서버 삭제를 보장하지 않는다. 계측용 큐와 실험 게이트는 제품 SDK에 넣지 않았다.

공식 패키지의 net10 런타임 의존성 버전을 공유 props와 잠금 파일로 유지한다. 원본 SIPSorcery NuGet DLL을 런타임 대체 경로로 남기지 않는다. 상류 소스 프로젝트만 스타일 분석을 제외하고 앱의 정적 분석은 유지한다.

## 자동 준비와 식별

- `native/Directory.Build.targets`가 일반 build/run/publish에서 SDK를 준비한다. Python이나 Git 실행 파일은 SDK 준비에 필요하지 않다.
- 최초에는 약142MiB 상류 압축본과 잠긴 NuGet 의존성을 내려받는다. 전체 압축본 SHA256을 확인하고 SDK 소스와 원본 라이선스만 추출한다.
- `.local/patched-sdk`에 입력·출력 해시를 보존하며 동시 빌드는 파일 잠금으로 직렬화한다. 캐시 재사용과 출력/publish DLL 해시를 검사한다. 준비 실패 시 원본 DLL로 조용히 돌아가지 않는다.
- 실제 식별자는 `10.0.17+myeongdong.1`, 패치 메타데이터 `udp1-turn1`이다. `--sdk-build-info`와 `--sdk-build-check`로 실제 로드된 어셈블리를 확인한다.
- 배포 출력에는 원본 SIPSorcery 라이선스를 함께 복사한다.

## 검증 결과

1. 일반 Release 빌드 경고/오류0. `verify.ps1 -NoRestore -Integration`의 관리형 회귀·서버·IPv4/IPv6 WebRTC/SRTP/RTCP 검사 모두 통과했다. 가변2.5/5/10ms SRTP와27초 미디어 시간의 통제 재생 검사도 통과했다. 후자는 실제 장치/네트워크 장시간 시험이 아니다.
2. 제품 SDK의 순수 UDP20,000패킷 시험3회에서 각각 정체성 중복·미관측·형식 오류0이었다. 예전 실험 게이트를 original로 지정해도 제품 보호는 꺼지지 않았다.
3. 실제 TURN 할당 종료/같은 포트 재할당 통제 시험6개 행 모두 성공했다. 예전 삭제 환경 변수를0으로 지정해도 제품 삭제 경로는 적용됐다. 서버 정리 주기를 고려한2초 간격의 별도 시험이며 앱 재접속에2초 대기를 추가하지 않았다.
4. Git 후보 소스만 공백이 있는 새 경로에 복사하고 SDK 캐시 없이 locked restore/build를 통과했다. 설치된 .NET과 기존 NuGet 다운로드 캐시는 사용했다. 상류 다운로드를 포함한 한 번의 빌드는17.16초였으며 새 장비의 다운로드 시간 보장은 아니다.
5. 새 경로에서 publish 후 배포 파일만 다시 복사해 실행해도 제품 SDK 식별자가 확인됐다. 라이선스도 포함됐다. 일반 StageOnly 배포와 `publish --no-build --no-restore`도 통과했다.
6. 원본 NuGet DLL을 넣은 별도 출력은 해시 검사에서 거부됐다. 실제 deps 그래프는 수정 DLL reference를 사용하며 원본 NuGet 패키지 런타임 항목을 포함하지 않았다.

원시 로그·캐시·소스 압축본·배포 파일은 무시된 `.local`에만 보존하고 Git에는 빌드 도구·패치 조각·잠금 파일·검증 소스·문서만 포함한다.

## 해석과 남은 범위

이번 검증은 수정 SDK가 정상 사용자 실행과 배포에 실제 적용되는지를 확인했다. 새로운 두 PC/외부 친구 통화나 게임 부하 시험을 수행했다는 뜻은 아니다. 이전 두 호스트 결과는094/095를 참고한다. 남은 네트워크 지터·PLC·자동 경로 유지 실패와 모든 NAT의437 복구를 해결했다고 일반화하지 않는다. 실제 입→귀 지연 수치의 개선도 이번 빌드 연결 시험으로 주장하지 않는다.

정상 실행과 식별 명령은 [SDK 빌드 가이드](../SDK-BUILD.md)에 정리했다. 이후 우선순위는 외부 NAT·다른 사용자·게임 부하에서 동일 식별자를 확인한 회귀와 남은 연결/연속성 문제의 분리다.
