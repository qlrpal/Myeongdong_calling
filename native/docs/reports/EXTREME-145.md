# EXTREME-145 — 같은 주기의 캡처 경로 비교와 워밍업 큐 재현

2026-11-03 · 기반 `e8a140b` 및 미커밋 실행 계획 보존. 사용자가 약6시간의 자율 검증을 요청한 작업의 첫 단계다. 별도 Windows 관리자 승인·장치/네트워크 설정 변경 없이 진행한다.

## 같은 주기의 캡처 대조

기존 캡처 경로와 자체 공유 캡처의 차이를 staging 효과와 분리했다. 기존 경로→자체 native→기존, 자체 native→staged→자체 native를 각12초(처음2초 제외) PC와 노트북에서 실행했다. 동일 장치·형식·실제 주기를 유지하고 음성은 저장하지 않았다. 실제 캡처 패킷 QPC→콜백의 나이이며 물리 수음→귀나 송수신 전체 시험이 아니다.

PC의 실제 입력 주기는 모든 회차10ms, 콜백 나이 중앙값은19.03~19.04ms/P95는19.05~19.06ms였다. 노트북은5.333ms이며 기존/자체/기존 중앙값7.54/7.35/7.56ms, P95 13.02/12.80/13.11ms였다. 자체/staged/자체 중앙값7.50/7.59/7.54ms, P95 12.93/13.09/13.04ms였다. 각 회차 입력 불연속/시각 오류는0이었다.

PC에서 자체10ms 루프로 교체해 캡처 전달을 수 ms 줄인다는 가설은 이번 대조에서 지지되지 않았다. 노트북의 작은 변동도 native 경로 자체가 이미 기준선에서 사용돼 경로 개선으로 해석하지 않는다. staging의 일관된 정상 지연 이득은 없다. 따라서 두 후보를 제품 기본값으로 승격하지 않는다. 게임 부하·장시간에서의 리스 보유/실패율 차이는 이 짧은 시험으로 배제하지 않는다.

비교용으로 기본 주기 허용과 staging을 분리하는 내부 진입점을 만들었다. 기존 실험의 staging 동작은 보존하며 UI/사용자 설정에는 새 선택지를 추가하지 않았다. 기본 주기 선택도 fundamental/min/max 범위와5~10ms 조건을 확인한다. 같은 주기라고 다른 경로의 스레드 스케줄링까지 동일한 단일 요소 비교라고 표현하지 않는다.

## 워밍업 가설의 결정적 재현

실제 `RtpOpusPlayoutBuffer`/native Opus와 규칙적 도착, 결정적인 장치 패딩 소비 산술을 연결했다.128/256/480샘플 읽기, 네 도착 위상, 미디어 시작1초/3초를 비교했다. 처음48조건에서 기존2초 워밍업과 처음부터 desired 패딩을 쓰는 모델을 비교했다. 후자는 진단 대조일 뿐 실제 장치에서 안전한 제품 정책으로 채택하지 않았다.

첫 미디어가1초에 시작한 경우30~60초 소스 큐 평균은, 워밍업이 없는 모델 대비256샘플 읽기에서 약2.42ms,480샘플 읽기에서 약5.07ms 높았다.128샘플 읽기는 출력 용량=목표여서 차이가 없었다. 미디어가3초에 시작하면 세 읽기 모두 차이가 없었다. 패딩 축소가 이미 시작한 미디어의 상위 큐에 영향을 주고 제어 법칙이 그 차이를 남길 수 있다는 재현 근거다.

이는 실제 장치의58ms를 정확히 설명하거나9ms가 모두 고착된다는 증거가 아니다. 인접 전환 표본의 큐 차이에는 도착·소비도 포함된다. `TotalInventoryMs`는 소스 큐+모델 패딩의 재고 산술이며 물리 지연으로 사용하지 않는다. 실제 장치·OS/CPU·네트워크·음향을 모델링하지 않는다.

## 다음 후보와 실제 수정 범위

음성을 읽고 버리지 않고, 출력 패딩 축소에서 생긴 유한한 소스 샘플 예산만 한 번의 제한적 소비율 증가로 정착시키는 후보를 구현했다. 추가 가속 최대0.5%, 전체 소비율 상한1%, 수신20ms와 현재 요청량 외 여유가 있을 때만 적용한다. PLC/부족·재버퍼·시간축 초기화/폐기 때 남은 예산은 취소한다. 통계는 실제 폐기량과 구분한 요청/적용/남은/취소 제어 예산이다.

추가24조건으로 총72조건의 규칙적 재현에서 PLC/재버퍼/PCM 부족/trim/모델 장치 소진은0이었다.480샘플 읽기 소스 큐 평균은 기존25.066ms→후보20.021ms였고, late media/128샘플 조건에는 예산을 부여하지 않았다. 무할당 예산 갱신/보존·취소·안전 여유 및 최대율 회귀를 포함했다. 모델 합격만으로 제품에 적용하지 않고 실제 장치와 두 PC 비교를 [146](EXTREME-146.md)에서 진행한다.

검사기에는 `--capture-path-device`, `--warmup-transfer-checks`를 추가했다. 비교용 capture/output-settle 내부 설정은 기본값이 꺼져 있다. 장시간 pair 검사 범위를 최대3600초로 확장하고300초 초과 시 baseline 표본을1초 간격으로 제한했다. 상세 trace는 기존45초 상한을 유지한다. 이 변경은 검사 범위 확대이며 기존 앱 재생 정책 변경이 아니다.

## 복구·원본·미실시

노트북의 원래 검사 도구는 대조 뒤 원본 SHA256 일치와 대상 검사 프로세스0을 확인해 복구했다. 기존 배포본·서버·장치·전원·드라이버·라우팅/VPN/AP 설정은 변경하지 않았다. Git 제외 `native/.local/extreme-145/`의 캡처 양쪽 원본·로그, `warmup.json`, `warmup-candidate.json`, 빌드·복구 자료에 보존한다. 커밋·푸시·릴리즈는 하지 않는다.

물리 입→귀·실제 게임·외부 친구/독립 회선·이번 후보의 장시간/중계/다인 품질은 본 보고서에서 미실시다. 기존 RTP/시계 자체 회귀와 경고/오류0 빌드는 통과했고, 후보 최종 전체 회귀와 채택 여부는 후속 결과로 구분한다.


후속 정리: 같은 주기 캡처·staging의 정상 지연 이득이 입증되지 않아 비교용 제품 경로/옵션은147에서 제거했다. `--capture-path-device`도 활성 CLI에서 제거했으며 당시 재현 소스/원본은 Git 제외145/147 폴더에 보존한다. 일회성 보정과 지속 제어도147에서 기각했다. 활성 `--warmup-transfer-checks`는 보정 없는 기존 정책과 desired-from-start 산술 대조48조건만 남긴다. 이 보고서의72조건은 당시 후보 빌드의 결과이며 최종 제품 정책을 설명하는 수치가 아니다.
