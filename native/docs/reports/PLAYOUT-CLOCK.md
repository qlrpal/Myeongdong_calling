# 소비율 보정과 큐 대기 회복 · 0.5.2

RTP 패킷의 순서와 코덱 설정은 유지하고, 출력으로 내보내는 PCM의 샘플 소비율을 보정합니다. 0.5.0/0.5.1의 고정 소비율에서는 작은 클록 차이만으로 큐 정리나 재버퍼링이 발생했고, 실제5분 통화에서는 높은 대기가 오래 남았습니다.

## 구현

- 출력 요청 뒤 남은 큐를 출력 샘플 수 기준으로 평활화합니다. 별도 타이머/스레드를 만들지 않습니다.
- 시작2초 동안 기준을20~30ms 범위에서 학습합니다. 이미 쌓인100ms 대기를 정상 기준으로 학습하지 않습니다. 기준 주변5ms는 보정하지 않습니다.
- 큐가 늘면 최대+1%, 줄면 최대−0.2%까지 소비율을 조절합니다. 변화는 완만하게 적용하며, 큐가 정상 범위로 돌아오면 보정도 줄어듭니다. 이는 하드웨어 클록 오차를 직접 측정한 값이 아닙니다.
- 인접 PCM 샘플의 인과적 선형 보간을 사용합니다. 별도의 프레임 대기를 추가하지 않으며 중립 속도에서는1샘플(약0.021ms) 지연으로 원래 PCM을 보존합니다. 프레임을 통째로 버리는 대신 필요한 만큼 샘플 소비량을 조절합니다.
- 보간은 피치를 보존하는 시간 신축 알고리즘이 아닙니다. 특히 대기를 따라잡는 동안 최대1%의 속도·피치 변화가 가능합니다. 주관적 음질 동등성을 보장하지 않습니다.
- 단일 패킷 손실에는 기존 소비율 추정을 유지하고 큐 관측을 건너뜁니다. 손실 때마다 학습을 초기화하면1% 손실 환경에서 클록 보정이 계속 중단되므로 이를 피했습니다. 실제 부족/재버퍼링과 장치·SSRC·시간축 초기화에서는 재학습합니다.
- 기존 PLC60ms 상한과 앱 큐120ms 최종 보호 장치는 유지합니다. PCM 복귀 경로는 변경하지 않았습니다.

`PlayoutClockController`는 소비율 피드백, `RtpOpusPlayoutBuffer`는 PCM 보간과 패킷 시간축을 담당합니다. 진단에 소비율 보정 ppm·누적 샘플 증감·출력 요청 P95/최대·읽기 직후 큐를 추가했습니다. 마지막 항목은 읽기 사이에 수신된 패킷을 포함하는 일반 큐 스냅샷과 다릅니다. 소비량(ms/s)은 보정 중1000에서 벗어날 수 있습니다.

## 결정적 부하 검사

조건별10분 상당의 가상 시간 검사13개입니다. 실제 장치·네트워크·음질 실측과 구분합니다. 동일한 코드에서 `correctClock:false`를 대조로 실행했습니다.

| 조건 | 보정 끔 | 보정 켬 |
|---|---|---|
| +200ppm | 큐 정리1회·최대120ms | 정리/부족/PLC0·최대약45ms |
| −200ppm | 재버퍼링4회·부족120ms·PLC240ms | 재버퍼링/부족/PLC0 |
| +500ppm·40ms 출력 요청 | 별도 대조 없음 | 정리/부족/PLC0 |
| −500ppm·40ms 출력 요청 | 별도 대조 없음 | 정리/부족/PLC0 |
| 초기80ms 대기 | 별도 대조 없음 | 60초 시점35.06ms·프레임 정리/PLC0 |
| 1% 손실+0~10ms 지터+±200ppm | 별도 대조 없음 | 주입 손실만 PLC·재버퍼링/부족/정리0 |

일정 송수신·추가 지연0~25ms·독립 손실1%·100ms 연속 손실에서도 기존 결과를 유지했습니다. 연속100ms 손실은 PLC 상한을 넘으므로 재버퍼링/무음이 남습니다. 보정으로 네트워크 단절 자체를 없앴다는 뜻은 아닙니다.

중립 보간은 실제 Opus 디코딩 출력의 패킷/출력 경계에서1샘플 지연 외에 차이가 없는지 검사했습니다. 소비율 상·하한, 초기화, 시간축 순환·중복·지연 도착과 기존 회귀도 확인합니다.

```powershell
./native/verify.ps1 -NoRestore -Integration -Stress
```

정적 분석 경고를 오류로 취급한 빌드, 기존 회귀, 서버7개, 실제 ICE/DTLS/SRTP·RTCP·데이터 채널 검사는 통과했습니다. 원본 로그와 부하 JSON은 Git 제외 경로 `native/.local/reports/clock-*` 및 `rtp-stress-verify.json`에 보존합니다.
