# EXTREME-102 · 실제 끊김 한 사건의 최초 관측 실패 경계

2026-10-26 / `codex/extreme-latency`. 다른 최적화는 보류하고 EXTREME-101의 최종 앱 바이너리·모드·직접 경로를 고정했다. 앱·SDK 동작이나 프레임/버퍼 설정을 수정하지 않았다. 이번 변경은 기존 기록을 읽는 분석 도구와 문서뿐이다.

## 이번에 확인한 것

**두 번의 실제 PC↔노트북 시험에서 상세 기록으로 대응한 `late`62건은 모두 수신 RTP 콜백이 관측되기 전에 해당 RTP 시각의 PLC가 이미 시작된 경우였다.** 이 사건들을 버퍼 입장 뒤 잠금·디코딩 대기만으로 설명할 수는 없다.

관측 범위는 송신 API 호출→수신 RTP 콜백이다. 수신 콜백은 SDK 처리 뒤이므로 **앱 전체를 무죄로 판단하거나 Wi-Fi가 원인이라고 확정하지 않는다.** 소켓/OS/네트워크/SDK의 콜백 이전 처리는 아직 미분리다. 모든 PLC·출력 부족 사건을 분류한 것도 아니다.

## 기존101 기록에서 먼저 좁힌 사건

6엔진의 마지막5초 기록에서 `late`104개는 모두 다른 호스트에서 온 프레임이며, 모두 같은 RTP 시각의 선행 PLC와 대응했다. 같은 호스트 방향의 `late`는 이 기록 구간에서0이었다. 같은 호스트의 모든 끊김이 없었다는 뜻은 아니다.

한 사건 E1의 동일 패킷 쌍을 연결했다.

| 관측 | 값 |
|---|---:|
| 수신 PC에서 이전 RTP 콜백→현재 콜백 | 37.585ms |
| 송신 노트북에서 같은 두 프레임의 API 호출 시작 간격 | 11.367ms |
| 이전 수신 콜백→첫 PLC hold | 30.266ms |
| 첫 PLC hold→늦은 패킷의 버퍼 호출 | 7.320ms |
| 주변 수신 Read 최대 호출 간격 | 2.694ms |
| 주변 수신 Read 최대 실행시간 | 0.031ms |
| 주변 버퍼 입장 잠금 대기 최대 | 0.0002ms |

수신 큐가 소진된 뒤 hold PLC, 타임스탬프를 진행시키는 loss PLC, 이후 실제 프레임의 `late` 거부가 이어졌다. 수신 처리량을 늘리거나 디코더를 빠르게 만드는 것만으로 이 사건의 콜백 이전 공백을 없앨 수 있다는 근거는 없다. 송신 간격11.367ms도 완전히 일정하지 않았으므로 송신 스케줄링의 기여를 배제하지 않는다.

## 재현 조건 고정

- 실제 PC·노트북의 1:1 직접 UDP, `opus-adaptive`, 네이티브 Opus, 조건별60초를 두 번 실행.
- 동일 앱/프로브/SDK DLL 해시를 양쪽에서 확인했다. 제품 코드 재빌드·DLL 교체 후보 비교가 아니라 같은 빌드의 반복 재현이다.
- 실제 공유 입력/출력에 합성 음성을 공급했다. PC 캡처10ms/출력2.667ms, 노트북 캡처5.333ms/출력10ms.
- 측정 마지막30초의 상세 기록을 분석했다. 양쪽 모든 trace의 EvictedRecords=0.
- 프레임·버퍼·우선순위·드라이버·공유기·라우팅·개인 장치 설정을 변경하지 않았다. 게임 부하 시험은 하지 않았다.

| 반복 / 수신 측 | 전체 진단 구간 PLC 증가 | 출력 부족 증가 | 마지막30초 대응 late |
|---|---:|---:|---:|
| R1 / PC | 120ms | 12.23ms | 16 |
| R1 / 노트북 | 112.5ms | 25ms | 16 |
| R2 / PC | 287.5ms | 83.98ms | 16 |
| R2 / 노트북 | 115ms | 20ms | 14 |

전체 진단 구간은 첫/마지막 표본 사이 약59~60초이며 마지막30초 trace와 분모가 다르다. late 프레임 수를 전체 PLC 개수나 지속시간과 동일시하지 않는다. 두 반복 모두 양쪽 종료 코드0, 미디어 증가를 확인했지만 연속성 합격은 아니다.

## 각 방향에서 큰 콜백 공백을 보인 사건

아래는 각 반복·방향에서 인접 패킷 간 API→콜백 구간의 간격 증가가 가장 컸던 **선택 사건**이다. 전체 지연의 중앙값/p95가 아니다.

| 반복 / 방향 | 송신 API 시작 간격 | 수신 콜백 간격 | 간격 증가 |
|---|---:|---:|---:|
| R1 / PC→노트북 | 9.361ms | 62.577ms | 53.216ms |
| R1 / 노트북→PC | 5.944ms | 57.654ms | 51.710ms |
| R2 / PC→노트북 | 9.868ms | 66.656ms | 56.788ms |
| R2 / 노트북→PC | 10.419ms | 64.038ms | 53.620ms |

수신 측 첫 PLC는 실제 콜백보다 약34~48ms 먼저 시작됐다. 선택 사건의 입장 잠금 대기는0.0001~0.0007ms, 주변 Read 최대 실행시간은0.024~0.071ms였다.

각 간격은 해당 호스트의 단조 시계로 계산했다. 두 PC의 절대 시각을 직접 빼지 않았다. 간격 증가도 시계 진행률이 비교 가능하다는 가정이 있는 변동 지표이며 절대 편도 지연·물리 NIC 전송시간·입→귀 지연이 아니다. 소켓 송신 완료도 관측하지 않았으므로 API 기록을 실제 송신 완료로 부르지 않는다.

## 분석 도구·검증

`TransportProbe/Analysis/analyze_deadline_event.py`는 SSRC/RTP 타임스탬프로 송신·수신·입장·PLC를 대응한다. 최초 hold도 실제 오디오 대체로 취급해, 나중의 loss 결정 시점만 보며 최초 마감 실패를 놓치지 않게 했다.

분류는 다음 경계를 구분한다.

- PLC 시작 후에 콜백 관측: `missed-before-rtp-callback`.
- 콜백은 먼저 관측됐으나 입장 잠금은 이후: 해당 잠금 경계 추가 조사.
- 선행 상태 기록 없음, 중복 수신/이미 입장한 프레임, 역순 도착: 단정하지 않음.
- trace 축출 또는 모호한 송신 식별자: 분석 거부.

자체 검사는 독립 호스트의 시각 원점을 크게 바꿔도 결론이 같은지, hold/loss 순서, 누락된 이력, 중복·역순·축출 기록의 오판 방지를 확인했다.

```powershell
python ./native/TransportProbe/Analysis/analyze_deadline_event.py --self-test
python ./native/TransportProbe/Analysis/analyze_deadline_event.py SEND.json RECEIVE.json RESULT.json
```

현재 기록기 개별 기록 호출 최대는 네 표본에서0.021~0.144ms였다. 이것만으로 할당/GC를 포함한 전체 계측 영향이0이라고 주장하지 않는다. 이번에는 trace-off 대조를 새로 하지 않았다.

## 남은 경계와 다음 한 가지 시험

다음 대상은 **동일 RTP 사건의 OS 소켓 수신 관측→SDK 콜백** 경계다. 필요한 증거는 패킷 정체성을 맞춘 OS 수신 또는 소켓 완료 시각과 현재 콜백 시각이다. OS에도 늦게 나타나면 그 앞 구간, OS에는 일찍 있는데 콜백만 늦으면 소켓 배달/깨우기·SDK 처리 구간을 조사한다. 단순히 오래된 게이트웨이 RTT 시험을 반복하지 않는다.

현재 `RtpChannel` 관측기는 기존 SDK 처리기 뒤에 붙어 있다. 이를 복호화 전이나 OS 수신 경계로 재해석하지 않는다. 관리자 계측이 필요하면 기존 실행 세션·필터를 먼저 확인하고 제한된 수집·종료·복구 절차를 사용한다. 물리 전파/AP 원인을 구분하지 못하는 계측으로 물리 원인을 확정하지 않는다.

원인이 분리되기 전에는 수신 여유 확대, MMCSS/프레임 튜닝, 단일 믹서 구현을 하지 않는다. 현재 결과에 근거해 제품 동작 수정은 채택하지 않았다.
