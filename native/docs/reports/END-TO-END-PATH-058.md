# 0.5.8: 큐 이동 검증, 출력 후처리 우회, 앱별 LAN 선택

2026-10-19. 출력 padding이 줄었다는 사실과 전체 경로가 빨라졌다는 사실을 구분하기 위해, 동일한 합성 Opus 패킷의 수신→디지털 루프백 전달을 같은 호스트 시계에서 A/B/A로 측정했다. 이후 실제 두 PC 통화와 현재 OS 경로를 확인했다. 마이크·이어폰·게임·전역 VPN 설정은 변경하지 않았다.

## 구현한 변경

1. 저지연 RTP 재생에서 RAW 공유 출력과 GameChat 분류를 우선 사용한다. RAW를 지원하지 않으면 기존 공유 처리로 복귀한다. ‘통화 출력 효과 우회 우선’을 끄면 기존 출력 효과를 사용할 수 있다. 이 설정은 통화에서 나온 뒤 변경한다.
2. 이전 출력 공급량 제한을 유지한다. 처음에는 기존 여유로 재생하고, 안정화 뒤 한 주기＋5ms 목표를 사용한다. 버퍼 소진을 관측하면 전체 용량으로 안전 복귀한다.
3. 명시적인 미디어 네트워크 선택을 추가했다. 선택한 로컬 IPv4 주소로 RTP 소켓을 bind하고 Windows `IP_UNICAST_IF`를 적용한다. 선택 주소가 없어지거나 적용에 실패하면 오류로 처리하며 임의의 다른 인터페이스로 바꾸지 않는다. 기본값 ‘OS 자동’은 기존 VPN/OS 경로를 유지한다.
4. 진단에 RAW 실제 활성 여부와 선택한 미디어 주소를 표시한다. 수신 제외를 주소·토큰·역할·길이로 구분하여 ‘도착했지만 검증에서 제외된 패킷’을 물리 손실로 해석하지 않도록 했다.

[Microsoft RAW 정의](https://learn.microsoft.com/en-us/windows/win32/api/audioclient/ne-audioclient-audclnt_streamoptions)에 따르면 RAW는 스트림 처리 일부를 우회하지만 장치별 항상 켜진 APO·드라이버·하드웨어 처리는 남을 수 있다. EQ·보정 등 통화의 소리 특성이 달라질 수 있으며, 코덱·시스템 장치 설정을 바꾼 것은 아니다. [GameChat 분류](https://learn.microsoft.com/en-us/windows/win32/api/audiosessiontypes/ne-audiosessiontypes-audio_stream_category)는 다른 스트림의 볼륨을 낮추지 않는 게임 채팅 용도다. 독점 모드·ASIO를 사용하지 않는다.

## 같은 신호로 큐＋출력을 함께 비교

각 회차32초, 같은 사전 생성 Opus 패킷과 10ms 도착 계획을 사용했다. 각 회차14개 고유 chirp 구간을 기준으로 실제 디코딩·제출된 RTP 시작 패킷과 디지털 루프백에서 상관도가 충분한 신호를 대응시켰다. 합성 신호 외의 원음은 파일에 저장하지 않았다. 루프백 혼합 샘플은 상한이 있는 임시 메모리에서 분석한 뒤 해제했다.

아래 값은 **패킷 추가 시각→해당 디코딩 신호 샘플을 포함한 루프백 콜백 수신 시각**의 중앙값이다. 수신 큐와 출력 이후 구간을 함께 포함한다. 콜백 전달·샘플 묶음·스케줄링의 대기도 포함하며 물리 스피커 시각이나 입→귀 지연은 아니다.

| 수신 장치 | 기존 A1 | RAW GameChat＋제한 공급 B | 기존 A2 | 유효 신호 수 A1/B/A2 |
|---|---:|---:|---:|---:|
| PC |51.36ms |45.16ms |50.30ms |13/14, 14/14, 14/14 |
| 노트북 |234.06ms |155.34ms |236.04ms |14/14, 14/14, 14/14 |

PC에서는 약5–6ms, 노트북에서는 약79–81ms 낮은 중앙값을 관측했다. 단계별 분위수를 더한 값이 아니라 같은 신호의 양 끝 시각을 직접 뺀 결과다. PC의 한 신호는 상관도 기준에 미달하여 제외했고 0ms로 채우지 않았다. 이 조건에서는 ‘기기 버퍼에서 줄인 양이 전부 상위 큐로 옮겨갔을 뿐’이라는 설명과 맞지 않는다. 순차 시험이며 모든 장치·게임 부하에 대한 보증은 아니다.

노트북에서 RAW만 바꾼 별도 A/B/A의 native QPC 중앙값은222.30→152.70→226.85ms였다. 따라서 큰 개선은7ms 버퍼 조정만의 효과가 아니며, 앱이 요청하는 출력 처리 경로의 영향이 컸다. RAW Other→RAW GameChat→RAW Other 비교는 뚜렷한 추가 개선을 보이지 않아 GameChat 선택 자체의 지연 이득으로 주장하지 않는다.

### 시각 측정에서 발견한 한계

PC에서는 native loopback QPC가 실제 콜백 시각보다 미래인 구간을 발견했다. 최초의 PC native QPC 절대값 약66ms를 확정적인 출력 지연으로 사용하지 않는다. 분석기는 실제 콜백 수신 시각을 비교에 사용하고, 새 도구는 `nativeQpcTrusted=false`인 QPC 값을 유효 절대값과 분리한다. 샘플 상관 위치를 정밀하게 찾는 것과 시각 자체의 정확도는 별개다. [GetBuffer 시각 정의](https://learn.microsoft.com/en-us/windows/win32/api/audioclient/nf-audioclient-iaudiocaptureclient-getbuffer)도 함께 확인했다.

## 실제 통화 A/B/A

기존 출력→새 출력→기존 출력을 각75초 비교했다. 코덱·입력·20ms RTP 정책은 유지했다. PC 송신→노트북 디지털 루프백은 각 회차3개씩 유효했고, 기존 검출기의 범위 중간값 중앙값은257.13→187.01→252.94ms였다. 이 도구는 시계 보정 범위와 ±20ms 검출 여유를 포함하므로 정밀한 물리 입→귀 측정이 아니다.

또한 실제 선택 경로가 첫 회차와 이후 회차에서 달랐다. 앞의 통화 숫자만으로 RAW 단독의 인과 효과를 계산하지 않는다. 네트워크를 제외한 위 동일 호스트 시험을 주요 근거로 사용한다. 반대 방향 마지막 회차는3개 중1개만 유효했고2개는 검출 시각 불일치로 제외했다. 반대 방향의 완전한 A/B/A 성공으로 표시하지 않는다. 비교 도구도 미디어 진행과 지연 측정 완료 여부를 별도로 판정하도록 고쳤다.

## 현재 네트워크에서 확인한 원인

합성 UDP 검증에서 노트북이 보낸 패킷이 PC에 `172.30.1.64` 출발로 도착했다. 기대한 노트북 주소는 `172.30.1.30`이므로 PC에서 수신 제외됐다. ‘유효 수신0개’가 실제 패킷 도착0개는 아니었다.

읽기 전용 경로 조회 결과, 노트북에는 동일한 `172.30.1.0/24`에 대한 Wi-Fi 경로와 Tailscale 경로가 함께 있었다. OS는 낮은 metric의 Tailscale 경로를 선택했고, PC 주소로의 `Find-NetRoute`도 Tailscale을 반환했다. 실제 ICE에서도 다른 LAN 출발 주소의 peer-reflexive 경로나 TURN이 선택되는 회차가 있었다. TURN을 거치지 않는다는 표시는 물리 LAN을 곧바로 지났다는 보장이 아니었다.

시스템 설정을 바꾸지 않고 시험 소켓만 PC 이더넷88/노트북 Wi-Fi30으로 고정하자15초 합성 UDP가 양방향으로 검증됐다. PC는1500개 전부 수신했고, 노트북은 독립 실행 시작 시각 차이에 따른 앞부분을 제외한1409개를 수신했다. 이는 전체 네트워크 무손실률 측정이 아니며, 지정한 LAN 소켓으로 실제 양방향 경로가 성립함을 확인한 결과다. 주소·토큰·역할 검증 제외는 PC에서0개였다.

이번 결과는 **현재의 겹친 서브넷 경로 문제**에 대한 근거다. 과거 ETW의 모든50–131ms 공백을 소급하여 Tailscale 하나의 원인으로 확정하지 않는다. 무선 재전송·AP·드라이버의 순간 지연도 이 변경만으로 없어진다고 주장하지 않는다. 준비 중이던 QoS 비교는 기본 경로가 달라 유효 비교가 되지 않았으므로 평가·기본 적용하지 않았고 미검증 QoS 구현도 제거했다.

## LAN을 명시한 최종 5분 실통화

PC `172.30.1.88`과 노트북 `172.30.1.30`을 각각 선택하여 양쪽300초 통화를 완료했다. 양쪽 모두 디지털 루프백 측정5/5개를 얻었고 도구 오류는 없었다. 모든 기록 표본이 두 LAN 주소 사이 직접 연결이었다. 마지막 RTCP RTT는 PC3.24ms, 노트북3.44ms였다.

앱 재생의 누적 무음 채움은 양쪽0ms, 재버퍼링은 양쪽0회였다. PLC 보완은 PC170ms, 노트북110ms로 남아 있어 ‘패킷 공백이나 보완이 전혀 없었다’고 표현하지 않는다. 마지막 수신 보고의 누적 손실은 양쪽0패킷이었다. 출력 장치 오류·재시작도 양쪽0회였다.

PC는 목표15.17ms/용량22.31ms를 유지했고 장치 버퍼 소진0회·안전 복귀0회였다. 노트북은 버퍼 소진2회와 안전 복귀1회를 기록하여 마지막에는 목표/용량22ms로 돌아왔다. RAW는 양쪽 활성 상태였다. 따라서 노트북까지15ms 공급을 계속 유지했다고 주장하지 않는다. 안정성 복귀가 실제로 작동한 결과다.

두 PC 측정은 시계 불확실성과 검출 여유가 여전히 크고 반대 방향의 편차도 컸다. RTT3ms를 전체 음성 지연으로 사용하지 않으며 정밀한 출력 개선의 근거는 앞의 동일 호스트 비교다. 이 시험에서 게임 부하를 통제하지 않았으므로 새 버전의 게임 부하 검증으로 취급하지 않는다.

## 최종 검증

경고를 오류로 처리한 Release 빌드, 기본 회귀 검사, 서버 검사7개 및 실제 WebRTC ICE/DTLS/SRTP/RTCP 통합 검사를 통과했다. 합성 신호 상관 검사는 무음 배제·감쇠 신호·긴 샘플 인덱스를 검증한다. 최신 RAW/GameChat 출력의 시작·재시작·중복 시작·중복 종료 장치 검사를 PC와 노트북에서 통과했다. 화면 미리보기에서 새 출력 설정과 네트워크 목록의 표시를 확인했다.

## 실행

기본 실행은 OS/VPN 경로를 유지한다. 명시적인 LAN 통화를 하려면 네트워크 목록에서 사용할 인터페이스를 선택하거나 현재 환경에서는 다음처럼 실행한다. 주소가 바뀌면 목록에서 현재 주소를 다시 선택한다.

```powershell
# PC: 이 앱의 미디어 UDP만 이더넷 사용
./native/run.ps1 -MediaAddress 172.30.1.88

# 노트북 소스 실행 시: 이 앱의 미디어 UDP만 Wi-Fi 사용
./native/run.ps1 -MediaAddress 172.30.1.30
```

HTTPS 연결 관리와 다른 앱의 경로·Tailscale 설정은 유지한다. 명시적인 인터페이스 선택은 이 앱의 미디어에 대해 OS 자동 경로 대신 선택한 경로를 사용하겠다는 설정이다. 기본값을 임의로 물리 LAN으로 바꾸지 않았다.

원본·중간 실패 기록·분석은 Git 제외 경로 `native/.local/render-path-058/`에 보관한다. 일부 시험 도구의 인덱스·닉네임 검증 오류로 실패한 실행은 비교에서 제외했다. 최종 소스 분석기는 `analyze_render_path.py`이며 원본 JSON을 덮어쓰지 않는다. 서버·포트포워딩·배포 ZIP은 변경하지 않았다.
