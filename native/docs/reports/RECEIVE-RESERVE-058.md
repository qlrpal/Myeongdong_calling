# 0.5.8 후속: 수신 여유 20/10ms와 출력 이후 대기

2026-10-19. 목적은 수신 여유를 낮춘 이득이 실제 디지털 출력에서도 유지되는지, 네트워크 변동에서 보완 음성이 늘어나는지 확인하는 것이다. 제품의 기본 여유20ms는 변경하지 않았다. 마이크·이어폰·전역 오디오·VPN 설정도 변경하지 않았다.

## 구현

- `WindowsAudioDevice`에 범위가 제한된 `rtpReserveMs` 비교 인자를 추가했다. 기존 호출의 기본값20ms를 유지하고 UI·통화 엔진의 기본 정책을 바꾸지 않았다.
- `--render-reserve-path-device OUTPUT`: RAW/GameChat·제한 공급·10ms Opus 패킷을 유지한 채 수신 여유20→10→20ms를 비교한다. 각 회차32초, 고유 합성 신호14개를 사용한다. 마이크나 네트워크 시계는 사용하지 않는다.
- `--playout-reserve-replay INPUT OUTPUT`: 같은 실제 수신 순서·장치 읽기 크기에서20/10ms를 반사실 재생한다. 원음 대신 합성 Opus 무음을 사용한다.
- 분석기에 수신→제출과 제출→루프백 콜백의 **각 신호별 차이** 요약을 추가했다. 서로 다른 표본의 분위수를 빼서 구간 지연으로 사용하지 않는다. 미완료·장치 오류 보고서는 거절한다.

## 두 장치의 A/B/A

동일 호스트 시계의 패킷 추가→대응 신호를 포함한 디지털 루프백 콜백 수신 중앙값이다. 물리 입→귀·DAC 시각은 아니며 루프백 전달 및 콜백 묶음·스케줄링을 포함한다.

| 장치 | 여유20ms A1 | 여유10ms | 여유20ms A2 |
|---|---:|---:|---:|
| PC |45.62ms |34.75ms |45.55ms |
| 노트북 |155.77ms |153.99ms |155.15ms |

모든 회차14/14개 신호가 유효했다. PC의 회차 중앙값 차이는 약10.8ms, 공통 신호별 A1/A2 평균과 B 차이의 중앙값은9.18ms였다. 노트북은 회차 중앙값 기준 약1.2~1.8ms 차이였고 신호별 차이 중앙값은1.47ms였다. 두 통계는 정의가 다르므로 혼용하지 않는다.

모든 회차 앱 무음 채움0ms·PLC0ms였다. PC는 세 회차 모두 제한 공급 유지, 장치 버퍼 소진0회였다. 노트북 A1은 장치 버퍼 소진1회로 전체22ms 공급에 안전 복귀했다. B/A2는15ms 제한 공급을 유지했다. 이 차이와 순차 시험의 한계 때문에 노트북의 작은 차이를 수신 여유만의 확정적인 효과로 해석하지 않는다. RAW는 모든 회차 활성 상태였다.

### 어느 구간에 남았는가

| 장치·회차 | 패킷 추가→제출 중앙값 | 제출→루프백 콜백 중앙값 |
|---|---:|---:|
| PC A1 / B / A2 |28.60 / 20.15 / 30.02ms |20.25 / 20.22 / 20.24ms |
| 노트북 A1 / B / A2 |20.92 / 19.03 / 20.54ms |134.88 / 134.78 / 134.70ms |

각 열은 같은 신호 단위로 계산한 별도 중앙값이므로 합계가 전체 중앙값과 일치할 필요는 없다. 노트북에서 관측되는 큰 대기는 수신 큐만 낮추어 제거되지 않았다. 그러나 제출은 앱 provider의 PCM 공급 시점이고 루프백은 Windows 수집 지점이다. 따라서 약135ms를 순수 하드웨어 지연·특정 APO의 지연으로 확정하거나 물리 스피커 시각으로 주장하지 않는다. RAW도 항상 켜진 처리와 드라이버·하드웨어를 모두 우회하는 것은 아니다.

## 실제 네트워크 기록 재생

기존 양쪽 약120초 수신 기록을 사용했다. 아래는 시작5초와 끝1초를 제외한 약114.85초의 구간이다. 장치와 독립적으로 같은 패킷 도착 및 읽기 요청 순서를 재생했다.

| 수신 기록 | 여유 | 추가→디코딩/재생 호출 중앙값 | PLC 보완 | 늦은 패킷 | 무음 채움 / 재버퍼링 |
|---|---:|---:|---:|---:|---:|
| PC |20ms |28.11ms |70ms |1 |0ms / 0회 |
| PC |10ms |20.89ms |140ms |5 |0ms / 0회 |
| 노트북 |20ms |23.64ms |120ms |6 |0ms / 0회 |
| 노트북 |10ms |13.94ms |190ms |11 |0ms / 0회 |

10ms는 모델상 큐 대기를 줄였지만 양쪽 모두 PLC·늦은 패킷이 늘었다. PLC는 끊김 방지를 위한 합성 보완이므로 무음 채움0ms만으로 품질 문제가 없다고 판단할 수 없다. 이 기록은 초기 버퍼 전체 이력이 없는 cold-start 반사실 재생이며, 실제 음질·물리 지연을 검증한 시험이 아니다. 기록 당시의 네트워크 경로도 최신 명시적 LAN 시험과 같다고 가정하지 않는다.

## 결정과 다음 조사 범위

10ms를 공통 기본값으로 적용하지 않는다. 지연 우선 목표에서도 작은 지연과 함께 잦은 늦은 패킷·보완 증가를 고려해야 한다. 특히 노트북의 전체 수신 경로에서는 이득이 작았다. 이번 변경은 비교 도구와 분석 개선이며 제품의 전체 통화 지연을 추가로 낮췄다고 발표하지 않는다.

다음 출력 조사는 제출 이후 약135ms 관측을 중심으로, 장치의 실제 진행 위치와 루프백 수집·전달의 관계를 검증해야 한다. 이 관계가 확인되기 전에 앱 큐를 반복해서 낮추거나 특정 드라이버를 원인으로 지목하지 않는다. 일반 장치 설정 변경·독점 모드·ASIO는 적용하지 않는다.

## 재현 및 자료

```powershell
./native/TransportProbe/bin/Release/net10.0-windows10.0.19041.0/TransportProbe.exe --render-reserve-path-device native/.local/reserve-058/pc.json
./native/TransportProbe/bin/Release/net10.0-windows10.0.19041.0/TransportProbe.exe --playout-reserve-replay INPUT.json OUTPUT.json
python native/TransportProbe/Analysis/analyze_render_path.py SUMMARY.json PC.json LAPTOP.json
./native/verify.ps1 -NoRestore -Integration
```

원본 및 분석 결과는 Git 제외 경로 `native/.local/reserve-058/`에 보관한다. 처음 재생 명령은 새 빌드 완료 전에 예전 실행 파일을 실행하여 실패했으며 비교 근거에서 제외했다. 이후 새 빌드로 양쪽 재생을 완료했다. 첫 서버 검사는 샌드박스의 localhost EACCES로 실패하여 정상 네트워크 권한에서 다시 실행했다.

최종 Release 빌드는 경고0·오류0이었다. 회귀 검사, 서버7개 검사, 실제 ICE/DTLS/SRTP/RTCP와 RTP 재생 통합 검사를 모두 통과했다. 종료 후 로컬 통화·진단 프로세스가 남아 있지 않음을 확인했다. 배포 ZIP과 서버는 변경하지 않았다.
