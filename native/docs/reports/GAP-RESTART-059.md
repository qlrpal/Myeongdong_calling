# 반복 수신 공백 뒤 재생 재개 개선

2026-10-21. 지연 우선 원칙에 따라 기존 게임 시험에서 확인한 재버퍼링 뒤 대기를 줄였다. 적용 범위는 선택 가능한 **자동 저지연 (시험)** 모드이며 기본 고정 20ms 모드는 유지한다.

## 적용한 동작

PLC 최대 60ms를 소진해 재버퍼링한 사건이 RTP 원본 시간 기준 3초 안에 3회 쌓이면, 다음 재개에 필요한 여유를 10ms와 실제 장치 요청 크기의 합으로 낮춘다. 정상 목표 15–30ms 자체를 낮추지는 않는다. 최초 시작·단발성 공백·장치 재시작은 기존 여유를 사용한다. 원본 시간이 진행되면 반복 공백 이력은 만료된다. 추가적인 강제 오디오 폐기는 도입하지 않았다.

진단에는 빠른 재시작 횟수와 재개 여유를 추가했다. 연속 PLC 상한과 큐·속도 제어 한도는 유지한다.

## 같은 기록을 이용한 대조

기존 게임 시험 양쪽 6개 기록과 이전 구간 시험 양쪽 6개 기록을 같은 입력 도착·출력 요청 일정으로 재생했다. 아래는 가장 나빴던 PC 게임 A1 120초 기록의 기존 자동 모드와 개선 모드 비교다. 실제 통화의 추가 A/B 시험이나 청감 평가가 아니다.

| 지표 | 기존 자동 | 반복 공백 복구 적용 |
| --- | ---: | ---: |
| 누적 무음 채움 | 949.50ms | 837.31ms |
| 누적 PLC 보완 | 5,190ms | 5,250ms |
| 재버퍼링 | 19회 | 18회 |
| 복구 시 폐기한 오디오 | 460ms | 450ms |
| 빠른 재시작 | 0회 | 4회 |
| 수신→출력 제출 중앙값 | 41.93ms | 41.37ms |
| 수신→출력 제출 P95 | 96.42ms | 96.10ms |

**112ms는 120초 동안 줄어든 누적 무음이며, 통화 지연이 112ms 줄었다는 뜻이 아니다.** PLC는 60ms 늘었다. 나머지 11개 기록에서는 빠른 재시작이 활성화되지 않았고 비교한 무음·PLC·재버퍼링·폐기 지표도 기존 자동 모드와 같았다.

조건 없이 재개 여유를 낮춘 후보는 이전 단발성 공백 기록의 무음과 PLC를 늘려 제외했다. 연속 도착 꼬리를 추가로 요구하는 후보도 선택한 방식보다 무음이 많아 제외했다.

## 검증

- 정상 입력의 출력 PCM 해시 일치, 최초·단발성·장치 재시작 여유 유지, 반복 조건·이력 만료·RTP 래핑·60ms PLC 상한 검사 통과.
- 실제 WASAPI 공유 출력에 합성 무음 패킷의 150ms 공백을 3회 넣은 순차 시험 통과. 기존/개선 빠른 재시작은 0/1회, 무음 채움은 273.4/263.2ms, PLC는 양쪽 180ms였다. 장치 요청을 통한 경로 작동 확인이며 순차 시험 수치의 차이를 정확한 인과 효과로 해석하지 않는다.
- `native/verify.ps1 -NoRestore -Integration` 통과. 경고를 오류로 취급한 빌드, 정적 분석·회귀 검사, 서버 7개 검사, 실제 로컬 WebRTC/DTLS/SRTP·RTCP·지연 계측 통합 검사 포함.

장치 시험 때 게임은 종료된 상태였다. 새 코드의 게임 부하 및 실제 음성 청감 검증은 남아 있다. 큰 수신 공백의 발생 원인은 이 변경으로 확정하거나 제거한 것이 아니다.

원본은 무시되는 로컬 폴더 `native/.local/restart-reserve-059/`의 `pressure/` 및 `shared-device.json`에 보관했다. 이전 실시간 게임 결과는 [게임 비교 보고서](GAME-RESPONSIVE-059.md)를 참고한다.
