# EXTREME-093 — RTP 수신 경계와 SDK 동시 수신 시작 재현

2026-10-25. EXTREME-092의 노트북 같은 호스트 방향 미관측 패킷을 추적했다. 기존 배포본·라우팅·공유기·드라이버 설정은 변경하지 않았다. **SDK 경쟁 조건은 순수 UDP에서 재현했지만, 실제 통화 문제의 동일 원인 확정과 제품 수정 검증은 남아 있다.**

## 가설과 관측 경계

가설은 송신 API 이후부터 앱의 복호화 RTP 콜백 사이에서 패킷 정체성이 누락되거나 중복된다는 것이다. 선택적 PipelineTrace에 SDK RTPChannel 이벤트의 RTP 헤더 정체성·길이·수신 버퍼 크기를 기록했다. 음성 페이로드는 저장하지 않는다. 관측은 기존 SDK 핸들러 **뒤**에 붙으므로 소켓 완료·복호화 전 시각이나 물리 NIC 수신 시각이 아니다. 앞선 핸들러의 버퍼 변경·예외도 고려해야 한다.

실제 SRTP 통제 fixture는 송신115개, 채널 관측115개, 의도적으로 관측을 막은 앱 콜백5개를 정확히 구분했다. legacy 진단에 새 필드가 없으면 분석기는 측정 불가로 처리한다.

## 실제 두 호스트 6인 시험

PC와 노트북 각각 엔진3개, 명시 LAN 주소, 공유 오디오, 2.5ms 송신으로90초 시험했다. 양쪽 연결·종료 정리는 완료했다. 마지막5초의 양끝 일치 RTP 범위에서 각 방향1999개를 비교했다.

|노트북 내부 방향|채널 미관측|채널 중복|채널에만 관측|
|---|---:|---:|---:|
|3→5|241|240|5|
|4→5|245|245|7|
|5→3|136|137|3|

나머지 노트북 내부3방향, PC 내부 및 호스트 간 방향에서는 이 구간의 미관측·중복이0이었다. 앱에만 관측된 정체성은 모든 방향0이었다. 수신 소켓 버퍼는 모두1,000,000바이트였다. 단순 재생 마감 초과만으로 채널 정체성 중복을 설명할 수 없다. 그렇다고 이 이벤트만으로 OS 소켓 손실이나 SRTP 원인을 확정하지 않는다.

## SDK 소스와 순수 UDP A/B/A

사용 패키지는 SIPSorcery10.0.17, 저장소 커밋 `08c2ed0ad72c423ca06950dee2e842488a219884`다.

- [UdpReceiver](https://github.com/sipsorcery-org/sipsorcery/blob/08c2ed0ad72c423ca06950dee2e842488a219884/src/SIPSorcery/net/RTP/UdpReceiver.cs)는 일반 bool 확인·변경으로 수신 시작을 제어하고 동일 수신 버퍼를 사용한다.
- [RTPChannel](https://github.com/sipsorcery-org/sipsorcery/blob/08c2ed0ad72c423ca06950dee2e842488a219884/src/SIPSorcery/net/RTP/RTPChannel.cs)의 송신 경로와 수신 완료 경로 양쪽에서 수신 재시작을 호출할 수 있다.

`--sdk-receive-race REPORT ADDRESS 50000`는 오디오·RTP·암호화를 제외한다. 같은 호스트에64바이트 고유 순번 UDP를 동기 송신하고 별도3스레드가 SDK의 공개 수신 재시작 경로를 경쟁시킨다. B만 파생 수신기의 `BeginReceiveFrom` 호출을 lock으로 직렬화한다. 소켓 버퍼와 송신 방식은 같다. 각 구간50,000개, 원본A1→직렬화B→원본A2 순서다.

|호스트·구간|중복|미관측|잘못된 길이/순번|
|---|---:|---:|---:|
|PC A1|0|0|0|
|PC B|0|0|0|
|PC A2|15331|15331|0|
|노트북 A1|23183|23183|0|
|노트북 B|0|0|0|
|노트북 A2|17461|17461|0|

모든 구간 콜백 총수는50,000개였으며 보고된 예외는 없다. 같은 개수의 중복과 누락이 발생했다. 별도 짧은 PC5000개 시험에서는 원본도 재현되지 않았다. 따라서 발생은 비결정적이며 원본의 모든 실행이 실패하지는 않는다.

**해석:** 이 공개 API의 동시 호출 조건에서는 SDK 수신 시작 직렬화가 정체성 중복·누락을 제거하는 대조를 얻었다. 집 Wi-Fi나 코덱 없이 재현되므로 이 시험의 현상을 무선 손실만으로 설명할 수 없다. 단,3개 재시작 스레드와 약2000pps 스트레스는 실제 통화의 발생 빈도·지연을 나타내지 않는다. 실제6인 통화와 같은 결함인지, 실제 경로에서도 수정이 유효한지는 아직 미확정이다. 제품 SDK는 교체하지 않았다.
