# RTP 부하·연속 통화 검증 및 진단 수정 · 0.5.1

2026-10-16에 0.5.0 오디오 경로로 가상 부하 검사와 두 PC 5분 연속 통화를 수행했습니다. 짧은 LAN 비교에서 확인한 대기 감소가 긴 통화에서도 유지된다고 일반화할 수 없었습니다. 이 결과를 근거로 오디오 파라미터를 임의 변경하지 않고, 잘못된 루프백 성공 처리를0.5.1에서 수정했습니다.

## 가상 부하: 조건별10분 상당

실시간으로10분씩 기다린 검사가 아닙니다. 가상 송신/도착 시각과10ms 출력 요청을 사용하고 실제 Opus 디코더·RTP 버퍼를 구동합니다. 랜덤 시드는1234이며6조건 총60분 상당입니다. 장치·네트워크·음질 실측과 구분해야 합니다.

|---|---:|---:|---:|---:|---:|
| 일정한 송수신 | 0ms | 0ms | 0 | 0 | 30ms |
| 추가 도착 지연0~25ms | 0ms | 0ms | 0 | 0 | 50ms |

100ms 손실은60ms PLC 상한을 넘으므로 무음/재버퍼링이 예상됩니다. 랜덤 손실의 실제 주입량은636패킷으로1.06%였습니다. 클록 차이만으로 큐 정리나 재버퍼링이 발생한 것은 현재 고정 버퍼의 한계입니다. 검증 도구의 `BOUNDS/PROGRESS PASS`는 큐 상한·진행·오류 방어 검사를 통과했다는 뜻이며, 무음 없는 품질 합격을 뜻하지 않습니다.

PC 큐 중앙값은 분별32→40→82→99→100ms로 높아졌습니다. 마지막 약2분은 부족이 추가되지 않았지만 높은 대기가 유지됐습니다. 노트북 큐는 처음부터 약96ms로 높았습니다. 목표 여유20ms와 실제 대기가 다름을 다시 확인했습니다. 큐 통계는 약1초 간격 표본이므로 출력 주기와의 위상에 영향을 받지만, 아래 추적 패킷에서도 긴 앱 대기가 관측됐습니다.

입력 불연속은 PC에서 시작 스냅샷1→최종2, 노트북9→18이었습니다. 노트북 송신을 받는 PC에서 부족이 더 많았다는 상관은 있지만, 입력 불연속만으로 모든 현상의 원인을 설명할 수는 없습니다. 실제 PC의 큐 증가는 ±200ppm 가상 검사와 분리된 관측이며 실제 클록 오차를 측정했다고 주장하지 않습니다.

### 루프백 결과와 유효성

0.5.0에서는 방향별5회가 모두 측정 성공으로 기록됐습니다. 원본을 재검토하니 노트북→PC 첫 측정은 시작 패킷의 수신 기록만 있고 디코딩·출력 제출 기록이 없었습니다. 해당 시점의 지연 도착·PLC와 재버퍼링도 증가했습니다. 뒤따른 테스트음을 검출했을 수 있으므로 이1회는 **추적 검증 불충분으로 제외**합니다.

완전한 추적은 PC→노트북5회, 노트북→PC4회입니다. 수신→출력 제출 중앙값은 각각88.11ms,93.31ms였습니다. 전체 디지털 루프백 중간값 중앙값은 PC→노트북311.49ms였으며, 노트북→PC는 제외 전175.92ms라 최종 비교 지표로 채택하지 않습니다. 물리 입→귀 실측은 아닙니다. 앞선75초 검사와 네트워크/스케줄링 상태가 동일하다는 보장이 없어 단순 회귀율로 계산하지 않습니다.

## 0.5.1 수정

- RTP에서 늦어서 재생하지 못한 추적 패킷을 폐기로 표시합니다. 이미 디코딩한 패킷의 늦은 중복은 기존 정상 기록을 지우지 않습니다.
- 디지털 루프백은 시작 패킷의 캡처·송신·정상 단일 수신·디코딩·출력 제출과 해시 일치를 모두 확인해야 유효 측정으로 기록합니다. 누락·폐기·중복은 오류로 제외합니다.
- 빠진 시작 프레임과 정상 추적, 폐기/중복/해시 불일치를 확인하는 회귀 검사를 추가했습니다. 오디오 버퍼·코덱 파라미터는0.5.0과 같습니다.
- `--rtp-stress-test`와 `--rtp-soak-test`를 검증 도구에 추가했습니다. 연속 통화 도구는 연결/미디어 진행 성공과 품질 지표를 분리해 해석해야 합니다.

정적 분석 경고를 오류로 취급한 빌드는 경고0/오류0이며 기존 회귀·서버7개·실제 WebRTC 통합 검사는 모두 통과했습니다. 최종 코드로 가상 부하6조건도 다시 실행해 같은 수치를 확인했습니다. 진단 수정 후 새5분 실통화를 반복한 결과는 이 문서에 포함하지 않습니다.

## 다음 구현 우선순위

1. 출력 요청 크기와 프레임별 큐 체류 시간을 수집해 시작/복구 후90~100ms 대기가 남는 지점을 좁힙니다. 높은 여유를 계속 유지하는 현상을 먼저 제어해야 합니다.
2. 가상 클록 차이 검사에서 드러난 시간축 불일치를 미세한 소비율 보정으로 다룹니다. 무조건 큰 버퍼를 추가하는 방식은 지연 우선 목표에 맞지 않습니다.
3. 도착 지터와 손실을 구분해 작은 목표 여유를 적응 조절하고 동일한 부하 시나리오에서 검증합니다. 이후 두 PC에서 동일 조건 비교를 반복합니다.

이번5분 검사만으로 장기 안정화를 완료했다고 판단하지 않습니다. 물리 마이크/이어폰의 자체 지연은 이번 수정 대상에 포함하지 않습니다.
