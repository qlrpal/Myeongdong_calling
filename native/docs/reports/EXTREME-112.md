# EXTREME-112 · 정상 직접 연결의 기준선과 단일 출력 대조

2026-10-28 / `codex/extreme-latency`. 111에서 성공한 양쪽 통화 소켓 LAN 지정 조건을 사용해 실제 PC·노트북1:1의 기준선을 수집했다. 같은 빌드·파형·LowLatency·10ms·고정20ms RTP 여유·장치·요청 출력40ms를 유지하고 기존 출력 A1 → 단일 출력 B → 기존 출력 A2를 비교했다. 시스템 VPN·경로·방화벽·장치 설정·일반 앱 기본값·dist는 변경하지 않았다. 이전 미커밋 작업을 보존했다.

## 실행 도구 보완

- `PairFunctionalProbe`/`test-pair.ps1`에 `-ObserveSeconds`를 추가했다. baseline만5–300초로 확장하며 기본은 기존5초다. 양쪽 관측 시간이 다르면 진단 채널에서 설정 불일치로 중단한다.
- 연결 후2초의 고정 준비 시간을 제외하고 baseline을 각60초 관측했다. 기존 음소거·해제·각자의 퇴장/재참가·정리 검사는 유지했다. 각 조건은 새 실행 ID·새 C# 프로세스다.
- 250ms 진단 스냅샷과 구간 C# 프로세스 CPU·할당·GC 정지 합계를 기록했다. 진단 수집 비용도 포함되며 audiodg·드라이버·다른 프로세스 비용은 제외한다.
- `pair-observation.mjs`/`analyze-pair-observation.mjs`는 양쪽 기능 성공, 서로 다른 호스트 식별자, A/B/A 순서, 동일 빌드/장치/코덱/인터페이스/프레임/여유, 실제 출력 구조와 카운터 역행·미완료 구간을 확인한 뒤 요약한다. 누락 지표는0으로 바꾸지 않는다.
- 큐와 송신 대기는 스냅샷 분포다. RTT는 같은 로컬 시계의 보고 나이로 새 RTCP 보고만 집계한다. PLC는 관측 시간 대비 마스킹 오디오 시간이며 패킷 손실률이 아니다. 출력 목표 패딩/API 참고값은 실제 하드웨어 대기와 구분해 JSON에 남긴다.

## 동일 조건과 결과

세 조건 모두 양쪽6개 기능 검사와 최종 정리를 완료했다. 실제 수집된 코덱은 네이티브 Opus LowDelay64/64kbps였다. PC의 실제 캡처/출력 주기는10/2.667ms, 노트북은5.333/10ms로 각 호스트 안에서 세 조건 모두 같았다. 출력 포맷·장치도 같았다. 공통 출력 후보의 실제 stream/source가 각각1개임을 확인했다. **1:1에서는 기존 출력도 한 개이므로 다인의 출력 수 절감 효과를 평가하는 시험이 아니다.**

큐 분포는 역할별234–236개의 스냅샷이다. CPU/할당 구간은 약60초, 누적 카운터 차분은 첫/마지막 스냅샷의 약59.7초다. 재생 큐는 실제 입→귀 지연이 아니다. 출력 공급 부족은 PCM 공급 지표이며 사람이 그 시간만큼 끊김을 들었다고 단정하지 않는다.

RTCP RTT 중앙값은 역할·단계별2.581–3.511ms이며 새 보고는10–12개다. 양쪽 모두 송신 프레임 폐기0, 관측 구간의 잘못된 RTP 오디오0, 렌더 장치 EmptyEvents0이었다. 출력 목표 패딩은 PC5.833ms·노트북15ms로 세 조건에서 일정했다. A1 PC에 PCM 공급 부족30.938ms와 재버퍼1회가 있어 기준선을 무끊김으로 선언하지 않는다.

관리형 할당은 기존 약1.231MiB/s, 단일 약1.238MiB/s였다. GC 정지는 PC 약7.97–8.45ms/60초, 노트북 약13.59–21.51ms/60초였다. GC와 특정 끊김의 인과관계를 계측한 것은 아니다. 실제 물리 지연을 측정하거나 이 수치들을 단순 합산하지 않는다.

## 결정

단일 출력에서 PC 큐·CPU와 양쪽 PLC가 낮아지는 방향은 관측됐다. 반면 노트북 큐 P95는 기존51.354/52.792ms보다 높은61.792ms였고 CPU도 기존0.071–0.100코어보다 높은0.122코어였다. **이번 한 차례 A/B/A에서 양방향 지연·자원 이득이 일관되게 확인되지 않아 기본값 승격은 보류한다.** 통계적으로 유의한 일반적 성능 퇴행을 확정하거나 PC의 큐 차이를 물리 지연 감소로 표현하지 않는다.

기존 출력·프레임·재생 여유는 유지한다. 단일 출력은 다인 스트림 수 감소를 확인할 선택 후보로 남기며 이1:1 결과로 다인 성능을 결론내리지 않는다. 효과가 확인되지 않은 새 튜닝이나 OS 설정 변경을 추가하지 않았다. 이번 작업은 재현 가능한 기준선/비교·기각 근거를 만든 것이며 실제 입→귀 지연 개선을 달성했다고 선언하지 않는다.

## 검증·한계·재현

경고0·오류0 빌드, 최종 제품 검사와10개 Node 실행/병합/분석 테스트를 통과했다. 분석 테스트는 짧은 구간·상대 교체·카운터 역행·자원 누락·대조 설정 변화·출력 구조 불일치를 거부하고, 관측 완료를 물리 지연/품질 합격으로 표시하지 않는지 확인한다. 실제 두 PC의 새60초×3 비교가 이번 C# 변경의 주요 통합 검증이다. 제품 오디오 코드는 이번에 변경하지 않았으며 전체 verify Integration을 다시 반복하지 않았다(직전111에서 통과). 구문·공백 검사를 확인했다.

시험 소유 프로세스와 노트북 기본 입력/출력을 확인했고 잔여 시험 프로세스는 없었다. OS 자동 경로는 Tailscale로 유지됐다. 기존 앱·운영 서버·dist·설정은 덮어쓰지 않았고 격리 시험 복사본과 원본은 보존했다. 한 번의1:1 대조이며 배경 부하를 완전히 통제하지 않았고 의도적인 게임 부하는 부여하지 않았다. 다른 회선·다인·장시간·물리 장치 분리·주관적 음질·물리 입→귀 지연은 미실시다.

실행은 [두 PC 가이드](../PAIR-CHECKS.md)의 양쪽 `-ObserveSeconds 60 -MediaAddress LOCAL_IP`를 사용한다. 후보만 양쪽 `-SharedOutput`을 추가하고 각 단계는 새 실행 ID를 사용한다. `analyze-pair-observation.mjs MANIFEST.json OUTPUT_DIRECTORY`로 같은 분석을 재생성한다.

Git 제외 원본은 `native/.local/extreme-112/output-comparison-results.json`의 양쪽 보고서와 `analysis/comparison.md/json`에 보존했다. 파일 시각은 UTC이며 한국 시각2026-10-28 시험이다. CPU·GC·할당·목표 패딩·실제 주기와 송신 대기 등 상세 값은 JSON을 참고한다. 아직 커밋·푸시하지 않았다.
