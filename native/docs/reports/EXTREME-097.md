# EXTREME-097 — 네이티브 Opus 할당 감소와 두 호스트 회귀

2026-10-26 / `codex/extreme-latency`, 제품 기반0.6.0.

**소프트웨어에서 줄일 수 있는 큰 할당 지점을 확인해 네이티브 Opus 백엔드를 연결했다. 같은 빌드의 두 호스트 A/B/A에서 관리형 할당은 약49~50%, GC 정지 합계는 약49%, 프로세스 CPU는 약19~22% 감소했다.** 프레임·재생 여유를 늘리지 않았다. PLC와 간헐적인 연결 실패 전체를 해결하거나 물리 입→귀 지연의 ms 개선을 확정한 결과는 아니다.

## 계측에서 확인한 내용

수정 SDK가 실제 로드되는지 확인하고 PC·노트북에 각각 실제 엔진3개를 실행했다. 합성 음성은 실제 공유 캡처의 PCM을 인코딩 직전에 대체한다. 각 피어는 실제 WASAPI 공유 출력으로 재생한다. 이 시험은6대 독립PC나 실제6명의 발화를 대신하지 않는다.

기존 관리형 구성에서 호스트당 약85MB/s의 관리형 할당이 관측됐다. 초기 기능 구간의20초 EventPipe GC 할당 샘플은 약1.59GB를 기록했고, `Int32[]`가 약48%였다. 큰 스택은 Concentus CELT 인코딩/디코딩의 배열 생성과 BouncyCastle AES-GCM 초기화였다. 이는 샘플링된 귀속이며 개별 객체별 정확한 총량이나 특정 패킷 지연의 인과 증명이 아니다. 최종10분 유지 구간에는 프로파일러를 붙이지 않았다.

관리형/네이티브의 독립 코덱 시험과 실제 앱 재생 버퍼 벤치마크도 수행했다. 워밍업한2.5ms 코덱 인코딩+디코딩 쌍의 관리형 할당은 약19.5KB에서 거의0으로, 앱의2.5ms 패킷 입장+재생은3944B에서0B로 감소했다. 네이티브 내부 메모리 할당까지0이라는 뜻은 아니다. 장치·네트워크·스케줄링을 제외한 미세 벤치마크이며 물리 지연값으로 사용하지 않는다.

## 적용한 변경

1. 실행 프로젝트에 공식 `Concentus.Native`와 `Concentus.Native.NetCore`1.5.2를 잠금 의존성으로 추가했다. 일반 실행은 네이티브 우선이며, 지원 자산이 없거나 로드되지 않으면 관리형으로 대체한다. 시험의 `native` 강제 모드는 대체를 허용하지 않는다.
2. 앱 폴더의 아키텍처별 DLL을 절대 경로로 로드하고 Concentus의 P/Invoke를 그 모듈로 연결한다. 프로세스 수명 동안 유지하며 현재 작업 폴더를 바꾸거나 그곳의 DLL을 복사·삭제하지 않는다. 실제 인코더/디코더·라이브러리 해시·fallback 이유를 진단에 포함했다.
3. 네이티브 디코더의 음수 오류 반환을 처리했다. 초기 후보의 기존 malformed-input 회귀에서 음수 PCM 길이가 다음 Read에 남아 배열 범위를 벗어나는 문제를 발견했다. 디코딩 결과를 검증한 뒤 PCM 길이를 반영하고, PLC 오류에서도 길이를 비우고 재버퍼링한다. 관리형 예외와 네이티브 오류 코드를 모두 처리하며500개 무작위 입력과 큐 비음수 검사를 통과했다. 최초 실패 로그도 보존했다.
4. 그룹 보고서에 실제 SDK/코덱 식별자, 경과 시각이 붙은 상태 이벤트, 제한된 ICE 후보 변경 기록, 구간 할당 바이트·GC 정지 시간을 추가했다. 민감한 SDK formatter를 호출하지 않는 검사를 유지했다.
5. 새 실행 경로의 방화벽 조건을 확인하는 읽기 전용 `inspect-test-firewall.ps1`을 추가했다. 규칙 목록은 유효 정책 전체 판정이 아니며, 허용 규칙이 없다는 사실만으로 차단을 확정하지 않는다.
6. 선택적 ReadyToRun 배포에서 SDK 변환으로 원본 해시 검사가 실패하는 회귀를 확인했다. 검증된 SIPSorcery.dll만 R2R 변환에서 제외하고 나머지 R2R 설정을 유지했다. 해시 검사를 약화하지 않았다. SDK 자체의 JIT 제거까지 보장하는 구성은 아니다.

WASAPI 공유 모드, 프레임 길이, RTP 타임스탬프, 코덱 프로필·목표 비트레이트, 재생 여유와 시스템 라우팅의 기본값은 그대로다. 네이티브 구현의 패킷 내용이 관리형과 비트 단위로 같다는 주장은 하지 않는다.

## 같은 빌드의 관리형 → 네이티브 → 관리형

두 호스트 모두 같은 엔진·프로브·수정 SDK 해시를 확인했다.6인90초, 호스트당3엔진,2.5ms 프레임, 같은 합성 음성·설정·실행 경로를 사용했다. 각 회차의 실제 백엔드도 보고서로 검증했다. 시스템 시계는 바꾸지 않고 시작 시각의 차이와 조회 불확실성을 기록했다.

|호스트|조건|관리형 할당 MB/s|GC 정지 ms/s|프로세스 CPU 코어|
|---|---|---:|---:|---:|
|PC|A1 관리형|86.081|6.002|0.460|
|PC|B 네이티브|43.354|3.067|0.354|
|PC|A2 관리형|86.293|5.947|0.449|
|노트북|A1 관리형|84.766|20.911|0.711|
|노트북|B 네이티브|43.067|10.687|0.599|
|노트북|A2 관리형|85.049|20.856|0.764|

MB는10^6바이트다. GC 정지는 구간 누적 정지 시간을 구간 초로 나눈 값이다. CPU1코어는 논리 코어1개의 시간을 사용한 양이며, 프로세스에 청구된 사용자/커널 시간을 포함한다. audiodg.exe·다른 프로세스·별도 시스템/드라이버 작업 전체의 CPU가 아니다. 수치는 각각3개 엔진 부하의 합이며 일반1인 클라이언트 부하로 대입하지 않는다.

A1/A2 평균과 비교한 감소율이다. 한 차례 A/B/A의 관측값이므로 모든 하드웨어·회선에서 같은 개선율을 보장하지 않는다. 프레임 길이는 모든 회차에서2.5ms였다. 네이티브 전환은 코덱 구현과 비트스트림에도 영향을 줄 수 있으므로 PLC 변화의 원인을 GC 하나로 단정하지 않는다.

**PLC는 일관되게 개선되지 않았다.** 예를 들어 노트북 같은 호스트 방향의 PLC 비율은 A1 약0.090%, B 약0.240%, A2 약0.227%였다. CPU·할당 감소와 통화 연속성 합격을 구분한다. PLC에는 보간 유지와 늦은 도착·마감 정책도 포함될 수 있어 물리 패킷 손실률과 같지 않다.

## 실제 연결·제품·배포 검사

- 관리형의 전체 자동 경로 시험은3인→6인→1명 퇴장→재참가→엔진 재접속→전체 퇴장→6인600초를 양쪽 모두 완료했다. PC74개·노트북72개 피어/단계 구간에서 미디어 증가와 정리를 확인했다.
- 네이티브 자동 경로6인600초도 양쪽 모두 완료했다. 호스트별15개 수신기 검사와 마지막 제한된 추적의30개 방향 대조를 통과했다. 그 추적의 수신 미관측은0이었다. 전체600초 무손실·무PLC라는 뜻은 아니다. 두 장시간 시험은 기능 유지 검사이며 성능 감소율의 근거는 위의 같은 빌드 A/B/A다.
- 기본10ms 네이티브 구성의 실제 OCI TURN 제품 흐름을 두 PC에서3회 연속 완료했다. 마이크 음소거/해제, 상대 볼륨, 강제 복구, 기본 장치 재입장, 종료를 포함한다. 총48개 피어/단계 구간의 송수신·디코딩 증가, 실제 TURN 경로와437 기록0을 확인했다.
- 네이티브/관리형 양방향 Opus 상호운용,2.5/5/10/20ms,120샘플 lookahead, 리셋·PLC를 확인했다. 최종 관리형 강제 RTP 회귀도 통과했다.
- 정적 분석·관리형 회귀·서버8개·IPv4/IPv6 WebRTC/SRTP/RTCP·가변 프레임·6316패킷 결정적 재생·경계 fixture를 통과했다. localhost가 샌드박스에서 EACCES로 거부된 실행은 별도 보존하고 네트워크가 허용된 환경에서 전체 검사를 완료했다.
- 일반 StageOnly 배포와 win-x64 ReadyToRun StageOnly 배포에서 실제 수정 SDK·네이티브 코덱·라이선스를 확인했다. 기존 dist는 덮어쓰지 않았다. RID 배포의 루트 `opus.dll`과 일반 배포의 `runtimes` 배치를 모두 확인했다.
- 네이티브 자산 누락·손상 시 관리형 대체와 이유 기록, 네이티브 필수 모드의 누락 거부, 임의 CWD의 기존 `opus.dll` 내용 보존을 확인했다.

네이티브 DLL의 두 호스트 SHA256은 `9827076182C7E0A22D42468B03B01225634BBA8EBE44FFE880A5AC005F2209A9`였다. 라이브러리가 자체 보고한 문자열은 `libopus unknown`이다. 패키지 버전을 DLL의 자체 보고 버전으로 바꿔 적지 않는다. 수정 SDK 식별자는 `10.0.17+myeongdong.1 / udp1-turn1`을 유지했다.

## 기각·미확정 결과의 보존

초기 자동 경로3→6인 시험은 최신 SDK에서도 연결 끊김을 재현했다. 양쪽 LAN 주소 지정과 PC만 지정한 짧은 시험은 통과했다. 하지만 이후 자동 경로에서도 장시간 유지에 성공해 주소 지정만을 단일 원인이나 필수 해결책으로 확정하지 않는다.

PC가 선택한 상대 주소가 노트북 SSH 주소와 다른 사례를 관측했지만, 그 주소는 성공한 통화에서도 나타났다. 주소 차이만으로 잘못된 인터페이스 선택이나 물리 네트워크 원인을 확정하지 않는다.

새 시험 실행 폴더에는 명시적인 UDP 차단 규칙이 확인됐다. 그 폴더에서 수행한 소켓 계열 대조는 원인 판단에서 제외했다. 기존 허용 실행 경로를 사용했으며 방화벽 규칙을 변경하지 않았다. 노트북 임시 폴더로 되돌린 시험도 이후 통과했으므로 모든 초기 실패를 방화벽 탓으로 소급하지 않는다.

기존 허용 경로의 추가 IPv4 wildcard 후보는 수렴에 실패했다. PC에서는 자동 할당 주소, 노트북에서는 VPN 주소가 host 후보로 나와 소켓 계열 외에 후보 선택도 달라졌다. 이는 순수 IPv4/IPv6 대조가 아니므로 후보를 기각하고 관련 진단 분기를 최종 코드에서 제거했다. 기본 이중 스택·OS 경로·VPN 설정은 바꾸지 않았다.

## 남은 범위와 다음 우선순위

1. 남은 PLC·부족·간헐적 자동 경로 실패를 분리한다. 이번 성공으로 과거 실패나 모든 NAT의 재접속 문제를 해결했다고 선언하지 않는다.
2. 샘플에서 함께 확인한 BouncyCastle SRTP 할당을 다음 소프트웨어 조사 대상으로 둔다. 암호화·인증·재전송 방지·스레드 수명·상호운용성을 유지하는 대조가 필요하며 이번에는 수정하지 않았다.
3. 외부 사용자·독립된 장치·게임 부하와 동일 조건의 실제 입→귀 지연은 별도 검증한다. NIC 소프트웨어 경계를 실제 전파 송수신 시각으로 대입하지 않는다.

실행·대조·fallback·라이선스는 [네이티브 Opus 안내](../NATIVE-OPUS.md), 그룹 시험은 [두 호스트 가이드](../TWO-HOST-GROUP-TEST.md)를 참고한다. 원시 보고서·실패 로그·트레이스·시험 빌드는 ignored `.local/extreme-097/`에 보존한다.

## 최종 코드 확인과 복구

기각한 IPv4 진단 분기를 제거한 뒤 Release 경고/오류0과 전체 회귀·IPv4/IPv6 통합을 다시 통과했다. 그 최종 동일 빌드로 두 PC의3→6인 자동 경로 시험과 기본10ms TURN 제품 흐름을 추가 완료했다. 최종 제품 흐름의16개 피어/단계 구간도 미디어 증가를 통과했다. 앞선3회와 합하면 제품 흐름은4회, 총64개 관측 구간이다. 최종 보고서와 앞선 성능 시험의 빌드 식별자는 구분해 보존했다. 삭제된 진단 분기는 기본 경로에서 비활성이었으며 코덱·프레임·재생 동작은 바꾸지 않았다.

노트북의 기존 허용 시험 경로에 있던 파일은 덮어쓰기 전에 백업했다. 종료 후 원본 바이트를 복원하고 파일별 SHA256을 재확인했으며, 이번에 추가한 파일과 빈 디렉터리만 제거했다. 양쪽의 TransportProbe/VoiceNative 시험 프로세스는 남지 않았다. OCI의 coturn·신호 서버·nginx도 시험 후 active를 확인했다. 공유기·라우팅·전원·개인 오디오 설정과 기존 dist는 변경하지 않았다.

최종 소스의 일반 및 ReadyToRun StageOnly 배포도 다시 완료했다. 이번 작업은 소스·검증·문서까지 정리했으며 새 안정판 태그나 커밋·푸시는 하지 않았다.
