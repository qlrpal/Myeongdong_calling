# 양쪽 OS 경계 비교 — 2026-10-16

**두 PC 사이에서 발생한 큰 간격91개 중88개는 송신 OS UDP 이벤트와 상대 수신 OS UDP 이벤트 사이에서 추가된 변동으로 분류됐다.** 수신 콜백이나 디코더 뒤쪽보다 네트워크·NIC·드라이버·OS 네트워크 처리 경로를 우선 조사할 근거가 생겼다. 개별 장치를 원인으로 확정한 것은 아니다.

## 시험

PC 시각12:18:39~12:20:40 KST, 양쪽 약120초 통화. 각각180초의 메타데이터 전용 ETW를 동시에 수집했다. PC는 유선, 노트북은 Wi-Fi, 직접 LAN 경로다. 고정20ms 여유·10ms Opus·소비율 보정을 유지했고 테스트 신호는 넣지 않았다.

노트북의 첫 스크립트 시작은 실행 정책 때문에 실패했다. 신뢰된 로컬 스크립트에 대해 실행 프로세스에만 `-ExecutionPolicy Bypass`를 적용하고 시험을 재시작했다. 시스템 전체 실행 정책·NIC·공유기 설정은 바꾸지 않았다. PC에서는 앞서 승인된 UAC 관리자 추적을 사용했다.

원본과 분석은 Git 제외 `.local/dual-os-054/`에 있다.

## 시각 기준 보완

처음에는 ETW의 UTC 변환 시각과 시작 시 QPC/UTC 앵커를 사용했다. 노트북에서 이벤트 경계를 맞추는 오차가 관측돼 이 결과를 확정하지 않았다. UTC 호출 전후의 QPC 폭은 **호출 시간의 범위일 뿐, UTC API 자체의 해상도·변환 오차까지 보장하지 않는다.**

원본 ETL의 QPC를 `tracerpt -rts`로 직접 추출했다. Trace Header V2의 QPC clock type과 주파수를 확인하고, 양쪽 모두10,000,000Hz인 원시 시각을 각 호스트의 앱 `Stopwatch` 시각과 비교했다. CSV→JSON 변환은 `export_raw_network.py`가 담당한다. UTC 변환 입력·지원하지 않는 헤더·예상과 다른 UDP 필드는 거부한다. 양쪽 비교 분석도 raw QPC 입력을 요구한다.

서로 다른 PC의 절대 QPC를 빼지 않았다. RTP 식별자로 연결한 앱 패킷 쌍에서 **각 호스트 내부의 OS 송신 간격과 OS 수신 간격**을 구하고, 두 간격의 차이를 비교했다. 따라서 벽시계가 약2초 다른 것은 이번 간격 비교에 영향을 주지 않는다. 고정 단방향 지연은 측정하지 않는다.

기존 단일 PC 시험도 원시 QPC로 재분석했다. 30ms 초과54개 간격이 OS UDP 이벤트에도 존재한다는 이전 결론은 유지됐다. 이전 보고서의 UTC 앵커 반폭을 절대 시각 정확도로 해석하면 안 된다.

송신 쪽 OS 이벤트는 비교적 정상 간격인데 수신 OS 이벤트에서 이미 크게 벌어진 사례들이다. 대표 사례의 앱 기준 시각과 가까운 OS 이벤트의 경계 차이는PC 약0.02~0.13ms, 노트북 약0.1~0.24ms였다. 이 값은 개별 패킷 처리 지연이 아니라 **시각/간격 연계의 일관성 확인**에 사용했다.

혼합2개는 OS 수신 간격이 OS 송신 간격보다 약18~20ms 길어 분류 기준20ms를 확실히 넘지 못했다. 불확실1개는 송신 시간창에 다른 UDP 이벤트가 들어 있어 같은 원인으로 분류하지 않았다. 불확실한 사례를 강제로 네트워크 원인으로 합치지 않았다.

분류는 휴리스틱이다. OS 이벤트에는 RTP timestamp/sequence가 없으며, 같은 UDP tuple에 제어 트래픽도 포함된다. 가까운 이벤트를 이용한 간격 연계이므로 정확한 개별 패킷 단방향 지연을 주장하지 않는다. 이전 실행과 부하·주변 환경을 통제한 A/B가 아니므로 사건 개수 증감도 성능 회귀의 증거가 아니다.

## 좁혀진 범위와 다음 검사

이번 실행의 주된 큰 간격은 **송신 OS 이벤트 이후~상대 수신 OS 이벤트 이전**이다. 이 구간에는 송신 NIC/드라이버 큐, 무선·공유기·LAN, 수신 NIC/드라이버/DPC, OS의 수신 이벤트 이전 처리가 들어 있다. OS 이벤트는 NIC 하드웨어가 실제 전파/케이블에서 패킷을 받은 시각이 아니다.

따라서 “공유기가 문제” 또는 “노트북 Wi-Fi가 문제”라고 아직 단정하지 않는다. 유의미한 다음 대조는 노트북 유선 연결과 기존 Wi-Fi 연결 비교 또는 NIC/드라이버 단계의 추가 계측이다. 경로 비교 시 한 번에 한 조건만 바꾸고, 두 방향 OS 간격과 부족·PLC를 함께 비교해야 한다.

앱 내부의 상시 수신 큐31~36ms는 별도의 최적화 대상이다. 이번 순간 변동을 해결하려고 근거 없이 큐를 늘리거나 코덱을 바꾸지 않았다. 다른 실행에서 관측된 PC 캡처/콜백 지연 사건도 별도 조사 대상으로 남는다.

## 재현 도구와 검증

양쪽에서 상세 통화 기록과 `trace-network.ps1`을 동시에 실행한다. ETW 수집에는 관리자 권한이 필요하다. 원본 ETL·종료 JSON·`tracerpt -summary`의 손실 요약을 보존한다.

```powershell
python native/TransportProbe/Analysis/analyze_dual_os.py PC_JSON PC_UDP PC_ANCHOR PC_SUMMARY LAPTOP_JSON LAPTOP_UDP LAPTOP_ANCHOR LAPTOP_SUMMARY OUTPUT_JSON
python native/TransportProbe/Analysis/export_raw_network.py --self-test
python native/TransportProbe/Analysis/analyze_dual_os.py --self-test
```
