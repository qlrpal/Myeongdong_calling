# EXTREME-128 — 두 PC의 자동 사건 기록 실측 검증

2026-10-30 / `codex/extreme-latency`, 기준 `ab9718a`에 미커밋126–127 보완을 포함했다. 사용자 승인으로 노트북 SSH를 사용했다. 기존 주소는 연결 불가였으며 사용자가 알려준 새 주소에서 기존 노트북 SSH 호스트 키와 일치를 확인했다. 개인 주소·계정·진단 원본은 이 보고서에 포함하지 않는다.

## 변경과 조건

`PairFunctionalProbe.RunAsync` 보고서에 `baselineIncident`와 `finalIncident`를 추가했다. 기준선 뒤/시험 실패 시 자동 기록을 보존해 재참가가 첫 통화 기록을 지우는 문제를 피한다. `incidentIncludesStartup=true`로 명시하며 기존 수동 baselineTrace와 구분한다. 일반 앱/음성 정책은 이번 시험에서 변경하지 않았다.

실제 Windows PC+노트북에서 같은 VoiceNative/TransportProbe DLL을 사용했다. VoiceNative SHA256은 `C512F41012DA094F8A992AA4AA1D821E5E0057AAE85A0357D2E401CC6A8FEC39`, probe는 `9D619E6A3D283DEE8595C09CE8A49A4293C0AB0EC02DEB701EDF6DCE4B5AB317`이다. 미커밋 빌드이므로 HEAD만으로 이를 재현한다고 주장하지 않는다.

- 실제 공유 캡처/렌더, 합성 PCM 대체 입력, 앱 상대 볼륨1%. 실제 마이크 음성은 전송하지 않는다.
- 기본10ms LowDelay64/Opus, 수신 여유20ms, 기존 상대별 출력. 시스템/장치 설정을 변경하지 않는다.
- 공개 HTTPS 신호 서버, 직접 및 강제 TURN(UDP) 각60초 기준선. 앱 미디어 소켓만 각 호스트의 LAN 인터페이스에 지정했다. VPN/OS 라우팅은 변경하지 않았다.
- 기존 수동 상세 추적은 꺼져 있고 자동 사건 기록만 켜져 있다. 양쪽6검사(기준선·음소거·해제·양쪽 재참가·정리)를 실행했다.

## 자연 관측 결과

|경로/수신기|PLC 음성시간|재버퍼|늦음|송신 폐기|입력 불연속|큐 중앙값|
|---|---:|---:|---:|---:|---:|---:|
|직접 PC|22.5ms|0|1|0|0|30.79ms|
|직접 노트북|12.5ms|0|0|0|0|31.97ms|
|TURN PC|107.5ms|0|3|0|0|36.14ms|
|TURN 노트북|50ms|0|0|0|0|37.81ms|

수치는 기준선 첫/마지막250ms 표본 사이 약59.8–60.0초의 증분이다. PLC는 프레임 개수가 아닌 음성시간이다. 두 시험 모두 양쪽6검사와 병합을 통과했다. 작은 PLC가 남았으므로 완전 무끊김 판정은 아니다. 경로별 한 번의 측정이며 TURN의 일반적인 추가 지연을 이 큐 차이로 확정하지 않는다.

자동 기록은 네 조건 모두 Rolling 상태로8192개를 유지했다. 이번 조건에서는 트리거 임계값의 큰 사건이 없었으므로 동결되지 않는 것이 정상이다. 보존된 꼬리에서 송신 생성/큐/API·RTPChannel 관측·인증 후 콜백·버퍼 입장·읽기·렌더 공급이 모두 존재했다. PC에서 콜백529/528개는 각각 같은 SSRC/타임스탬프의 입장 및 후속 SDK 관측과 대응했다. 노트북 직접은752개가 대응했고 TURN은753개 콜백 중 후속 SDK 관측751개가 대응했다. 상한/기록 충돌이 있으므로 미대응을 네트워크 손실로 판정하지 않는다.

기록 충돌 누락은 직접 PC/노트북24/24개, TURN16/35개였다. 오디오 스레드를 기다리게 하지 않고 누락을 카운터로 남기는 동작을 실제로 확인했다. 긴 통화의 순환 덮어쓰기도 명시된다. 전체 앱/진단 표본의 할당·GC 정지는 원본에 보존했지만 새 기록만의 비용으로 귀속하지 않는다. 실제 두 PC에서 기록 켬/끔 A/B는 미실시다.

## 별도 인위적 정체 시험

자연 관측과 분리한 새 직접 연결 시험에서 RunId로 확인한 **자체 노트북 시험 프로세스 하나만**100ms 일시 정지했다. 외부 SSH 제어 프로세스의 finally에서 재개했고 재개 상태0을 확인했다. 일반 앱·다른 프로세스·네트워크·장치 설정은 변경하지 않았다. 실제 정지 총시간이 정확히100ms라는 보장은 없다.

양쪽 기능6검사와 병합을 통과했다. PC는 rebuffer, 노트북은 receive-gap으로 동결됐고 각7191/6307개를 보존했다. 사건 직전4095개와 트리거·후속 기록을 유지했으며 EndReason은 duration-limit였다. 충돌 누락3/5개도 보고했다. 노트북 기록에는 render-empty1개와 캡처 간격120.34ms가 포함됐다. 이 시험의 PLC212.5/75ms·PC 재버퍼1회 등은 인위적 정체 결과이므로 자연 관측 표와 합치지 않는다.

동일 SSRC/RTP 타임스탬프의 양끝을 대응하고 **각 호스트 내부의 간격만** 계산했다.

|방향|송신 API 진입 간격|상대 인증 후 콜백 간격|RTP 시간 간격|
|---|---:|---:|---:|
|정지한 노트북→PC|125.893ms|126.067ms|10ms|
|PC→정지한 노트북|9.384ms|115.197ms|10ms|

전자는 송신 앱 처리 공백이 수신에서도 관측되는 경우, 후자는 송신 호출은 정상 주기지만 수신 콜백이 밀리는 경우를 구분할 수 있음을 보여준다. **기존 자연 발생 문제의 원인 확정은 아니다.** 소켓 완료·NIC/물리 송수신·SRTP 거부 원인·실제 입→귀는 관측하지 않았다.

## 복구·한계·재현

기존 노트북 격리 시험 디렉터리를 통째로 백업한 뒤 최신 DLL을 넣었고, 종료 후 원래 디렉터리로 복구해 VoiceNative SHA256 일치를 확인했다. 자체 노트북 probe 잔류0이었다. 일반 dist·공개 베타·사용자 설정·시스템 라우팅은 유지했다. 새 결과와 시험 빌드는 별도 임시 폴더에 보존했다.

실제 게임 부하·독립 외부 회선·사용자 목소리/헤드셋·장시간 다인·실제 입→귀 및126의 상대 PCM16 장치 적용은 미실시다. 두 PC 모두 이번 장치 믹스는48kHz float였으므로 PCM16 물리 장치 합격으로 표현하지 않는다.

원본은 Git 제외 `native/.local/extreme-128/`의 각 result/analysis/injection-boundaries/restoration JSON과 두 호스트 참가자 보고서다. [두 PC 검사](../PAIR-CHECKS.md)의 양쪽 동일 RunId·반대 역할에 `-Route direct` 또는 `relay`, `-ObserveSeconds 60 -ReserveMs 20 -MediaAddress LOCAL_IP -NoBuild`를 사용하고 **TraceBaseline은 생략**한다. 인위적 프로세스 정지는 제품 사용 절차가 아니며 이번에만 별도로 실행했다.
