# 현재 구현·검증 상태

2026-10-26 / `codex/extreme-latency`. 제품 기반0.6.0이며 새 안정판 태그나 기존 버전 전체 대체를 확정하지 않았다.

## 목표와 실행

게임과 함께 사용하는 Windows 통화 앱이다. 우선순위는 **실제 지연 → 게임 중 연속성 → CPU·GC·스케줄링 부담 → 음질 → 부가 기능**이며 WASAPI 저지연 공유 모드, WebRTC 직접 연결 우선·TURN 대체 경로를 사용한다.

```powershell
./native/run.ps1                            # 기존 기본 구성
./native/run.ps1 -Experiment opus-adaptive  # 선택적 지연 우선 비교 후보
./native/verify.ps1 -NoRestore -Integration
```

.NET10 SDK·Node.js22 이상, Windows10 2004 이상이 필요하다. 양쪽에 같은 소스의 최신 빌드를 사용한다. [실행/모드 가이드](EXTREME-LATENCY.md), [Git 소스 배포](GIT-RELEASE.md), [두 호스트 그룹 시험](TWO-HOST-GROUP-TEST.md)을 참고한다. 로컬 변경은 커밋·푸시 전까지 원격에 반영되지 않는다.

## 최근 보완

[EXTREME-105](reports/EXTREME-105.md): 시험 통화의 Wi-Fi 경로를 고정해 송신 API·Wi-Fi Tx·PC Rx·콜백을 연결했다. 첫 시험의 큰 공백24건은 양끝이 모두 대응했고, 대표 사건은 Tx4.158ms→Rx131.594ms였다. 계측 영향 대조 B에서도 Tx10.756ms→Rx60.805ms를 대응했다. 노트북 계측을 꺼도 약53ms 공백이 재현됐다. 이 사건들의 큰 간격 증가는 송신 Wi-Fi 소프트웨어 Tx 뒤→PC 소프트웨어 Rx 앞이며 하위 드라이버/무선/AP·메시는 미분리다. 계측 영향0·전체 원인 규명·해결 완료는 아니다. 제품 코드는 바꾸지 않았다.

[EXTREME-104](reports/EXTREME-104.md): 노트북의 현재 OS 경로가 Tailscale의 LAN 서브넷 경로임을 확인했다. 두 사건에서 송신 API/가상 Tx 약11ms 간격이 PC Rx 약43ms로 증가했다. 통화별 Wi-Fi 선택 A/B/A의 PC RTCP RTT 중앙값은9.716→2.581→9.468ms였다. 시스템 VPN·라우팅은 변경하지 않았다. Wi-Fi 선택에서도 PLC 및35.960/57.008ms 콜백 공백이 남았으므로 전체 끊김 해결은 아니다. 다음은 이 Wi-Fi 통화 경로를 고정한 실제 송신 Tx 관측이다.

[EXTREME-103](reports/EXTREME-103.md): 불완전한 Pktmon 수집은 원인 판정에서 제외했다. 기존 Npcap으로 I3의 수신12030개/late279개, Npcap 단독 B의12014개/late61개를 모두 대응했다. B의 가장 큰 사건은 송신 API 간격10.344ms, PC 소프트웨어 수신 관측138.751ms, 콜백138.662ms였다. 큰 간격 증가는 송신 API→PC 소프트웨어 수신 관측 사이에 있다. 캡처 끔/켬/끔에서도 끔 상태의 큰 공백을 재현했으나 계측 영향0을 증명한 것은 아니다. 다음은 송신 측 소프트웨어 Tx 관측이며 제품 튜닝은 계속 보류한다.

[EXTREME-102](reports/EXTREME-102.md): 제품 빌드·직접 경로·모드를 고정한 두 PC60초 반복2회에서 상세 기록의 late62건 모두 수신 RTP 콜백 관측 전에 PLC가 시작됐음을 확인했다. 큰 선택 사건은 송신 API 간격6~10ms에 비해 수신 콜백 간격58~67ms였다. 입장 후 잠금/디코딩만으로 이 사건을 설명할 수 없으며, 콜백 전 SDK·소켓/OS·네트워크는 아직 미분리다. 제품 동작 변경 없이 분석 도구만 추가했다. 다음은 동일 패킷의 OS 수신 관측과 SDK 콜백을 연결하는 시험이다.

[EXTREME-101](reports/EXTREME-101.md): FineClock의 작은 장치 요청에서 정상 입력 묶음을 정리하며 PLC를 반복 생성하던6조건을 수정했다. 묶음 위상을 고려한 시계 피드백을 함께 적용했고 확장83조건이 기준을 통과했다. 두 조건은 큐 평균이1.3~2.2ms 줄었지만 원래 정상인 조건은0.2~0.8ms 늘었다. 실제 두 PC의 직접/TURN 및6엔진 미디어·종료 검사는 완료했으나 PLC·출력 부족·재버퍼는 남아 있다. **모든 조건의 평상시 지연 감소나 물리 입→귀 지연 개선을 입증한 것은 아니다.** 기본 모드 승격 없이 기존 실험 경로만 보완했다.

[EXTREME-100](reports/EXTREME-100.md): 최신 기준선과 인라인/전용 송신을1:1·3명·6명에서 비교했다. 전용의 캡처 작업은 줄었지만 평상시 송신 API 전달은 빨라지지 않아 기본값 승격을 기각했다. 전용 실험 큐의 정상 묶음 보존·나이 제한, 실험 RTP backlog 정리 후 재시작 불가를 수정했다. 당시 추가 분수 출력 진단21조건 중6조건이 실패했으며 후속101에서 보완했다. 물리 지연 개선은 입증하지 않았다.

[EXTREME-099](reports/EXTREME-099.md): 짧은 공백 보류 PLC를 출력 요청에 맞춰 분할해 불필요한 잔여 큐를 줄였다. 동일 조건 A/B90쌍 중19쌍에서 PLC·큐 감소, 나머지는 같았다. 전체 입→귀 지연이나 무선 스파이크 해결 수치는 아니다.

[EXTREME-098](reports/EXTREME-098.md): 인증 전 RTP 초기 상태 변경과 첫 순번0 거부를 수정했다. 실제 협상 프로필 진단과 PLC hold/advance 분해를 추가했다. 실제 통화에서 효과가 없었던 GCM 키 재사용 후보는 제외했다.

## 구현된 내용

- 방 참가/나가기, 최대6명 메시, 장치 선택, 마이크/상대 음소거·볼륨, 연결 복구, UTF-8 진단 내보내기.
- 기본10ms Opus와 선택적2.5/5ms·PCM 시험, 수신 시간축/PLC·큐 상한·장치 시계 보정, 지원 범위 내 공유 장치 주기 선택.
- 전역 피어 잠금 없는 송신과 종료 수명 보호, 패킷 풀/제한 정렬 저장소, 캡처·렌더 경로 계측.
- 선택적 양쪽 패킷/마감 기록 분석과 실제 두 호스트 다중 엔진·입퇴장·재접속·10분 유지 시험 도구.
- 1:1 수신 피드백 기반 프레임 비교/복귀. 다인 통화는 현재 송신 길이를 유지한다.

## 최신 검증 결과와 미해결 항목

[097 네이티브 Opus·두 호스트 회귀](reports/EXTREME-097.md): 관리형 CELT 배열 할당을 계측하고 네이티브 Opus 우선·관리형 대체를 연결했다. 같은 빌드의6인90초 A/B/A에서 관리형 할당 약49~50%, GC 정지 합계 약49%, 프로세스 CPU 약19~22% 감소를 확인했다. 프레임·재생 여유는 유지했다. 관리형 전체 입퇴장/재접속+6인10분, 네이티브6인10분, 기본10ms 네이티브 TURN 제품 흐름3회가 양쪽 모두 완료됐다. PLC는 모든 방향에서 줄지 않아 연속성·물리 지연 합격으로 일반화하지 않는다. 잘못된 패킷의 네이티브 음수 반환 처리와 R2R SDK 해시 검증도 보완했다. [백엔드 식별·배포](NATIVE-OPUS.md).

일반 빌드/실행/publish의 수정 SDK 자동 연결을 추가했다. 원본 NuGet DLL 대신 고정 소스를 빌드하며 수신 시작 보호·UDP TURN 종료 삭제가 환경 변수 없이 적용된다. 현재 실제 로딩 식별자는 `10.0.17+myeongdong.2 / udp1-turn1-rtp0`이며, 초기 SRTP 인증 상태 수정은 [098](reports/EXTREME-098.md)에 기록했다. [SDK 빌드·검증](SDK-BUILD.md), [096 기본 연결 검증](reports/EXTREME-096.md). 아래094/095의 별도 빌드 지위는 당시 기록이며 이후 기본 연결로 바뀌었다. 기존 dist는 별도로 다시 빌드해야 한다.

[095 TURN 재연결 수정](reports/EXTREME-095.md): 실패한 재연결에서 Allocate437을 확보했다. OS 자동 UDP 포트가 닫힌 포트를 재선택해 남은 TURN 할당과 충돌하는 것을 통제 재현했다. **일반 앱 소스**는 최근 포트 보존과 명시적 난수 포트 선택으로 재사용을 피한다. 별도 SDK 후보는 정상 UDP 종료 시 인증된 Refresh(0)를 추가했다. 결합 후보는 두 PC의 제품 흐름3회 연속, 송수신/디코딩48개 구간, 실제6인90초, 정상/수정 SDK 로컬 통합 검사를 통과했다. 당시 기본 NuGet·기존 dist는 유지했으며 외부 사용자·장기 신뢰도·입→귀 지연 합격을 선언하지 않는다.

[094 SDK 수신 시작 보호](reports/EXTREME-094.md): 정확한 상류 소스의 수신 상태 확인·설정을 짧은 잠금으로 보호한 별도 시험 빌드를 추가했다. 실제6인 A/B/A에서 원본은 중첩·정체성 중복/미관측을 재현했고 수정 구간의30개 수신기는 모두 중첩0이었다. 노트북 내부 방향 미관측은447→0→620개, PLC 비율은2.283%→0.153%→4.975%였다. 이는 관측 구간의 합산 값이며 입→귀 지연이나 장기 발생률이 아니다. 호스트 간 미관측·PLC는 남았고, 제품 재연결 시험은 원본과 수정 모두 실패 사례가 있어 **기본 배포본 승격은 보류**한다. [시험 빌드 준비·실행](../sdk-experiment/README.md)은 원본/수정 대조용으로 남겨 두었다. 현재 정상 실행은096의 수정 SDK를 사용한다.

[093 수신 경계·SDK 경쟁 보고서](reports/EXTREME-093.md): 실제6인90초 시험에서 노트북 내부 일부 방향의 SDK 채널 이벤트에서도 중복·미관측을 확인했다. 이어 오디오·RTP 없는 순수 UDP 원본/수신 시작 직렬화/원본 대조에서 SDK 동시 수신 시작 문제를 양쪽 호스트에서 재현했다. 직렬화 구간은 중복·미관측0이었다. **시험 전용 수정이며 실제 통화의 동일 원인 확정이나 제품 해결 완료는 아니다.** 최신 Release 빌드는 경고/오류0이다. 통합 검사의 IPv6 RTCP는 최초 시간 초과 후 해당 검사 재실행이 통과했다.

[092 두 호스트 그룹 보고서](reports/EXTREME-092.md): 실제 공유 오디오를 사용하는 엔진을 PC/노트북에 각각3개 실행했다.3명/6명 성립, 입퇴장·재참가·명시적 Leave/Join 재접속·전체 종료/재입장을 확인했다. OS 자동 경로의6명 장시간 시험은 약93초에 연결이 끊겨 **실패**했다. 앱에 LAN 인터페이스를 명시한 조건에서는3명/6명 대조와6명10분 연결·디코딩·종료 정리 검사가 양쪽 모두 완료됐다. 새 세션/순서도 달라 경로의 단일 원인을 확정하지 않는다.

**통화 연속성 합격은 아니다.** PLC·부족이 남았고, 특히 노트북 같은 호스트 방향에서도 송신 API 기록과 복호화된 RTP 콜백 사이의 미관측 프레임이 확인됐다. 재생 버퍼 이전의 SDK/전송·검증·로컬 OS 경계가 미분리다. 이 문제를 집 무선망이나 물리 손실만으로 설명하지 않는다.6대 독립PC·다른 사용자 회선·게임 부하·물리 입→귀 지연 시험을 대신하지 않는다.

최종 원본 소스 Release 빌드 경고/오류0, 관리형 회귀·서버8개·로컬 IPv4/IPv6 WebRTC/SRTP/RTCP 통합을 통과했다. 그룹 시험의 기능 완료와 품질/지연 합격을 구분한다. 메모리에는 보존 중인 진단 자료가 포함돼 전후 값만으로 누수를 판정하지 않는다.

## 다음 우선순위

2026-10-26 사용자 지시: **현재 실제 통화의 끊김 원인 규명·해결 전까지 다른 개선과 기능 작업을 보류한다.** 단일 출력 믹서, 추가 프레임/버퍼 튜닝, 할당 최적화, 부가 기능, 배포 승격은 진행하지 않는다. 원인 확인에 꼭 필요한 계측·수정·회귀만 수행한다.

1. 105에서 확인한 송신 Wi-Fi Tx 뒤→PC 소프트웨어 Rx 앞 구간을 더 나눈다. 다음 후보는 노트북 통화별 Wi-Fi 선택을 유지하고 PC의 기존 Ethernet/이미 연결된 Wi-Fi를 통화별로 대조하는 것이다. 사용 가능한 실제 인터페이스를 읽기 확인하고, NIC와 매체 경로가 함께 달라지는 대조라는 한계를 명시한다. OS 자동은 현재 VPN을 포함할 수 있으므로 물리 LAN 경로라고 가정하지 않는다. 수집 완전성·양끝 대응·계측 영향을 먼저 검증한다. 새 드라이버 설치나 전역 VPN/라우팅 변경부터 하지 않는다. 다른 PC의 비동기 시각을 직접 빼거나 소프트웨어 관측을 물리 송수신 시각으로 부르지 않는다. 아직 미분류인 출력 부족 사건을 이 결론으로 일괄 설명하지 않는다.
2. 기존 기록으로 구분되지 않는 경계만 선택 계측한다. `late`라는 결과만으로 네트워크 지연이나 앱 시간축 오류를 단정하지 않는다. 새 계측의 부하도 대조하며 여러 설정을 동시에 바꾸지 않는다.
3. 식별한 경계를 통제 재현하고 원인에 한정한 변경을 A/B 또는 A/B/A로 검증한다. 단순 연결 성공·빌드 통과·가상 검사 통과로 해결을 선언하지 않는다. 실제 동일 조건에서 문제 사건 감소와 정상 지연·연속성의 회귀 여부를 함께 확인한다. 미관측 경계·미실시 검증은 남은 문제로 표시한다.

기존 ICE/NAT·외부 회선·게임 부하·다인 구조의 별도 작업은 보존된 계획으로 남긴다. 현재 끊김의 원인 검증에 필요하다는 근거가 생길 때만 범위에 포함한다. 기본 OS/VPN 경로·공유기·개인 장치 설정은 임의 변경하지 않는다.
