# Mumble·SYNCROOM에서 적용할 요소

확인일: 2026-10-18. 목표는 Windows 음성 통화의 **지연 감소 → 음질 → 부가 기능** 순서다. 개인 마이크·이어폰 조정은 제외한다. 이 문서는 참고 설계와 제안이며 새 기능을 구현했다는 기록이 아니다.

사용 조건: 게임과 동시에 사용하므로 **WASAPI 저지연 공유 모드**를 목표로 고정한다. 게임 소리와 통화의 동시 재생을 유지해야 한다. 오디오 인터페이스가 없는 환경을 기준으로 하며 독점 모드·ASIO 구현은 현재 범위에서 제외한다. 아래의 다른 제품 관련 설명은 해당 제품의 사실이며 우리 구현 계획과 구분한다.

## 확인한 사실

### Mumble

- 공식 설정은 패킷에 담는 음성 길이, 수신 지터 버퍼, 장치 출력 대기를 별개로 다룬다. 작은 값은 대기를 줄일 수 있지만 장치·회선에 따라 끊김이 늘 수 있다. 로컬·서버 루프백도 구분한다. [공식 오디오 설정](https://www.mumble.info/documentation/user/audio-settings/)
- 공개 master의 `AudioInput.cpp`는 저지연 허용 및 64kbps 이상 조건에서 Opus `RESTRICTED_LOWDELAY`를 선택한다. 문서의 약15ms 절감 안내를 우리 앱에 그대로 적용할 수 없다. 우리는 이미 저지연64/96kbps 옵션이 있고 기존 검사에서 코덱 선행 대기 약6.5→2.5ms를 확인했지만, 앞선 전체 경로 A/B/A에서는 일관된 감소가 확인되지 않았다. [인코더 구현](https://github.com/mumble-voip/mumble/blob/master/src/mumble/AudioInput.cpp), [우리 비교 기록](reports/OPUS-COMPARISON.md)
- 공개 `AudioOutputSpeech.cpp`는 사용자별 지터 버퍼·Opus 손실 보정·출력 요청량에 따른 디코딩을 사용한다. 조용한 구간에 버퍼 지연 조정을 허용하는 코드도 있다. 모든 버퍼 조정이 무음에서만 일어난다는 뜻은 아니다. [수신 구현](https://github.com/mumble-voip/mumble/blob/master/src/mumble/AudioOutputSpeech.cpp)
- `AudioOutput.cpp`는 여러 사용자의 오디오를 모아 출력 버퍼에 혼합한다. [믹서 구현](https://github.com/mumble-voip/mumble/blob/master/src/mumble/AudioOutput.cpp)

Mumble의 공개 master는 읽은 시점의 개발 코드이며 모든 배포 버전이 동일하다고 보장하지 않는다.

### SYNCROOM

- 방 관리 서버와 참여자별 직접 음성 연결을 분리한다. 최고 음질은 비압축48kHz·16bit·스테레오다. [공식 FAQ](https://syncroom.yamaha.com/global/v2/play/faq/index_pc.html)
- NETDUETTO는 연결 상태에 맞춰 작은 버퍼를 설정하고, 연결 중에도 지연 변동을 관찰하고 보정한다고 설명한다. 세부 알고리즘·임계값은 공개 설명만으로 재현할 수 없다. [기술 설명](https://syncroom.yamaha.com/global/about/)
- Windows에서 ASIO·WASAPI 독점/공유 등의 입출력 경로를 제공한다. 상대별 수신 버퍼 조정과 재최적화 기능도 있다. ASIO 권장은 지원 장치 조건이 있으며, 독점 모드는 다른 앱의 장치 사용을 제한한다. [공식 매뉴얼](https://syncroom.yamaha.com/global/v2/play/manual/index_pc.html)

## 우리 프로젝트에 적용하는 판단

아래는 위 자료와 현재 소스·검증 결과를 바탕으로 한 프로젝트 제안이다. 상대 제품의 실제 성능을 우리 앱의 성능으로 간주하지 않는다.

| 우선순위 | 요소 | 현재 상태와 적용 방향 |
|---|---|---|
| 1 | 오디오 입출력 경로 대기 축소 | WASAPI 저지연 공유 모드 안에서 캡처 전달17~19ms 중 앱의 누적·변환·프레임 조립에서 줄일 부분부터 확인한다. 게임 소리 동시 재생과 게임 부하 중 통화 안정성도 검증한다. 저지연 경로를 사용할 수 없을 때도 표준 공유 모드로 복귀한다. 독점 모드·ASIO 구현은 제외한다. |
| 2 | Opus 저지연 모드 | 64/96kbps 비교 옵션은 이미 구현. 새 코덱 작업을 반복하지 않고, 같은 입출력·버퍼 조건에서 실제 대화와 전체 경로의 개선이 확인될 때 기본값을 결정한다. |
| 3 | 상대별 최소 안정 버퍼 | 상대별 RTP 버퍼·PLC·소비율 보정은 이미 존재. 0.5.5 기본 정책을 유지하면서 필요할 때만 제한적으로 여유를 늘리고 안정 후 복귀하는 방향을 검토한다. 기존 적응20~40ms 옵션을 무조건 켜거나 버퍼를 새로 작성하지 않는다. |
| 3 | 말하는 도중의 회복 손상 억제 | 현재 최신 큐 재시작은 음성을 생략할 수 있다. 급한 부족은 즉시 처리하되, 비긴급 큐 축소는 조용한 구간에 수행하는 방법을 비교한다. 효과가 있어야 채택한다. |
| 4 | 사용자별 버퍼 + 공통 출력 믹서 | 현재는 상대별 WindowsAudioDevice가 출력 경로를 가진다. 그룹 통화 확대 전에 사용자별 네트워크 시간축은 유지하고 하나의 출력 장치로 혼합하는 구조를 검토한다. 이것만으로 1:1 지연이 줄어든다고 가정하지 않는다. |
| 유지 | 출력 요청에 맞춘 디코딩·재생 | 이미 render-driven RTP 재생이며 별도 디코딩 타이머가 없다. 이 구조를 유지하고 추가 대기 큐를 쌓지 않는다. |
| 유지 | 전송과 방 관리 분리 | WebRTC 직접 연결 우선과 TURN을 유지한다. Mumble의 서버 경유 구조나 NETDUETTO 자체를 복제하는 작업은 진행하지 않는다. |
| 활용 | 비교 가능한 측정 | 기존 로컬·루프백·경로 측정을 재사용한다. 동일 장치·경로·음성으로 입→귀와 끊김을 비교하며, RTT·재생 큐·코덱 대기를 같은 수치처럼 비교하지 않는다. |

## 당장 추가하지 않을 요소

- SYNCROOM의 비압축 스테레오 기본화: 순수 오디오만 상대당1.536Mbps(48,000×16×2)이고 네트워크 헤더가 더해진다. 코덱 대기 제거 이득과 대역폭 비용을 입증한 뒤 별도 모드로 검토한다.
- ASIO 필수화, 음악 합주용 동기화·메트로놈·VST·녹음, 위치 음향·게임 연동·채널 권한 체계: 현재 지연 중심 통화 목표의 우선 작업이 아니다.
- 에코 제거·잡음 제거·VAD를 한꺼번에 기본 활성화: 필요성·처리 비용·실제 음질을 별도로 확인한 뒤 추가한다.
- WebRTC 전면 교체·새 중계 서버 작성: 현재 확인된 앱 내부 대기를 먼저 줄인다.

## 실행 순서와 채택 기준

2026-10-18 첫 구현: [0.5.6 공유 입력 주기 단축](reports/SHARED-CAPTURE-PERIOD.md). 지원 장치에 약5ms를 요청하고 미지원 장치는 기존 공유 경로를 유지한다. 노트북의 첫 샘플→인코딩 중앙값은 약3ms 줄었지만 P95가 약1.8ms 늘었으므로 전체 환경의 최적값으로 확정하지 않는다. 입력 주기 단축만 끄는 복귀 선택을 제공한다.

1. **캡처·출력 경로:** WASAPI 저지연 공유 모드와 현재 재생 정책을 기준으로, 요청 주기·누적·변환·프레임 조립을 한 번에 하나씩 최적화한다. 게임 소리 동시 재생과 게임 부하 중 안정성을 확인한다.
2. **코덱 기본값:** 기존 LowDelay64/96을 재사용하고, 음성의 명료도·끊김과 전체 경로 지연을 비교한다.
3. **상대별 버퍼 회복:** 필요한 상대에게만 여유를 주고, 말하는 중 생략과 복귀 지연을 줄인다.
4. **그룹·원거리 검증:** 공통 출력 믹서 검토와 실제 직접/TURN 통화를 확인한다.

채택하려면 같은 조건에서 재생 가능한 음성의 지연이 줄어야 하며, PLC·무음 부족·의도적 생략량도 함께 제시한다. 큐 숫자만 낮아지거나 설정값만 작아지는 변경은 개선으로 확정하지 않는다. 판단에 필요한 자료가 모이면 진단 확장보다 제품 반영을 우선한다.
