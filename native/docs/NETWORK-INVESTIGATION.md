# 네트워크 지연 조사 기준과 남은 관측 경계

목표는 게임 중 실제 지연과 연속성이다. 이 문서는 앱 처리·경로·집 환경의 서로 다른 사건을 한 원인으로 합치지 않기 위한 기준이다. 완료한 상세 실험은 보고서 원문을 따른다.

## 같은 검사를 반복하지 않는 기준

- RTT 최대값 하나나 다른 PC 절대 시각 차이를 입→귀 지연으로 사용하지 않는다.
- Npcap/NDIS/ens3를 물리 전파/회선 시각으로 표현하지 않는다.
- 드롭 카운터0은 모든 패킷의 개별 대응이나 무선 무손실을 보장하지 않는다.
- 스캔·MCC·qWAVE·지속 트래픽·무선 모드/보안의 기존 무효 대조는 새 관측/반증 조건 없이 반복하지 않는다.
- AP/대역/어댑터를 함께 바꾼 결과를 단일 원인의 확정으로 취급하지 않는다.
- 설정 변화와 계측 변화는 별도 변수다. 실험 간 배경 상태가 다르면 지연 감소를 제품 기본값으로 채택하지 않는다.

## 비용 없는 도구의 현재 범위

- SDK·자동 사건 기록·Npcap/tshark·OCI tcpdump: 같은 패킷을 관측 경계 사이에 연결한다. 인터넷/가정망의 내부 노드를 새로 만들어 주지는 않는다.
- WPR/WPA/ETW: 현재 실행 권한으로 추가 시작이 가능한지 먼저 확인한다. 사용자가 응답할 수 없는 동안 UAC 창을 띄우거나 기다리지 않는다. 072의 기존 DPC 실행시간 검사를 새 원인 규명처럼 반복하지 않는다.
- Windows WLAN 이벤트: 로밍/연결/재인증 등이 실제 기록되면 사건과 대응한다. 빈 로그를 절전·재시도 없음으로 해석하지 않는다.
- 드라이버 통계/모드 조회: 지원을 실제 확인한다. 일반 어댑터 discard/error0을 802.11 재전송0으로 바꾸지 않는다. 모드 지원 조회와 실제 모니터 캡처 성공은 다르다.
- 제한 부하: 자체 서버에 상한·기간을 정해 한 방향씩 적용한다. 로컬 게이트웨이·외부·다른 NIC·측정 루프를 함께 관측한다. 낮은 속도에서 악화가 없었다고 회선 포화 큐를 배제하지 않는다.

## 추가 측정의 채택 조건

1. **앱/NIC 앞뒤 잔여가 크게 늘어남:** 동일 패킷의 송수신 관측과 스레드 실행 대기를 대응한다. 충분한 권한/자료가 없다면 미실시로 남긴다.
2. **게이트웨이와 외부가 함께 늦고 다른 NIC는 정상:** 해당 로컬 분기 후보가 강화된다. 같은 시각 창·전송 주기·실제 송신 진행을 확인하며 AP 응답 처리 차이를 남긴다.
3. **로컬은 정상이고 외부만 함께 늦음:** WAN/외부/서버 하위 후보를 우선한다. 서버 부하와 실제 서버 패킷 경계를 확인하기 전 통신사로 단정하지 않는다.
4. **제한 부하에서 가역적 변화:** 반복·원복과 계측 조건을 확인한 뒤 그 조건의 영향으로 보고한다. 변화가 뒤집히면 확정 원인/완화책으로 채택하지 않는다.
5. **NIC 관측 사이만 남고 지원 통계 없음:** 현재 장비의 관측 한계다. 같은 ping/캡처를 무한 반복하지 않는다. 앱 버퍼 축소나 임의 시스템 설정으로 물리 원인을 해결했다고 표시하지 않는다.

시스템 라우팅·VPN·장치·전원 계획·AP/드라이버 설정은 새로운 명시적 변경 승인 없이 바꾸지 않는다. 배포본·사용자 진단·비밀값을 실험 도구에 섞거나 커밋하지 않는다. 추가 하드웨어 구매/교체를 자동 추진하지 않는다.136은 사용자가 새로 준비해 연결한 ASIX 유선 구성의 명시적 시험 요청으로 수행했으며 기존 무선의 물리 관측 한계 자체를 해결한 것은 아니다.
