# 설계 토론 기록

2026-11-09. 사용자, Claude, ChatGPT(Codex)가 기존 명동콜링을 전면 재작성하기로 하고 5라운드 교차 검토로 설계를 합의했다. 같은 논쟁을 반복하지 않도록 경과와 철회·기각 사항을 남긴다.

## 출발점

- 기존 프로젝트(`codex/extreme-latency`, 커밋 `3ab162b`): C#/.NET 10, WinForms, NAudio+WASAPI, SIPSorcery WebRTC(수정 SDK), Opus 10ms, 수신 여유 20ms, Node + coturn 서버. 150개가 넘는 실험 보고서.
- 사용자 판단: **극저지연이 여전히 최우선이며, 현재 개발 스택으로는 충분히 구현하기 어렵다.** 스택과 서버를 모두 갈아엎는다.
- 사용자 지시: 기존 측정값을 맹신하지 말 것. 환경이 달라지면 충분히 달라질 수 있으니 참고용으로만 쓸 것(→ R1).
- 사용자 지시: 토론은 합의될 때까지 하되, 측정이 필요한 쟁점은 실험 방법과 판정 기준 합의로 닫는다(→ R2).

## 설계 변경 메모

- `CLOCK_CONTINUOUS` 플래그(5라운드 제안) → `ClockDomainId`를 프레임에 싣는 방식으로 대체(구현 단계). 수신 측은 ID 동일 여부로 드리프트 상태 유지를 결정한다. 패킷 v3 암호화 영역에 `clock_domain u32` 추가.

- P0 분석기 검출 기준(2026-11-09). 동기 검출 q_min을 0.5에서 0.4로(검증 후보), 중첩 경로 시각 허용을 2샘플로(검증 후보) 바꿨다. 근거: A단계 합성 실측에서 q_min 0.5는 겹친 −6 dB 경로를 놓쳤고, 0.3은 비트 처프 구간 q 0.287과 여유가 없었다. 누화 보호는 고정 1ms 대신 리그 자체 검증 교정값(채널 오프셋·누화 지연 범위 ±2샘플)으로 정한다. 실제 경로와 누화가 구분되지 않으면 Ambiguous로 보고하고 낮은 지연으로 확정하지 않는다. 판정 지표는 동기 q 여유가 아니라 최종 분류 수준의 잘못 확정·놓침 비율이다. 기존 실패 수치와 판정 기준은 `docs/experiments/001-analyzer-validation.md`. 사용자 승인(검증할 후보로만). 검증 실행 전 개정 3회: 중첩 범위 ±marker_len, 짝을 못 찾은 해독 불가 후보를 Ambiguous로, 판정 지연 원시 R−L·Missing은 "마커 미검출, 원인 미확정"·구분 가능 조건은 주입 조건만으로. 판정 수치는 유지했지만 합격 난이도가 달라질 수 있음을 실험 파일에 기록했다. 채택·동결은 Windows와 Linux 검증 후에만 한다.

- P0 측정 신호 마커 ID 배치 A0(2026-11-10, **실험 002 채택 전 후보**). 마커 순번 i를 코드워드 인덱스 π(i)로 보내는 결정적 배치표(길이 1,704, FNV-1a 64 해시 `0xf04865d91d86aa86`)를 쓴다. 근거: 실험 001에서 3비트 오정정된 이웃 ID가 earliest 규칙으로 먼저 선택돼 600ms가 100ms Normal로 확정됐다. 순차 ID(π(i) = i)에서는 출처 창 안 마커끼리 코드 거리가 4까지 가까워진다. A0는 연속 6개 순번 안의 모든 쌍을 거리 ≥ 8로 만들어, 창 안 다른 마커로 오확신하려면 비트 오류가 7개 이상 필요하게 한다. 일정 길이 상한(1,704)을 부호 공간(2,048)과 분리하고 ID를 재사용·순환하지 않는다. 생성 WAV가 바뀐다. 함께 A3 소거 복호(소거 1개·오류 0개까지 확정, 소거 2개 이상 거부)를 구현했다. 채택·동결은 실험 002 합격(Windows·Linux) 뒤에만 한다. 설계와 판정 기준은 `docs/experiments/002-analyzer-revalidation.md`(동결 개정 5.1).

- 실험 002 진행 방식 변경(2026-11-10, 사용자 결정). 개정 5.3(`30bc57a`)에서 문서 개정을 멈춘다. (이후 개정 5.4는 아래 기준에 따른 1a 수정이다.)
  - 근거 [사실]: 개정 1~5.3을 거치며 의무·플래그·칸이 계속 늘었다. 개정마다 구멍 하나를 막는 규칙이 다른 칸과 충돌해 예외를 새로 만들었다(5.3: 누화 후보 정의 → 겹침 구간 → G7-edge 충돌 → E6·G7-edge-limit·cellE6·R2e). [추정] 근본 원인은 W·Z·X·누화 크기 같은 실측값 없이 경계 규칙을 먼저 확정한 것이다.
  - 진행: 구현 ③ A1, ④ A4는 개정 5.3대로 한다. 독립 하네스와 본실행은 리그 자체 검증으로 실측값을 얻은 뒤, 실험 002의 범위를 줄일지 사용자와 다시 정한다.

## 구현 중 확인한 사실과 검토 항목

- 수신 PC Realtek 마이크의 공유 모드 장치 위치는 패킷 프레임 수와 단위가 다르다(2026-11-11, P1-b 프로브).
  - [사실] 측정 경계: 앱의 `IAudioCaptureClient::GetBuffer` 반환값. 조건: 수신 PC `마이크(Realtek(R) Audio)`, 공유 모드 이벤트 구동, 믹스 형식 48kHz, MMCSS Pro Audio, 미커밋 빌드, 구성당 30초 1회. 공유 최소(139프레임 요청)에서 패킷은 139~140프레임인데 장치 위치(`pu64DevicePosition`)는 패킷마다 128씩 늘었다(10,335쌍 전부). 공유 기본(488프레임)에서는 패킷 487~488프레임에 위치 증가 448(2,953쌍 전부). 두 비율 모두 44100/48000과 일치한다. 같은 조건의 fifine USB 마이크는 위치 증가와 패킷 프레임이 480으로 같았다.
  - [추정] 이 장치는 44.1kHz로 동작하고 공유 엔진이 48kHz 믹스 형식으로 변환한다. 장치 위치는 장치 쪽 프레임 단위다.
  - [사실] 공유+RAW(`AUDCLNT_STREAMOPTIONS_RAW`, `AudioCategory_Other`)로 열면 믹스 형식 자체가 44.1kHz로 조회됐고, 주기 조회값은 기본 448 / 최소 128프레임이었다. 패킷 프레임과 위치 증가량이 448(기본), 128(최소)로 일치했다(불일치 0, 미커밋 빌드, 구성당 30초 1회). 위 [추정]의 "44.1kHz 장치"는 이 조회로 확인됐다. 일반 공유의 48kHz·487~488프레임은 변환을 거친 결과다. 변환이 어느 단계에서 일어나는지는 확인하지 않았다.
  - 검토 항목: `DESIGN.md` 4.2의 `CaptureTimeline`은 "장치 위치 = 예상 위치"로 연속을 판정한다. 이 장치의 공유 모드에서는 위치 증가량이 패킷 프레임 수와 달라 그 전제가 그대로 성립하지 않는다. 판정 단위(장치 프레임 vs 스트림 프레임)와 독점 모드에서의 동작을 확인한 뒤 4.2를 고칠지 정한다. 아직 DESIGN은 바꾸지 않았다.

  - 결정(사용자): Tailscale은 켜 둔 채, 측정하는 두 PC에서만 `tailscale set --accept-routes=false`로 서브넷 경로 수신을 끈다. 광고하는 쪽은 건드리지 않는다. 측정 대상은 상대의 mDNS 이름(`<호스트명>.local`)으로 지정한다(Tailscale IP·MagicDNS 이름 금지). LAN IP는 DHCP 할당이라 바뀔 수 있어 고정값으로 쓰지 않는다.

  - 사전 점검: `mdc-rig-route-check --remote <호스트명.local | LAN IP>`. 이름을 해석해 나온 주소마다 경로를 조회하고, 해석된 주소를 `resolved=`로 출력한다. 경로가 Tailscale 인터페이스거나 해석 결과에 Tailscale 주소가 섞여 있으면 이유를 출력하고 0이 아닌 코드로 끝난다. 해석·조회에 실패해도 통과시키지 않는다. 링크 로컬 IPv6 주소는 점검하지 않고 표시만 한다. 두 PC에서 수신을 켠 상태(차단), 끈 상태(통과), 짧은 이름(차단)을 확인했다. 두 PC 사이 측정은 시작 전에 양쪽에서 이 점검을 통과해야 하고, 측정에는 점검이 출력한 주소를 쓴다.
  - 미확인: 수신 PC는 Wi-Fi(`172.30.1.33`)도 같은 대역에 붙어 있어 `.local` 이름이 Wi-Fi 주소로 해석될 수 있다(이번에는 이더넷 주소였다). 점검은 경로의 인터페이스만 보며 유선·무선은 구분하지 않는다. `--accept-routes=false`가 재부팅 뒤에도 유지되는지는 확인하지 않았다.

## 기존 앱 기록에서 얻은 가설 (R1: 판정 근거 아님)

- 평상시 큰 구간은 캡처 전달·프레임 조립, 수신 재고 유지, 출력 장치 경로였고, 코덱·송신 큐 연산은 작았다.
- 노트북 출력 경로에서 DTS endpoint 효과 하나가 큰 고정 지연을 만들었다. 출력 효과를 반드시 확인할 것.
- FIFINE AM8 USB 마이크는 공유 모드 10ms 주기에 묶였다.
- SDK 수신 후처리는 평상시 작았고, 큰 수신 공백은 SDK 이전(OS·NIC·무선·경로)에서 이미 존재했다. 유선 연결에서 변동이 작았다.
- 수신 여유를 단순히 줄이는 후보들은 PLC 증가로 반복 기각됐다 → 이번에는 Pareto 탐색과 드리프트 보정 선행으로 접근.
