2026-11-09. Claude와 ChatGPT(Codex)가 5라운드 교차 검토로 합의한 내용이다. 경과와 철회된 주장은 `DISCUSSION-LOG.md`에 있다.

## 1. 목표와 범위

- Windows 전용 음성 통화 앱. 최대 6인 P2P 메시, 초기에는 1:1.
- **최우선 목표: 실제 입→귀 지연 최소화.** 게임과 동시 실행이 주 사용 환경이므로 최종 출력은 게임 소리와 공존해야 한다(공유 모드 렌더).
- 원칙: **먼저 지연의 바닥을 찾고, 그 바닥 구조를 유지하며 안정성을 올린다.**
- 초기(P0~P5)에는 손실·PLC·끊김을 허용하되 보존율을 항상 함께 기록한다. 안정화(FEC, 중복 전송, 적응형 지터)는 P6.

## 4. 미디어 시간축 (`crates/timeline`, 구현됨)

### 4.1 의미
- **`ClockDomainId`**: 물리 발진기(캡처 장치 인스턴스). 같은 ID면 epoch가 바뀌어도 속도(ppm) 추정이 유효하다. 장치가 바뀔 때만 바뀐다.
- **`SampleIndex` (u64)**: 한 `StreamKey`(peer, stream, epoch) 안의 송신 캡처 장치 샘플 카운터. **같은 StreamKey 안에서만 차이가 의미 있다.** epoch가 다르면 같은 클록 도메인이어도 오프셋 관계가 없다(속도 관계만 유지). 48kHz에서 사실상 순환하지 않는다.
- **`Epoch`**: 디코더와 지터 기준점의 세대. 엄격히 증가한다. 클록 도메인 변경은 반드시 epoch 변경을 동반하지만, 역은 성립하지 않는다.
- **`MediaFrame`**: `StreamKey`, `ClockDomainId`, `SampleRange`, `Codec`, `FrameFlags`, 고정 1KB 인라인 `Payload`. 힙 할당·참조 카운팅 없음. 생성자가 불변식을 검사한다.

### 4.2 송신 측 캡처 불연속 처리 (`CaptureTimeline`)
WASAPI `GetBuffer`의 장치 위치(`pu64DevicePosition`)로 판정한다.

| 판정 | 조건 | 처리 |
|---|---|---|
| 연속 | 위치 = 예상 위치 | 그대로 이어서 배치 |
| 정확한 공백 | 위치 > 예상, 차이 ≤ 상한 | 차이만큼 SampleIndex 건너뜀, 다음 프레임에 `GAP_BEFORE` |
| 재설정 | 위치 역행 / 상한 초과 / 신뢰 불가 | **임의 길이를 만들지 않고 새 epoch**. 같은 장치면 클록 도메인 유지 |
| 장치 변경 | 호출자가 알림 | 새 epoch + 새 클록 도메인 |

### 4.3 수신 측 프레임 분류 (`FrameLedger`)
모든 프레임은 AEAD 인증 후 들어오므로 충돌·겹침은 공격이 아니라 송신자 버그로만 생긴다.

| 분류 | 조건 | 처리 |
|---|---|---|
| New | 처음 보는 범위 | 기록 |
| Duplicate | 같은 `(start, len)` | 먼저 받은 것 유지, 내용 비교 없음 |
| Conflict | 범위가 다르게 겹침 | 나중 것 버림, 프로토콜 오류 카운터 |
| Late | 재생 지점보다 앞서 시작 | 버림 |
| StaleEpoch / NewerEpoch | epoch 비교 | 이전 것 버림 / 새 것은 상태 전환 후 처리 |

"엄격 증가·비중첩"은 **송신자가 생성하는 신규 프레임**에 대한 불변식이고, 수신 순서에는 적용하지 않는다.

## 5. 스레드·데이터 소유 구조

| 스레드 | 소유 | 비고 |
|---|---|---|
| 캡처 | WASAPI 캡처 클라이언트, `CaptureTimeline`, 인코더, 송신 키 상태(인라인 모드) | 깨어날 때마다 `GetNextPacketSize`로 쌓인 패킷을 모두 비운다 |
| 송신 작업자 (작업자 모드만) | 송신 키 상태, 소켓 송신 | 모드는 **실행 전 고정**. 동적 전환은 필요가 측정되기 전까지 구현하지 않음 |
| 수신 | UDP 소켓 수신, 복호화, 세션별 재전송 방지 창 | 소켓은 **하나**(모든 상대 공유, receiver_index로 구분). 홀펀칭에서도 같은 로컬 포트가 필요 |
| 렌더 | 상대별 디코더·`FrameLedger`·지터·드리프트 보정, 믹서, WASAPI 렌더 클라이언트 | **pull 구조**: 마감 시점에 디코딩 또는 PLC |
| 제어 | 핸드셰이크, 세션 설치·폐기, 장치·설정 변경 | 키 객체 해제는 여기서만 |
| 진단 | 기록 수집·저장 | 비실시간 |

| 경로 | 생산자 → 소비자 | 구조 |
|---|---|---|
| 수신 패킷 | 수신 → 렌더 | 상대별 SPSC 링 (6인 = 5개) |
| 송신 프레임 (작업자 모드) | 캡처 → 송신 작업자 | SPSC 1개 |
| 세션 키 | 제어 → 캡처·수신 | 사전 할당 슬롯 또는 소유권 이전 메시지. **원자적 포인터 교체만으로 즉시 해제하지 않는다** |
| 계측 기록 | 각 실시간 스레드 → 진단 | 스레드별 SPSC |
| 제어 명령 | 제어 → 각 실시간 스레드 | 스레드별 SPSC |

- 링이 가득 차면 생산자가 새 항목을 버리고 센다. 가득 참은 소비자 정체를 뜻하는 오류로 다룬다.
- 한 상대의 폭주는 그 상대의 링만 채운다. 수신 스레드의 복호화 비용은 공유되므로 상대별 수신율 상한을 둔다.
- [사실] lock-free 구조 자체가 지연 최소화를 보장하지 않는다. 전체 경로를 외부 리그로 판정한다.

## 6. 크레이트와 의존성 방향

```
timeline   (의존성 없음)
codec, wire-mc, wire-rtp, jitter, drift, audio  → timeline
signal     (의존성 없음, 시그널링 메시지 타입)
transport  → timeline, signal        (wire-* 연결은 P3에서 어댑터로)
engine     → timeline, audio, codec, jitter, drift, transport, wire-mc
app        → engine
rig        → audio, timeline
server     → signal
```

- [사실] `cargo tree`로 순환 없음 확인. `server`는 미디어 크레이트를 끌어오지 않는다.
- `timeline`은 공통 미디어 의미론, `wire-*`는 형식 변환만 한다. RTP 대응 시 sample_index 하위 32비트 ↔ RTP timestamp이며 수신 측은 SSRC별로 순환을 추적해 64비트로 복원한다. SSRC 변경이 곧 새 장치 시계를 뜻하지는 않으므로 클록 연속성은 `timeline`이 따로 관리한다.

## 7. 오디오 (WASAPI)

### 7.1 사실
- [사실] `IAudioClient3::InitializeSharedAudioStream`의 주기는 `GetSharedModeEnginePeriod`가 주는 **fundamental** 주기의 정수배이고 min~max 안이어야 한다.
- [사실] Windows 기본 HDAudio 드라이버는 공유 모드에서 128~480샘플(48kHz 기준 2.67~10ms)을 지원하도록 업데이트됐다. 모든 장치에 일반화하지 않는다.
- [사실] Windows 기본 USB Audio Class 2 드라이버는 Microsoft 설명으로 일반 소비자용이며 최소 지연이 보통 10ms다. Microsoft·Yamaha의 저지연 UAC2+ASIO 드라이버는 선택 설치형 프리뷰 단계라 제품 의존성으로 두지 않는다.
- [사실] `GetBuffer`는 첫 프레임의 장치 위치와 QPC 위치(100ns 단위)를 준다.
- [사실·이전 앱] RAW 스트림 옵션은 노트북의 DTS endpoint 효과를 우회하지 못했다. DTS 등록을 제외했을 때만 장치 시계→루프백이 크게 줄었다(R1: 가설 생성용). 즉 RAW를 켰다고 출력 지연이 충분히 낮다고 판단하지 않는다.

### 7.2 구성 방침
- 캡처: **독점 모드를 우선 시도**, 실패하면 공유(+RAW). [추정] 독점은 엔진 처리와 캡처 APO를 거치지 않는다. 마이크 독점은 게임 소리 출력과 충돌하지 않는다(단점: 통화 중 다른 앱이 마이크 사용 불가).
- 렌더: 공유 + 최소 주기(+RAW). 게임 소리 때문에 독점 렌더는 비교 기준으로만 측정한다.
- `audio` 크레이트는 처음부터 공유·독점 두 경로를 같은 인터페이스로 구현한다.
- 출력 장치에 endpoint 효과(EFX)가 등록돼 있으면 감지해 경고한다. 사용자 레지스트리는 자동 수정하지 않는다.
- 블루투스 출력은 측정 대상에서 제외하고 사용자에게 유선 사용을 안내한다.

### 7.3 P1 프로브 기록 (`crates/audio`, 타입 정의됨)
`DeviceInfo`(공유 주기 4값, 독점 주기, RAW 지원, 드라이버), `StreamRequest`/`StreamActual`(요청과 실제를 분리 기록), `CaptureRecord`(깨어남, GetBuffer 반환, 장치 위치, 첫 프레임 QPC, 플래그, 처리 완료), `RenderRecord`(깨어남, 패딩, 쓴 프레임, 장치 시계 위치·QPC, 원본 샘플 대응, 처리 시간, 마감 초과). 앱 QPC 틱(`QpcTicks`)과 WASAPI 100ns 값(`Hns`)은 타입으로 분리했다.

### 7.4 ASIO 제외 이유
지연 한계가 아니라 **보유 장치 지원과 개발 비용** 때문이다. ASIO가 유리해지는 조건은 기본 USB 드라이버가 10ms에 묶인 장치에 벤더 ASIO 드라이버가 더 작은 버퍼를 허용하는 경우다. 다중 클라이언트 ASIO 드라이버도 존재하므로 "게임 소리와 공존 불가"는 일반 사실이 아니다.

## 8. 코덱과 프레임 정렬

비교 대상: **PCM 128, 표준 Opus 120(2.5ms), 표준 Opus 240(5ms), Opus Custom 128.**

[사실·계산] 캡처 패킷 128샘플을 가정하고, 원본 샘플마다 "캡처 시각 → 그 샘플이 든 프레임이 인코딩 가능해지는 시각"을 계산한 값(인코딩 시간, 코덱 선행 지연, 네트워크 제외):

| 구성 | 평균 | P50 | P95 | 최대 | 정렬 구성 대비 평균 추가 |
|---|---:|---:|---:|---:|---:|
| PCM 128 | 1.34ms | 1.35 | 2.54 | 2.67 | 0 |
| Opus Custom 128 | 1.34ms | 1.35 | 2.54 | 2.67 | 0 |
| 표준 Opus 120 | 2.51ms | 2.52 | 4.27 | 5.00 | +1.17ms |
| 표준 Opus 240 | 3.68ms | 3.69 | 6.35 | 7.33 | +2.33ms |

- 표준 Opus 120은 1920샘플마다 프레임 16개가 패킷 15개에 걸쳐 완성되어, 완성 간격이 2.67ms와 0ms 두 값만 나온다. **송신 측이 스스로 지터를 만든다.**
- 모델 가정: 캡처 패킷이 항상 정확히 128샘플. 공유 모드에서는 패킷 크기가 달라질 수 있어 P1에서 확인한다.
- 이 차이를 그대로 입→귀 개선량으로 해석하지 않는다. 코덱 선행 지연, 실행 시간, 송신 불균일, 수신 마감이 따로 있다.
- [사실] 표준 Opus의 2.5/5ms 프레임은 CELT 전용이며 CELT 선행 지연 2.5ms가 프레임 크기와 무관하게 붙는다.
- [가설] Opus Custom의 선행 지연(MDCT overlap)은 모드에서 유도되므로 2.5ms보다 작을 수 있다.
- [사실, `opus_custom.h` 주석 기준·P2 재확인] Custom 프레임은 64~1024샘플, 소인수가 2·3·5뿐이어야 한다.
- **10ms 캡처 장치에서는** 프레임을 쪼개도 송신 시점이 같아 이득이 없다(송신 시점이 같으면 개선 아님). 이 비교는 짧은 주기 장치에서만 한다.
- LAN에서는 PCM을 진단용이 아니라 실제 모드 후보로 둔다(코덱 지연 0, 48kHz 16비트 모노 768kbps).

## 9. 지터·재생

- 렌더 마감 시점에 디코딩하는 pull 구조. 마감 직전 도착 패킷도 쓸 수 있고, PLC 판단과 디코더 상태가 한 스레드에서 일관된다.
- 수신 여유는 장치 출력 시계와 재생 마감 기준으로 정의한다(도착 후 고정 대기가 아님).
- 초기 정책: 늦은 패킷은 기다리지 않고 버린다. 무음 또는 최소 PLC.
- 최소 여유는 단일 값이 아니라 **지연–보존율 Pareto frontier**로 탐색하고, 시작 위상·드리프트·네트워크 변동을 고려해 재시작 반복한다.
- 재생된 모든 PCM 블록에 원본 `(StreamKey, SampleIndex)` 또는 PLC/무음 표시를 기록한다. 보존율은 이 기록으로 계산한다.

## 10. 시계 드리프트

- 장기 드리프트 추정기와 단기 재생 마감 정책을 **분리**한다.
- 수신 렌더 장치 시계는 `IAudioClock` 위치–QPC 쌍으로 네트워크 없이 직접 잰다. 네트워크로 추정할 것은 송신 측 시계뿐이다.
- 송신 시계 추정: 송신 SampleIndex와 수신 QPC 도착 시각의 **하한 포락선** 기울기. 지터는 지연을 늘리기만 하므로 창별 최솟값이 스파이크를 걸러낸다.
- 실패·편향 조건과 대응:
  - 최소 경로 지연의 계단 변화(경로·전송률·TURN 전환): 잔차 점프 감지 시 회귀 재시작.
  - 수십 초 지속되는 큐 적체: 하한 자체가 올라 드리프트처럼 보임. 물리적 범위(±300ppm)로 제한, 연속 두 창 일관 시에만 반영.
  - [추정] 일정하게 변하는 최소 네트워크 지연과 시계 드리프트는 단일 관측으로 원리적으로 구분할 수 없다 → 보정 상한, 교차 검증, 어긋나면 보정 보류.
- 교차 검증: 재생 큐 추세에서 **정책 동작으로 넣고 뺀 샘플 수를 뺀 값**. 큐 재고를 1차 신호로 쓰지 않는 이유는 보정기가 자기 보정에 반응하는 되먹임 때문이다.
- 보정 방식은 P3에서 세 가지 비교: 저에너지 구간 삽입·삭제 / 가변비 선형 보간 / 짧은 다상 리샘플러. 명목 탭 수로 지연을 단정하지 않고 임펄스로 측정한다.
- 드리프트 상태는 `ClockDomainId` 기준으로 유지한다. 같은 장치의 epoch 변경에서는 초기화하지 않는다.

## 11. 패킷 형식 v3 (조건부 채택, P3 전 문서 확정)

### 11.1 형식
평문 헤더 14B (AEAD AAD로 인증): `type/ver u8 | reserved u8 | receiver_index u32 | counter u64`

암호화 영역: `stream_id u32 | epoch u32 | clock_domain u32 | codec u8 | n_frames u8`, 그리고 프레임마다 `sample_index u64 | sample_count u16 | flags u8 | len u16 | data`

헤더 크기는 지연 레버가 아니다(1Gbps에서 수십 바이트는 수십 ns). 기준은 정확성이다.

### 11.2 불변식
- **I1** 세션 안에서 `(receiver_index, counter)`는 유일. counter는 키별 nonce이며 재사용하지 않는다.
- **I2** `(stream_id, epoch)` 안에서 송신자가 만드는 신규 프레임의 sample_index는 엄격히 증가하고 겹치지 않는다. 유실 샘플은 정확한 길이를 알 때만 건너뛴다.
- **I3** `GAP_BEFORE`는 직전 샘플이 캡처 단계에서 유실됐을 때만.
- **I4** epoch는 엄격히 증가. 수신 측은 epoch 변경 시 디코더·지터 기준점을 전환하고 이전 epoch 패킷은 버린다. 드리프트 상태는 클록 도메인이 같으면 유지.
- **I5** 키 교체는 미디어 필드를 바꾸지 않는다.
- **I6** 재전송 방지 창은 세션별, AEAD 인증 성공 후에만 갱신.
- **I7** 표준 Opus의 프레임 길이 변경은 같은 epoch에서 허용. 코덱·Custom 모드 변경은 epoch 증가.

### 11.3 검증한 사례 (F=128)
| 상황 | 패킷 | 수신 복원 |
|---|---|---|
| 정상 | c10[1280], c11[1408], c12[1536] | 순서대로 |
| 중복 2개 | c13[1664, 1536, 1408] | 이미 있으면 Duplicate |
| 불연속 직후 과거 중복 | 256샘플 유실. c14[2048 GAP_BEFORE, 1664] | 절대 인덱스라 모호성 없음 |
| 송신 생략 | 다음 패킷 인덱스 2F 증가, counter +1 | counter 연속 + 샘플 공백 = 송신 생략(네트워크 손실 아님) |
| 키 교체 중 역전 | B·c0[2304] → A·c15[2176] | A 키는 유예 기간 보관, 세션별 창, 인덱스 순 정렬 |
| 32비트 순환 | 해당 없음(u64) | — |
| 프레임 크기 변경 | 표준 Opus 같은 epoch / Custom↔표준은 epoch+1 | frame_samples로 복원 / 디코더 초기화 |
| 이전 epoch 지연 도착 | E+1 시작 후 E 패킷 | StaleEpoch로 버림 |

### 11.4 epoch와 드리프트 초기화
| 사건 | epoch | 클록 도메인 | 드리프트 상태 |
|---|---|---|---|
| 표준 Opus 프레임 길이 변경 | 유지 | 유지 | 유지 |
| 코덱·Custom 모드 변경 | 증가 | 유지 | 유지 |
| 길이 모르는 불연속 (같은 장치) | 증가 | 유지 | 유지 |
| 마이크 장치 변경 | 증가 | 변경 | 초기화 |
| 새 통화 | 새 세션 | — | 초기화 |

## 12. 보안 세션 (자체 UDP 선택 시, P3 전 확정)

- Noise 핸드셰이크 하나 = 세션 하나. 세션은 방향별 CipherState 두 개.
- **키 교체는 Noise `Rekey()`가 아니라 새 핸드셰이크로 일원화**한다(합의). Noise 명세상 `Rekey()`도 정상적인 방법이지만, 메커니즘을 하나로 줄여 해석 모호성을 없애기 위한 선택이다.
- receiver_index는 수신자가 자기 활성 세션 중에서 무작위로 고르고 로컬 충돌 시 다시 뽑는다.
- 교체 시점: T_rekey(예: 120초) 또는 counter 한도 근접. 새 세션 확인 전까지 이전 세션으로 송신(공백 없음). 새 세션 **설치**와 송신 **전환**을 구분한다.
- 이전 세션 수신 키는 유예 기간 G 동안 보관 후 제어 스레드에서 안전하게 폐기한다.
- IP만 바뀐 재연결은 세션이 유효하면 인증된 패킷의 출발 주소로 상대 주소를 갱신(핸드셰이크 없음). 만료 후 재연결은 새 핸드셰이크.
- 신뢰 모델(P5에서 결정): 서버 배포 + TOFU 고정 + 선택적 지문 표시. Noise XX도 후보.

## 13. 전송 계층 (P3 관문에서 결정)

### 13.1 조사한 사실
- [사실] str0m은 Sans-IO다. 네트워크를 직접 다루지 않고 내부 스레드·async 작업이 없다.
- [사실] RTP 모드(`set_rtp_mode(true)`)는 내부 패킷화를 우회하고 `write_rtp`로 송신, `Event::RtpPacket`으로 수신한다. 재정렬 설정은 무시된다.
- [사실] TURN은 지원하지 않는다. relay 주소 확보는 앱 책임이다. 외부에서 얻은 relay 후보를 ICE 검사에 포함하는 것은 가능하다.
- [사실] 유지보수자가 주로 테스트하는 용도는 SFU이며 P2P는 테스트가 적다고 명시한다.
- [사실] 0.24부터 오디오 코덱 설정에 RED(RFC 2198) 플래그(`enable_opus(enabled, use_red)`)와 `set_red_distances`가 있다. [추정] 코덱 페이로더 기능이므로 RTP 모드에서는 적용되지 않는다. PCM·Custom Opus는 RTP 모드가 필수라 앱이 RED를 직접 만든다.
- [사실] 오디오 송신 버퍼(`set_send_buffer_audio`, 기본 50)가 write와 poll_output 사이에 패킷을 둔다.
- [사실] `Rtc`는 상태 변경 후 `poll_output()`을 Timeout까지 소진해야 하는 단일 변경 불변식을 가진다. **캡처 스레드와 수신 스레드가 같은 `Rtc`를 독립적으로 변경할 수 없다.**

### 13.2 판단
- 지연 관련 제어권(즉시 송신, 앱 재생 관리, 소켓 옵션)은 두 안이 거의 같다. [추정] 성능 차이는 0에 가깝다.
- TURN 클라이언트는 두 안 모두 str0m 바깥이다. 이 항목은 두 안을 가르지 않는다.
- **str0m을 택하면 송신 작업자 모드가 강제된다**(`Rtc` 직렬화). 즉 인라인 송신 실험의 한쪽이 사라진다.
- 패킷 형식 논쟁(순번과 시간축 분리, 불연속, 스트림 재시작)은 RTP가 이미 해결한 문제다. 자체 UDP를 택해도 **미디어 의미론은 RTP 모델을 따른다.**
- P3 관문 판단 기준: 스레드 구조 호환성, 핫패스 투명성(복사·할당), 보안 세션 복잡도, NAT 통과 전략(자체 홀펀칭 / 기존 ICE 구현 / str0m), 외부 의존성 위험.
- 전송 교체 비용은 transport 크레이트 하나로 끝나지 않는다(연결 수명, 인증, 경로 변경 이벤트). 엔진은 `TransportSession`, `TransportEvent`, `MediaDatagram`, `TransportDiagnostics` 경계만 보고 Noise·DTLS·ICE·RTP 내부 타입을 참조하지 않는다. 미디어 시간축과 패킷 마감은 전송 추상화가 숨기지 않는다.

## 14. 서버·릴레이 (P5)

- `signal` 크레이트에 시그널링 메시지 타입. 서버는 미디어 형식에 의존하지 않는다.
- **릴레이 라우팅 ID는 Noise receiver_index와 별개다.** receiver_index는 수신자 로컬에서만 유일하므로 서버 전역 라우팅 키가 될 수 없다. 릴레이는 자체 할당 ID의 캡슐화 헤더를 쓴다(TURN ChannelData와 같은 발상). 또는 coturn + TURN 클라이언트.
- 릴레이 경로 지연은 리전에 좌우된다. OCI 서울·춘천 리전을 확인한다.

## 15. 구조적 위험

1. **렌더 스레드 마감 초과.** 상대 5명의 디코딩·지터·믹스를 128샘플(2.67ms) 주기 안에 게임 부하와 함께 처리하지 못하면 pull 구조를 바꿔야 한다. P2 첫 작업으로 측정한다. 가장 큰 위험.
2. **str0m 선택 시 스레드 구조 변경.** 13.2.
3. **독점 캡처 불가 환경.** 다른 앱이 마이크 사용 중이거나 장치가 거부. 공유 경로를 항상 유지한다.
4. **Custom Opus 빌드 의존성.** libopus 빌드 플래그. 위험 낮음.
5. **시간축 타입 의미 혼동.** 4.1의 정의를 타입과 테스트로 보호한다.
6. **크레이트 경계의 복사·할당.** `MediaFrame` 1KB 값 이동 비용을 P2 마감 시험에서 함께 잰다.
